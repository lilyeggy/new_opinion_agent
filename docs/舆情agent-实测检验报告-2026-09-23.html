实测检验报告：罗永浩吐槽野人先生事件

2026-09-23 · 真实模型 + 真实搜索，无人工介入 · 检验方法：必中清单召回（先标注后对照）+ 逐条忠实性人工审计 + 九阶段诊断链复核

一、今天发生了什么：两次运行，一个完整的事故-诊断-复跑循环

Run 1（10:01，31 步终止，0 findings）：24 次读取全部失败。诊断链 5 分钟定位根因——错误记录显示 Jina Reader rejected authentication with HTTP status 401，且 retryable=false。用生产 transport 实证复现：.env 从未配置 JINA_API_KEY（keyless 模式），curl/httpx 直连均 200——401 是 Jina 对 keyless 流量的临时性限制，不是配置错误。1.5 小时后同一请求恢复 200。

Run 2（10:24，60 步，4 findings）：Jina 恢复后重跑：11 搜 / 16 读（8 存 8 败，败因均为 qq/wenxuecity 反爬）/ 8 来源 7 域名 / 48 条证据 / review 执行（3 supported / 1 partial）/ finish 被闸门拒绝 29 次。终态 partial，诚实发布。

新发现的架构短板（Run 1 的代价）：失败分类表把 provider 的 401 一律视为「认证失败、不可重试」——但 keyless 模式下 Jina 的 401 实际是临时性限流。24 次「不可重试」的失败全额计入 read 预算（24/24 耗尽），在搜索/模型/时间预算还剩 60–75% 的情况下强制终止。一次 20 分钟的供应商抖动，吃掉了整个 run。修复方向：keyless 401 应归类为可退避重试的临时错误，且失败读取不应与成功读取同额计预算。

二、我们如何检验（不是现成 benchmark）

GAIA/BrowseComp 类公开 benchmark 评「点状事实问答」（唯一答案，exact match），评不了舆情报告这种「面状地图」。本次检验用自建三件套，关键纪律：先看世界，再看系统——

① 必中清单召回（评检索层） 运行前：不看系统任何输出，用独立搜索标注 10 项「合格调查必须找到的事实」， 每项附独立来源证据 → 运行后：对照系统候选/已读正文算命中，并逐项人工复核 ② 逐条忠实性审计（评可信度） 每条 finding 与其引用的证据摘录逐对导出，人工核对： 引语是否逐字在原文？数字日期是否在支持摘录里？判断是否被自有证据推翻？ ③ 对抗埋点 replay（评判断力，D4 已建，本次复用结论） 冻结材料中埋更正/反方/错误数字，真实模型回放，0/1 计命中

防自欺设计：标注在运行前完成（防循环论证）；脚本初判 + 人工复核（防关键词虚报——本次就抓到 2 项虚报，见下）；模型 review 结论与人工审计对照（检验审查器本身）。

五、结论

信任机制全部经受住了真实事故的考验：Jina 抖动 → 诊断链 5 分钟定位 + 实证复现 + 确认非配置错误；报告零虚构；partial 诚实发布；失败计数不粉饰；评审器与人工审计 3/4 一致。

质量上限被三个同族缺口压住，全部指向「分析/收口层」而非「检索层」：

  1. 证据→判断转化率 50%：材料在库里，问题在留白——缺「整理库存证据成判断」的动作；
  2. 陈旧判断无更新：新证据到库后不回溯修订旧 finding，审查器只验「摘录支持文本」不验「判断与全库一致」；
  3. finish 空转 29 次：闸门拒绝没有转化为补查/整理动作，近半数步数被收工重试消耗。

修复方向（优先级序）：① 新增 consolidate 类动作：强制在 finish 被拒 N 次后，将库存证据按问题聚类生成 finding；② review 增加「全库一致性」检查：finding 与后到的证据冲突时标记为「待复评」；③ finish 拒绝反馈中附带「可立即转化的证据-问题对」引导；④ 失败分类表细分 provider 401（keyless 临时性 → 可退避重试）；失败读取降权计预算。①②③ 都在 domain/策略层，不动 Runtime 骨架——这恰好是「harness 修得起」的论据。
