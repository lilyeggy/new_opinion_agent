## 4. 必须先处理的缺口与风险

本节区分“代码直接可见的缺口”和“需要测试复现的风险”。逐项写测试或检查证据后再改，不要把所有推测写成已确认 bug。

### 4.1 第一优先级：可信性、发布一致性与用户问题

| 编号 | 当前观察 | 要求的行为与验证 |
|---|---|---|
| R01 | `structured_context` 的 `input.material` 可整段 DROP；主 Compiler 的 `memory.state` 也可 DROP | 审查不能在丢掉原文后继续成功。必需问题、当前判断及本批审查原文不可静默丢弃；超限缩小批次或明确 partial。用长上下文测试验证 |
| R02 | Manager Hook 在终态 checkpoint 时即可把 draft 标为 completed/partial，report 写入发生在后面 | 用户可见终态须等待报告完整写入。SSE 晚加入不能先收到“完成”却取不到报告。设置生成/发布中状态或统一发布恢复协议，并测试写入间崩溃 |
| R03 | 更新初始化把所有旧 finding 设为 inactive；diff 把 before 有、after 无直接当 withdrawn | 失败、取消或尚未重查不是撤回。保留“尚未重新评估”，只有显式修订/撤回与理由才能做语义变化断言 |
| R04 | 保留用户明确问题主要依赖 planner 提示词；没有原始问题到计划问题的完整覆盖契约 | 保存用户必答问题及其映射，程序检查不得丢弃或降为 optional。允许合并但保留所有原问题和理由；超出 8 个核心问题时合理归组，不能截断 |
| R05 | `response_search_complete` 看三个 purpose 和全局 read_errors；未检查搜索是否实质覆盖事件/机构以及候选是否处理 | 建立问题级查找范围、机构与事件定向搜索、后续材料处置记录。失败与未完成必须 unknown；标签齐全不代表查找完成 |
| R06 | 每条 finding 只有 response 分类，没有明确“此回应对应哪条主张、覆盖哪一部分”的完整结构 | 形成可验证的 claim/issue → response evidence → covered/uncovered components → reason。不要仅凭同属 issue 就认定充分回应 |
| R07 | 精确正文重复关系有代码，`origin_url` 暂无完整取证路径 | 建立可解释的转载/转述/引用关系及证据；不同域名不等于独立来源。关系未知时保留未知，不能凭模型猜测确证 |
| R08 | `State` 验证了引用 ID 和片段长度等结构，未因此证明正文支持语义 | Processor/存储边界需核对 `original[start:end] == excerpt` 和 content hash；reviewer 必须读到正确版本原文；不能用 ID 存在代替支持度检查 |

特别说明：当前 Reviewer 是独立调用，但通常使用与主 Agent 相同的模型配置。这符合“独立审查调用”，不能称为独立事实来源，也不能称为人工审查或真值认证。

### 4.2 第二优先级：可恢复、搜索、时间与预算

| 编号 | 当前观察或待验证风险 | 处理要求 |
|---|---|---|
| R09 | Resolver 对拼接后的 query 使用 `[:600]` | 不静默截掉用户实体或域名约束；在工具限制内构建查询并验证参数，必要时拆分有界查询。仍须在读取前后做范围验证 |
| R10 | 搜索结果分类有 empty/filtered/duplicate/error；filtered 主要表示 URL 范围过滤 | 补足“无关材料”的明确处置；不要把有候选数当有效来源数；按 issue 保留发现与拒绝理由 |
| R11 | read_attempts 一旦记录就禁止本轮再次读取，包括失败 URL | 定义有界重试和失败恢复语义；已有成功正文可 retrieve，读取失败不能永久假装已读。避免无限换 query 或永久跳过关键来源 |
| R12 | ReadResult 增加 updated_at，不代表 Jina 已解析该元数据 | 检查真实响应字段；不可获得即 null。保存日期出处和未知情况，不让模型自由填写发布/更新时间 |
| R13 | cutoff 当前取初始 State 创建时；fetched_at 则在之后；更新时间可能沿用父报告旧时间范围 | 定义事件时间、材料时间、抓取时间、调查截止与本轮增量范围。更新默认检查父版之后至本轮截止的新材料，同时允许发现旧文；不能永远复用旧日期导致搜不到更新 |
| R14 | `budget.start()` 在规划后调用；规划 model 计数已发生，规划耗时却未计入总时限 | 统一总预算起点。20 分钟包含活动规划、工具、审查；用户等待澄清不应耗光活动预算。暂停/进程中断是否计入需明确，恢复不能归零已用预算 |
| R15 | Budget 支持 limits 注入，但 Manager 尚未接通部署配置 | 由服务端配置默认预算并持久化快照；不新增 CLI 参数产品。避免让客户端随意绕过额度限制 |
| R16 | 无活跃 worker 时取消只改 draft；异常 worker 只留下笼统失败文案 | 保留已提交状态，并允许查看已获材料/受限结果。证明取消、异常与崩溃后不会覆盖父报告或丢失可展示证据 |
| R17 | Executor、工具缓存、checkpoint 间存在多个持久化边界 | 用故障注入证明每个窗口恢复结果一致；成功缓存复用，已提交 delta 不二次应用；不承诺远端 exactly-once |
| R18 | 同 URL 相同正文复用旧 SourceVersion；新抓取没有完整独立观测记录 | 保留每轮何时重新检查该 URL 的记录，不改旧正文版本的时间；页面内容变更时间未知时不可把“此次首次观察到”写成确切修改时间 |
| R19 | CaseLock 是 flock；列表读取和后台发布仍需验证并发、文件损坏、进程退出 | 跨进程同事件排他，退出释放；单个损坏 draft 不应让全部历史崩溃。旧活动锁不可靠删除文件强行解除 |
| R20 | 新 profile 已定义，Web 尚无旧版本只读适配 | 旧报告仍能浏览/下载；旧格式未完成 run 不能由新流程 resume。明确错误码与版本说明，不原地迁移旧 checkpoint |

### 4.3 报告与更新的具体缺口

- `report.py` 当前将 run 的 `partial` 和 response 的 `partial` 共用中文标签，调查状态会被翻译成“部分回答”。分离不同枚举的展示映射。
- Markdown 时间线当前直接选有 `event_time` 的 finding，未按时间排序，也未在每项保留审查状态。未审查判断不能以时间线事实的形式绕过限定。
- 当前差异主要按 issue 下文本集合与引用集合比较，不能据此可靠断言“支持加强/减弱”。需要稳定的判断关联、显式修订理由及新增依据；显示文案变化与证据变化的区别。
- “无实质变化”需要完成足够的本轮查找和旧判断复核；一次成功搜索、没发现不同文本不是充分条件。
- `new_publication` 只是新增发布材料，不自动等于事件发生新进展。分别呈现发布时间和材料所述事件时间。
- 报告应有独立的回应覆盖、已确认/分歧/未知、范围与证据附录；当前简版 Markdown 未完整覆盖目标结构。
- 问题状态 note、时间线、变化原因等同样可能含事实断言，不能只审查核心结论而放过其他用户可见重要断言。
- 显示“未发现回应”时必须带截止时间和查找范围；由于读取失败不能判断的，要在该问题位置显示。
- 不可将完整 raw source hash、内部 ID、工具 JSON 放到主界面；开发者视图可以提供。

## 5. 目标工作链路：实现时按此闭环，不得跳步

### 5.1 输入、澄清与问题计划

1. Web 提交事件、关注点、可选地区、可选时间、可选参考 URL。
2. 服务端验证输入类型、长度、URL 协议和公开来源范围、时间可解析性；保留原始输入，记录规范化结果。
3. 解析身份、机构、地点、时间、别名。用户提供的“事实”只作调查线索，不当作已验证证据。
4. 若身份有影响结果的歧义，持久化待澄清草稿与问题；刷新后继续。明确输入自动开始，不强制确认提纲。
5. 无法解析的时间进入澄清；拒绝把时间条件悄悄清空。澄清后重新校验并保存，而不是只改浏览器表单。
6. 生成 3–6 个核心问题，之后最多 8 个。保存用户必答子问题与核心问题映射；合并、关闭、重开有原因和历史。
7. 固化本轮执行配置、预算计量状态、事件范围和时间边界；创建新格式 checkpoint。

### 5.2 搜索、读取、重新取证

每次 SearchDecision 必须绑定 issue 和目的：原始材料、相关方诉求、独立核查、机构回应、事件回应、后续修订。Query 可使用实体别名，时间/语言/域名约束传给 Brave；有界分页且计入 20 次搜索预算。

搜索结果只是候选；必须判断身份与范围相关性。分别记录无结果、无关、重复、读取失败。不能把摘要直接变为最终证据。

Reader 成功后保存不可变全文版本，至少具有：

```text
requested_url, final_url, fetched_at
published_at?, updated_at?, 时间出处/未知说明
content_hash, artifact_ref, version_id
原始或转载等角色、重复/引用关系及关系依据
```

同 URL 变文新增版本；不同 URL 同正文标记重复；同 URL 同正文保留本轮检查记录。禁止改旧正文来“更新缓存”。

FTS 建索引时英文按词，中文确定性双字切分；原文与检索文本分开。片段使用已保存原文的字符区间定位，不能用切词后的偏移。明确采用 Python Unicode 字符索引，不伪称网页 DOM 定位。

RetrieveDecision 可按新问题重搜已保存全文。命中片段校验原文版本、hash、start/end，经过 Processor → Delta → Reducer 才进入 Evidence。SQLite 删除或损坏后必须可重建。

### 5.3 争议、回应、审查和结束

围绕每个问题保存以下信息，而不是只输出一段综合看法：

```text
问题
  → 主体、具体措施、主张、表达性质
  → 支持/反驳证据与原始出处
  → 可对应的回应证据
  → 回应覆盖哪些部分、未覆盖哪些部分、判定理由
  → 尚缺材料、问题处置状态、下一步补查方向
```

表达性质：事实、归因转述、解释、诉求；态度必须针对具体措施。诉求是价值表达，不按真假直接裁决。

回应分类固定为：直接回答、部分回答、涉及但未实质回答、未发现可对应回应、无法判断。回应覆盖、实际解决、群体满意必须分开。

独立审查逐项读对应原文，检查支持度、归因、日期数字否定与限制、转载独立性、回应对应、样本外公众态度推断。保存审查配置、判断文本/证据版本绑定和理由。发生文本或证据变更后旧审查失效。

审查不通过：补取证、限定措辞、撤回或删除，然后重新审查；预算不允许继续则 partial。报告最终不得再生成未经审查的新强断言。

必答问题须落到：已回答、证据分歧、范围内查找后未发现、无法判断。后两者不是随便退出的理由，需要查找范围/缺失原因。重大未完成事项一律 partial；不能为了 completed 放宽检查。

### 5.4 报告与版本发布

报告依次呈现：核心回答与限制、事件时间线、按问题组织的争议和各方主张、回应覆盖、确认/分歧/未知、范围与来源证据附录。

重要断言可以点击打开证据面板，看到原文、标题、公开链接、时间、版本定位、支持或反驳关系。引用失败、审查不足和查找缺口必须就近显示。

先完整写报告与关联资源，再原子发布可见版本/最新引用。任一崩溃点之后读者只能看到旧可用版本或完整新版本，不能出现已完成却无报告、父报告被半成品替代。

### 5.5 按需更新

1. 从 completed 或 partial 报告点击“补充新进展”，填写本轮 focus。
2. 同事件获取活动锁，生成新的 run/version，与父报告关联。保留旧版只读。
3. 继承历史材料和稳定问题身份，标注哪些旧判断待复核；补查用户 focus 和旧版未解决事项。
4. 调整本轮时间查询范围，刷新可获得的原来源，查找新增材料；新发现旧文与新发布材料分开。
5. 新证据导致问题重开或判断修订时记录具体理由、before/after、对应证据。
6. 完整发布新版本后展示新增材料/问题、加强/减弱/修订/撤回、未解决事项、未变部分和查找范围。
7. 取消、失败、partial、无新增材料有各自页面状态；供应商故障不得解释成“没有新进展”。

## 6. 后端和 Web 的实施契约

### 6.1 存储布局

建议把新流程置于现有 runs_root 下独立命名空间（例如 `investigations/`），避免与旧 `opinion-.../run.json` 混淆。这是接入时的目标，当前 Manager 直接使用传入的 root。

```text
<new-root>/
  cases/<case_id>/
    active.lock
    artifacts/                  # 不可变 Reader 正文
    corpus.sqlite3              # 派生索引
    latest.json                 # 完整版本发布后切换
  runs/<run_id>/
    draft.json                  # 输入、澄清、状态及父版本关系
    budget.json                 # 已用预算与执行配置快照
    run.json                    # 新领域 checkpoint
    action_results/             # 现有成功工具缓存
    observations/               # 已产生 observation 的恢复记录
    report.json
    report.md
```

如需增加 source fetch history、审查完整配置或发布 manifest，优先增加明确的数据对象/文件，不另建一套权威数据库。正文与报告一经发布不可就地改写。

草稿和进度是可更新元数据；报告正文、证据版本、父子关系的历史语义不可随刷新或升级悄悄改变。对 current working draft 的原子写不等于对一组报告文件完成事务，发布协议必须独立验证。

### 6.2 建议的新 API

下列是**待实现契约**，不是现有接口。可在实现前做小幅命名调整，但必须在文档与前端一致，不得只实现接口、不实现对应页面。

| 方法与路径 | 职责 | 关键行为 |
|---|---|---|
| `POST /api/investigations` | 创建调查草稿并启动识别 | 返回稳定 id 与 snapshot；配置错误清晰可见 |
| `GET /api/investigations` | 历史调查列表 | 服务端扫描持久化信息，不能只列进程内 worker |
| `GET /api/investigations/{id}` | 权威 snapshot | 状态、可恢复标志、问题进度、可用报告/版本摘要 |
| `POST /api/investigations/{id}/clarify` | 回答澄清 | 保存答案，重新校验；仅在待澄清状态合法 |
| `POST /api/investigations/{id}/cancel` | 取消当前任务 | 幂等或返回稳定状态，保留已提交材料 |
| `POST /api/investigations/{id}/resume` | 恢复中断任务 | 新格式且无其他活跃 worker；预算不清零 |
| `GET /api/investigations/{id}/events` | SSE 进度 | 首先可重建 snapshot；重连、晚加入和终态正确 |
| `GET /api/investigations/{id}/report` | Markdown 下载 | 下载该不可变版本，不跟随 latest 偷换内容 |
| `GET /api/investigations/{id}/evidence/{evidence_id}` | 证据定位 | 限定该版本引用，返回对应原文及上下文 |
| `POST /api/investigations/{id}/update` | 从报告发起更新 | 新 id + parent；只接受补查 focus，不覆盖父请求 |
| `GET /api/investigations/{id}/versions` | 同事件版本列表 | 能切换旧 completed/partial，区分失败尝试 |
| `GET /api/investigations/{id}/diff?base=...` | 版本差异 | 只比较同事件且有效的版本；新旧引用不串版本 |

小数据量时 versions/diff 可复用持久化报告的派生视图；独立接口保持清晰，避免重做第二套计算规则。

请求严格验证对象类型、额外字段、body 大小、ID、URL、时间。用户可见错误返回稳定 code 与中文 message；400/404/409 的区别要明确。不要返回密钥、内部路径或长堆栈。

SSE 可以采用“服务端持久化快照 + 有序版本号/更新时间”而非建设永久消息系统。必须能用一次 GET 恢复最终状态，断线不意味着调查失败，浏览器重连不应创建新的调查。

### 6.3 页面与脚本拆分

沿用现有 Web server。建议新页面为 `web/investigation.html`，脚本拆到 `web/assets/`；这些名称是建议，当前文件未建立。

- `api.js`：请求、错误解析、SSE 与重连。
- `app.js`：路由、历史、创建/澄清/进度状态。
- `report.js`：报告、版本选择、diff、下载。
- `evidence.js`：证据面板、定位、高亮和上下文。
- 独立 CSS：响应式布局、状态、阅读样式。

不要引入新构建框架；模块 import 与静态文件 Content-Type 必须经过浏览器验证。主界面使用正常产品文案，开发者信息放折叠面板或既有 `/dev`。

页面至少包含：

1. 创建页：事件和关注点主输入；地区、时间、参考链接为可选补充。
2. 待澄清页：展示原输入、少量必要问题、提交答案；刷新不丢失。
3. 进度页：阶段、正在调查的问题、有效材料、失败/替代尝试、取消；不显示精确百分比。
4. 报告页：目标六部分结构，关键判断可点证据，partial 等状态醒目。
5. 更新/对比页：补查输入、历史切换、before/after、变化原因、对应旧新依据。

所有不可信正文与模型文本使用安全文本渲染；Markdown 若渲染为 HTML 必须处理 XSS。公开链接限定允许协议，不能将任意字符串写入 href、innerHTML 或脚本。

### 6.4 兼容方案

主页切到新调查流程后，保留旧报告的只读入口（例如 `/legacy`），复用旧导出能力。不要简单把旧可写首页搬过去就宣称“旧格式只读”。旧未完成 run 必须明确说明不能由新流程继续执行。

旧 CLI 入口不新增业务能力、不主动删除；通用模型、搜索、Reader schema 改动保持其默认行为。旧 API 是否保留创建能力应限定于兼容需求，不让主界面误入旧调查流程。

## 7. 分阶段执行单：每阶段都有退出条件

顺序保留用户 A→B→C→D 的业务目标，并在当前半成品状态前增加一个收敛步骤。允许为修复前置依赖小范围调整，不允许跳过测试直接做完整漂亮界面。

### S0：接管工作区，修复高风险基础契约

输入：当前未提交代码、本文第 4 节。

工作：记录 git 状态；运行有限基线；建立 `tests/investigation/`；优先修复 R01/R02/R03/R04/R08，随后预算与恢复基础风险。不要先润色界面。

退出条件：

- [ ] 新模块导入、合成单次调查可复现。
- [ ] 审查原文不会被整段丢掉后照样通过。
- [ ] 用户必答问题无法静默删除。
- [ ] 原文 hash、offset、excerpt 能程序验证。
- [ ] 终态报告发布和取消/故障窗口有测试。
- [ ] 更新未复核不被误报撤回。
- [ ] 共享模块相关回归通过。

### A：建立业务基线

工作：按第 8 节确定 10 个真实事件、开发/保留划分、材料 provenance、必答问题和禁止结论；先选一个开发案例贯穿后续实现；冻结旧版基线条件和结果。

退出条件：

- [ ] 10 个案例登记完整；材料不可获得时明确 blocked，不用虚构替代。
- [ ] 开发和保留案例分开；保留答案不进入主 Agent 提示词或生产代码。
- [ ] 有来源可查的固定材料和至少一组双时点更新材料。
- [ ] 旧版在固定条件下的失败点可定位，不编造旧结果。

缺真实材料时可继续通用测试和 Web 接口，但 A 不能标完成，最终质量结论保持待验。

### B：可信单次调查，接通第一条 Web 主线

工作：完善输入澄清/时间/动态问题、搜索范围、全文版本与重查；接入 Manager、API、SSE、创建页、进度页、报告与证据面板。

退出条件：

- [ ] 浏览器提交明确事件自动开始；歧义/无效时间需要澄清。
- [ ] 刷新草稿与进行中任务，恢复状态且不重复创建。
- [ ] 长文章后半段能被新问题检索并定位。
- [ ] 重要结论可以在页面展开正确版本原文。
- [ ] 取消/断线/失败/partial 状态可实际操作观察。
- [ ] 旧报告仍只读浏览和下载，旧格式未完成任务被明确拒绝续跑。

### C：争议、回应与审查

工作：实现来源关系、主张与对应回应、覆盖及遗漏、独立审查和修订，完成六部分报告结构；修复 R05/R06/R07 及报告显示缺口。

退出条件：

- [ ] 三篇转载同一通稿不会成为“三个独立证据”。
- [ ] “机构称已解决”不能变成无归因的已解决事实。
- [ ] 回应只涵盖周末而问题涉及工作日时判部分回答。
- [ ] 有回应页面读取失败时显示无法判断，不是未发现回应。
- [ ] 未审查或审查失败的重要判断在对应位置降级，重大缺口导致 partial。
- [ ] 主界面清晰区分回应、解决、满意，证据关系可追查。

### D：按需更新、版本与恢复

工作：更新入口、版本继承/重开、旧网页重查、稳定判断变化记录、发布协议、版本切换与差异页面。

退出条件：

- [ ] 新证据使旧判断修订，旧报告/正文 hash 不变。
- [ ] 同 URL 变文产生新版本，旧引用仍定位旧文。
- [ ] 新发现旧材料、新发布材料、页面内容变化有明确区别。
- [ ] 无实质变化带本轮查找范围；provider 失败不显示无进展。
- [ ] 中断更新不会替换旧报告，也不会把待复核判断写成撤回。
- [ ] 跨进程同事件排他；崩溃恢复不重置预算、不重复提交 delta。
- [ ] 实际浏览器完成从提交到更新对比的全链。

### 收尾：固定条件验证与文档交付

完成有意义的完整回归、浏览器操作记录、真实联网发现检验、人工验收记录。未具备人工评分或供应商访问时提交明确 pending/blocked 项，而不是伪造 90%/95% 达标。

每个阶段更新执行记录：改动范围、关键契约、测试命令和结果、artifact 路径、失败/恢复语义、仍未完成项、下一步。阶段未通过前不得标 DONE。

## 8. 10 个真实事件案例与评估边界

当前只有合成公交案例，下面是**待建立的数据集要求**，不是现成数据集。

| 分组 | 开发案例 ID | 保留验收 ID | 选择要求 |
|---|---|---|---|
| 公共交通 | transport-dev | transport-holdout | 路线/时刻/收费等具体调整，有原始说明与相关方问题 |
| 公共设施 | facility-dev | facility-holdout | 开闭、使用、改造等，有适用人群与实施细节 |
| 文旅服务 | tourism-dev | tourism-holdout | 预约、开放、票务等，有规则文本及争议材料 |
| 服务规则调整 | rules-dev | rules-holdout | 新旧规则边界、适用对象、时间明确 |
| 机构回应与修正 | response-dev | response-holdout | 至少两个可区分材料时点，有补充回应或修正 |

优先选择公开原文可获取、身份明确、有限材料能覆盖的问题。案例不必追逐热点；不要选择依赖未授权社交抓取才能成立的事件。

建议 fixture 元数据包含：

```text
case_id, category, split, event_identity
user_request, required_questions
materials: url, final_url, title, fetched_at, published_at?, updated_at?,
           snapshot_path, sha256, source_role, dependency_relations
expected: supported_answers, acceptable_unknowns, response_coverage,
          required_evidence_locations, forbidden_claims
stages: T0_allowed_materials, T1_additional_materials
annotation: author_kind, reviewed_by_human, status, notes
```

禁止事项：

- 不把新闻题目加一段模型编写正文冒充快照。
- 不把今天抓取的页面标成历史某天完整状态。没有历史快照时，明确“固定材料回放”，不是还原历史互联网。
- 不提前把 T1 材料装入 T0 的可检索 corpus；不能只在 prompt 里说“请忽略未来材料”。
- 不把接手 agent 自己写的答案标为人工 gold。可以建立“模型预标注、待人工复核”的版本，但验收状态必须区别。
- 不依据保留案例答案调整生产代码里的专用 query、问题模板或结论。
- 不把 pytest 通过率、reviewer supported 比率当作人工引用支持率。

三类结果分开报告：

1. **机制测试**：fake/scripted，检验状态、约束、重试、恢复、UI。
2. **固定材料语义回放**：真实模型 + 冻结材料，检验问题回答、证据支持、回应/更新理解。
3. **真实联网运行**：真实模型 + Brave/Jina，检验发现能力、时效约束、材料可用性和费用。

初始质量门槛保持用户原要求：引用及定位结构完整性 100%；保留案例必答问题至少 90% 正确回答或恰当未知；人工检查重要断言至少 95% 得到引用支持或正确降级；关键归因、转载、回应遗漏、更新反转全部通过。

记录分母和判定单位：每条引用/定位、每个必答问题、每个重要原子断言。未知只有在解释与证据边界恰当时计入，不能通过把所有答案改成“不确定”投机提高分数。对 5 个保留事件的结果不能宣称广泛泛化。

基线比较冻结模型标识/参数、输入、材料开放规则、工具、预算、日期和配置。旧版不能直接执行新格式时使用薄测试适配器，不篡改旧领域语义。费用不足时先完成开发案例与机制验证，保留验收标待执行。

## 9. 必须覆盖的测试矩阵

新增测试建议放入 `opinion_search_agent/tests/investigation/`，Web e2e 放入现有 `tests/e2e/` 体系。fixture 和普通 Python 测试帮助模块不属于新增 CLI 功能。

| 测试组 | 输入/故障 | 必须观察到的结果 |
|---|---|---|
| 输入 | 明确事件；同名不同地点；无法解析日期；日期有空格 | 明确自动开始，歧义澄清，时间不静默忽略 |
| 问题 | 多个用户必答问题，模型遗漏/合并/设 optional | 程序拒绝遗漏或保留可追溯映射；有变更原因 |
| 检索参数 | 时间/语言/include/exclude、长 query、分页 | 真实 adapter 请求参数正确，有界且不截断关键约束 |
| 范围 | 社交域名、跳转到禁止来源、非公开 URL | 搜索候选及 Reader 边界拒绝，不能进入 Evidence |
| 二次取证 | 长文关键段在尾部；中文双字；英文；中英混合 | 新问题命中正确原文和字符区间 |
| 索引 | 删除/损坏 SQLite | 从正文版本重建；证据身份与正文不变 |
| 证据完整性 | 伪造 ID、错误 offset、错误 hash、跨版本 ID | 失败关闭，不能渲染成有效引用 |
| 来源 | 原文+两篇转载、转述、不同域同正文 | 重复/依赖可见；不声称独立验证 |
| 归因 | “机构称已解决”，新闻引用匿名观点 | 保留主张归属和适用范围，不变为无条件事实 |
| 回应 | 只答一半、相关套话、三类查找完成但关键网页读取失败 | partial/non_substantive/unknown 正确区别 |
| 未发现 | 定向查询与后续材料范围确已完成 | not_found 带截止与范围；未完成则 unknown |
| 审查 | 原文被注入指令；数字/否定不一致；审查返回漏项/未知 ID | 指令不改变控制规则；判定降级/拒绝；不能跳过问题 |
| 审查上下文 | 原文和状态超过 context 限制 | 缩小批次或明确 partial，不在无原文时通过 |
| 预算 | 搜索/Reader/model 重试、缓存命中、15 分钟/20 分钟、恢复 | 真实请求重试计数，缓存不计远端次数；已用不归零 |
| 恢复 | 工具成功缓存后崩溃、observation 保存后崩溃、delta 提交后崩溃 | 恢复相同语义结果；已提交 state 不重复应用 |
| 取消 | 搜索中、审查中、进程已退出 | 已提交材料保留，报告/状态不伪装成功 |
| 发布 | report JSON/Markdown/latest/draft 写入间故障 | 旧版可用，半成品不可成为最新可见报告 |
| 更新 | 新证据反转、同 URL 变文、首次发现旧文、完全无变化 | 明确 before/after 和依据，旧引用不串文 |
| 更新失败 | 只完成部分重查、provider 故障 | 不误报撤回/无进展，不覆盖旧版 |
| 并发 | 两进程同时更新同一事件 | 仅一个执行；另一个明确冲突，可恢复 |
| Web | 刷新、晚加入 SSE、断线重连、历史回访 | 来自持久化 snapshot，避免重复任务 |
| Web 证据 | 点击核心/时间线/争议引用，版本切换 | 对应原文高亮、日期、关系正确，下载固定版本 |
| Web 安全 | 标题/正文含 HTML/JS、恶意链接、非法静态路径 | 不执行内容，不越界读文件 |
| 旧兼容 | 历史报告、旧未完成 checkpoint、旧 CLI 默认行为 | 旧报告只读可导出；新版拒绝旧续跑；共享行为保持 |

不要只写镜像实现的测试，例如“字段存在”等同于“结论受支持”。高风险条目需要能失败的反例；Web 验收必须包括实际浏览器操作，HTTP 200 不能替代。

## 11. 文档同步、额度控制与停止规则

### 11.1 必须同步的文档

- `docs/public-opinion-search-agent-design.md`：canonical design，记录新的公开事件调查契约、Web 链路、完成条件与格式边界。对旧固定 gap 设计明确历史/新旧适用范围，避免两套同时声称生效。
- 建议新增 `docs/superpowers/plans/2026-09-10-web-event-investigation.md`：逐阶段执行清单和当前状态。不要把旧 5 天学习计划直接改写成新交付记录。
- `docs/opinion-search-agent-implementation-memory.md`：已实现且经过什么验证的事实。规划、未测试草稿、待人工确认必须明确标识，不能写成已完成。
- 本交接文档：保留交接快照语义；继续进度写执行计划/实现记录，不悄悄修改第 1 节历史证据。

每个节点的记录模板：

```text
节点 / 日期：
完成范围：
关键契约与不变量：
修改文件与主要符号：
验证命令 / 环境 / 结果 / artifact：

```

### 11.2 控制额度的方法

1. 优先本地检查和固定材料，不每改一处就跑真实大模型全链。
2. 一次只处理一个阶段的失败集合；失败复现后最小修复、定向回归，稳定后再做全量。
3. 不重新研究向量库、Agent 框架或更换供应商；需求和路线已明确。
4. 模型辅助人工预标注与真实联网运行需单独记录调用预算；不得把应用内 20/24/80 上限误解成无限次测试的总授权额度。
5. 供应商 key 不可用、额度耗尽时，不循环请求；继续完成不依赖网络的实现与验证，并标记待联网/人工项。
6. 剩余额度不足以结束当前阶段时，先保存可恢复代码、测试结果和精确下一步。不要为得到绿色状态删除断言或启用假的成功回退。

### 11.3 什么时候继续，什么时候必须停

**可以自主继续：** 当前范围内的修复、测试、接口与页面接入、文档维护、隔离目录下本地 QA。无需每一小步问用户批准。

**暂停依赖项，但继续独立工作：** 缺真实材料、provider 凭据、浏览器环境或人工评分。明确依赖和未覆盖范围，不把整个工程任务都锁死。

**必须请求用户决定：** 需要新增收费采购/公开部署/社交采集/框架迁移/向量数据库，或必须破坏旧数据、删除用户文件、改动其他项目才能继续。不要自行扩大授权。

**不能自行解决的语义分歧：** 先提出一个范围内且保守的具体方案并标注假设；不得通过弱化“引用支持”“必答问题保留”“不可变旧版”等硬约束消解分歧。

交付时区分三种状态：

- `implemented_verified`：代码和相应验证已完成，附证据。
- `implemented_unverified`：代码存在但缺环境/数据/人工验证，明确限制。
- `not_implemented` / `blocked`：未实现或存在具体依赖，给出继续所需最小输入。

不得用“基本完成”“生产级”“全链可靠”覆盖未执行的验收。
