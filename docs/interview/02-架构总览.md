# 02 · 架构总览

> 目标：建立一张能在白板上画出来的全局图。读完之后你应该能回答"这个项目由几块组成、谁依赖谁、一次 run 的数据怎么流"。
> 精确的逐层机制见 `03`；本文只讲结构和依赖方向。

## 1. 一句话架构

> **一个领域无关的 Runtime，被两套领域规则分别装配，靠构造函数注入连接。**

这句话是整个项目最容易讲错的地方。它不是"一个分层应用"，而是**一个 Runtime + 两个组合根**。理解这一点，后面所有"为什么有两个 compiler""为什么 Working Memory 只在一边"的问题都能自己推出来。

## 2. 三块结构

```text
┌──────────────────────────────────────────────────────────────────┐
│  入口层                                                           │
│    __main__.py（CLI: offline / live / resume）                    │
│    web/（HTTP: 3 个页面 + 2 套 API）                               │
├──────────────────────────────────────────────────────────────────┤
│  组合根层（谁把谁装起来）                                          │
│    app/service.py          → opinion 域装配（CLI + /legacy + /dev）│
│    investigation/service.py → investigation 域装配（/ 工作台）      │
│    investigation/manager.py → 调查编排、澄清、更新、预算、投影       │
├──────────────────────────────────────────────────────────────────┤
│  领域层（领域规则，知道"舆情"是什么）                               │
│    domain/opinion/          10 个模块：state / reducer / decisions  │
│                             / actions / action_resolver / processor│
│                             / completion / provenance / framing    │
│                             / brief                                │
│    domain/investigation/    2 个模块：models.py + engine.py        │
├──────────────────────────────────────────────────────────────────┤
│  Runtime 层（领域无关，不知道"舆情"是什么）                          │
│    runtime/loop.py          AgentLoop：状态分发器 + 恢复           │
│    runtime/lifecycle.py     RunStatus 六态 / StepPhase 七阶段      │
│    runtime/transaction.py   RunState / StepRecord / ResumeAction   │
│    runtime/checkpoint.py    JsonCheckpointStore（原子写 + profile） │
│    runtime/completion.py    CompletionDisposition / RunResult      │
│    runtime/errors.py        RuntimeFailureKind / RecoveryDirective │
│    runtime/cancellation.py  CancellationSignal                     │
│    runtime/protocols.py     四段信封 + StepRecord 不变量校验        │
├──────────────────────────────────────────────────────────────────┤
│  支撑层（能力接口，Runtime 与 Domain 都用）                          │
│    context/     section 模型 / 压缩 / 选择 / 目录 / opinion compiler │
│    memory/      WorkingMemory 模型与投影（仅 opinion 域使用）        │
│    tools/       Registry / Executor / circuit / cache / adapters   │
│    models/      ModelClient 契约 + OpenAI-compatible + Fake        │
└──────────────────────────────────────────────────────────────────┘
```

依赖方向**严格单向**：

```text
入口 → 组合根 → 领域 → Runtime → 支撑
```

关键约束（面试会问）：

- **Runtime 不 import Domain。** `runtime/` 里没有任何一行 `from opinion_search.domain...`。Runtime 只认 `runtime/protocols.py` 的信封类型和 `runtime/lifecycle.py` 的枚举。
- **Domain 不 import provider SDK。** `domain/` 里没有 httpx、没有 MCP、没有 Brave。领域层只产出"我要调 `search.web`，参数是这些"。
- **Runtime/Domain 里不出现 provider 名称。** provider id 只存在于 `tools/registry.py` 的绑定里，模型看到的只有 `ToolDefinition`。

## 3. 两套 domain 组合（最容易被追问的点）

`domain/opinion/` 有 **10 个**独立模块；`domain/investigation/` **只有 2 个**（`models.py` + `engine.py`，Validator / Resolver / Processor / completion / `reduce_state` 全在 engine 里）。这个不对称不是风格差异，它决定了三条事实：

| 能力 | `domain/opinion` | `domain/investigation` |
|---|---|---|
| 动作空间 | 4：`search` / `read` / `reflect` / `finish` | 6：`+ retrieve` / `review` |
| 状态 | `state.py` 的 `OpinionSearchState` | `models.py` 的 `State` |
| Reducer | `reducer.py` 的 `reduce_opinion_state` | `engine.reduce_state` |
| 校验 / 解析 / 处理 | `decisions.py` / `action_resolver.py` / `processor.py` | `engine.Validator` / `engine.Resolver` / `engine.Processor` |
| Context Compiler | `context/compiler.py` 的 `OpinionContextCompiler` | `investigation/context.py` 的 `Compiler` |
| Working Memory | **有**（`memory/projector.py`） | **没有这个对象** |
| Provenance | `domain/opinion/provenance.py` | 无（`evidence → version_id → source` 直接映射） |
| 入口 | CLI + `/legacy` + `/dev` | `/` 工作台 |

**两条必须记住的结论**：

1. **共享的只有 `context/models.py` 与 `context/compactor.py`。** `context/compiler.py`、`selector.py`、`catalog.py` 与整个 `memory/` 只被 `app/service.py`（opinion 路径）引用。说"两套 domain 共用同一套 Context Compiler"是错的。
2. **`WorkingMemory` 是 opinion 域的实现细节，不是 Runtime 概念。** 说"我们的 Working Memory 层服务于两条路径"是错的。

**为什么 investigation 不复用 `OpinionContextCompiler`？** 因为它硬类型检查 `OpinionSearchState`：

```python
if not isinstance(state.domain_state, OpinionSearchState):
    raise TypeError("OpinionContextCompiler requires OpinionSearchState")
```

而 investigation 的上下文要携带 issues / findings / `page_plan` / `next_action_constraint` / consolidate 指令，形状不同。复用 `ContextSection` 模型与 compactor 已经拿到了共享收益；强行统一 compiler 会让两边都变复杂。

## 4. Runtime 与 Domain 的接缝：11 个 Protocol + 1 个 Callable

这是"Runtime 领域无关"的**可验证证据**——`AgentLoop` 不知道"舆情"，它只知道 11 个契约接口。

`AgentLoop.__init__` 的注入清单：

| # | 参数 | 契约类型 | 声明位置 |
|---|---|---|---|
| 1 | `model` | `ModelClient` | `models/contracts.py` |
| 2 | `context_compiler` | `ContextCompiler` | `runtime/loop.py` |
| 3 | `decision_validator` | `DecisionValidator` | `runtime/loop.py` |
| 4 | `action_resolver` | `ActionResolver` | `runtime/loop.py` |
| 5 | `action_executor` | `ActionExecutor` | `runtime/loop.py` |
| 6 | `observation_processor` | `ObservationProcessor` | `runtime/loop.py` |
| 7 | `completion_evaluator` | `CompletionEvaluator` | `runtime/completion.py` |
| 8 | `reducer` | **普通 `Callable[[Any, Any], Any]`** | —— |
| 9 | `checkpoint_store` | `CheckpointStore` | `runtime/checkpoint.py` |
| 10 | `id_factory` | `IdFactory` | `runtime/loop.py` |
| 11 | `cancellation_signal` | `CancellationSignal` | `runtime/cancellation.py` |
| 12 | `hook` | `LoopHook` | `runtime/loop.py` |

**精确口径**：`loop.py` 内声明 **7 个** `Protocol`（#2–#6、#10、#12），另 **4 个**来自其他模块（#1、#7、#9、#11）；`reducer`（#8）是普通 `Callable`，**不是** `Protocol`。所以正确说法是"**11 个 Protocol 契约 + 1 个 Callable**"，说"十个协议接口"会被追问口径。

另有两个标量参数：`max_steps`、`max_decision_attempts`（默认 2）。

**这套设计带来什么**：换一套 domain 装配，就是另一条产品线。项目里确实这么做了——`app/service.py` 和 `investigation/service.py` 分别调用 `AgentLoop(...)`，注入各自的 11 个实现，`runtime/` 一行都不用改。

## 5. 一次 run 的端到端数据流

以 opinion 路径为例，**一步（step）**的完整生命周期：

```text
  ┌─ run() while True ────────────────────────────────────────────┐
  │                                                               │
  │  1. classify_resume(state)  ← 只看持久化状态，不看内存          │
  │        │                                                      │
  │        ├─ REQUEST_DECISION                                    │
  │        │    ├─ OpinionContextCompiler.compile(state)          │
  │        │    │    project_working_memory → collect → select    │
  │        │    │    → compact → render → CompiledContext         │
  │        │    ├─ model.decide(context)      → AgentDecision     │
  │        │    ├─ DecisionValidator.validate(...)  ← 领域规则     │
  │        │    ├─ DecisionEnvelope → accept_decision()           │
  │        │    └─ save(DECISION_ACCEPTED)                        │
  │        │                                                      │
  │        ├─ RESOLVE_ACTION                                      │
  │        │    ├─ ActionResolver.resolve(...) → OpinionAction    │
  │        │    ├─ ActionRequest(action_id=...)                   │
  │        │    └─ save(ACTION_RUNNING)      ← 副作用前最后一个点   │
  │        │                                                      │
  │        ├─ EXECUTE_ACTION                                      │
  │        │    ├─ ActionExecutor.execute()                       │
  │        │    │    └─ ToolExecutor: resolve → validate args     │
  │        │    │       → cache lookup → providers loop           │
  │        │    │       (circuit gate + bounded retry + timeout)  │
  │        │    ├─ ObservationEnvelope → record_observation()     │
  │        │    └─ save(OBSERVATION_READY)                        │
  │        │                                                      │
  │        ├─ REDUCE_OBSERVATION                                  │
  │        │    ├─ Processor.build_delta(...) → StateDelta        │
  │        │    ├─ mark_reducing() → save(REDUCING)               │
  │        │    ├─ commit_step(state, delta, reducer)             │
  │        │    │    └─ reduce_opinion_state()  ← 纯函数，唯一写入口│
  │        │    └─ save(STEP_COMMITTED)                           │
  │        │                                                      │
  │        └─ EVALUATE_CONTINUATION                               │
  │             ├─ CompletionEvaluator.evaluate(...) → Verdict?   │
  │             └─ apply_continuation() → save(CONTINUATION_APPLIED)│
  └───────────────────────────────────────────────────────────────┘
```

注意三个细节：

- **每一步都先 `save()` 再 `continue`**，回到 `while True` 顶部重新 `classify_resume`。没有嵌套流程，只有状态分发。
- **`save()` 不只是写盘**，它还触发 `LoopHook.after_checkpoint(boundary, state)`。Web 端就是靠这个 hook 推 SSE——Runtime 和 Domain 一行都不用改。
- **`classify_resume` 只读 `RunState`**，不读任何内存变量。这就是"首次执行与崩溃恢复同路径"的机制来源。

## 7. 两条入口的真实差异

CLI 和 Web 都跑同一个 `AgentLoop`，但装的是不同的 domain：

| | CLI / `/legacy` / `/dev` | `/` 调查工作台 |
|---|---|---|
| 组合根 | `app/service.py` | `investigation/service.py` + `investigation/manager.py` |
| Domain | `domain/opinion` | `domain/investigation` |
| 动作 | 4 | 6（+`retrieve` / `review`） |
| Context Compiler | `OpinionContextCompiler` | `investigation/context.py::Compiler` |
| 人机交互 | 无（一次跑完） | **有澄清轮次**：planner 可提最多 3 个问题，`Budget.pause()` 暂停计时 |
| 预算 | `max_steps` + 决策重试次数 | `Budget`（search 20 / read 24 / model 80 / 1200s）+ `ConsolidationValidator` 发布保留段 |
| 产物 | `report.md` + `outcome.json` | Run Bundle + 结构化工作台投影 + Markdown 报告 |

**共同点**（这是"Runtime 领域无关"的实证）：同一个 `AgentLoop`、同一套 `ToolRegistry`/`ToolExecutor`、同一个 checkpoint 格式（`schema_version = 4`）、同一个 `ContextSection` 模型、同一个 `LoopHook` 进度边界。

**不同点**：领域规则不同，Context Compiler 不同，Working Memory 只在一侧存在。
