## A · 基础层

### A1 一句话介绍这个项目

**答**：
> 一个面向公开 Web 舆情调查的**可恢复单 Agent Harness**。模型每轮只提一个决策，Runtime 负责校验、执行、提交和恢复；项目本体是执行骨架，不是搜索封装。

**追问链**：
- 什么叫"可恢复"？→ 崩在任一阶段边界都能定位并继续；首次执行与恢复同一条代码路径。
- 为什么说"单 Agent"？→ 显式自研 async loop，不是图框架；多 Agent 提案已否决。
- "Harness" 具体指什么？→ `runtime/` + `tools/` + `context/` + `memory/` 四块，领域无关。

---

### A2 这个项目最核心的设计是什么

**答**：
> **模型有提案权，没有写权。**
>
> 提交链是：`Decision → Validator → ActionResolver → ActionExecutor → Observation → Processor(Delta) → Reducer → Checkpoint`。模型只在第一个箭头出现，后面全是程序。Reducer 是权威状态的唯一写入口，而且是纯函数。

**追问链**：
- 为什么不让模型直接写 State？→ 模型可能绕过校验产生副作用，工具返回可能绕过领域规则成为事实，Runtime 也无法判断崩溃发生在哪一步。
- 那模型说的话还有什么用？→ 它决定**语义**：搜什么、读什么、认为哪个维度解决了。程序决定**这些说法是否合法、是否成立**。

---

### A3 一次 run 的完整流程

**答**：
> `run()` 是一个 `while True`。每轮开头 `classify_resume(state)` 只看持久化状态，决定这一步做什么——是开新 step、请求决策、解析动作、执行动作，还是提交状态、评估完成。每个分支做完就 `save()` 然后 `continue`，回到顶部重新判定。
>
> 一步内部是七个阶段：`opened → deciding → decision_accepted → action_running → observation_ready → reducing → committed`。

**追问链**：
- 为什么是 `while True` 而不是顺序流程？→ 把"恢复到哪"从控制流问题变成数据问题。
- `save()` 之后还做了什么？→ 触发 `LoopHook.after_checkpoint`，Web 端靠它推 SSE。

---

### A4 模型怎么调用工具

**答**：
> **它不调用工具，它表达意图。** 模型输出 `SearchDecision(query, target_gap_id, purpose)` 这样的语义决策；`ActionResolver` 把它翻译成 `ToolAction(tool_name="search.web", arguments={...})`；`ToolExecutor` 再去查 Registry、校验参数、查缓存、按顺序尝试 provider。
>
> 模型从来不知道背后是 Brave 还是 Serper——provider id 只存在于 Registry 的绑定里。

**追问链**：
- 为什么要多这一层？→ 让 `reflect` / `finish` 这类无外部副作用的动作也能走统一生命周期，同时让模型看不到 provider 存在。
- query 会被程序改吗？→ 会。Resolver 会追加 `site:` / `-site:`、限制长度、设结果数、分页、语言、时效。

---

### A5 Decision / Action / Observation / Delta 分别是什么

**答**：

| 对象 | 谁产生 | 是什么 |
|---|---|---|
| `Decision` | 模型 | **语义意图** |
| `Action` | `ActionResolver` | **可执行单元** |
| `Observation` | 环境（工具或内部动作） | **外部世界发生了什么** |
| `StateDelta` | `Processor` | **希望改哪些状态** |

> 四个对象代表四个事实阶段、四个责任主体。合并之后就无法判断崩溃发生在"动作未执行""结果已获得"还是"状态已提交"。

**追问链**：
- 为什么 ToolResult 不是 Observation？→ Observation 还要携带 `run_id/step_id/attempt/action_id`，而且 `reflect`/`finish` 这类内部动作也要产生 Observation。
- 为什么 Observation 之后还要 Delta？→ 同一个 SearchResults 要经过 URL 正规化、域过滤、去重才能进 State；同一个 ReadResult 要经过摘录选择。这些领域规则需要落点。

---

### A6 状态存在哪，长什么样

**答**：
> 唯一权威状态是领域 State，存在 checkpoint 里（`run.json`）。外层是 `RunState`，装 `run_id`、`status`、`domain_state`、`next_step_index`、`active_step`、`committed_steps`、`committed_action_ids`、`continuation_pending`、`stop_reason`、`failure`。
>
> 领域 State 有两套：opinion 域是 gap/claim/narrative 那一套，investigation 域是 issue/finding/review 那一套。

**追问链**：
- 为什么有两套？→ Runtime 领域无关的可验证证据；但长期要收敛，这一点我会主动说。
- 写入时怎么保证原子？→ `commit_step` 一次性改六个字段，`RunState` 的 validator 强制它们互相一致。

---

### A7 上下文怎么构造

**答**：
> 不是消息历史，是一条确定性流水线：`collect → select → compact → render`。每轮从 committed State 重新投影 Working Memory，再组装成 section。
>
> 每个 section 带 `origin` 和 `trust` 标签，而 `model / tool / provider` 这三种来源**永远**只能是 untrusted——这条写在 pydantic validator 里，非法组合构造不出来。

**追问链**：
- 上下文会不会随 run 增长？→ 不会。L0/L1 是固定地板，Evidence catalog 有界（64 + 历史块），近期交互只取最近 3 步。
- 放不下怎么办？→ 必需段超预算直接抛 `RequiredContextOverflow` 走 partial，不截断；可选段按降级序 TRUNCATE 再 DROP。

---

### A8 完成怎么判定

**答**：
> `finish` 只是模型的 proposal。`CompletionPolicy` 对**已提交状态**独立评估，返回四种处置：`accept_complete` → completed，`reject_and_continue` → 继续跑（不产生任何状态变化），`accept_partial` / `safety_stop` → partial。

**追问链**：
- 拒绝的时候模型看到什么？→ 拒绝理由。而且理由必须可执行——见 B10。
- 判定什么时候算的？→ 在 `finish` 从 Decision 变成 Action 的那一刻，结果打包进 `FinishAction`。所以判定依据是确定的。

---

### A9 崩溃了怎么恢复

**答**：
> 每个阶段边界都落 checkpoint，`classify_resume` 只看持久化状态决定这一步做什么。三个关键窗口：
>
> - **已保存 `ACTION_RUNNING`、Observation 未落盘**：重新执行，但先查磁盘上的成功结果缓存，命中则**零次 provider 调用**；
> - **Observation 已落盘、State 未提交**：重建 delta 并提交，**绝不再次调用工具**；
> - **State 已提交、调用方未拿到结果**：`continuation_pending` 保证先评估完成判断，不重复执行。

**追问链**：
- 能保证 exactly-once 吗？→ 不能。见 B4。

### A10 测试怎么做的

**答**：
> 89 个测试文件、约 18.8k 行，分 unit / contract / integration / e2e / security / investigation。但我不以数量为准，而是看每组测试对应哪个不变量：
>
> - **恢复矩阵**——构造每种持久状态，断言 model / resolver / executor / adapter 的**调用次数**；
> - **跨进程缓存复用**——全新组件 resume，断言 adapter 调用 0 次；
> - **100 步 / 640 Evidence 长轨迹**——证明 Context 有界、确定、resume 后字节一致；
> - **14 路注入矩阵**——证明信任标签不被洗白；
> - **真实 MCP E2E**——走完 discovery 到 ToolResult 全链路。

**追问链**：
- 数量是多少？→ 正常环境 779 passed / 2 skipped；我在受限沙箱里重跑是 788 passed / 3 failed / 2 skipped，3 个失败是轮询终态的时限断言被拖慢，不是逻辑失败。**（口径见 `05 §1`）**

## B · 进阶层

### B1 为什么不用 LangGraph / LangChain / LlamaIndex / AutoGen，是不是重复造轮子

**答（workload 层，主答 60 秒）**：
> 先看 workload：舆情搜索是**垂直 deep research**——开放问题、长程、多源、要引用、不能编。这类系统公开的实现有个共同点：**薄 loop + 厚策略/证据**。
>
> OpenAI 的 Deep Research 公开描述是端到端 RL 训练的浏览模型加工具，不是基于某个编排框架；Gemini 是自研 agentic system 去驱动浏览；Anthropic 的 Research 是自研 orchestrator，checkpoint / resume / tracing 自己做；Jina 的开源实现就是一个 search → visit → reflect → answer 循环加 gap 队列和 token 预算；dzhng 的版本刻意做到 <500 行。最出名的大规模 LangGraph 版本是 LangChain 自己的 open_deep_research，但作者后来写"bitter lesson"：早期 workflow / multi-agent 的编排结构成了瓶颈，最后只保留 low-level 的节点 / 边 / checkpoint。
>
> 所以不是"框架不能用"，是**结构该放在哪一层**。deep research 的经验是编排结构会随模型变强变成负担；舆情真正需要的结构在领域层：事实基线 / 立场 / 主叙事 / 反叙事四个 gap、时效窗、来源关系与独立信源、证据冻结与引用、信任标签、finish 验收、报告契约——这些没有框架提供，写进图里只会把研究策略打散。
>
> 我的选择是 loop 做薄（四个动作 + 七阶段事务），结构做厚在领域层，策略可以一周一改、用确定性测试验证。反过来，如果目标是两周做一个通用 deep research demo，我会直接用 LangGraph，甚至直接调 API。

**答（抽象层，15 秒，追问"更深一层"时用）**：
> 框架抽象的是**编排**——图、链、检索流程、多角色对话，共同点是"你写控制流，框架负责跑"。我抽象的是**提交**——一次 run 是一串可提交的事务，模型只是事务里的提案输入。前者问"Agent 怎么编排"，后者问"一次运行怎么被安全地提交和恢复"。

**答（框架清单版，30 秒）**：
> 这四个不是一类东西：LangChain 是框架层（集成 + middleware），LangGraph 是运行时层，LlamaIndex 是数据层，AutoGen 是多 Agent 层。
>
> 判断标准是 Agent Runtime 属于**实现手段**还是**要交付的能力**。这个项目要交付的正是执行语义——状态何时更新、工具调用如何恢复、step 如何提交、context 如何重建、finish 如何验收——所以我需要"我能证明的语义"，而不是"框架能跑的语义"。
>
> 如果目标是快速交付业务 Agent，我会直接用 LangGraph。脱离场景说谁更好都不专业。

**追问链**：
- 你说的抽象具体是什么？→ 五个问题：推进单位是 step（七阶段 + 一个 commit 点）、下一步由持久化状态经 `classify_resume` 纯函数推出、权威状态是最小领域 State、副作用按 `action_id` 认领（at-most-once 复用）、完成由 `CompletionPolicy` 对已提交状态判定。
- 这个抽象有什么代价？→ 表达力收窄：没有任意图、并行分支、动态拓扑，单 Agent 单写者；换来每个崩溃窗口有明确契约、每个组件调用次数可断言。只在"运行可靠性本身是交付物"时划算。
- 这不就是分布式系统 / 工作流引擎那套？→ 思想有重叠（durable execution、event sourcing、saga）；区别是这里的失败源多了两个：模型不确定、外部世界不可靠且不可回滚。所以我保留 action identity 和提交边界，但没有上完整工作流引擎。
- LangChain 的 open_deep_research 就用了 LangGraph，怎么解释？→ 对，而且它排到 DeepResearch Bench 前列，说明框架能做出 deep research。但作者复盘"bitter lesson"：最早的 orchestrator-worker workflow 和多 Agent 都因为预设结构成了瓶颈，最后只保留 low-level 节点 / 边 / checkpoint。说明框架不是胜负手，**结构能不能随时拆掉**才是。我的场景还多一层舆情证据纪律（来源关系、未核实、数字护栏），这层必须在领域层。
- 为什么不直接调 OpenAI / Gemini 的 Deep Research API？→ ① 领域字段：通用 API 给不了事件时间线、claim/response/narrative、来源关系、not_found 语义；② 可审计：报告要引用、数字护栏、trust 标签，产物要能回放；③ 成本与终止：长程舆情调查的预算和停止条件要自己定。另外 OpenAI 官方自承 deep research 的局限是"难分权威信息与谣言、置信度校准弱"——这恰好是舆情要解决的核心。
- 从 workload 看，四个框架分别缺什么？→ LangChain 缺研究策略（集成层）；LangGraph 缺领域结构（图不是覆盖率模型，也不是证据账本）；LlamaIndex 缺动态性（它假设可索引语料，舆情是开放 Web 实时调查，事件检索是 FTS5/BM25 + 时间窗）；AutoGen 缺单 Agent 的覆盖策略（多 Agent 试过，产出重复材料，且 Anthropic 自己测的多 Agent 是 15× token）。
- 它们具体差在哪？→ LangChain v1 的 `create_agent` 建在 LangGraph 上，选它基本等于选 LangGraph 的运行时 + 一层 middleware，而主要工作量在 validator / resolver / processor / reducer / compiler，它不覆盖；LangGraph 最接近，有 checkpointer 和 durable execution：checkpoint 落在 super-step 边界、节点输出以 pending writes 落盘（同一 super-step 内已成功的节点不重跑），但 checkpoint 之后的节点重放时会重新执行模型调用、外部请求和 interrupt，`interrupt()` 也从节点开头重跑。我这里按 7 个 `StepPhase` 和 `action_id` 恢复，外部副作用复用而不是重放，且图状态会和领域 State 形成两个事实源；LlamaIndex 的 Workflows 默认没有内置 checkpointer，恢复是 at-least-once，而且它假设有可索引语料，我的证据来自开放 Web；AutoGen 是多 Agent，AgentChat 只有手动的 save/load state 与 HITL 组件、没有 run 级 checkpointer，且已由 Microsoft Agent Framework 接替——多 Agent 我实现过并砍掉了。
- 那不就是重复造轮子？→ 有边界：`runtime/` 约 2.7k 行，provider 生态、追踪 UI、多 Agent、sandbox 都没做，pydantic / httpx / mcp 直接用。造的"轮子"是**可验证的事务语义**，这部分框架不承诺。
- 用框架更成熟，自己写 bug 更多吧？→ 正确性面更窄但可断言：恢复矩阵断言 model / resolver / executor / adapter 的调用次数，跨进程 resume 断言 adapter 0 次，构造的 100 步 / 640 Evidence 断言 context 有界且字节一致。代价也认：没有生态、维护成本自担。
- LangGraph 也能做吧？→ 能做，问题是账算给谁：语义它实现，我只能相信或读源码；语义我实现，我能证明。迁移时领域层可复用，重做的是事务映射，且要先验证 saver / interrupt 对三个崩溃窗口的调用次数承诺。
- 那 OpenAI Agents SDK / Google ADK / PydanticAI 这类更新的 SDK 呢？→ 同一标准：它们给 loop + handoff + guardrail + tracing，不给相位级事务和 action identity。不交付 Runtime 时，用它们更划算。
- 那我在 LangGraph 里写一个大节点，自己管提交和幂等，不就行了？→ 可以，但那时你是在框架之上重建语义：重放仍按它的 checkpoint 走、状态合并仍按 channel、幂等仍要你自己证明。成本没消失，只是从"实现"变成"对齐"。
- 那为什么不直接用 Temporal / Restate 这类 durable execution 引擎？→ 它们保证活动不丢、可重试，但不决定"下一步该发生什么"，也不管相位判定、action 幂等和 finish 验收；为单机 Runtime 引入它们，是拿运维复杂度换语义，不划算。
- 你说的 18 次拒绝，是机制还是 bug？→ 是设计缺陷，不是卖点：当时只有拒绝、没有诚实停止出口，模型空转到步数耗尽。后来补了可执行拒绝理由；另有一条 `ACCEPT_PARTIAL` 出口由领域策略决定诚实停止。
- 什么时候你会直接选框架？→ 当 Runtime 不是核心竞争力、需求偏向多节点业务编排和快速上线时。

（展开见 `04 §A1`；旁证见 `03 §L2`、`05 §2`）

### B2 多 Agent 你试过吗

**答**：
> 试过，评估后砍掉。实现过一版 planner / research / analyst / reviewer 的分层流水线，2026-09-21 归档到 `archive/harness-pipeline/`，三条理由：
>
> 1. 它重复了 PagePlan + targeted search 已有的能力；
> 2. 它绕过了 Runtime 的可靠性机制（没走 step transaction / checkpoint / completion gate）；
> 3. 它不解决真正的瓶颈——如果单 Agent 不知道该覆盖哪些维度，复制成四个只会**并行地产生更多散乱材料**。

**追问链**：
- 什么情况下多 Agent 才值得？→ 当"独立 SearchIntent 的并行"确实成为瓶颈，而且子任务的**状态合并语义**能说清楚的时候。顺序是先做清单 Agent 的覆盖策略，再考虑并行。
- 为什么说状态合并是难点？→ 因为要合并就必须决定冲突解决、并发 checkpoint、失败传播——这些都会侵蚀"单一权威状态"这个性质。

（展开见 `04 §A2`）

### B3 crash 在七个 StepPhase 各自如何恢复

**答**：

| 崩溃时 phase | resume 判定 | 恢复动作 |
|---|---|---|
| `OPENED` | `REQUEST_DECISION` | 进入 `mark_deciding`，重新请求决策 |
| `DECIDING` | `REQUEST_DECISION` | 直接重新请求决策（`attempt` 已在 checkpoint 里） |
| `DECISION_ACCEPTED` | `RESOLVE_ACTION` | 重跑 Resolver；**无外部副作用** |
| `ACTION_RUNNING` | `EXECUTE_ACTION` | 重新执行，但先查成功缓存，命中则零 provider 调用 |
| `OBSERVATION_READY` | `REDUCE_OBSERVATION` | 重建 delta 并提交，**绝不再次调用工具** |
| `REDUCING` | `REDUCE_OBSERVATION` | 同上；`commit_step` 幂等保护防重复应用 |
| `COMMITTED` | —— | 不是持久 phase；下一步是 `OPEN_STEP` 或 `EVALUATE_CONTINUATION` |

**追问链**：
- 哪个最危险？→ `ACTION_RUNNING`，它是唯一存在重复外部调用窗口的阶段。`OBSERVATION_READY` 则必须零调用。
- 怎么验证的？→ 恢复矩阵不只断言"最终完成"，还断言各组件的调用次数。

（展开见 `03 §L1`）

### B4 exactly-once 能保证吗

**答**：
> 不能。准确承诺是 **at-most-once 复用已持久化的成功结果**，加上**状态效果的幂等**——合起来可以说 effectively-once state effect。
>
> 真正的外部 exactly-once 需要 provider 接受幂等键、共享事务存储、outbox/inbox 或协调协议。当前结果缓存只有单机文件原子性和进程内锁；两个进程同时恢复同一个未缓存的 action，仍可能都调用 provider。
>
> 而且这个承诺依赖一个前提：**舆情工具是只读的**，重发安全。

**追问链**：
- 那"provider 已收到请求、结果还没写缓存"这个窗口怎么办？→ 无法完全消除，这正是不能声称 exactly-once 的原因。
- 生产化还需要什么？→ run ownership/lease、action record 的 compare-and-set、provider 支持时传 action_id 作为幂等键、有副作用工具的补偿或人工确认。

（展开见 `03 §L2`、`04 §B3`）

---

### B5 Decision retry 与 Tool retry 有什么区别

**答**：
> **Decision retry 换的是语义，Tool retry 保的是同一身份。**
>
> - Decision retry：同 `step_id`、`attempt + 1`，`action_id` **变**——模型要再想一次；
> - Tool retry：同 `action_id`，只有 `ToolInvocation.attempt` 递增——业务意图和参数没变，只是物理重试。
>
> 混淆的后果很具体：如果让模型处理底层重试，每次 retry 都会变成新 step、新 action_id，既污染调查历史，也无法统一控制退避、限流和熔断。

**追问链**：
- 跨 provider fallback 算哪种？→ Tool retry。业务意图和参数没变，只是执行者变了，所以 `action_id` 恒定。

（展开见 `03 §L4`）

---

### B6 为什么 Reducer 必须是纯函数

**答**：
> 三个理由：**可重放、可测试、恢复语义可判定**。
>
> - 可重放：窗口 B 的恢复就是"重新构造 delta 并提交"；
> - 可测试：给定旧状态和 delta 就能断言，不需要 mock；
> - 恢复可判定：如果 reducer 里有时钟，同一份 checkpoint 在不同时间恢复会得到不同状态。
>
> 所以 I/O 在 `ActionExecutor`，翻译在 `Processor`，纯状态合并在 `Reducer`。

**追问链**：
- 无变化时怎么办？→ 返回原对象、**不递增 revision**。所以 revision 变了精确等价于状态真的变了。
- 派生视图能写回吗？→ 不能。一旦能写回就有两个事实源。

（展开见 `03 §L3`）

---

### B7 为什么 ActionResolver 失败可以回退，Reducer 不变量必须 fail closed

**答**：
> 分界线是**是否已经产生了不可撤销的事实**。
>
> - `ActionResolver` 失败时还没有任何外部副作用，回退到 `DECIDING` 只是让模型再想一次，安全；
> - Reducer 不变量失败意味着**已提交的状态内部矛盾了**，继续跑会污染更多事实，必须转 `FAILED` 并带上 `RuntimeFailure`。

**追问链**：
- 回退是怎么实现的？→ `repair_accepted_decision` **从零重建** `StepRecord`，丢弃被拒的 Decision 和部分载荷，同时保留 prior failures 的顺序。
- 为什么不直接改现有 StepRecord？→ 重建比变异安全——变异容易留下上一个 attempt 的残留字段，而 `StepRecord` 的 phase↔payload validator 恰好会拒绝这种残留。

（展开见 `03 §L4`）

---

### B8 trust 和 priority 为什么正交

**答**：
> priority 决定"**预算紧张时先丢谁**"，trust 决定"**能不能当指令**"。
>
> 一个 untrusted 的高优先级证据——比如刚读到的关键报道——仍然只是**数据**，不能被当成指令执行。反过来，一个低 priority 的 trusted section 仍是可信控制信息，只是可能在预算不足时被丢掉。
>
> 正交的工程意义是：**降级策略不能影响安全策略**。压缩按 priority 排序，但无论怎么压，`model/tool/provider` 的 trust 标签都不会变。

**追问链**：
- 怎么保证不变？→ pydantic validator 直接拒绝 `model/tool/provider + trusted` 这个组合，构造不出来。
- 混合内容怎么办？→ 拆开。tool error 的 `kind/attempts/retryable/action_id` 是 trusted，`message` 是 untrusted；完成拒绝的 `disposition` 是 trusted，`reason` 是 untrusted。

（展开见 `03 §L5`、`04 §D2`）

---

### B9 为什么必需上下文放不下时不截断

**答**：
> 因为**截断会让"必需"名不副实**。L0 系统规则被砍掉一半，模型行为就不可预测了。
>
> 所以宁可 typed partial stop：抛 `RequiredContextOverflow`，run 以 `PARTIAL` 收尾。可选段才有降级——先按降级序 TRUNCATE（只对允许截断的段），再按降级序 DROP（只对非 required 且非 NEVER 的段）。

**追问链**：
- 降级顺序是什么？→ `(untrusted 优先, L3 优先, 低 priority 优先, section_id 打破平局)`。最后一项是确定性的关键。
- 为什么 untrusted 先降级？→ 因为它的信息价值可以被重新获取（重读页面），而 trusted 控制信息的价值无法从别处补。

（展开见 `03 §L5`、`04 §D4`）

---

### B10 为什么 finish 不由模型决定

**答**：
> 因为模型会受上下文长度、最近材料、生成偏好和推理预算影响，**不能同时当研究者和验收者**。它有"想收工"的激励。
>
> 所以 finish 只是 proposal，由 `CompletionPolicy` 对已提交状态做独立判断。判定依据不是模型说了什么，而是 State 里有什么。

**追问链**：
- 拒绝之后模型怎么办？→ 这是最关键的一环。**拒绝理由必须可执行**。原始实现只有一句 "Required investigation questions remain open."，模型没有任何可执行的下一步，一次 live run 里空转了 **18 次**。修复是让闸门对每个 open 问题输出"未处置证据 + 未读候选 + 三条合法出路"。
- 三种 disposition 的差别？→ `REJECT_AND_CONTINUE` 不产生任何状态变化；`ACCEPT_PARTIAL` 保留已提交成果。

（展开见 `03 §L7`、`06 §1`）

---

### B11 为什么 provider fallback 属于 Executor

**答**：
> 因为**模型不该知道 provider 存在**，**Adapter 只做协议归一化**。
>
> - 让模型处理底层重试 → 每次 retry 变成新 step、新 action_id，污染历史；
> - 让 Adapter 自己重试 → 每个 adapter 一套退避策略，退避上限、熔断状态、超时都散在各处，无法统一审计。
>
> 所以 retry / fallback 是**确定性执行策略**，由 `ToolExecutor` 统一拥有；模型只负责领域策略——换 query、换方向、换候选。

**追问链**：
- Adapter 的职责边界是什么？→ **恰好一次** provider 调用 + 协议归一化。docstring 里写着 "Each adapter performs exactly one provider invocation and never builds its own retry loop."
- 错误怎么分类？→ 三组：可重试（timeout/rate_limited/server_error）、立即停止（invalid_arguments/unknown_tool/cancelled）、可跨 provider 回退（auth/permission/not_found/unreadable_content/content_too_large/unknown_provider_error）。

（展开见 `03 §L6`）

---

### B12 为什么 auth 失败不触发熔断

**答**：
> 因为 auth / permission 是**配置问题**，不是 provider 健康度。如果它们计入熔断，一次配错的 API key 会把这个 provider 静默屏蔽，**掩盖真正的配置错误**。当前设计让它在下一次运行仍然可见。
>
> 只有 timeout / rate_limited / server_error / unknown_provider_error 才是"provider 现在不健康"的信号，计入熔断。

**追问链**：
- 熔断 key 为什么是 `(tool_name, provider_id)`？→ 只按 provider，某工具接口故障会让该 provider 其他能力一起不可用；只按 tool，一个 provider 故障会遮蔽另一个健康 provider。
- 熔断状态存哪？→ **只在内存**，重启即重置。它是执行健康度，不是领域状态，进 checkpoint 会带来"恢复时该不该恢复熔断状态"这种没有好答案的问题。

（展开见 `03 §L6`、`04 §B6/B7`）

---

### B13 MCP 已经 HTTPS 了，为什么还不可信

**答**：
> **HTTPS 证明的是传输加密和服务器身份，不证明返回内容拥有系统指令权限。** 信任按**内容生产者**划分，不按传输是否加密划分。
>
> 所以 remote description、annotations、content、`_meta` 全部是 untrusted 输入。

**追问链**：
- 那你们做了什么？→ 四重收紧：discovery **原子注册**（先全部验证再注册）、**schema pin**（canonical SHA-256 固定远端契约）、**递归元数据过滤**（每层剥离，且先过滤后验证）、**output schema fail closed**（声明了 schema 却返回非结构化 content 就直接失败）。
- 为什么不动态注册 server 返回的所有工具？→ discovery 是能力发现，**不是授权**。动态全注册会让 server 通过新增工具扩大 attack surface。

（展开见 `03 §L6`、`06 §4`）

## C · 深挖层

### C1 如果让你重做，你会改什么

**答**：
> 三件事，按优先级：
>
> 1. **把 domain 收敛成一套**。现在两套领域语义高度重叠，是"Runtime 领域无关"的好证据，但长期维护成本真实存在。
> 2. **补 run ownership / lease**。当前恢复语义清晰，但"两个进程同时恢复同一个 run"没有互斥——这是最直接的可靠性缺口。
> 3. **把 `collect` 阶段也抽成共享契约**。现在两个域各写一份 collect，共享的只有 compact 和 section 模型；如果再来第三个域，重复会变成负担。

**追问链**：
- 为什么不是先加功能？→ 因为这三件都是**已经在架构里留了位置**的事，加功能会让它们更难做。

---

### C2 这个系统最大的不足是什么

**答**：
> **基础设施深度强于领域搜索质量。** 具体证据：
>
> - 检索召回 60%（6/10 必中项），缺口来自聚合站偏向（66% 候选来自单一聚合站）和反爬读取失败（6/17）；
> - 反方材料**已读、已摘 5 条证据，但零 finding 引用**——说明"找到"和"用上"之间有断点；
> - 模型不会主动把长期无证据的问题从 `open` 转 `not_found`——这是 gate 拒 finish 18 次的原因（空转机制见 `06 §1`）；
> - 数字护栏只验**出处**不验**可信度**，真实 316.03 亿和埋点 3160.3 亿静默并存。

**追问链**：
- 哪个最该先修？→ "反方材料已读未用"和"不主动收口 `not_found`"是同一个病的两面：**Agent 缺少"覆盖度"这个显式的决策信号**。所以下一步是 OpinionAnalysisFrame + SearchIntent + CoverageMap 的最小闭环。
- 为什么不做多 Agent？→ 因为它不解决这个病。见 B2。
- 架构层最大的局限是什么？→ 三条，而且都能量化：① **验证自闭环**——不变量我定、断言我写，没有外部 conformance（LangGraph 有 checkpointer conformance suite，我没有）；② **单机无 lease**——两个进程同时恢复同一个未缓存 action 仍会双调 provider，承诺只在"工具只读 + 单写者"下安全；③ **全量快照写放大**——60 步 run 的 `run.json` 已约 700KB，每步 7 个边界各写一次全量，写放大我没有量化。所以它证明的是"我要的语义被实现了"，不是"分布式也成立"。

（展开见 `05 §6`）

---

### C3 怎么扩展到分布式

**答**：
> 分三步，而且**不需要改 Runtime 的语义**：
>
> 1. **run ownership / lease**——解决两个进程同时恢复同一 run；
> 2. **把 checkpoint / action result 抽象换成支持 CAS 的持久后端**——保留现有 schema 与 phase 语义；
> 3. **给有副作用工具加 idempotency capability metadata**——明确哪些 action 可安全重试。
>
> 熔断器需要共享 provider health 或引入 Tool Gateway。

**追问链**：
- 为什么说不用改语义？→ 因为 `CheckpointStore` 和 `ToolResultCache` 本来就是 `Protocol`，替换实现即可。这正是当初把它们抽成接口的收益。
- 最难的在哪？→ 第 3 步。前两步是工程问题，第 3 步需要领域判断——"这个工具能不能安全重试"不是 Runtime 能回答的。

---

### C4 为什么不用向量数据库

**答**：
> 当前是单 run、几百条 Evidence 的规模。这里首先需要的是**确定性引用和可恢复**，不是百万文档召回。
>
> 向量库会引入 embedding 版本、召回不确定性，以及**第二事实源**的风险——**检索结果不确定，"相同 State 生成相同 Context"这条性质就没了**。而这条性质是长轨迹测试和 resume 一致性的基础。

**追问链**：
- 那什么时候该用？→ 当 artifact 规模超过结构索引能力时，可以把向量检索作为**派生索引**加入，但不能取代 State。
- 现在怎么检索？→ 两层。Evidence catalog 用**语义关系**排序（不是相似度）；investigation 域的重访用 SQLite FTS5 + BM25，而且 FTS **每次从已提交的 source 重建**，本身不是权威。

（展开见 `03 §L5`、`04 §D6`）

---

### C5 CompletionPolicy 会不会太僵硬

**答**：
> 会——**对当前 milestone 是合适的，但不是通用解**。固定四维（事实基线 / 主体立场 / 主导叙事 / 反叙事）适合可测试的基线，但确实不适合所有舆情任务。
>
> 下一步应该由 `OpinionAnalysisFrame` 动态生成 required coverage，再让通用 completion engine 检查 `CoverageMap`。**关键是 Runtime 的 completion protocol 不需要改**——`CompletionVerdict` / `CompletionDisposition` 这两个类型已经够用。

**追问链**：
- 那固定四 Gap 现在有什么价值？→ 它保证 Agent 不会"找到几篇支持同一观点的页面就直接结束"。而且"反叙事缺失时宁可标不足也不强行生成"是保守的正确行为。
- 代价是什么？→ 覆盖率上限就是这四维的覆盖范围。

（展开见 `03 §应用层`）

---

### C6 两套 domain 怎么收敛

**答**：
> 我倾向收敛到 `domain/investigation`，理由是它更接近真实产品形态（有澄清、有更新、有 review、有 page plan），而 opinion 域的四个固定 gap 更像是可测试基线。
>
> 但收敛不该现在做，因为：
>
> 1. 两套并行是"Runtime 领域无关"的**唯一实证**，砍掉一套就只剩声明；
> 2. `domain/opinion` 的 `Claim / StakeholderPosition / Narrative` 是**权威对象**，而 investigation 把它们退化成了 finding 字段——收敛要先决定哪一种是长期正确的建模。

**追问链**：
- 那什么时候做？→ 当第三个领域出现时。那时候会有足够信息判断哪些是"领域共性"、哪些是"某个领域的特例"，而现在只有两个样本。

---

### C7 如果模型更强了，这套 Harness 还有价值吗

**答**：
> 有，而且**越强越需要**。理由是价值不在"弥补模型能力"，而在**约束模型能改变的范围**：
>
> - 模型再强也会输出格式错误、引用不存在的 ID、在长任务里漂移；
> - 模型再强也有"想收工"的激励，不会自己当验收者；
> - 模型再强也不该拥有直接改权威状态的权限——因为它会犯错，而状态错了后面全错。
>
> 反过来，模型越强，**Harness 的价值越体现在"放开多少自由度"上**——比如现在 `required_next_action` 会强制 reflect，如果模型自己就会合成，这条约束就该放松。

**追问链**：
- 有什么具体证据说明约束是必要的？→ 空拒绝导致 18 次空转、`required_next_action` 的注释写着"Prompt advice alone did not stop a live quality run..."。都是"模型自己没做到"的实测。

### C8 怎么保证测试不是只验证自己的假设

**答**：
> 风险存在，所以关键测试**从故障模型出发，而不是复现实现路径**：
>
> - 构造**撕裂的 phase**（phase 与载荷不匹配的 checkpoint）；
> - 构造**损坏的 cache**（损坏 JSON、截断的临时文件、identity 冲突）；
> - 用**跨进程的全新组件** resume，而不是复用同一个对象；
> - 用**恶意 MCP payload**（嵌套 metadata、循环引用、不可序列化对象）；
> - **14 路注入矩阵**和**长轨迹压力测试**。
>
> 另外真实 provider smoke 和 stdio MCP E2E 会验证 adapter 层的假设。

**追问链**：
- 那还缺什么？→ 缺**真实舆情数据集**上的领域效果验证。这是下一步，不能拿单元测试数量冒充效果评测。

（展开见 `05 §2`）

---

### C9 只能选一个下一步，你选什么

**答**：
> **OpinionAnalysisFrame + SearchIntent + CoverageMap 的最小纵向闭环。**
>
> 理由是当前 Runtime 已经足以承载复杂迭代，而最影响最终价值的是 **Agent 不知道"下一次搜索是为了补哪一类舆情语义覆盖"**。先解决决策质量，再考虑并行和平台化。

**追问链**：
- 具体怎么做？→ ① 把主题/事件/时间/stakeholder/aspect/风险问题冻结成任务结构；② 定义有限的 SearchIntent taxonomy；③ 从 Evidence 提取 holder-target-aspect-stance-time-source 结构化 OpinionSignal；④ 建 CoverageMap 回答"哪些主体/议题/立场/时段缺失"；⑤ 用 marginal information gain 和 saturation 作为下一步与停止信号。
- 这还算 Agent Infra 吗？→ 算。这些属于 Domain Policy，但它们会**反过来验证** Context selection、Working Memory 投影、Completion Control 和长程 Loop 是否真的支持复杂 workload。

（展开见 `agent-infra-interview-deepening.md` §3.3）

### C10 你觉得自己在这个项目里做对了什么

**答**：
> 三件我认为做对了的：
>
> 1. **把"信任"写成了类型约束而不是约定**。`model/tool/provider` 永远不能 trusted 这条，如果是靠 code review 守，早就破了。
> 2. **把恢复做成了主路径而不是补丁**。`run()` 的每个分支都以 `continue` 结尾，首次执行和恢复天然同路径——所以不会出现"恢复路径没跟上主路径"的漂移。
> 3. **砍掉了多 Agent**。写出来的东西很多，但**决定不做什么**更难，也更值钱。

**追问链**：
- 有没有做错的？→ 有。比如早期把"完成判定"和"状态变更"耦合得比较紧，导致被拒的 finish 也产生状态变化；后来才明确 `REJECT_AND_CONTINUE` 必须返回空 delta。
- 还有别的吗？→ 文档和代码的漂移。我后来做了一次全量核对，发现蓝图和决策清单描述的是已经归档的多角色路线。这件事的教训是**文档必须跟着代码走，而不是反过来**。

## D · 反问题

面试最后"你有什么想问的"，问这些能显专业度：

| 问题 | 想了解什么 |
|---|---|
| 团队现在的 Agent 是在框架上做，还是自研 Runtime？ | 判断团队对执行语义的重视程度 |
| 你们的 Agent 有长时间运行的需求吗？崩溃恢复目前怎么处理？ | 判断可靠性是否是真实痛点 |
| 模型输出不稳定的时候，你们是在 prompt 层解决还是加了程序约束？ | 判断团队踩过哪些坑 |
| 有没有做过模型升级导致的回归？怎么发现的？ | 判断可观测性成熟度 |
| Agent 的"完成"是模型说了算还是有独立判定？ | 直接对应本项目最核心的设计 |
| 你们怎么衡量 Agent 的质量？有 eval 体系吗？ | 判断工程成熟度（本项目明确没做） |

**不要问**：薪资、加班、"你们用什么技术栈"（太泛）。
