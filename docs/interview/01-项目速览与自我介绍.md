# 01 · 项目速览与自我介绍

> 这一篇是开场。面试前先背 `§1` 的一句话和 `§2` 的 30 秒版，其余按时间档位选用。
> 所有数字的口径见 `05`；所有代码符号的落点见 `09`。

## 1. 一句话定义

> **一个面向公开 Web 舆情调查的可恢复单 Agent Harness；它能在不可信工具输出、有限模型上下文和外部服务失败下，保持决策、执行、状态提交与恢复语义的一致性。**

这句话有四个承重词，每个都能被追问：

| 词 | 含义 | 展开在哪 |
|---|---|---|
| **可恢复** | 崩溃在任一阶段边界都能定位并继续；首次执行与恢复走同一条代码路径 | `03 §L1 / §L2` |
| **单 Agent** | 显式自研 async loop，不是图框架；多 Agent 提案已评估并否决 | `04 §2` |
| **Harness** | 项目本体是执行骨架，不是"调用模型 + 搜索 API"的薄封装 | `02` |
| **一致性** | 决策 / 动作 / 观察 / 状态四层分离，Reducer 是唯一写入口 | `03 §L3 / §L4` |

**项目规模**（可当场报）：`src/` 91 个 Python 文件、约 20.6k 行；`tests/` 89 个文件、约 18.8k 行；Python 3.12+ / asyncio / pydantic v2 / httpx，Web 层零新增依赖（stdlib `http.server`）。

## 2. 30 秒版

> 我做的是一个公开 Web 舆情调查的 Agent Harness。核心不是搜索，是**一次长程 Agent 运行怎么可靠地走完**。
>
> 模型每轮只提一个决策——`search` / `read` / `reflect` / `finish`。Runtime 把它校验、解析成内部动作、执行、拿回 Observation，再由领域处理器构造 Delta，经**纯函数 Reducer** 提交成新的权威 State。每个阶段边界都落 checkpoint，所以崩溃恢复不是补丁，是和首次执行**同一条代码路径**——`run()` 就是一个 `while True`，每轮开头用 `classify_resume(state)` 只看持久化状态决定这一步该干什么。
>
> 我刻意只深做两层：Harness/Runtime，和 Tool/MCP/Context/Run-scoped Memory。多 Agent、LangGraph、Eval 平台我都不做——多 Agent 那条线我实现过，评估后砍掉归档了。

## 3. 3 分钟版

按"问题 → 做法 → 取舍 → 证据"四段讲，每段约 45 秒。

### 3.1 问题（45 秒）

> 长程 Agent 最容易出问题的地方不在"模型够不够聪明"，而在**执行语义**。具体是四个问题：
>
> 一、模型说的和它做的不一致——它说"我要搜 A"，实际搜了 B，或者引用了一个不存在的证据 ID。
> 二、崩溃恢复不确定——进程在"工具已经返回、状态还没提交"之间死掉，重启后到底该重放还是该复用？
> 三、上下文随历史线性膨胀，而且网页里的恶意指令和系统指令混在一起。
> 四、模型有"想收工"的激励，它会用一个看起来完整、实际没证据的答案结束 run。
>
> 这四件事框架通常帮你决定了，但这个项目要交付的正是这四件事本身，所以我把它全部显式化。

### 3.2 做法（45 秒）

> 我把一次 step 拆成七个阶段：`opened → deciding → decision_accepted → action_running → observation_ready → reducing → committed`。每个阶段边界都 checkpoint，并且每个阶段对"该携带哪些载荷"有硬约束——`StepRecord` 用 pydantic validator 强制 `ACTION_RUNNING` 必须已有 decision 和 action、但绝不能提前有 observation；`OBSERVATION_READY` 必须三个都有。反序列化一个被篡改或半写的 checkpoint 会**直接失败**，而不是带着脏状态继续跑。
>
> 关键设计是四个对象分离：模型产 `Decision`（语义意图），Runtime 解析成 `Action`（可执行单元），环境返回 `Observation`（外部世界发生了什么），领域处理器构造 `StateDelta`（希望改哪些状态）。只有 Reducer 能写权威 State。模型有提案权，没有写权。
>
> 上下文不是聊天历史，是一条确定性的四段流水线：`collect → select → compact → render`。每一段都带 `origin` 和 `trust` 标签，而 `model / tool / provider` 这三种来源**永远**只能是 untrusted——pydantic validator 直接拒绝非法组合。所以网页内容、工具返回值、模型自己上一轮说的话，无论经过多少次 commit、checkpoint、resume，都不会变成指令。

### 3.3 取舍（45 秒）

> 三个我明确不做的：
>
> **不用 LangGraph。** 如果目标是快速搭一个业务 Agent，我会直接用框架。但这个项目的核心问题就是"状态何时更新、工具调用如何恢复、step 如何提交、context 如何重建、finish 如何验收"——用图执行会把这些藏起来，项目就退化成"会写节点和条件边"。
>
> **不做多 Agent。** 我实现过一版 planner / research / analyst / reviewer 的多角色流水线，评估后归档了。三条理由：它重复了 PagePlan + targeted search 已有的能力；它绕过了 Runtime 的可靠性机制；而且它不解决真正的问题——如果单 Agent 不知道该覆盖哪些维度，复制成四个只会并行地产生更多散乱材料。
>
> **不做 Eval 平台。** 我有的是人工标注的领域质量检验，不是 benchmark。这是边界纪律：什么都在项目里做一点，就什么都讲不清。

### 3.4 证据（45 秒）

> 四组：
>
> **恢复矩阵**——直接构造每种持久化状态（deciding / decision_accepted / action_running / observation_ready / reducing / committed+continuation / terminal），不只断言"最终完成"，还断言 model、resolver、adapter、processor、reducer 各自的**调用次数**。比如 Observation 已保存时，adapter 调用必须为 0。
>
> **跨进程缓存复用**——先让旧 Executor 调用 provider 并把成功结果写 cache、但不把 Observation 写进 state，模拟精确的崩溃窗口；然后用全新的 registry、adapter、executor、cache 和 loop resume，断言 fresh adapter 调用 0 次、原 action_id 不变、state revision 只增加一次。
>
> **长轨迹与注入矩阵**——100 个 committed step、640 条 Evidence 的压力测试证明 Context 有界、可复现、resume 后字节一致；14 路 prompt injection 矩阵证明 commit/resume 不洗白信任标签。
>
> **一次真实 live run**——60 步、17 次搜索、17 次读取、14 条 findings、92 处引用；review 阶段跑出 6 supported / 8 partial；completion gate 拒绝了 `finish` 18 次，宁可诚实 partial 也不带着未回答的必答问题收尾。
>
> 而且这次 partial 的**诊断链是完整的**：候选来源 66% 集中在单一聚合站、原发媒体零覆盖；6/17 次读取被反爬拦下；4 条 partial finding 全是"引语在原文但摘录没摘到"。**系统不仅发现了自己的不足，还把它记进了产物**——这比拿到一个好分数更能说明可靠性机制在工作。

## 4. 10 分钟版（提纲）

3 分钟版讲完，面试官如果让你展开，按这个顺序走——**每段都能独立展开成 `03` 里的一整层**：

## 5. 边界与非目标（必须主动说）

主动划边界比等着被问"你为什么不…"要强得多。五个明确非目标：

| 不做 | 理由（一句话） |
|---|---|
| Environment / Sandbox / 浏览器集群 | 本项目验证的是 Harness 执行语义，不是隔离与资源调度 |
| Control Plane / 分布式 worker / 任务队列 | 当前是单机单写者模型，恢复语义清晰；分布式是下一步而不是现在 |
| Trace ingestion / Dashboard / Observability 平台 | 有 Run Bundle 与 SSE 进度流，但那是产品功能不是观测平台 |
| Eval / Benchmark 平台 | 有人工标注的领域质量检验，但不建设评测基础设施 |
| Model Serving | 用 OpenAI-compatible 客户端，不碰推理侧 |

还有三条**技术上不做**的，也要能答：

- 不做**向量检索 / 长期记忆**——当前是 run-scoped 投影，几百条 Evidence 需要的是确定性引用和可恢复，不是百万文档召回。
- 不接**登录态社交平台**（微博/抖音/小红书等）——`SOCIAL_DOMAINS` 在 Resolver 里被显式 `-site:` 排除，因为那类数据需要登录且不可审计。
- 不声称**外部 exactly-once**——实际是 at-most-once 复用已持久化的成功结果，且依赖"舆情工具只读"这一前提。

## 7. 三条取舍叙事（浓缩版，展开见 `04`）

**① 为什么自研不用 LangGraph**
> 取决于 Agent Runtime 是"实现手段"还是"要交付的能力"。这个项目要交付的正是执行语义本身，所以我把框架通常隐藏的机制展开并验证。脱离场景说谁更好都不专业——如果 Runtime 不是核心竞争力、需求偏向多节点业务编排和快速上线，我会直接选框架。

**② 为什么不做多 Agent**
> 实现过、评估后砍掉。理由不是"做不了"，而是它重复了已有能力、绕过了 Runtime 的可靠性机制、并且不解决真正的瓶颈。真正的瓶颈是"单 Agent 不知道该覆盖哪些舆情维度"——把这个复制成四个 Agent，只会并行地产生更多散乱材料。

**③ 为什么 finish 不由模型决定**
> 模型会受上下文长度、最近材料、生成偏好和推理预算影响，不能同时当研究者和验收者。所以 `finish` 只是一个 proposal，由 `CompletionPolicy` 对**已提交状态**做独立判断，返回四种处置。
