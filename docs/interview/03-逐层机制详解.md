# L1 · Loop 与生命周期

## 1.1 必须能讲清的机制

### 三个枚举，是整层的地基

**`RunStatus`（6 态）** —— `runtime/lifecycle.py`

```text
created → running → completed | partial | failed | cancelled
```

终态集合 `_TERMINAL_RUN_STATUSES = {completed, partial, failed, cancelled}`。允许的迁移只有 5 条边：

```text
created → running
running → completed / partial / failed / cancelled
```

**关键设计**：终态是**不可逆**的，没有 `partial → running`。想继续调查必须开新的 run。这条约束让"这个 run 结束了"成为一个可靠事实，而不是一个可以被后续代码推翻的判断。

**`StepPhase`（7 阶段）** —— `runtime/lifecycle.py`

```text
opened → deciding → decision_accepted → action_running
       → observation_ready → reducing → committed
```

允许的迁移是**严格线性**的 6 条边，没有跳阶、没有回退。注意：`decision_accepted` **不在** `StepPhase` 的"回退目标"里，但 `repair_accepted_decision` 会重建一个 `DECIDING` 阶段的 `StepRecord`——这是**新对象**而不是状态回退，见 L4。

**`ResumeAction`（8 个）** —— `runtime/transaction.py`

```text
START_RUN / RETURN_RESULT / EVALUATE_CONTINUATION / OPEN_STEP
REQUEST_DECISION / RESOLVE_ACTION / EXECUTE_ACTION / REDUCE_OBSERVATION
```

**`CheckpointBoundary`（10 个）** —— `runtime/loop.py`

```text
run_started / step_opened / deciding / decision_accepted / action_running
observation_ready / reducing / step_committed / continuation_applied / run_terminated
```

注意：`CheckpointBoundary` 有 10 个，`StepPhase` 有 7 个——多出来的三个（`run_started` / `continuation_applied` / `run_terminated`）是 **run 级**边界，不是 step 级的。

### `run()` 是状态分发器，不是顺序流程

这是整层最重要的一句话：

```python
async def run(self, state: RuntimeState) -> RunResult[Any]:
    while True:
        resume_action = classify_resume(state)
        if resume_action is ResumeAction.RETURN_RESULT:
            return result_from_state(state)
        ...
```

`classify_resume(state)` 是**纯函数**，只读 `RunState` 的四个字段：`status`、`continuation_pending`、`active_step`、`active_step.phase`。它的判定顺序是：

```text
status == CREATED                → START_RUN
status in TERMINAL               → RETURN_RESULT
continuation_pending             → EVALUATE_CONTINUATION
active_step is None              → OPEN_STEP
phase in {OPENED, DECIDING}      → REQUEST_DECISION
phase == DECISION_ACCEPTED       → RESOLVE_ACTION
phase == ACTION_RUNNING          → EXECUTE_ACTION
phase in {OBSERVATION_READY, REDUCING} → REDUCE_OBSERVATION
```

**由此推出三条结论**：

1. **首次执行与崩溃恢复走同一条代码路径。** 新建的 `RunState(status=CREATED)` 和从磁盘读回来的 `RunState(status=RUNNING, active_step.phase=ACTION_RUNNING)` 走的是同一个 `while True`。`resume()` 只是"先从磁盘 `load()` 再调 `run()`"：
   ```python
   async def resume(self) -> RunResult[Any]:
       state = await self._checkpoint_store.load()
       return await self.run(state)
   ```
   resume 不是补丁，是主路径。
2. **每个分支都以 `continue` 结尾**，回到顶部重新判定。没有嵌套，没有"接着往下执行"。所以"恢复到哪里"是一个**数据问题**（`state` 长什么样），而不是控制流问题。
3. **`run()` 不持有跨轮次的内存状态。** 所有需要跨越 `await` 的东西都在 `state` 里。

### 取消：竞速而不是简单 cancel

取消不能直接 `task.cancel()`，因为要区分两种语义：取消"赢得了"正在进行的 await，还是取消"到达时该步已经观察完毕"。实现是 `_await_operation`：

```python
async def _await_operation(self, operation) -> Any:
    if self._cancellation_signal.is_cancelled():
        raise _RunCancelled
    operation_task = asyncio.create_task(operation())
    wait_task = asyncio.create_task(self._cancellation_signal.wait_cancelled())
    done, _pending = await asyncio.wait(
        {operation_task, wait_task}, return_when=asyncio.FIRST_COMPLETED,
    )
    if wait_task in done:
        operation_task.cancel()
        ...
        raise _RunCancelled
    wait_task.cancel()
    ...
    return await operation_task
```

`asyncio.wait(FIRST_COMPLETED)` 让"操作"和"取消信号"**竞速，先完成者胜出**。

而在 `run()` 顶部的取消判定有一个关键的例外：

```python
if (
    state.status is RunStatus.RUNNING
    and self._cancellation_signal.is_cancelled()
    and resume_action is not ResumeAction.REDUCE_OBSERVATION
):
```

**`REDUCE_OBSERVATION` 被排除在外**。含义是：如果 Observation 已经落盘，那么即使此刻取消信号已经置位，该步仍然会被 reduce 并提交**恰好一次**，然后才终止 run。否则"同一个 Observation 的命运取决于取消时序"——这是不可接受的。

### 步数上限：为什么是 partial 而不是 failed

```python
if resume_action is ResumeAction.OPEN_STEP:
    if state.next_step_index > self._max_steps:
        state = terminate_run(
            state, target_status=RunStatus.PARTIAL,
            reason="The maximum number of committed steps was reached.",
        )
```

达到步数上限时，**已提交的工作全部保留**，终态是 `partial`。同理，`ContextOverflowError`（必需上下文放不下）也走 `partial`。这体现一条原则：**"做不完"和"做坏了"是两种不同的失败**，前者要保留成果。

## 1.3 面试追问与参考答法

**Q：crash 在七个 StepPhase 各自如何恢复？**

| 崩溃时 phase | resume 判定 | 恢复动作 |
|---|---|---|
| `OPENED` | `REQUEST_DECISION` | 进入 `mark_deciding`，重新请求决策 |
| `DECIDING` | `REQUEST_DECISION` | 直接重新请求决策（`attempt` 已在 checkpoint 里） |
| `DECISION_ACCEPTED` | `RESOLVE_ACTION` | 重跑 `ActionResolver`；**没有外部副作用**，安全 |
| `ACTION_RUNNING` | `EXECUTE_ACTION` | 重新执行 action；先查 `JsonActionResultCache`，命中则**零次 provider 调用** |
| `OBSERVATION_READY` | `REDUCE_OBSERVATION` | 重建 delta 并提交，**绝不再次调用工具** |
| `REDUCING` | `REDUCE_OBSERVATION` | 同上；`commit_step` 的幂等保护防止重复应用 |
| `COMMITTED` | —— | 不是持久 phase；`active_step` 已清空，下一步是 `OPEN_STEP` 或 `EVALUATE_CONTINUATION` |

重点讲 `ACTION_RUNNING` 和 `OBSERVATION_READY` 这两个：前者是**唯一存在重复外部调用窗口**的阶段，后者是**必须零调用**的阶段。

**Q：为什么 `run()` 是 `while True` 而不是顺序流程？**

> 把"恢复到哪"从控制流问题变成数据问题。顺序流程需要 `if crashed_at_step_3_phase_5` 这样的分支，而状态分发只需要看 `state` 长什么样。副产品是首次执行和恢复天然同路径，不需要为恢复写第二套代码，也就不会出现"恢复路径没跟上主路径"的漂移。

**Q：取消为什么不能简单 `task.cancel()`？**

> 因为取消有两种语义要区分。如果取消赢得竞速，正在等待的操作要被取消，且**不产生任何状态效果**；如果取消到达时 Observation 已经落盘，那这一步已经"发生过"了，必须 reduce 并提交恰好一次，否则同一个 Observation 的命运会取决于取消的时序，恢复语义就不可判定。所以顶部判定显式排除了 `REDUCE_OBSERVATION`。

**Q：`LoopHook` 为什么放在 Runtime 而不是 Web 层？**

> 因为"进度边界"是 Runtime 的概念，不是产品功能。`after_checkpoint(boundary, state)` 在每个 checkpoint 之后触发，Web 端把它接到 SSE 上。Runtime 和 Domain 一行都没为 Web 改过。这也意味着任何新的前端（CLI 进度条、日志、trace）都复用同一个接缝。

**Q：达到 `max_steps` 为什么是 partial？**

> "做不完"和"做坏了"是两种失败。步数耗尽时已经提交的工作是有价值的，必须保留。所以走 `PARTIAL` 而不是 `FAILED`。同理 `ContextOverflowError` 也是 `PARTIAL`。

# L2 · Step 事务与恢复

## 2.1 必须能讲清的机制

### 单写者提交链

```text
模型 Decision → Validator（合法性）→ ActionResolver（翻译成动作）
→ ActionExecutor（产生 Observation）→ Processor.build_delta（构造 Delta）
→ Reducer（纯函数，State × Delta → State'）→ Checkpoint
```

**这条链上，模型只在第一个箭头出现。** 后面五个箭头全是程序。这是整套设计的底线。

### `RunState` 与它的不变量

`RunState` 是 checkpoint 的顶层对象（`runtime/transaction.py`）：

```python
run_id: str
status: RunStatus = CREATED
domain_state: DomainStateT          # 领域状态，泛型
next_step_index: int = 1
active_step: StepRecord | None = None
committed_steps: tuple[StepRecord, ...] = ()
committed_action_ids: tuple[str, ...] = ()
continuation_pending: bool = False
stop_reason: str | None = None
failure: RuntimeFailure | None = None
```

它的 `validate_invariants` 是本层最密集的一段代码。核心不变量：

| 不变量 | 为什么 |
|---|---|
| `active_step.phase` 不能是 `COMMITTED` | 已提交的 step 必须从 `active_step` 移走 |
| `committed_steps` 里每个 step 的 phase 必须是 `COMMITTED` | 防止半提交混入历史 |
| 所有 step 的 `run_id` 必须等于 `RunState.run_id` | 防止跨 run 污染 |
| 所有 `step_id` 在 run 内唯一 | 防止重复提交 |
| `committed_action_ids` 必须等于 `committed_steps` 里 action 的 id 序列 | ledger 与历史必须一致 |
| `next_step_index == len(committed_steps) + 1` | 游标必须由历史推导，不能独立漂移 |
| `continuation_pending` 为真时：status 必须是 RUNNING、`active_step` 必须为空、必须有 committed step | 保证"待评估 continuation"是一个明确状态 |
| `status == CREATED` 时，运行历史必须全空 | 新建 run 不能带脏历史 |
| 终态：`active_step` 必须为空、`continuation_pending` 必须为假、`stop_reason` 必须有 | 终态必须干净且可解释 |
| 非终态不能有 `stop_reason` | 同上，反向 |
| `FAILED` 必须有 `failure`；非 `FAILED` 不能有 | 失败原因只在失败时存在 |

**注意最后一条的力度**：`stop_reason` 是 `NonEmptyText`，终态**必须**有停止原因。也就是说，"为什么停了"永远是可回答的。

### `StepRecord`：阶段 ↔ 载荷的硬约束

`runtime/protocols.py` 里有一张表：

```python
_STEP_PAYLOAD_FIELDS_BY_PHASE = {
    StepPhase.OPENED:             frozenset(),
    StepPhase.DECIDING:           frozenset(),
    StepPhase.DECISION_ACCEPTED:  frozenset({"decision"}),
    StepPhase.ACTION_RUNNING:     frozenset({"decision", "action"}),
    StepPhase.OBSERVATION_READY:  frozenset({"decision", "action", "observation"}),
    StepPhase.REDUCING:           frozenset({"decision", "action", "observation"}),
    StepPhase.COMMITTED:          frozenset({"decision", "action", "observation"}),
}
```

`StepRecord.validate_recovery_invariants` 检查三件事：

1. **实际载荷集合必须精确等于该阶段的期望集合**——多一个报 `premature`，少一个报 `missing`。
2. **每个信封的 `(run_id, step_id, attempt)` 必须与 step 一致**。
3. **`action.action_id` 必须等于 `observation.action_id`**。

**意义**：反序列化一个被篡改或半写的 checkpoint 会**在构造时直接失败**，而不是带着脏状态继续跑。这个校验不是靠 code review 守的，是靠 pydantic validator 让非法组合**构造不出来**。

### 四段信封：为什么需要它们

```python
DecisionEnvelope   { run_id, step_id, attempt, decision }
ActionRequest      { run_id, step_id, attempt, action_id, action }
ObservationEnvelope{ run_id, step_id, attempt, action_id, observation }
StateDelta         { run_id, step_id, attempt, action_id, delta }
```

`decision` 载荷本身不知道属于哪个 run、哪个 step。信封统一携带关联信息，`StepRecord` 再验证这些关联完全一致。

**后果**：一个旧 Observation 不可能被误提交给新的 attempt；一个 provider 的返回值不可能替换 action identity。

### `commit_step`：幂等与游标

```python
def commit_step(state, state_delta, reducer):
    if state_delta.action_id in state.committed_action_ids:
        # 已提交过 → 只做关联校验，返回原 state（幂等）
        ...
        return state

    step = _require_active_step(state, StepPhase.REDUCING)
    _validate_correlation(step, state_delta)
    ...
    new_domain_state = reducer(state.domain_state, state_delta.delta)
    validate_step_transition(step.phase, StepPhase.COMMITTED)
    committed_step = _validated_copy(step, phase=StepPhase.COMMITTED)

    return _validated_copy(
        state,
        domain_state=new_domain_state,
        active_step=None,
        committed_steps=state.committed_steps + (committed_step,),
        committed_action_ids=(state.committed_action_ids + (state_delta.action_id,)),
        next_step_index=state.next_step_index + 1,
        continuation_pending=True,
    )
```

三个要点：

1. **幂等**：同一个 `action_id` 的 delta 只会产生一次状态效果。已提交过就返回原 state。
2. **一次写入六个字段**：新领域状态、清空 `active_step`、追加历史、追加 ledger、推进游标、设置 `continuation_pending`。这六个字段**必须在一次构造里同时变**，否则 `RunState` 的 validator 会拒绝——这是用不变量强制原子性。
3. **`continuation_pending=True`**：专门封住"commit 已完成、完成判断尚未完成"这个窗口。没有它，恢复时可能错误地打开下一个 step，或者重放上一个 step。

### `apply_continuation` 与 `terminate_run`

```python
def apply_continuation(state, *, target_status, reason=None):
    if target_status is RUNNING:
        return _validated_copy(state, continuation_pending=False)
    # 只有 COMPLETED / PARTIAL 是合法目标
    ...
```

`apply_continuation` 是"评估完 continuation 之后"的出口：继续跑就清标志，要结束就转终态。**它只能转 `COMPLETED` 或 `PARTIAL`**——`FAILED` / `CANCELLED` 必须走 `terminate_run`，因为那两个需要 `failure` 或有明确语义。这个分工避免了"正常完成判断路径"和"异常终止路径"混在一起。

`terminate_run` 的约束：只能从 `RUNNING` 转；目标只能是 `PARTIAL / FAILED / CANCELLED`；必须有 `reason`；`FAILED` 必须有 `failure`，非 `FAILED` 必须没有。

### checkpoint 的可靠性

`JsonCheckpointStore._save_sync` 的写入流程：

```text
payload = { schema_version: 4, execution_profile: "...", state: {...} }
→ json.dumps(..., sort_keys=True, separators=(",", ":"))
→ NamedTemporaryFile（在目标目录内）
→ write → flush → os.fsync
→ os.replace(temporary, target)
```

三层保护：

1. **原子替换**：`os.replace` 在同文件系统内是原子的。读者永远看不到半个 JSON。
2. **`fsync`**：数据真正落盘后才替换，避免掉电后"文件存在但内容为空"。
3. **`sort_keys=True` + 紧凑分隔符**：序列化结果确定，便于 diff 和调试。

加载时的四道校验：

| 校验 | 失败异常 |
|---|---|
| JSON 能否解析 | `CheckpointReadError` |
| 根必须是 object | `CheckpointReadError` |
| `schema_version` 必须等于 4 | `CheckpointVersionError` |
| `execution_profile` 必须匹配 | `CheckpointProfileError` |
| `state` 字段存在且能被 `model_validate` | `CheckpointReadError` |

**`execution_profile` 是最容易被忽略但很关键的一条**。它由 `_execution_profile_id(*parts)` 生成：

```python
def _execution_profile_id(*parts: str) -> str:
    material = "\x1f".join(parts)
    return "profile-" + sha256(material.encode("utf-8")).hexdigest()[:16]
```

live 组合的 parts 包含：profile 名、`model_base_url`、`model_name`、两个 provider 名、`max_steps`、`max_decision_attempts`、`max_context_tokens`、`output_headroom_tokens`、`model_timeout_seconds`、`tool_timeout_seconds`、`allow_insecure_model_endpoint`。

**为什么要它**：换模型或换工具组合后，"重放同一个 action"的语义已经变了。必须在**动作重放之前**拒绝，而不是让新模型去解释旧决策。同时它**不保存密钥和 provider 配置本身**——只有一个不透明摘要。

### 三个崩溃窗口

这是本层最核心的面试内容。

**窗口 A：已保存 `ACTION_RUNNING`，但还没保存 Observation**

Runtime 知道准备执行哪个 action，但不知道 provider 是否已经响应。

```text
resume → classify_resume = EXECUTE_ACTION
       → ActionExecutor.execute(request)
       → ToolExecutor.execute(ToolCall)
       → result_cache.get(call)   ← 先查持久化成功缓存
          ├─ 命中 → 直接返回，fresh adapter 调用 0 次
          ├─ miss → 只读工具，可以再次执行同一 action
          └─ 损坏 → 抛 typed read error（不当作 miss）
```

**为什么缓存损坏不能降级为 miss**：miss 表示"从未记录成功"，损坏表示"可能记录过成功但证据丢了"。二者风险完全不同。把损坏当 miss，等于把不确定性隐藏成安全重试。

**这个窗口无法完全消除**：在"provider 已收到请求、结果尚未写缓存"之间崩溃，仍然会重发。这就是**不能声称 exactly-once** 的原因。

**窗口 B：Observation 已保存，但 State 尚未提交**

checkpoint 里已有完整 `ObservationEnvelope`。resume 直接进 `REDUCE_OBSERVATION`，重建 delta 并提交，**绝不再次调用工具**。Reducer 必须确定、无 I/O，才能安全重放。

**窗口 C：State 已提交，但调用方还没拿到结果**

`commit_step` 已同时写入新 State、committed step、`committed_action_ids`、`next_step_index`，并设置 `continuation_pending=True`。恢复后先评估 continuation，不再次执行工具或 Reducer。

### action identity

```text
step_id   = {run_id}:step:{step_index}
action_id = {step_id}:attempt:{attempt}:action
```

由 `DeterministicIdFactory` 生成（`models/fake.py`）。这条规则推出一组重要区分：

| 场景 | `step_id` | `attempt` | `action_id` | 说明 |
|---|---|---|---|---|
| 模型修复 Decision | 不变 | **+1** | **变** | 换的是语义，是新的业务动作 |
| 同 provider timeout retry | 不变 | 不变 | **不变** | 保的是同一动作身份，只有 `ToolInvocation.attempt` 增加 |
| 跨 provider fallback | 不变 | 不变 | **不变** | 业务意图与参数没变，只是执行者变了 |

`action_id` 同时贯穿五处：信封关联、ToolResult 缓存键、committed ledger、`StateDelta` 重放、恢复矩阵的调用次数断言。

### 成功结果缓存

`tools/persistent_cache.py` 的 `JsonActionResultCache`：

- 一个 action_id 一条记录；**文件名是 action_id 的 SHA-256**，所以任意 action_id 都不可能变成文件系统路径（路径安全）。
- 同时存**请求的 `ToolCall`** 和 `ToolResult`——这样即使跨进程重启，也能检测 identity 冲突。
- 写用临时文件 + `fsync` + `os.replace`。
- **只缓存成功结果**。临时失败若缓存，会让恢复永久复用旧的 timeout/rate-limit。
- `get`/`put` 由进程内 `asyncio.Lock` 串行化；**明确不声称分布式锁或跨进程互斥**。

### Run Bundle

终态 run 自动在 checkpoint 旁边落：

```text

report.md           原子写入的 Markdown brief
outcome.json        typed 结果
action_results/     跨进程成功缓存
artifacts/          reader 产出的正文（内容寻址）
```

`RunBundleWriter` 的 docstring 里写明了三条：report 是**最新终态领域状态的确定性投影**，所以允许覆盖；reader artifact 留在原处**不复制**；**不序列化任何密钥或配置值**。

## 2.3 面试追问与参考答法

**Q：exactly-once 为什么通常无法由 Agent Runtime 单方面保证？本项目实际保证到什么程度？**

> 真正的外部 exactly-once 需要 provider 接受幂等键、共享事务存储、outbox/inbox 或协调协议。本项目的结果缓存只有**单机文件原子性和进程内锁**；两个进程同时恢复同一个未缓存的 action，仍然可能都调用 provider。
>
> 所以准确承诺是 **at-most-once 复用已持久化的成功结果**，加上 **状态效果的幂等**（同一个 delta 只产生一次状态变化）。合起来可以说是 "effectively-once state effect"，但**不是**外部服务 exactly-once。这个承诺成立还依赖一个前提：舆情工具是只读的，重发是安全的。
>
> 生产化至少还需要：run ownership/lease、action record 的 compare-and-set、provider 支持时传 action_id 作为幂等键、对有副作用工具定义补偿或人工确认。

**Q：为什么缓存损坏不直接重新执行？**

> 因为 miss 和损坏是两种不同的事实。miss = "从未记录成功"，损坏 = "可能记录过成功，但证据丢了"。把损坏降级成 miss，就把不确定性伪装成了安全重试。

**Q：取消发生在 Observation 已落盘之后怎么办？**

> 在 reduction 阶段延迟取消：先把已观测的结果 commit，再终止 run。否则恢复后同一个 Observation 的命运会取决于取消时序。同时要说清边界：取消只中止本地协程，**不承诺远端回滚**。

**Q：为什么 `execution_profile` 要进 checkpoint？**

> 因为换模型或换工具组合后，重放同一个 action 的语义已经变了。必须在动作重放**之前**拒绝，而不是让新模型去解释旧决策。它是不透明摘要，不保存密钥。

**Q：为什么 `commit_step` 要一次性改六个字段？**

> 因为 `RunState` 的 validator 会检查它们之间的相互一致性——`next_step_index` 必须等于 `committed_steps` 数量加一，`committed_action_ids` 必须与历史里的 action 对应。分两次改，中间那个状态是非法的，构造不出来。**用不变量强制原子性**，而不是靠"记得同时改"。

**Q：`continuation_pending` 到底封住什么窗口？**

> 封住"step 已提交、完成判断还没做"这一小段。没有它，恢复时 `classify_resume` 看到 `active_step is None` 会直接 `OPEN_STEP`——于是上一个 step 的完成判断被跳过了。有了它，恢复先走 `EVALUATE_CONTINUATION`。

# L3 · 状态与 Reducer

## 3.1 必须能讲清的机制

### Reducer 是权威状态的唯一写入口

**签名就说明了一切**：

```python
def reduce_opinion_state(
    old_state: OpinionSearchState,
    accepted_delta: OpinionSearchDelta,
) -> OpinionSearchState: ...
```

纯函数。没有 `self`，没有 I/O，没有时钟，没有随机。给定相同的 `(old_state, delta)`，永远返回相同的 `new_state`。

返回值规则：

```python
if all(getattr(old_state, key) == value for key, value in values.items()):
    return old_state                      # 无变化 → 返回原对象，revision 不变
return OpinionSearchState(**values, revision=old_state.revision + 1)
```

**无变化时不递增 revision**——这很重要，它让"revision 变了"精确等价于"状态真的变了"，从而可以当作缓存失效与变更检测的信号。

### 为什么必须纯

三个理由，都要能说：

1. **可重放**。窗口 B 的恢复就是"重新构造 delta 并提交"，如果 reducer 有副作用，重放会重复副作用。
2. **可测试**。给定旧状态和 delta 就能断言新状态，不需要 mock 任何东西。
3. **恢复语义可判定**。如果 reducer 里有时钟或网络，同一份 checkpoint 在不同时间恢复会得到不同状态，"恢复"这个词就没意义了。

**推论**：I/O 在 `ActionExecutor`，环境结果到领域变化的**翻译**在 `Processor`，**纯状态合并**在 `Reducer`。三层责任不重叠。

### 不变量：fail closed

`ReducerInvariantError` 在以下情况抛出（`domain/opinion/reducer.py`）：

| 检查 | 例子 |
|---|---|
| delta 引用的 gap 必须存在 | `delta references unknown gaps: [...]` |
| delta 不能修改已关闭的 gap（除非是**精确重放**） | `delta changes non-open gaps: [...]` |
| 不能添加没有 candidate 的 source | `cannot add a source without a candidate` |
| evidence 必须引用已知 source 与已知 gap | `evidence references an unknown source` |
| claim / position / narrative 引用的 evidence 必须存在 | `claim references unknown evidence` |
| candidate identity 冲突 | 同一 URL 但 `(url, title)` 不同 → `candidate identity conflict` |
| claim 的证据不能既支持又反驳 | `claim evidence cannot both support and contradict` |
| `final_synthesis` 不可被覆盖 | `final synthesis cannot be overwritten` |

**"fail closed" 的含义**：一旦不变量被破坏，**终止 run 为 `FAILED`**，而不是跳过这条变更继续跑。因为已经提交的状态内部矛盾了，继续跑会污染更多事实。

对比 L4 的 `ActionResolver` 失败：那里**回退到 DECIDING 而不终止**，因为还没发生任何外部副作用。**两者的分界线是"是否已经产生了不可撤销的事实"**。

### `_is_exact_closed_gap_replay`：一个容易忽略的细节

Reducer 原则上禁止修改已关闭的 gap。但恢复时会出现一种合法情况：同一个 delta 被重放。所以有一个精确判定：

```python
def _is_exact_closed_gap_replay(gap, *, queries, source_ids, assessment) -> bool:
    if not set(queries).issubset(gap.attempted_queries):
        return False
    if not set(source_ids).issubset(gap.attempted_source_ids):
        return False
    if assessment is not None:
        return (
            assessment.outcome is gap.status
            and assessment.rationale == gap.resolution_note
            and set(assessment.evidence_ids).issubset(gap.evidence_ids)
        )
    return not queries and not source_ids
```

**只有逐项完全一致才算重放**，否则仍然是非法修改。这是"幂等"和"非法"之间的精确边界。

### 权威状态最小化

原则：**派生对象不得成为第二事实源**。

| 对象 | 是否权威 | 说明 |
|---|---|---|
| `OpinionSearchState` / `State` | **是** | 唯一权威，落 checkpoint |
| `WorkingMemory` | 否 | 纯函数投影，可重建，**不落盘**（仅 opinion 域） |
| `CompiledContext` | 否 | 单次模型输入，带 `content_sha256`，**不落盘** |
| `Artifact` | 原始材料 | 内容寻址落盘，不是"状态" |
| `PagePlan` | 否 | `investigation/page_plan.py` 从 `EventProfile + Issue + Finding` 重建 |
| `OpinionCoverageCell`（memory）/ `Metric`（`investigation/metrics.py`）/ `ContentDocument`（`report_contract/contracts.py`） | 否 | 派生视图 |
| `SearchReportView` / workbench 投影 | 否 | 从 committed State 渲染 |

`page_plan.py` 的模块 docstring 把这条讲得最清楚：

> It is intentionally rebuilt from EventProfile, Issue and Finding records instead of becoming another mutable authority in the checkpoint.

**为什么**：一旦派生视图能写回权威状态，就有两个事实源；渲染层失效会污染领域事实。

### 两个域的 State 对比

**`OpinionSearchState`**（`domain/opinion/state.py`）：

```text
request, gaps, task_frame, current_focus
candidates → sources → evidence
claims / stakeholder_positions / narratives
final_synthesis, reflections, revision
```

链路是严格递进的：`candidate`（搜索命中，未读）→ `source`（已读并正规化）→ `evidence`（从正文选出的可定位摘录）→ `claim / position / narrative`（语义对象）。`validate_invariants` 检查这条链的每一跳：每个 source 必须来自某个 candidate；每条 evidence 必须引用已知 source 与已知 gap；每个 gap 的 `evidence_ids` 必须存在；`final_synthesis` 引用的 evidence 与 limitation gap 必须存在。

还有两个有意思的领域不变量：

- `CandidateSource.source_id` **必须等于**它的 canonical URL；`Source.source_id` **必须等于**请求的 canonical URL。
- `Source.publication_status` 必须与 `published_at` 一致——有发布时间才能标 `reported`，否则只能是 `unavailable`。**模型不能从正文猜日期。**

**`State`**（`domain/investigation/models.py`，`schema_version = 2`）：

```text
request, subject, aliases, cutoff, required_questions
issues（含 components）→ candidates → sources → evidence → findings
retired, checks, reviews, searches, relations
read_attempts, read_errors, history, conclusion_ids
profile (EventProfile), update_intent, revision
```

它的 `references` validator 有一条特别值得说：

```python
covered = {text for issue in self.issues for text in issue.origin_questions}
if not set(self.required_questions) <= covered:
    raise ValueError("a user question was dropped from the investigation plan")
```

**用户提的问题不允许在调查计划里丢掉**——这条不变量把"不能悄悄降级用户需求"写成了构造期约束。

另外 `Evidence` 的校验是 `x.end - x.start == len(x.excerpt)`——**摘录长度必须与定位区间一致**，这样 locator 才可信。

## 3.3 面试追问与参考答法

**Q：为什么 Reducer 必须是纯函数？**

> 可重放、可测试、恢复后结果一致。窗口 B 的恢复就是"重新构造 delta 并提交"——如果 reducer 里有时钟或网络，同一份 checkpoint 在不同时间恢复会得到不同状态，"恢复"这个词就失去意义了。所以 I/O 在 ActionExecutor，翻译在 Processor，纯状态合并在 Reducer。

**Q：为什么 ActionResolver 失败可以回到 deciding，而 Reducer invariant 必须 fail closed？**

> 分界线是**是否已经产生了不可撤销的事实**。ActionResolver 失败时还没有任何外部副作用，回退到 deciding 只是让模型再想一次，安全。Reducer 不变量失败意味着**已经提交的状态内部矛盾了**——继续跑会污染更多事实，所以必须 fail closed，转 `FAILED` 并带上 `RuntimeFailure`。

**Q：派生视图为什么不能写回权威状态？**

> 一旦能写回就有两个事实源。渲染层失效、PagePlan 计算错误、覆盖率统计 bug，都会污染领域事实。所以 PagePlan 这类对象每次从 `EventProfile + Issue + Finding` 重建，可以持久化用于诊断，但**不得成为第二权威**。

**Q：`revision` 有什么用？**

> 它是"状态真的变了"的精确信号。Reducer 在无变化时返回原对象、不递增 revision，所以 revision 变了就等价于状态变了。`CompiledContext.state_revision` 记录它是从哪个版本编译的，用于诊断和一致性断言。

**Q：两个域的 State 为什么差别这么大？**

> 因为领域语义不同。opinion 域的核心是"一张 evidence-linked 舆情地图"——事实基线、主体立场、主导叙事、反叙事四个维度，所以它需要 `Claim / StakeholderPosition / Narrative` 作为权威对象。investigation 域的核心是"回答用户提的具体问题"，所以它的权威对象是 `Issue`（含 `QuestionComponent`）和 `Finding`（含 response/coverage 判断），叙事与立场退化成 finding 的字段。
>
> 这两套并行是"Runtime 领域无关"的可验证证据，但作为长期维护的项目迟早要收敛——这一点要主动说。

# L4 · 决策协议与校验

## 4.1 必须能讲清的机制

### Decision ≠ Action

这是本层最容易讲漏、也最显功力的一条。

| | `Decision` | `Action` |
|---|---|---|
| 谁产生 | 模型 | Runtime 的 `ActionResolver` |
| 性质 | **语义意图** | **可执行单元** |
| 关心什么 | `target_gap_id`、`purpose`、`focus` | 稳定 `tool_name` + 已校验 `arguments` |
| 知道 provider 吗 | 不知道 | 不知道（provider 只在 Registry 里） |
| 例子 | `SearchDecision(query, target_gap_id, purpose)` | `ToolAction(decision_action="search", tool_name="search.web", arguments={"query": ...})` |

opinion 域的 4 个决策（`domain/opinion/decisions.py`，`discriminator="action"`）：

```text
SearchDecision  { query, target_gap_id, purpose }
ReadDecision    { candidate_source_id, target_gap_id, focus, source_kind }
ReflectDecision { assessment, next_focus, gap_assessments,
                  claim_proposals, stakeholder_position_proposals, narrative_proposals }
FinishDecision  { answer_candidate, resolved_gap_ids, unresolved_gap_ids }
```

investigation 域的 6 个决策（`domain/investigation/models.py`，`discriminator="action"`）：

```text
SearchDecision   { issue_id, query, purpose, page, background, target_gap }
ReadDecision     { issue_id, url, focus, role }
RetrieveDecision { issue_id, query, version_id }        ← 重访已保存文档
ReflectDecision  { findings, assessments, add_questions, retirements, source_relations, reason }
ReviewDecision   { finding_ids }                        ← 最多 8 个
FinishDecision   { conclusion_ids }                     ← 最多 8 个
```

**为什么 `reflect` / `finish` 不是"假工具"**：如果 `Decision` 就是 `ToolCall`，那 `reflect` 和 `finish` 要么被伪装成假工具，要么绕开统一生命周期。更重要的是，它们**没有外部副作用**——`ReflectAction` / `FinishAction` 只是把已校验的内容包装成可执行单元，`OpinionActionExecutor` 直接构造对应 Observation，不走 ToolExecutor。

opinion 域的 3 个 Action（`discriminator="kind"`）：

```text
ToolAction   { decision_action: "search"|"read", tool_name, arguments }
ReflectAction{ assessment, next_focus, assessed_gap_ids }
FinishAction { completion_verdict }
```

`ToolAction` 有一个 validator 强制 `decision_action` 与 `tool_name` 的对应关系：

```python
_TOOL_BY_DECISION_ACTION = {"search": "search.web", "read": "read.web"}
```

**这样模型不可能说"我要 search"却调用 read 工具。**

### ActionResolver 的职责：翻译与加固

`OpinionSearchActionResolver.resolve` 做的事：

- `SearchDecision` → `ToolAction(tool_name="search.web", arguments=_search_arguments(state, query))`。`_search_arguments` 从持久化的 `TaskFrame` 投影 `freshness`（仅有界时间窗口）与 `search_lang`；`country` 与 `offset` 显式排除。domain 约束仍在候选入库时后过滤。执行 profile 因 payload 变化已升级（offline v3 / fallback v2 / live v6），旧 run 不能续跑。
- `ReadDecision` → `ToolAction(tool_name="read.web", arguments=ReaderArguments(url=candidate_source_id))`。
- `ReflectDecision` → `ReflectAction`。
- `FinishDecision` → `FinishAction(completion_verdict=self._completion_policy.evaluate(state, decision))`。

**注意最后一个**：`finish` 的完成判定是在 **Resolver 阶段**就调用了 `CompletionPolicy`，结果打包进 `FinishAction`。所以 `finish` 从"决策"变成"动作"的那一刻，它已经被程序判定过了。

investigation 域的 `Resolver` 加固更多（`domain/investigation/engine.py`）：

```python
scope = build_task_frame(state.request, anchor_date=state.cutoff.date()).temporal_scope
core = decision.query
if state.request.include_domains:
    core += " (" + " OR ".join("site:" + d for d in state.request.include_domains) + ")"
exclusions = tuple(dict.fromkeys((*SOCIAL_DOMAINS[:6], *state.request.exclude_domains)))
suffix = " " + " ".join("-site:" + d for d in exclusions)
query = core + suffix if len(core + suffix) <= 600 else core
if len(query) > 600:
    raise ValueError("search query is too long; split the request into bounded queries")
```

它做的事：按 `include_domains` 追加 `site:` OR 组、**自动排除社交平台**（`SOCIAL_DOMAINS` 前 6 个 + 用户排除域）、限制 query ≤ 600 字符、`max_results=10`、`offset=decision.page`、按语言设 `search_lang`、按任务时间窗设 `freshness`（`background=True` 时不设）。

**这解释了"模型从来不知道背后是 Brave 还是 Serper"**——query 加固、结果数、分页、语言、时效，全在 Resolver 里，模型只管说"我要搜什么"。

另外 review 决策会在这里被打包成 `review_context`：

```python
context = {"findings": [...], "evidence": [...], "sources": [...], "issues": [...]}
return Action(decision=decision, review_context=json.dumps(context, ensure_ascii=False))
```

**给 reviewer 的上下文是冻结快照**，不是让它自己去查。

### 三层校验

| 层 | 在哪 | 检查什么 | 失败后果 |
|---|---|---|---|
| **结构层** | pydantic，`extra="forbid"` + frozen | 字段名、类型、必填、枚举、长度、唯一性 | 模型响应解析失败 → `ModelClientError` |
| **state-aware 层** | `DecisionValidator.validate(state, decision)` | ID 是否真实存在、是否重复行动、状态是否允许 | `DecisionValidationError` → 可修复 |
| **终态层** | `CompletionPolicy` / `completion()` | 已提交状态是否满足完成标准 | `CompletionVerdict` → 拒绝或降级 |

**结构层**的例子（`domain/opinion/decisions.py` 的 model validator）：

- `ClaimProposal` 必须有至少一个证据引用，且证据不能既支持又反驳。
- `GapAssessmentProposal`：`outcome == RESOLVED` 时必须有证据。
- `ReflectDecision` 必须至少有一个 gap assessment，且 gap_id 不重复。
- `FinishDecision`：resolved 与 unresolved 不能重叠。

**state-aware 层**的例子（`OpinionSearchDecisionValidator.validate`）：

| 决策 | 检查 |
|---|---|
| `SearchDecision` | 目标 gap 必须**当前 open**；query 不能是 `gap.attempted_queries` 里已有的 → 否则 `REPEATED_ACTION` |
| `ReadDecision` | 目标 gap 必须 open；`candidate_source_id` 必须在 `state.candidate_source_ids` 里；不能在 `read_source_ids` 里 → 否则 `REPEATED_ACTION` |
| `ReflectDecision` | 每个 assessment 的 gap 必须 open；引用的 evidence ID 必须真实存在；时间窗校验；claim/narrative 的 kind 不能与已有对象冲突；**语义维度覆盖校验** |
| `FinishDecision` | `resolved_gap_ids` 必须等于 `state.resolved_gap_ids`；`unresolved_gap_ids` 必须等于 `state.open_gap_ids` |

两个特别值得讲的：

**① 时间窗校验**（`_validate_temporal_gap_evidence`）：如果任务有界时间范围，那么"resolved 某个 gap 所引用的 evidence"，其**发布时间必须已知且在窗口内**。否则拒绝，报出具体哪些 evidence ID 不合格。

**② 语义维度覆盖**（`_validate_opinion_dimension_semantics`）：要 resolve 某个维度，必须有一条**对应类型的语义记录**挂在被引用的证据上：

| 维度 | 必须存在 |
|---|---|
| `gap-factual-baseline` | 一条 `ClaimKind.FACT` 的 Claim |
| `gap-stakeholder-positions` | 一条 `StakeholderPosition` |
| `gap-dominant-narratives` | 一条 `DOMINANT` 或 `EMERGING` 的 Narrative |
| `gap-counter-narratives` | 一条 `COUNTER` 的 Narrative |

失败时给出的错误信息还带**可执行线索**：

```python
raise DecisionValidationError(
    "resolved opinion dimensions lack matching semantic records: "
    f"{missing}; eligible_resolved_gap_ids={eligible}"
)
```

**这是"模型不能靠说'我认为解决了'就把维度关掉"的机制保证。**

### 决策失败可修复：两种修复，不是一种

`runtime/loop.py` 的 `_recover_decision_failure` 是本层最核心的一段：

```python
if failure.kind is RuntimeFailureKind.REPEATED_ACTION:
    → terminate_run(PARTIAL)                    # 重复行动直接停，给已有成果

non_retryable = {MODEL_AUTHENTICATION, MODEL_CONFIGURATION_ERROR}
if failure.kind not in non_retryable and step.attempt < self._max_decision_attempts:
    if step.phase is StepPhase.DECIDING:
        → retry_decision(state, failure)          # 同 step_id，attempt+1
    else:
        → repair_accepted_decision(state, failure) # 回退到 DECIDING
else:
    → PARTIAL if state.committed_steps else FAILED
```

**`retry_decision` vs `repair_accepted_decision`**：

| | `retry_decision` | `repair_accepted_decision` |
|---|---|---|
| 触发 | `step.phase == DECIDING` 时校验失败 | `step.phase == DECISION_ACCEPTED` 时 Resolver 失败 |
| 语义 | 模型说错了，让它再说一次 | 决策合法但解析不出可执行动作 |
| 实现 | 新建 `StepRecord`，`attempt + 1`，保留 `failures` | **从零重建** `StepRecord`，丢弃被拒的 Decision 和任何部分载荷 |
| 关键点 | —— | **没有外部副作用**，所以可以安全回退到同一 step |

`repair_accepted_decision` 的 docstring 说明了为什么要"从零重建"：

> The active StepRecord is rebuilt from scratch (not mutated) so the rejected Decision and any partial payload are discarded while prior failures are preserved in order.

**`failures` 会被保留并累积**，而且它们会进入下一轮 Context——见 L5 的 `_active_failure_sections`。

### `RuntimeFailureKind` 与 `RecoveryDirective`

`runtime/errors.py` 定义了 20 种失败类型和 5 类恢复指令：

```text
RecoveryDirective = RETRY_ATTEMPT | FEEDBACK_AND_CONTINUE
                  | PARTIAL_STOP | FAIL_RUN | CANCEL_RUN
```

映射表（`_RECOVERY_DIRECTIVE_BY_FAILURE_KIND`）的分类逻辑：

| Directive | 适用失败类型 | 理由 |
|---|---|---|
| `RETRY_ATTEMPT` | `MODEL_MALFORMED_RESPONSE` / `MODEL_EMPTY_RESPONSE` / `MODEL_REFUSAL` / `MODEL_TIMEOUT` / `MODEL_RATE_LIMITED` / `MODEL_SERVER_ERROR` | 瞬时或可恢复，重试有意义 |
| `FAIL_RUN` | `MODEL_AUTHENTICATION` / `MODEL_CONFIGURATION_ERROR` / `TOOL_CONFIGURATION_ERROR` / `REDUCER_INVARIANT` / `CHECKPOINT_READ` / `CHECKPOINT_WRITE` / `CHECKPOINT_VERSION` | 配置或完整性错误，重试无用 |
| `FEEDBACK_AND_CONTINUE` | `INVALID_DECISION` / `INVALID_ACTION` / `TOOL_ERROR` | 把结构化反馈交给模型，让它改 |
| `PARTIAL_STOP` | `CONTEXT_OVERFLOW` / `REPEATED_ACTION` / `SAFETY_LIMIT` | 做不完但成果有价值 |
| `CANCEL_RUN` | `CANCELLED` | 用户意图 |

**`RuntimeFailure.directive` 是一个 property**，从 kind 推导——不存在"kind 与 directive 不一致"的失败对象。

`DecisionValidationError` 还限制了它能携带的 kind：

```python
if kind not in {RuntimeFailureKind.INVALID_DECISION, RuntimeFailureKind.REPEATED_ACTION}:
    raise ValueError("decision validation error requires decision kind")
```

**这是防止把任意失败伪装成"决策问题"从而获得重试机会。**

## 4.3 面试追问与参考答法

**Q：为什么 Decision retry 与 Tool retry 不是同一种 retry？**

> **Decision retry 换的是语义，Tool retry 保的是同一身份。**
>
> Decision retry 是同 `step_id`、`attempt + 1`——因为模型要**再想一次**，语义可能完全不同，所以 `action_id` 会变。Tool retry 是同一个 `action_id` 下 `ToolInvocation.attempt` 递增——业务意图和参数都没变，只是物理重试，所以身份必须保持。
>
> 混淆的后果很具体：如果让模型处理底层重试，每次 retry 都会变成新 step、新 action_id，既污染调查历史（看起来模型做了 5 件事，其实是一件事重试了 5 次），也无法统一控制退避、限流和熔断。

**Q：给出"合法但无帮助""格式错误""引用不存在证据"三个决策，各自在哪一层被处理？**

> - **格式错误**：结构层（pydantic）——解析失败，变成 `MODEL_MALFORMED_RESPONSE`，走 `RETRY_ATTEMPT`。
> - **引用不存在证据**：state-aware 层——`DecisionValidationError`，走 `retry_decision`（同 step，attempt+1），并在下一轮 Context 里带上结构化反馈。
> - **合法但无帮助**（比如重复 query）：state-aware 层的 `REPEATED_ACTION` → `PARTIAL_STOP`，**不重试**。因为重复本身说明模型在原地打转，再给它一次机会只是浪费预算。

**Q：`DecisionValidationError` 为什么限制只能带两种 kind？**

> 防止把任意失败伪装成"决策问题"从而获得重试机会。只有 `INVALID_DECISION` 和 `REPEATED_ACTION` 是真正的决策层失败；其他失败（工具、checkpoint、reducer）各有自己的恢复策略，不能借决策重试通道绕过去。

**Q：失败反馈怎么回到模型？**

> 两条路。**控制面**：`RuntimeFailure.kind` 和 `directive` 作为 trusted 的 `active.failure.N.control` section。**内容面**：`failure.message` 作为 **untrusted** 的 `active.failure.N.message` section。分开是因为控制信息是 Runtime 确定的、可信的；而 message 里可能混有 provider 或模型生成的文本，不能被当成指令。

**Q：`repair_accepted_decision` 为什么不直接改现有 StepRecord？**

> 因为要**丢弃被拒的 Decision 和任何部分载荷**，同时**保留 prior failures 的顺序**。重建比变异更安全——变异容易留下上一个 attempt 的残留字段，而 `StepRecord` 的 phase↔payload validator 恰好会拒绝这种残留。所以重建是让不变量来保证干净，而不是靠手工清理。

## 5.1 必须能讲清的机制

### 先分清共享与专用（最容易讲错的一层）

**两个域真正共享的只有两处**：

| 共享 | 内容 |
|---|---|
| `context/models.py` | `ContextSection` / `ContextBudget` / `CompiledContext` / `ContextPlan` / `ContextSectionMeasure` / `ContextLayer` / `TrustBoundary` / `ContextContentOrigin` / `CompactionMode` / `render_sections` / `HeuristicTokenEstimator` / `RequiredContextOverflow` |
| `context/compactor.py` | `compact_context_sections` |

**只有 opinion 域用的**：`context/compiler.py`（`OpinionContextCompiler`）、`context/selector.py`、`context/catalog.py`、`memory/models.py`、`memory/projector.py`、`domain/opinion/provenance.py`。

**只有 investigation 域用的**：`investigation/context.py`（`Compiler` + `structured_context` + `make_context`）。

所以正确说法是：**"`collect → select → compact → render` 是共享的描述，但 collect 和 select 两个域各自实现；真正共享的是 compact 与 section 模型。"** 说"两套 domain 共用同一套 Context Compiler"是错的。

### 权威梯度

```text
State（唯一权威，落盘）
  │ 纯函数投影 project_working_memory()
  ▼
WorkingMemory（派生认知视图，可重建，不落盘）   ← 仅 opinion 域
  │ collect → select → compact → render
  ▼
CompiledContext（单次模型输入，带 content_sha256，不落盘）
```

`WorkingMemory` 的删除-重建必须得到**相等结果**——这是它"不是事实源"的可验证定义。`project_working_memory` 里有一行直接体现这个性质：

```python
current_gap_id = max(open_gaps, key=lambda gap: gap.priority).gap_id
```

它不存"当前 gap"这个状态，而是每次从 `gaps` 和 `priority` **算出来**。

### L0–L3 四层

`ContextLayer`（`context/models.py`）：

| 层 | 值 | 内容 | 约束 |
|---|---|---|---|
| **L0** 不可变指令 | `l0_instructions` | Runtime 核心指令、领域语义规则 | 必须 `required`、必须 `trusted`、origin 必须 `app_config`、必须 `NEVER` 压缩 |
| **L1** 稳定任务 | `l1_task` | 任务请求、decision schema、tool specs | 必须 `required`、必须 `trusted`、origin 必须是 `app_config` 或 `user_task`、必须 `NEVER` |
| **L2** 工作记忆 | `l2_memory` | gap 覆盖、evidence、claim、position、narrative、候选、失败方向 | 按需选择，可 DROP/TRUNCATE |
| **L3** 近期交互 | `l3_recent` | 最近若干 step 的 decision/observation/错误/拒绝理由 | 按需选择，**降级时优先被截断** |

`ContextSection.validate_required_layers` 把这些约束写成了构造期校验：

```python
if self.layer is ContextLayer.IMMUTABLE_INSTRUCTIONS:
    if not self.required: raise ValueError("L0 sections must be required")
    if self.trust is not TrustBoundary.TRUSTED: raise ValueError("L0 sections must be trusted")
    if self.origin is not ContextContentOrigin.APP_CONFIG:
        raise ValueError("L0 immutable instructions require app_config origin")
    if self.compaction is not CompactionMode.NEVER:
        raise ValueError("L0 sections cannot be compacted")
```

**含义：一条 L0 section 如果不是 required / trusted / app_config / NEVER，它根本构造不出来。** 这是把安全策略写成类型约束，而不是靠 code review 守。

### 信任分层：本层最重要的一条

`ContextContentOrigin` 有 6 个值：`runtime / app_config / user_task / model / tool / provider`。

```python
_ALWAYS_UNTRUSTED_ORIGINS = frozenset({
    ContextContentOrigin.MODEL,
    ContextContentOrigin.TOOL,
    ContextContentOrigin.PROVIDER,
})

# 在 ContextSection.validate_required_layers 里：
if (self.origin in _ALWAYS_UNTRUSTED_ORIGINS
        and self.trust is TrustBoundary.TRUSTED):
    raise ValueError("model/tool/provider origin can never be trusted")
```

**这三行是整个 Context 安全模型的核心。**

它保证：**commit / checkpoint / resume 只赋予持久性，不洗白信任。** 网页内容、工具返回值、模型自己上一轮说的话，无论经过多少次状态提交和恢复，都不会变成指令。

**trust 与 priority 正交**：

| | 决定什么 | 例子 |
|---|---|---|
| `trust` | **能不能当指令** | 一个 untrusted 的网页正文，哪怕 priority=100 也只是数据 |
| `priority` | **预算紧张时先丢谁** | 0–100，越高越先保留 |

**混合内容会拆分**。最典型的是 tool error：控制信息（`kind` / `attempts` / `retryable` / `action_id`）是 Runtime 确定的，作为 **trusted** 的 `{prefix}.tool-error`；而 `message` 可能含 provider 文本，作为 **untrusted** 的 `{prefix}.tool-error-message`。完成拒绝同理：`disposition` 是 trusted，`reason` 是 untrusted。

**渲染层还有一道防线**（`render_sections`）：

```python
def _escape_embedded_section_markers(content: str) -> str:
    return content.replace("[CONTEXT_SECTION", "［CONTEXT_SECTION") \
                  .replace("[/CONTEXT_SECTION]", "［/CONTEXT_SECTION］")
```

**防止外部正文伪造 section 标记**，把自己的内容伪装成系统段落。注意用的是全角字符替换——保留可读性的同时让标记失效。

### 编译四段流水线

```text
collect → select → compact → render
```

**collect**（`OpinionContextCompiler._collect`）从 `WorkingMemory` 和 `RunState` 组装所有候选 section，顺序是：

```text
instructions.core                 (L0, app_config, required, NEVER)
instructions.opinion-semantics    (L0, app_config, required, NEVER)
task.request                      (L1, user_task,   required, NEVER)
protocol.decision-schema          (L1, app_config, required, NEVER)
protocol.tool.N                   (L1, app_config, required, NEVER)  ×N
memory.current-focus              (L2, model,      UNTRUSTED, DROP)
memory.current-gap                (L2, runtime,    required, NEVER)
memory.open-gaps / pending-candidates / read-sources / resolved-gaps / blocked-gaps
memory.opinion-coverage           (L2, runtime,    required, NEVER)
memory.evidence-catalog.current   (L2, runtime,    required, NEVER)
memory.evidence-catalog.history.N (L2, runtime,    DROP)
memory.reflection.N / gap.N / gap-query-history.N / gap-note.N
memory.candidate.N / source.N / evidence.N / claim.N / position.N / narrative.N
recent.step.N.decision / observation / tool-error / finish-rejection
active.failure.N.control / .message
```

注意 trust 的分布规律：**凡是 Runtime 从已提交状态算出来的（gap ID、覆盖率、目录、控制信息）都是 trusted；凡是模型或工具产生的文本都是 untrusted**。连"当前焦点"（`memory.current-focus`，来自模型上一轮的 `next_focus`）都是 untrusted。

**select**（`select_context_sections`）做两件事：

1. **按语义键去重**。键是 `(trust, origin, layer, normalized_content)`——**包含 trust 和 origin**，所以不同来源或不同权限的相同文本**不会被合并**。赢家由 `_rank` 决定，`provenance_refs` 会合并。
2. **稳定排序**：
   ```python
   def _rank(section, *, current_gap_id):
       gap_relevant = current_gap_id is not None and current_gap_id in section.provenance_refs
       return (
           _LAYER_ORDER[section.layer],   # L0 < L1 < L2 < L3
           0 if section.required else 1,  # required 优先
           0 if gap_relevant else 1,      # 与当前 gap 相关优先
           -section.priority,             # 高 priority 优先
           section.section_id,            # 最后用 ID 打破平局 → 确定性
       )
   ```
   **最后一项 `section_id` 是确定性的关键**——没有它，相同 rank 的 section 顺序会依赖插入顺序。

**compact**（`compact_context_sections`）三级降级：

```python
# 第 0 步：锁定段的地板
locked = tuple(s for s in sections if s.required or s.compaction is NEVER)
if _measure(locked, estimator) > input_token_limit:
    raise RequiredContextOverflow("required context exceeds the available input budget")

# 预算够 → 直接返回
if _measure(tuple(working), estimator) <= input_token_limit:
    return _result(...)

# 第 1 步：TRUNCATE（按降级序）
truncation_candidates = sorted(
    (s for s in working
     if s.compaction is TRUNCATE and len(s.content) > _MIN_COMPACTED_CHARACTERS),
    key=_degradation_rank,
)
# 截到前 96 字符 + "\n[content compacted]"

# 第 2 步：DROP（按降级序）
droppable = sorted(
    (s for s in working if not s.required and s.compaction is not NEVER),
    key=_degradation_rank,
)

# 第 3 步：还是放不下 → 抛错
if measured > input_token_limit:
    raise RequiredContextOverflow("non-removable context exceeds the available input budget")
```

降级顺序 `_degradation_rank`：

```python
return (
    0 if section.trust is UNTRUSTED else 1,        # untrusted 先降级
    0 if section.layer.value == "l3_recent" else 1, # L3 先降级
    section.priority,                               # 低 priority 先降级
    section.section_id,                             # 确定性打破平局
)
```

**为什么必需段放不下时不截断，而是抛错？** 因为截断会让"必需"名不副实——L0 系统规则被砍掉一半，模型行为就不可预测了。宁可 typed partial stop（`ContextOverflowError` → `PARTIAL`），也不静默破坏语义。

**render**（`render_sections`）输出带元数据头的文本：

```text
[CONTEXT_SECTION id=memory.evidence.3 layer=l2_memory origin=tool trust=untrusted]
Untrusted source-backed evidence
{...json...}
[/CONTEXT_SECTION]
```

**每一段都自带来源与信任标签**——这是"模型能看见什么、为什么可信"的直接体现。

### 预算与 headroom

```python
class ContextBudget(BaseModel):
    max_context_tokens: int          # ge=2
    output_headroom_tokens: int      # ge=1

    @property
    def input_token_limit(self) -> int:
        return self.max_context_tokens - self.output_headroom_tokens
```

校验：`output_headroom_tokens < max_context_tokens`。

**为什么要 headroom**：如果上下文占满整个窗口，模型就没有空间输出结构化 Decision 了。所以输入预算是"窗口 − 输出预留"。

默认值：live 组合 `max_context_tokens=32000` / `output_headroom_tokens=2000`；offline 组合 `16000` / `2000`。

### `CompiledContext`：可复现

```python
class CompiledContext(BaseModel):
    run_id, step_id, step_index, state_revision
    sections, rendered, content_sha256
    estimated_input_tokens, input_token_limit, output_headroom_tokens
    plan: ContextPlan
```

它的 validator 强制：

```python
expected_rendered = render_sections(self.sections)
if self.rendered != expected_rendered:
    raise ValueError("rendered context does not match sections")
expected_hash = sha256(expected_rendered.encode("utf-8")).hexdigest()
if self.content_sha256 != expected_hash:
    raise ValueError("content_sha256 does not match rendered bytes")
```

**所以 `CompiledContext` 不能被构造出一个 hash 与内容不符的实例。**

`ContextPlan` 记录 `selected_section_ids` / `dropped_section_ids` / `compacted_section_ids` / `section_measures`，并且要求 `section_measures` 的顺序与 `selected_section_ids` 完全一致、`compacted_section_ids ⊆ selected_section_ids`。

**注意**：`content_sha256` 与 `section_measures` **都不落 checkpoint**——它们是单次模型输入，不是状态。

### 有界 Evidence catalog

`context/catalog.py` 的 `EvidenceCatalogPolicy`：

```python
required_evidence_limit: int = 64
history_chunk_size: int = 64
coverage_sample_limit_per_gap: int = 16
```

**为什么需要它**：模型 Reflect 时必须**准确复制不透明的 Evidence ID**（不能自己编顺序别名），所以关键目录必须保留；但全量 required 目录会随 run 无限增长。

分区结果：

| 部分 | 上限 | 性质 |
|---|---|---|
| `required`（当前窗口） | 64 | `required=True` + `NEVER` 压缩——**预算不足直接抛错** |
| `history`（历史块） | 每块 64 | `priority=40` + `DROP`——可降级 |
| `coverage` 采样 | 每个 gap 16 | 同时保留精确的 `evidence_count` / `source_count` |

**`required` 的选取顺序**（`_rank_current_gap`），这是"语义覆盖 ≠ 获取意图"的实现：

```python
def group(item):
    if current_gap_id in item.semantic_gap_ids: return 1        # 语义覆盖当前 gap
    if not (item.semantic_gap_ids or item.supporting_claim_ids
            or item.contradicting_claim_ids or item.position_ids
            or item.narrative_ids): return 2                     # 完全未链接
    if item.acquired_for_gap_id == current_gap_id: return 3      # 仅为当前 gap 获取
    if item.evidence_id in contested_ids: return 4               # 有争议
    return 5
```

**组 1 排在组 3 前面**——"**实际支持**该 gap"优先于"**为**该 gap 搜到"。这正是 `acquired_for_gap_id` 不等于 semantic coverage 的落地。

`ProvenanceIndex` 的 docstring 把这条原则写得很清楚：

> Acquisition intent (`acquired_for_gap_id`) is kept separate from semantic relations; acquisition alone does not link an Evidence.

**trusted coverage cell 只采样真实语义链接**：

```python
def source_ids_for_gap(self, gap_id: str) -> tuple[str, ...]:
    # 只取 gap_id in record.semantic_gap_ids 的记录
```

所以"搜索过某个方向"不会在覆盖率里显示成"这个方向已被证据覆盖"。

### token 估算

```python
class HeuristicTokenEstimator:
    def estimate(self, text: str) -> int:
        if not text: return 0
        return max(1, ceil(len(text.encode("utf-8")) / 4))
```

**诚实口径**：这是启发式估算（4 字节 ≈ 1 token），**不保证与 DeepSeek tokenizer 逐 token 一致**，可以注入测试 estimator 替换。项目证明的是"选择和降级机制有界"，不是"估算公式绝对精确"。

## 5.3 面试追问与参考答法

**Q：Full State / Working Memory / Context 的一致性来源分别是什么？**

> Full State 的一致性来自 **Reducer 提交**——它是唯一写入口，纯函数保证可重放。
> Working Memory 的一致性来自**纯函数投影**——`project_working_memory(state)`，删掉重建必须相等。
> Compiled Context 的一致性来自**编译配置 + active step**——相同的 State、配置和 estimator 必须生成字节一致的结果，这一点由 `content_sha256` 和 validator 强制。
>
> **补一句**：Working Memory 只在 opinion 路径存在，investigation 域没有这一层。

**Q：trust 与 priority 为什么正交？**

> priority 决定"预算紧张时先丢谁"，trust 决定"能不能当指令"。一个 untrusted 的高优先级证据——比如刚读到的一篇关键报道——仍然只是**数据**，不能被当成指令执行。反过来，一个低 priority 的 trusted section 仍然是可信的控制信息，只是可能在预算不足时被丢掉。
>
> 正交的工程意义是：**降级策略不能影响安全策略**。压缩按 priority 排序，但无论怎么压，`model/tool/provider` 的 trust 标签都不会变。

**Q：semantic Gap relevance 为什么不能只从 `acquired_for_gap_id` 推导？**

> 因为"为什么获取"和"实际证明了什么"是两件事。一个页面可能是为找反叙事而读的，但正文只提供了事实；也可能为事实基线而读，却包含某个主体的立场。
>
> 所以 `acquired_for_gap_id` / `discovered_for_gap_ids` / `target_gap_id` 只记录**获取意图**；Evidence 对哪个 gap 有语义作用，必须由 Reflect **显式提交**，由 Validator 检查引用的 Evidence ID 真实存在，最后由 Reducer 写入。
>
> 不做这个区分，最常见的错误就会发生：把"搜索过某个方向"当成"这个方向已被证据覆盖"。

**Q：required Evidence catalog 为什么必须有界？超过窗口后如何降级？**

> 因为模型 Reflect 时要**准确复制不透明的 Evidence ID**，不能自己编顺序别名——所以关键目录必须在场。但全量 required 目录会随 run 无限增长，最终把系统指令挤出去。
>
> 分三档：当前窗口 64 条是 required + NEVER（预算不够直接抛错，不静默截断）；历史块每块 64 条是 optional + DROP；覆盖率每个 gap 采样 16 条，但同时保留精确的 `evidence_count` 和 `source_count`，所以模型知道"还有多少没看到"。
>
> 选取优先用**语义关系**而不是获取意图，见上面的分组顺序。

**Q：checkpoint 为什么不能把模型文本升级为 trusted？**

> 因为"持久"和"可信"是两件不同的事。模型的话被写进 State、被 checkpoint、被 resume，只说明它**发生过**，不说明它**有指令权限**。所以 `_ALWAYS_UNTRUSTED_ORIGINS` 在构造期就拒绝 `model/tool/provider + trusted` 这个组合——无论调用方是谁、无论经过多少次提交。

**Q：如何证明 100 步 run 的 Context 不随历史线性增长？**

> 三个机制加一个实验。机制：L0/L1 是固定地板；必需窗口（catalog 64 + coverage 16/gap）有界；`recent.step` 只取最近 3 步（`recent_step_limit=3`）。实验：100 步 / 640 条 Evidence 的压力测试，断言 10/50/100 步都能编译、required catalog 不超过 64、coverage 采样不超过 16、两次编译 hash 相同、JSON resume 后 rendered/plan/hash 相同。

**Q：为什么不用向量数据库？**

> 当前是单 run、几百条 Evidence 的规模。这里首先需要的是**确定性引用和可恢复**，不是百万文档召回。向量库会引入 embedding 版本、召回不确定性和"第二事实源"的风险——检索结果不确定，"相同 State 生成相同 Context"这条性质就没了。
>
> 等 artifact 规模超过结构索引能力时，可以把向量检索作为**派生索引**加进来，但不能取代 State。

**Q：压缩以后还能找回原始证据吗？**

> 能，因为压缩只影响"这一轮模型看见什么"，不删除 Full State 和 Artifact。溯源链是：
> `Claim/Narrative → Evidence ID → Source ID → artifact_ref → 原始正文 + locator`。
> Evidence 保存 `source_id`、`excerpt` 和 `locator`，Source 保存 `artifact_ref`，`ProvenanceIndex` 保存 Evidence 与 gap/claim/position/narrative 的关系。
>
> **诚实补一句**：目前**缺少**让模型主动 re-read artifact 局部内容的专用 action（investigation 域的 `retrieve` 是重访已保存文档、换 focus 重新抽取，不是任意读取）。人工审计和报告溯源已经存在，但"模型自己取回局部原文"是下一步可补的能力。

**Q：为什么 L0 的约束写在 pydantic validator 里而不是靠约定？**

> 因为"永不信任"这种事靠 code review 守不住。加一个新 section 的人可能没注意到规则，或者注意到了但觉得"这次特殊"。写成 validator 之后，非法的组合**在构造时就不存在**——不是"不应该"，是"构造不出来"。

# L6 · 工具执行

## 6.1 必须能讲清的机制

### 逻辑工具 vs 物理 provider

模型看到的只有 `ToolDefinition`：

```python
class ToolDefinition(BaseModel):
    name: str                    # "search.web"
    description: str
    capability: str
    input_model: type[BaseModel] = Field(exclude=True)

    def model_spec(self) -> dict:
        return {
            "name": self.name,
            "description": self.description,
            "input_schema": self.input_model.model_json_schema(),
        }
```

`input_model` 被 `exclude=True` 排除——**模型看到的是 JSON schema，看不到 Python 类型**。

`ToolRegistry` 允许**同一个 `ToolDefinition` 绑定多个 provider**：

```python
registry.register(definition, adapter)                    # provider_id = "default"
registry.register_provider(definition, "primary-search", adapter_a)
registry.register_provider(definition, "secondary-search", adapter_b)
```

两条硬约束：

- 追加 provider 时，`definition` 必须**完全相等**，否则 `DuplicateToolError`——避免"模型看到同一 schema，实际 provider 接受不同参数"。
- `provider_id` 必须匹配 `^[a-z][a-z0-9_-]*$` 且 ≤ 64 字符。

**provider_id 和 adapter 从不进入 `model_specs()`。** 模型只知道 `search.web`，不知道背后是 Brave、Serper 还是 MCP。

### 四段工具对象

```text
ToolCall         { action_id, tool_name, arguments: dict }        ← Runtime 产出
ToolInvocation   { action_id, tool_name, attempt, arguments: 已校验类型 }  ← 交给 adapter
ToolAdapterResponse { payload, artifact_refs }                    ← adapter 返回
ToolResult       { action_id, tool_name, payload, artifact_refs, attempts } ← 成功
ToolError        { action_id, tool_name, kind, message, attempts, retryable } ← 失败
ToolOutcome      = ToolResult | ToolError
```

**注意 `ToolResult` 不是 `Observation`。** `ObservationEnvelope` 还要携带 `run_id` / `step_id` / `attempt` / `action_id`，而且 `reflect` / `finish` 这类**内部动作也要产生 Observation**。所以 ToolResult 是"某类环境结果"，Observation 是"Runtime 可以恢复和关联的统一事实"。

这个区别在失败时尤其重要：**`ToolError` 可以成为一个合法 Observation**，让下一轮模型知道"搜索超时了"或"页面不可读"。它不自动意味着 run failed，也不能直接改写 gap。

### `ToolErrorKind`（12 种）与三分类策略

```python
class ToolErrorKind(StrEnum):
    UNKNOWN_TOOL, INVALID_ARGUMENTS, TIMEOUT, RATE_LIMITED, SERVER_ERROR,
    AUTHENTICATION, PERMISSION, NOT_FOUND, UNREADABLE_CONTENT,
    CONTENT_TOO_LARGE, CANCELLED, UNKNOWN_PROVIDER_ERROR
```

`ToolExecutor` 把它们分成三组：

```python
_RETRYABLE_KINDS = {TIMEOUT, RATE_LIMITED, SERVER_ERROR}          # 同 provider 重试
_STOP_IMMEDIATE_KINDS = {INVALID_ARGUMENTS, UNKNOWN_TOOL, CANCELLED}  # 立即返回
_FALLBACKABLE_KINDS = _RETRYABLE_KINDS | {AUTHENTICATION, PERMISSION,
    NOT_FOUND, UNREADABLE_CONTENT, CONTENT_TOO_LARGE, UNKNOWN_PROVIDER_ERROR}  # 换 provider
```

**`retryable` 是推导出来的，不是传进来的**：

```python
@model_validator(mode="before")
def derive_retryability(cls, raw):
    kind = ToolErrorKind(values["kind"])
    expected = kind in _RETRYABLE_ERROR_KINDS
    if "retryable" in values and values["retryable"] != expected:
        raise ValueError("retryable does not match ToolError kind")
    values["retryable"] = expected
```

**所以不存在"一个 timeout 错误却标着 retryable=False"的 ToolError。**

### `ToolExecutor.execute` 的完整流水线

```text
1. registry.resolve(tool_name)
     └─ 失败 → UNKNOWN_TOOL（attempts=0）
2. definition.input_model.model_validate(arguments)
     └─ 失败 → INVALID_ARGUMENTS（attempts=0）
3. result_cache.get(call)
     └─ 命中 → 直接返回（零 provider 调用）
4. for binding in registered.providers:          ← 按注册顺序
     a. circuit.allow_request((tool_name, provider_id))
          └─ 不允许 → continue 到下一个 provider
     b. for local_attempt in 1..max_attempts_per_provider:
          - global_attempt += 1
          - ToolInvocation(action_id, tool_name, attempt=global_attempt, arguments)
          - asyncio.timeout(timeout_seconds) 包裹 binding.adapter.invoke(invocation)
          - 成功 → circuit.record_success → 构造 ToolResult → cache.put → return
          - 失败 → circuit.record_failure(key, kind)
              ├─ kind in RETRYABLE 且还有本地重试次数 → backoff → continue 内层
              ├─ kind in STOP_IMMEDIATE → 立即返回 ToolError
              ├─ kind in FALLBACKABLE → 记下 final_kind/message，break 到下一个 provider
              └─ 其他 → 立即返回 ToolError
5. 所有 provider 都不允许请求 → UNKNOWN_PROVIDER_ERROR（attempts=0）
6. 全部 provider 都失败 → 返回最后一次的 ToolError
```

**四个责任边界**（这是面试重点）：

| 组件 | 负责 | **不**负责 |
|---|---|---|
| `ToolRegistry` | 名称解析、provider 绑定、definition 一致性 | 参数校验、重试、缓存 |
| `ToolExecutor` | 参数校验、成功缓存、同 provider 重试、跨 provider fallback、超时、熔断、安全错误构造 | provider 协议翻译 |
| `Adapter` | **恰好一次** provider 调用 + 协议归一化 | **不建立自己的 retry loop** |
| 模型 | 领域策略（换 query、换方向） | 底层重试与 provider 选择 |

`ToolExecutor` 的 docstring 把这层写得很明确：

> Each adapter performs exactly one provider invocation and never builds its own retry loop.

**两条异常处理纪律**：

```python
# 1. CancelledError 永远不捕获 —— 必须穿透到 AgentLoop 的取消处理
# 2. 其他未知异常统一归一化
except Exception:
    kind = ToolErrorKind.UNKNOWN_PROVIDER_ERROR
    message = "Tool provider returned an unexpected error."
```

**注意归一化的 message 是固定字符串，不含 `repr`**——这是防止 provider 的原始异常文本（可能含 endpoint、header、响应体）泄漏进模型上下文。

**还有一个刻意的例外**：缓存 identity 冲突**不**被转成 ToolError，而是让 `ToolCacheConflictError` 继续向上抛。因为那是**程序错误**（同一个 action_id 被复用于不同 ToolCall），不是运行时可恢复的情况。

### 退避与超时

```python
class RetryPolicy(BaseModel):
    max_attempts_per_provider: int = 3
    timeout_seconds: float = 10.0
    backoff_seconds: float = 0.0
    max_backoff_seconds: float = 30.0

    def backoff_after(self, attempt, *, retry_after_seconds=None) -> float:
        exponential = self.backoff_seconds * (2 ** (attempt - 1))
        delay = max(exponential, retry_after_seconds or 0)
        return min(delay, self.max_backoff_seconds)
```

指数退避**受上限约束**，并且**尊重 provider 的 `retry_after`**（`ToolAdapterError.retry_after_seconds`）。

实际装配值：opinion live 路径 `max_attempts_per_provider=2, timeout_seconds=config.tool_timeout_seconds（默认 30）, backoff_seconds=0`；investigation 路径 `max_attempts_per_provider=2, timeout_seconds=30, backoff_seconds=0`；offline 路径 `timeout_seconds=5`。

### 熔断器

`tools/circuit.py` 的 `ProviderCircuitBreaker`：

```python
ProviderCircuitKey = (tool_name, provider_id)
failure_threshold = 3
cooldown_seconds = 30.0
```

**key 为什么是 `(tool_name, provider_id)` 而不是单独一个**：

- 只按 provider 熔断 → 某个工具接口故障会让该 provider 的**其他能力一起不可用**。
- 只按 tool 熔断 → 一个 provider 的故障会**遮蔽另一个健康 provider**。

**只有"中毒类"错误计入**：

```python
_POISONING_KINDS = {TIMEOUT, RATE_LIMITED, SERVER_ERROR, UNKNOWN_PROVIDER_ERROR}
```

**`AUTHENTICATION` / `PERMISSION` 不算**，理由写在注释里：

> Authentication and permission failures are usually configuration-specific and must remain visible on the next run instead of permanently opening a breaker.

**配置错误必须下一次仍然可见**，不能被熔断器用 30 秒冷却假装自愈了。

**状态机**：

```text
CLOSED --(连续 failure_threshold 次中毒失败)--> OPEN
OPEN   --(冷却时间到)--> HALF_OPEN
HALF_OPEN --(probe 成功)--> CLOSED
HALF_OPEN --(probe 中毒失败)--> OPEN（重新计时）
HALF_OPEN --(probe 非中毒失败)--> CLOSED（释放 probe）
```

**half-open 只允许单个 probe**（`probe_in_flight` 标志），并且**任何 probe 结果都必须释放 probe**——否则熔断器会永久卡在 half-open。

**状态只在内存**：docstring 明确写了"State is intentionally in-memory: it resets on process restart and is execution health, not Domain State or checkpoint data"。**它是执行健康度，不是领域状态，不该进 checkpoint。**

| | `InMemoryActionResultCache` | `JsonActionResultCache` |
|---|---|---|
| 位置 | `tools/cache.py` | `tools/persistent_cache.py` |

### HTTP 边界

`tools/http.py` 的 `HttpxTransport` 有一个具体的安全取舍：**不自动跟随 redirect**（`follow_redirects=False`）。

理由：Brave 使用自定义 credential header。跨域 redirect 时不能假设 HTTP client 会剥离所有非标准鉴权头，所以 3xx 交给 adapter 正规化。**牺牲自动跳转便利，换 credential 不被意外带到第二个域名。**

### MCP 边界（独立的一层安全）

原则：**内部 Tool Protocol 先成立，MCP 只是 adapter。**

四个收紧位置：

**① Discovery 是完整的原子流程**

```text
paginate all tools
→ detect cursor cycles
→ reject duplicate remote names
→ require explicit allowlist match
→ verify canonical input/output schema hashes
→ check local Registry conflicts
→ atomically register all bindings
```

**任何一步失败，Registry 保持不变**——不会出现"三个工具中前两个已注册、第三个 schema 不匹配"的半更新状态。

本地工具名用 `mcp.<server_id>.<remote_name>` namespace，防止不同 server 的同名工具冲突。

**② schema pin**：允许某个工具名**不代表**允许它随意改参数或输出结构。canonical schema hash 对**排序稳定的 JSON schema** 做 SHA-256；server schema 变化时必须由应用显式更新 pin。错误只暴露 remote name 和 expected/actual hash，**不把整个未知 schema 放进日志或模型上下文**。

**③ 递归元数据过滤**——这是一个真实的演进故事（见 `06`）。最终策略：

```text
1. 根据 BaseModel 字段名和 alias 判断 metadata
2. 在序列化之前跳过这些字段
3. 对 Mapping / sequence / 嵌套模型递归投影
4. 检测当前递归路径中的循环引用
5. 最后验证整个公开投影是 JsonValue
6. 所有失败归一为固定安全 ToolAdapterError
```

**关键是"先过滤、后验证"**，而不是在不可信对象上先做复杂序列化。

**④ output schema fail closed**：如果应用 pin 了 output schema，但 server 只返回非结构化 content，**不降级成"尽量解析文本"，而是直接失败**。否则 schema pin 只约束了一个实际没被使用的字段，契约形同虚设。

**transport 层还有**：stdio 的 environment 是显式 allowlist（不继承整个进程环境）；生产 HTTP 必须是正规化后的公开 HTTPS；loopback HTTP 只在显式 development flag 下允许；每次 SDK 操作开闭 client context（**不支持 stateful session 复用**）。

**模型看到的 description 只来自 app config，不使用 remote prose**；**remote annotations 没有策略权威**。

## 6.3 面试追问与参考答法

**Q：为什么 provider fallback 属于 Executor，而不是模型或 Adapter？**

> **模型不该知道 provider 存在。** 如果让模型处理底层重试，每次 retry 都会变成新 step、新 action_id，既污染调查历史，也无法统一控制退避、限流和熔断。
> **Adapter 只做协议归一化。** 让它自己重试，等于每个 adapter 一套退避策略，退避上限、熔断状态、超时都散在各处，无法统一审计。
> 所以 retry / fallback 是**确定性执行策略**，由 `ToolExecutor` 统一拥有；模型只负责领域策略——换 query、换方向、换候选。

**Q：同 provider retry 与跨 provider fallback 的计数与 identity 如何定义？**

> `ToolInvocation.attempt` 是**跨 provider 的全局物理调用次数**，单调递增。`action_id` 在**整个 retry 与 fallback 过程中保持恒定**——因为业务意图和参数没变，只是执行者或次数变了。
> 只有模型收到最终 `ToolError` 之后生成新的 Decision，才进入新的 attempt（`step.attempt + 1` → 新 `action_id`）。

**Q：为什么 auth 失败不触发熔断？**

> 因为 auth / permission 是**配置问题**，不是 provider 健康度。如果它们计入熔断，一次配错的 API key 会把这个 provider 静默屏蔽 30 秒甚至更久，掩盖真正的配置错误。当前设计让它在**下一次运行仍然可见**。
> 对比：timeout / rate_limited / server_error / unknown_provider_error 才是"provider 现在不健康"的信号，它们计入熔断。

**Q：circuit 重启后怎么办？**

> 当前是**内存级保护，重启即重置**。这是单 Runtime 的明确边界，不是遗漏。多 worker 生产环境需要共享 provider health 或引入 Tool Gateway。这个取舍的理由是：熔断器是**执行健康度**，不是领域状态，进 checkpoint 会带来"恢复时该不该恢复熔断状态"这种没有好答案的问题。

**Q：MCP discovery 为什么必须原子注册？**

> 半成功注册会让 Registry 处于"部分工具可信"的中间态。具体危害是：模型看到的是应用配置声明的完整工具集，但实际只有前几个可用，于是行为在应用未变更的情况下漂移；而且这种漂移难以诊断——它看起来像"模型选择有问题"。
> 所以流程是"先全部验证，再一次性注册"，任何一步失败 Registry 保持不变。

**Q：MCP 已经通过 HTTPS 了，为什么还不可信？**

> **HTTPS 证明的是传输加密和服务器身份，不证明返回内容拥有系统指令权限。** 信任按**内容生产者**划分，不按传输是否加密划分。所以 remote description、annotations、content、`_meta` 全部是 untrusted 输入。

**Q：为什么错误必须使用 safe message？**

> 原始异常可能包含 endpoint、response body、command、header 甚至 credential。如果直接把异常文本反馈给模型，就把 provider 边界变成了数据泄漏路径——因为模型上下文会被记录、会被 checkpoint、会被展示。
> 所以 adapter 只能抛带**固定 `safe_message`** 的 `ToolAdapterError`；未知异常统一变成不含 `repr` 的 `unknown_provider_error`。

**Q：为什么只缓存成功结果？**

> 临时失败若缓存，会让恢复**永久复用**旧的 timeout / rate-limit——一个 30 秒的限流会变成这个 action 的永久结论。成功结果才用于 at-most-once 复用。
> 另外，cache identity conflict 是**程序错误**，不能转成普通 `ToolError`——那会让"同一个 action_id 被复用于不同 ToolCall"这个 bug 看起来像一个正常的 provider 失败。

**Q：为什么缓存损坏不直接重新执行？**（同 L2）

> miss = "从未记录成功"，损坏 = "可能记录过成功但证据丢了"。把损坏降级成 miss，就把不确定性伪装成了安全重试。

# L7 · 完成控制与失败恢复

## 7.1 必须能讲清的机制

### finish 只是一个 proposal

这是本层的第一句话。模型提出 `FinishDecision`，Runtime 用 `CompletionPolicy` 独立评估，返回四种处置：

```python
class CompletionDisposition(StrEnum):
    ACCEPT_COMPLETE = "accept_complete"
    REJECT_AND_CONTINUE = "reject_and_continue"
    ACCEPT_PARTIAL = "accept_partial"
    SAFETY_STOP = "safety_stop"
```

映射到终态（`status_for_completion`）：

| disposition | 目标状态 | 含义 |
|---|---|---|
| `ACCEPT_COMPLETE` | `COMPLETED` | 全部完成标准满足 |
| `REJECT_AND_CONTINUE` | `RUNNING` | **不产生任何状态变化**，继续循环 |
| `ACCEPT_PARTIAL` | `PARTIAL` | 有可交付成果，但没到完整标准 |
| `SAFETY_STOP` | `PARTIAL` | 安全原因停止 |

**诚实口径**：`SAFETY_STOP` 在 `status_for_completion` 里有明确映射（→ `PARTIAL`），但**当前两个领域策略都没有产出它**。说"我们有四种处置"是准确的（类型和映射都在）；说"四种处置都在生产中用到"是不准确的。

**关键**：`REJECT_AND_CONTINUE` 时**不产生任何状态变化**。`OpinionSearchObservationProcessor.build_delta` 里写得很直白：

```python
if observation.completion_verdict.disposition is CompletionDisposition.REJECT_AND_CONTINUE:
    return OpinionSearchDelta()
```

返回一个**空 delta**。被拒的 finish 不改状态，只把拒绝理由带回下一轮 Context。

### 完成判定的位置：Resolver 阶段

`OpinionSearchActionResolver.resolve` 的最后一个分支：

```python
return FinishAction(
    completion_verdict=self._completion_policy.evaluate(state, decision)
)
```

**完成判定在 `finish` 从 Decision 变成 Action 的那一刻就发生了**，结果打包进 `FinishAction`，由 `OpinionActionExecutor` 直接转成 `FinishObservation`——**不经过 ToolExecutor，没有任何外部调用**。

然后在下一轮 `EVALUATE_CONTINUATION` 里，`OpinionSearchCompletionEvaluator` 从 Observation 里取出这个 verdict：

```python
def evaluate(self, state, decision, observation) -> CompletionVerdict | None:
    if not isinstance(decision, FinishDecision):
        return None
    return observation.completion_verdict
```

**设计要点**：verdict 是**决策时算的**，不是"完成时"算的。这意味着判定所依据的状态是**确定的、可复现的**——而不是"几步之后状态变了再回头看"。

### opinion 域的完成策略（14 道检查）

`OpinionSearchCompletionPolicy.evaluate` 按顺序检查：

**第 1 组：账目一致性（拒绝）**

1. `set(proposal.resolved_gap_ids) != set(state.resolved_gap_ids)` → `REJECT_AND_CONTINUE`
2. `set(proposal.unresolved_gap_ids) != set(state.open_gap_ids)` → `REJECT_AND_CONTINUE`

**模型不能报错账**——它必须准确说出当前哪些 gap 已解决、哪些还开着。这迫使模型真正读状态，而不是凭印象收工。

**第 2 组：还不该结束（拒绝）**

3. `state.open_gap_ids` 非空 → `REJECT_AND_CONTINUE`（附上还开着哪些 gap）

**第 3 组：可以交付但不完整（降级为 partial）**

4. 没有 source 或没有 evidence → `ACCEPT_PARTIAL`（"No source-backed evidence supports a complete outcome."）
5. 时间窗校验失败（`_temporal_scope_failure`）→ `ACCEPT_PARTIAL`
6. 有 `BLOCKED` 的 gap → `ACCEPT_PARTIAL`
7. 没有 claim → `ACCEPT_PARTIAL`
8. 缺少必需维度 → `ACCEPT_PARTIAL`
9. 事实基线缺 evidence-linked fact claim → `ACCEPT_PARTIAL`
10. 主体维度缺 evidence-linked position → `ACCEPT_PARTIAL`
11. 主导叙事维度缺 dominant/emerging narrative → `ACCEPT_PARTIAL`
12. 反叙事维度缺 counter narrative → `ACCEPT_PARTIAL`
13. 语义链接的来源少于 2 个 → `ACCEPT_PARTIAL`
14. 有争议的 claim 由少于 2 个来源支撑 → `ACCEPT_PARTIAL`

**全部通过** → `ACCEPT_COMPLETE`。

第 13、14 条是最有味道的：

```python
provenance = build_provenance_index(state)
semantically_linked_source_ids = {
    source_id
    for gap in state.gaps
    for source_id in provenance.source_ids_for_gap(gap.gap_id)
}
if len(semantically_linked_source_ids) < 2:
    → ACCEPT_PARTIAL("...fewer than two distinct, semantically linked source records.")
```

**注意 `source_ids_for_gap` 只看 `semantic_gap_ids`**——"为某个 gap 搜到但没被语义引用"的来源**不算覆盖**。而且这里刻意用 `semantically_linked` 而不是 `len(state.sources)`：**读过几个页面**不等于**有几个独立来源支撑结论**。

**诚实口径**：这里的"两个来源"是 **URL 级别的记录多样性**，**不等于出版方独立性**。说"我们保证了来源独立性"是错的。

第 14 条同样：

```python
for claim in state.claims:
    if claim.status is not ClaimStatus.CONTESTED:
        continue
    linked_ids = claim.supporting_evidence_ids + claim.contradicting_evidence_ids
    source_count = len({provenance.record(item_id).source_id for item_id in linked_ids})
    if source_count < 2:
        → ACCEPT_PARTIAL("A contested claim is backed by fewer than two distinct source records.")
```

**一个有争议的主张不能只靠一个来源**——否则它不该被称为"有争议"。

### investigation 域的完成闸门

`domain/investigation/engine.py` 的 `completion(state)`：

```python
open_required = [x for x in state.issues if x.required and x.status == "open"]
if open_required:
    return CompletionVerdict(REJECT_AND_CONTINUE, reason=_open_questions_guidance(state, open_required))

stale = _stale_negative_findings(state)
if stale:
    return CompletionVerdict(REJECT_AND_CONTINUE, reason=_stale_findings_guidance(stale))

active = [x for x in state.findings if x.active]
problems = [x for x in state.issues if x.required and x.status == "unavailable"]
component_problems = [...]
unreviewed = [x for x in active if (r := accepted_review(state, x)) is None or r.verdict != "supported"]
answered_without_findings = [...]
module_gaps = required_module_gaps(state)

if not active or not state.evidence or problems or component_problems or unreviewed or answered_without_findings or module_gaps:
    return CompletionVerdict(ACCEPT_PARTIAL, "Material or review limitations remain; inspect the issue-level caveats.")

return CompletionVerdict(ACCEPT_COMPLETE, "Required questions have explicit dispositions and active findings passed evidence review; this is not a truth guarantee.")
```

**注意最后那句 "this is not a truth guarantee"**——完成标准的措辞刻意避开了"结论是真的"这种承诺。它保证的是"每个必答问题都有明确处置"+"所有 active finding 通过了证据审查"。

两个拒绝条件特别值得讲：

**① `_open_questions_guidance`——那个把"空拒绝"变成可执行指令的修复**（完整故事见 `06 §1`）。

原始实现只有一句 `"Required investigation questions remain open."`，模型拿到之后**没有任何可执行的下一步**，于是反复重试 finish，直到步数耗尽。修复后的版本对**每个** open 问题输出：

```text
Required investigation questions remain open.
- issue-xxx (问题前 60 字):
  N saved evidence excerpts for this question are not disposed by any
  finding or assessment (ev-1 «摘录前 80 字»; ev-2 «...»). Reflect to
  dispose them, or retrieve the saved page with a new focus.
  M discovered candidates remain unread (e.g. https://...). Read one
  before another search.
  No saved evidence and no unread candidates address it. Search a
  different direction (new alias, origin, or material type), or reflect
  to close it honestly: not_found only after the scoped response searches
  complete, otherwise unavailable.
```

**它给的是"程序能看见什么" + "三条合法出路"**：处置已保存证据（reflect / retrieve）、继续获取（read / search）、或者诚实关闭问题（`not_found` 仅在 scoped 搜索完成后，否则 `unavailable`）。

**② `_stale_negative_findings`——防止"未回应"变成陈旧断言**

这个检查针对一类特别危险的 finding：否定存在性主张（"X 尚未回应"）。

```python
_NEGATIVE_EXISTENCE = re.compile(
    r"未(?:公开)?(?:表态|回应|发声|发布声明)|尚未(?:公开)?(?:回应|表态|发声|发布)|"
    r"没有(?:公开)?(?:回应|表态|发声)|未见[^。；，]{0,16}?(?:回应|声明|表态|发声)|"
    r"no (?:public )?(?:response|statement)|has not (?:responded|issued)",
    re.IGNORECASE,
)
```

**为什么它最危险**：否定存在性主张是"live 调查里最陈旧的判断"，因为**后来抓到的证据可以静默地反驳它**。触发场景（注释里写了实测）：一次 2026-09-23 的 live run 发布了"该品牌尚未公开回应"，而证据库里**已经存着官方回应**——读了，但从未转成任何 finding。

**闸门不能判断真伪，但它可以拒绝收尾**：只要有"含回应标记 + 与 finding 主题重叠"的未处置证据存在，就拒绝 finish，并给出退出路径——**一次 reflect 引用该证据（支持或反驳都行）就能处置它**。

**这个设计的分寸感值得注意**：它没有试图判断"官方到底回应了没有"，它只检查"有没有可能反驳的未处置证据"。**程序不越界做语义判断，只做它确定能做的检查。**

还有几个辅助机制：

- `_content_tokens`：中英文混合分词，**减掉 `_GENERIC_TOKENS`**——因为回应/否定词汇在陈旧主张的两侧天然都会出现（"未回应" vs "回应了"），所以它们不构成主题重叠的证据。
- `unbacked_specifics`：确定性数字校验（见下）。
- `accepted_review` + `finding_hash`：**审查绑定 finding 的内容哈希**。

```python
def finding_hash(finding: Finding) -> str:
    return uid("finding-version", finding.model_dump_json())

def accepted_review(state: State, finding: Finding) -> ReviewRecord | None:
    return next((r for r in reversed(state.reviews)
                 if r.finding_id == finding.finding_id
                 and r.finding_hash == finding_hash(finding)), None)
```

**改写 finding 会让它的审查自动失效。** 这堵住了"先让一个弱 finding 通过审查，再改写成强主张"的路径。

### `unbacked_specifics`：确定性数字闸门

审查是模型辅助的，所以有一个**确定性守卫**（`investigation/service.py`）：

```python
def unbacked_specifics(finding, evidence) -> tuple[str, ...]:
    """Numeric/date/percentage tokens in a finding that its cited excerpts omit."""
```

它提取 finding 里的数字/百分比/度量（带 `万`/`亿` 缩放），检查是否出现在被引用摘录中。审查结果为 `supported` 但有缺失项时，**程序把它降级为 `partial`**：

```python
if result.verdict == "supported" and missing:
    result = result.model_copy(update={
        "verdict": "partial",
        "reason": (result.reason + "；程序核验：" + "、".join(missing)
                   + " 未在支持摘录中出现，已降级为部分支持。").strip("；"),
    })
```

**这是"模型审查 + 程序复核"的双层结构**：模型判断语义支持性，程序确定性地检查具体数字是否真的有出处。

### 发布保留段：`ConsolidationValidator`

这是 investigation 域最有辨识度的机制（`investigation/service.py`）：

```python
class ConsolidationValidator:
    """Enforce the investigation's review/finish reserve at the action boundary."""

    def validate(self, state: State, decision) -> None:
        self.inner.validate(state, decision)
        limit = self.budget.limits["model"]
        if self.budget.snapshot()["model"] < math.ceil(limit * 2 / 3):
            return                                       # 还没到 2/3，正常放行
        active = [f for f in state.findings if f.active]
        if not active:
            if not isinstance(decision, ReflectDecision) or not decision.findings:
                raise ValueError("consolidation reserve requires synthesizing "
                                 "evidence-linked findings before finish or more acquisition")
            return
        unreviewed = [f.finding_id for f in active if accepted_review(state, f) is None]
        if unreviewed:
            if not isinstance(decision, ReviewDecision):
                raise ValueError("consolidation reserve requires reviewing current findings "
                                 "before any more acquisition or synthesis")
            if not set(decision.finding_ids) <= set(unreviewed):
                raise ValueError("consolidation review may only reference findings "
                                 "without a current review")
            return
        if not isinstance(decision, FinishDecision):
            raise ValueError("all current findings have been reviewed; finish now with "
                             "the supported subset instead of changing evidence or findings")
```

**逻辑**：模型调用用掉 2/3 之后，剩余调用变成**发布保留段**，动作空间被锁成三步：

```text
无 active finding      → 必须 reflect 并创建 finding
有未审查的 finding     → 必须 review（且只能 review 未审查的）
全部已审查             → 必须 finish（且只能用 supported 子集）
```

**它做的事是"缩小动作空间"，不是"替模型做决定"。** 模型仍然自己选具体动作，但选项被限制在正确的类别里。

**为什么在 2/3 而不是 9/10**：要保证"有限预算内一定有经过审查的产出"。设太晚会出现"跑完预算但一堆 unreviewed"，设太早会挤压调查时间。2/3 留出 1/3 给 review + finish。

配套地，`investigation/context.py` 会在同一时刻注入 `memory.consolidate` section，把同一个约束用**自然语言**告诉模型：

```text
Consolidation phase: choose review next for up to eight IDs from unreviewed_finding_ids.
Do not search, read, retrieve, add questions, or add findings before that review.
```

**Context 与 Validator 成对**：前者告诉模型"该做什么"（可读、可理解），后者保证"不做就不行"（强制）。缺任何一个都会退化——只有提示词会被忽略，只有校验会让模型反复撞墙。

### `required_next_action`：更早的一道动作空间收窄

在 2/3 保留段之前，还有一道更早的引导（`domain/investigation/engine.py`）：

```python
FIRST_REFLECTION_SOURCE_LIMIT = 4
FIRST_REFLECTION_DUPLICATE_STREAK = 2
ONGOING_REFLECTION_UNDISPOSED_LIMIT = 8
```

规则：

| 条件 | 要求的动作 | 理由 |
|---|---|---|
| 已有 active finding 且未处置证据 ≥ 8 | `reflect`（允许只做 assessment） | 读而不用在堆积 |
| 无 active finding、`len(sources) >= 4` | `reflect`（必须创建 finding） | 攒够材料必须先合成 |
| 最近 2 次搜索全是 duplicate 且有未读候选 | `read`（附 `allowed_urls`） | 重复搜索先消化已知候选 |
| 最近 2 次搜索全是 duplicate 且无未读候选 | `reflect` | 无新料，先合成 |

**这个机制的动机写在注释里**：

> Prompt advice alone did not stop a live quality run from spending its full model budget without creating a Finding.

**又是"提示词不够、需要程序强制"的同一个教训。**

### `response_search_complete`：`not_found` 的前置条件

```python
RESPONSE_PURPOSES = {"official_response", "event_response", "followup"}

def response_search_complete(state, issue_id):
    """A 'no response found' claim needs scoped, substantive, finished searching."""
    attempts = [x for x in state.searches if x.issue_id == issue_id and x.purpose in RESPONSE_PURPOSES]
    covered = {x.purpose for x in attempts if x.outcome in {"candidates", "empty"}}
    if not RESPONSE_PURPOSES <= covered or state.read_errors:
        return False
    unread = [c for c in state.candidates
              if c.get("issue_id") == issue_id and c["url"] not in state.read_attempts
              and allowed_url(c["url"], state)]
    return not unread
```

**说"没有回应"必须满足三个条件**：三个 scoped 搜索方向都有实质性结果（`candidates` 或 `empty`，**不是 error**）、没有读取错误、没有还没读的候选。

**这直接实现了"provider 失败不能解释成 not_found"**——一次搜索报错（`outcome == "error"`）不会让 `covered` 包含那个 purpose，于是 `response_search_complete` 返回 False，`not_found` 被 Validator 拒绝：

```python
if item.response == "not_found" and not response_search_complete(state, item.issue_id):
    raise ValueError("missing-response assessment requires successful scoped response searches")
```

### 双层防御：为什么时间窗校验出现两次

`_validate_temporal_gap_evidence`（Validator 层）和 `_temporal_scope_failure`（Completion 层）做的是同一件事。**这不是重复，是 input validation 与 terminal invariant 的双层防御**：

- **Validator 层**：在决策提交前拦下，给模型**修复机会**。
- **Completion 层**：对**已提交状态**做最终防线，防止旧 checkpoint、边界 bug 或组合变化绕过前置校验。

`TaskFrame` 在 run 创建时**冻结 anchor date**，所以 resume 不会按第二天重新解释"过去一周"。`Source.publication_status` 与 `published_at` 的强绑定（L3）保证了"reader 只在 provider 提供可解析发布时间时才标 reported，不允许模型从正文猜日期"。

### `RecoveryDirective`：失败后的五条路

见 L4 的映射表。这里补充它在 Context 里的落地：

```python
for index, failure in enumerate(state.active_step.failures, start=1):
    # 控制面（trusted）
    section(f"active.failure.{index}.control", {
        "kind": failure.kind.value,
        "directive": failure.directive.value,
        "attempt": state.active_step.attempt,
    }, origin=RUNTIME, trust=TRUSTED, priority=99)
    # 内容面（untrusted）
    section(f"active.failure.{index}.message",
            {"message": failure.message},
            origin=MODEL, trust=UNTRUSTED, priority=99)
```

**模型看到的是"失败类型 + 恢复指令 + 第几次尝试"（可信）和"失败消息"（不可信）**，而不是一坨原始异常。

## 7.3 面试追问与参考答法

**Q：为什么 finish 不由模型决定？**

> 因为模型会受上下文长度、最近材料、生成偏好和推理预算影响，**不能同时当研究者和验收者**。它有"想收工"的激励——尤其在上下文快满、或者刚读完几篇看起来很完整的材料时。
> 所以 finish 只是 proposal，由 `CompletionPolicy` 对**已提交状态**做独立判断。判定依据不是模型说了什么，而是 State 里有什么。

**Q：为什么拒绝理由要写这么长？**

> 因为实测教训。原始实现只有一句 `"Required investigation questions remain open."`，模型拿到之后**没有任何可执行的下一步**——它知道被拒了，但不知道该做什么，于是反复重试 finish。一次真实 live run 里 completion gate 拒绝了 `finish` **18 次**，直到步数耗尽，终态是诚实但代价高昂的 `partial`。
>
> 修复是让闸门对每个 open 问题输出"程序能看见什么"（未处置证据的数量、ID 和摘录预览；未读候选的数量和例子；失败读取）加上**三条合法出路**（处置已保存证据 / 继续获取 / 诚实关闭问题）。对应回归在 `tests/investigation/test_finish_guidance.py`。
>
> 这个教训的一般化是：**拒绝必须附带可执行的下一步**，否则拒绝就退化成了死循环。

**Q：为什么在 2/3 处设发布保留段？**
> 为了保证"有限预算内一定有经过审查的产出"。设太晚（比如 9/10）会出现"预算跑完但一堆 unreviewed finding"——成果都在，但没有一条经过证据审查，报告不可交付。设太早会挤压调查时间，导致材料不足。
> 2/3 留出 1/3 给 review 和 finish，是从"必须留够收束预算"倒推的。

**Q：`ConsolidationValidator` 和 `memory.consolidate` section 是不是重复？**

> 不是，它们是**提示词与强制**的配对。Context 里的 `memory.consolidate` 用自然语言告诉模型"现在该 review 了"，模型能理解并自然配合；Validator 保证"不做就不行"。
> 只有提示词会被忽略——这一点有实测支撑（`required_next_action` 的注释就写着 "Prompt advice alone did not stop a live quality run from spending its full model budget without creating a Finding"）。只有校验会让模型反复撞墙，因为它不知道为什么要这样。

**Q：为什么"未回应"这类 finding 要特殊对待？**

> 因为**否定存在性主张是 live 调查里最陈旧的判断**——后来抓到的证据可以静默地反驳它，而主张本身看起来仍然成立。
>
> 实测场景：一次 live run 发布了"该品牌尚未公开回应"，而证据库里已经存着官方回应，只是**读了但没转成 finding**。闸门不能判断真伪，但它可以拒绝收尾：只要有"含回应标记 + 与 finding 主题重叠"的未处置证据，就拒绝 finish，并给出退出路径——一次 reflect 引用该证据（支持或反驳都行）就能处置它。
>
> 这里的分寸是：**程序不越界做语义判断，只做它确定能做的检查**。

**Q：`unbacked_specifics` 和模型审查是什么关系？**

> 双层。模型审查判断**语义支持性**——这段摘录是否支持这个主张；程序确定性检查**具体数字是否真的有出处**——finding 里的每个数字/日期/百分比是否出现在被引用的摘录里。
> 模型审查可能被一段长复合句带偏（看起来整体支持，但其中一个具体数字没有出处），所以程序复核会把 `supported` 降级为 `partial`，并把缺的具体项写进理由。这是"模型负责判断、程序负责核实"的分工。

**Q：`accepted_review` 为什么要绑 `finding_hash`？**

> 堵住"先让一个弱 finding 通过审查，再改写成强主张"的路径。审查绑定 finding 的**内容哈希**，所以任何改写都会让审查自动失效，必须重新审查。这比"审查后禁止修改"更实用——它允许修改，但修改的代价是重新走审查。

**Q：`REJECT_AND_CONTINUE` 为什么不产生状态变化？**

> 因为被拒的 finish 不包含任何**新的领域事实**。它只是模型的一个提议。如果它产生了状态变化（比如记录了"我曾经想收工"），就会污染权威状态，而且让"被拒"变成一种可以被利用的信号。
> 所以 `build_delta` 直接返回空 delta，拒绝理由只通过 Context 回到模型。

**Q：为什么时间窗校验在 Validator 和 Completion 里各做一次？**

> 这是 **input validation 与 terminal invariant 的双层防御**，不是重复。Validator 层在决策提交前拦下，给模型修复机会；Completion 层对已提交状态做最终防线，防止旧 checkpoint、边界 bug 或组合变化绕过前置校验。
> 两层检查的对象不同：前者检查"这个决策"，后者检查"这份状态"。

# 应用层 · 领域包

## 8.1 必须能讲清的机制

### 这一层的定位

**它是 Harness 的验证载体，不是项目本体。** 但要讲清两件事：Runtime 到底提供了什么抽象，以及领域规则为什么必须留在领域层。

### opinion 域：一张 evidence-linked 舆情地图

核心问题：**舆情调查通常没有唯一正确答案**。系统要建立的不是"答案"，而是：

```text
发生了什么（factual baseline）
哪些主体公开表达了什么（stakeholder positions）
主要叙事如何组织事实（dominant narratives）
有哪些反叙事或争议（counter narratives）
```

所以有**四个固定 Investigation Gap**（`app/service.py::default_investigation_gaps`）：

| gap_id | 优先级 | 问题 |
|---|---|---|
| `gap-factual-baseline` | 5 | 哪些可核查的事件与主张构成了事实基线？ |
| `gap-stakeholder-positions` | 5 | 哪些主体公开表态了，说了什么？ |
| `gap-dominant-narratives` | 4 | 哪些主导或新兴叙事在框定这件事？ |
| `gap-counter-narratives` | 4 | 哪些反叙事、批评或实质性分歧在挑战主框架？ |

**它们的作用**：保证 Agent 不会"找到几篇支持同一观点的页面就直接结束"。四个维度天然要求它去找**不同的**东西。

**状态链路**：

```text
CandidateSource（搜索命中，未读）
  → Source（已读并正规化）
    → Evidence（从正文选出的可定位摘录）
      → Claim / StakeholderPosition / Narrative（语义对象）
        → GapAssessment（维度是否解决）
          → FinalSynthesis（终态结论）
```

每一跳都有不变量（见 L3）。特别是 `Candidate → Source → Evidence` 的分离：**搜索 snippet 只能生成 CandidateSource**，因为它是搜索供应商截断和重写的导航信息；页面成功 read 并正规化后才产生 Source；从正文中选出的可定位 excerpt 才是 Evidence。

**证据摘录的选择**（`processor.py::_select_evidence_excerpts`）：

```text
按空行切块
→ 过滤低质量块（推广/登录/注册/导航密集/信息量不足）
→ 按 casefolded 文本去重
→ 按 focus 词打分（重叠 * 4 + 含数字奖励）
→ 取前 3 块
```

`block_limit = 1200` 字符，`max_blocks = 3`。**每个 Source 默认最多提交 3 条 Evidence**，这样 State 不会变成网页 dump，但 Evidence 仍可通过 locator 回到未破坏的 artifact。

### investigation 域：回答用户的具体问题

核心对象是 `Issue`（含 `QuestionComponent`）和 `Finding`。

**复合问题的分解**：一个问题可以拆成多个 `QuestionComponent`，每个独立处置：

```python
class QuestionComponent(Record):
    text: Text
    status: Literal["open", "answered", "disputed", "not_found", "unavailable"] = "open"
    evidence_ids: tuple[str, ...] = ()
    note: str = ""
```

Validator 有一条：`assessment.status == "answered"` 时，**不允许留下任何非 answered 的 component**：

```python
if assessment.status == "answered" and any(
        component.status != "answered" for component in assessment.components):
    raise ValueError("an answered issue cannot keep a non-answered component")
```

**这条防的是"把部分回答伪装成完整回答"。**

**`Finding` 的 response 判断**有一套严格的一致性要求：

| response | 要求 |
|---|---|
| `not_found` | `response_search_complete` 必须为真 |
| `direct, partial, non_substantive` | 必须有 `coverage_reason` |
| `direct` | `uncovered` 必须为空（"直接回答"意味着每一部分都答了） |
| `partial` | `uncovered` 必须非空（否则应该是 `direct` 或 `non_substantive`） |

**这是把"回应覆盖度"的判断变成可检查的结构，而不是自由文本。**

**`EventProfile` / facets**：模型提出事件侧重点（`rule_change` / `service_change` / `billing_remedy` / `investigation_correction` / `general`），**由程序确认**。docstring 写得很清楚：

> Facets are product content policy, not agent types: they select whitelisted PagePlan modules and their evidence fields. Unknown values are dropped by the confirmation step; they never widen the module or renderer whitelist.

**facets 不是 agent 类型**——这个澄清很重要，防止被误读成"轻量多 Agent"。

**`PagePlan`**（`investigation/page_plan.py`）是**程序拥有的页面与调查契约**：

- 从 `EventProfile + Issue + Finding` **重建**，不进 checkpoint；
- 决定页面 section、必需 module 字段、以及**搜索目标**（`search_targets`）；
- `required_module_gaps(state)` 只返回**属于用户必答问题**的缺口。

`plan_id` 是内容的 SHA-256：

```python
canonical = json.dumps(plan, ensure_ascii=False, sort_keys=True, separators=(",", ":"))
plan["plan_id"] = "page-plan-" + sha256(canonical.encode()).hexdigest()[:20]
```

**为什么要有它**：模型提出"缺哪些字段"，但**只有程序决定"哪些字段是必需的"**。`_required_fields` 会根据 issue 的**用户措辞**匹配 `FIELD_REQUIREMENT_TERMS`——用户问了"多久办完"，`deadline` 才变成必需字段。**程序从用户语言推导需求，而不是让模型自己决定要查什么。**

### 哪些规则必须在 domain

这是本层最重要的一问。以下规则一旦写进 Runtime，Runtime 就变成"舆情专用"了：

| 规则 | 位置 | 为什么不能上移 |
|---|---|---|
| 时间窗校验 | `_validate_temporal_gap_evidence` / `_temporal_scope_failure` | "发布时间必须在任务窗口内"是舆情调查的领域要求 |
| `not_found` 的 scoped 搜索前置 | `response_search_complete` | "没找到回应"的判定标准是领域知识 |
| 语义维度覆盖 | `_validate_opinion_dimension_semantics` | "resolve 事实维度需要 fact claim"是舆情语义 |
| finding 与 review 的哈希绑定 | `finding_hash` / `accepted_review` | "审查绑定内容版本"是领域策略 |
| 四个固定 gap / facets / module 白名单 | `default_investigation_gaps` / `FACET_MODULE_TYPES` | 纯领域概念 |
| 社交平台排除 | `SOCIAL_DOMAINS` | 领域内容政策 |
| 发布保留段 | `ConsolidationValidator` | 依赖"调查 → 审查 → 发布"的领域流程 |

**Runtime 提供的抽象只有**：状态分发、事务、恢复、信封关联、完成协议的**类型**（`CompletionVerdict` / `CompletionDisposition`）。**判定内容全在 domain。**

## 8.3 面试追问与参考答法

**Q：为什么有两套 domain？**

> 这是"Runtime 领域无关"的**可验证证据**——同一份 `runtime/` 代码，换一套 domain 装配就是另一条产品线，`runtime/` 一行都不用改。
> 但我要主动说：作为长期维护的项目，两套领域语义高度重叠（gap/claim/narrative vs issue/finding/review），迟早要决定收敛到哪一套。现在保留两套的价值是"证明抽象成立"，不是"准备长期并行"。

**Q：固定四 Gap 的偏差是什么？**

> 好处是提供最小的全局结构，保证 Agent 不会过早收敛到单一视角。偏差是**可能固化调查视角**——如果真实事件的关键维度不在这四类里，系统不会自己发现。
> 而且当前实现里，"反叙事缺失"时宁可标不足也不强行生成——这是正确的保守行为，但也意味着四 Gap 框架的覆盖率上限就是它的覆盖范围。下一步应该由 `OpinionAnalysisFrame` 动态生成 required coverage，再让通用 completion engine 检查 CoverageMap；Runtime 的 completion protocol 不用改。

**Q：为什么 `source_kind` 不参与真实性判断？**

> 因为它只是**模型生成的分析标签**。`ReadDecision.source_kind` 的字段描述里写得很明确："An untrusted analytic label proposed by the model. Runtime completion never treats this label as verified source quality."
> 把模型自报的来源类型当成可信质量信号，等于把幻觉变成了事实。

**Q：`Facet` 是不是一种轻量多 Agent？**

> 不是。`EventProfile` 的 docstring 专门澄清了这一点：facets 是**产品内容政策，不是 agent 类型**。它们选择白名单里的 PagePlan module 和对应证据字段，未知值会被确认步骤丢弃，**永远不会扩大 module 或渲染器白名单**。
> 也就是说 facets 影响的是"页面要展示哪些结构化字段"，不是"谁来执行任务"。执行主体始终是一个 AgentLoop。

**Q：`PagePlan` 为什么由程序生成而不是模型生成？**

> 因为"哪些字段是必需的"是**产品契约**，不是模型判断。模型可以提出"这个事件属于规则变更类"，但 `MODULE_ANCHOR_FIELDS` / `FIELD_REQUIREMENT_TERMS` / `REQUIRED_MODULE_FIELDS` 这些白名单由程序持有。
> 具体机制是：`_required_fields` 会根据 issue 的**用户措辞**匹配 `FIELD_REQUIREMENT_TERMS`——用户问了"多久办完"，`deadline` 才变成必需字段。**程序从用户语言推导需求，而不是让模型自己决定要查什么。** 这既保证了模块不会缺失，也防止模型通过"我觉得需要这个字段"来扩大调查范围。
