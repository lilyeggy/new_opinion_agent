## 1. 自动化测试基线

### 1.1 命令

```bash
cd opinion_search_agent
TMPDIR="$PWD/.pytest_tmp" .venv/bin/python -m pytest -q --no-header -p no:cacheprovider
```

**为什么要设 `TMPDIR`**：在受沙箱约束的环境里，pytest 无法在系统临时目录下创建自己的根目录（`mkdir` 被拒），会导致 155 个用例在 setup 阶段报错——**看起来像大面积失败，实际是环境问题**。把临时目录指到项目内即可。这一点项目实现记忆里已有记录（"沙箱环境需 `--basetemp` 指向项目内目录"）。

### 1.2 本次实测结果（2026-09-25）

```text
3 failed, 788 passed, 2 skipped in 762.07s (0:12:42)
```

**测试规模**：89 个测试文件、约 18.8k 行；分 `unit` / `contract` / `integration` / `e2e` / `security` / `investigation` 六组。

**2 个 skip 是设计内的**——`tests/e2e/test_real_web_smoke.py` 的两个 live-gated smoke，需要真实 provider key 才启用：

```text
SKIPPED test_real_web_smoke.py:29  set RUN_LIVE_TOOL_TESTS=1 to enable provider smoke tests
SKIPPED test_real_web_smoke.py:88  set RUN_LIVE_AGENT_TESTS=1 to enable the live Agent smoke test
```

**3 个 failed 是环境时序问题，不是逻辑失败。** 这三个用例是：

| 用例 | 失败断言 | 它的时间预算 |
|---|---|---|
| `test_publish_protocol.py::test_running_snapshot_never_claims_terminal_without_report` | `run did not terminate in time` | 400 次轮询 × 5ms ≈ **2 秒** |
| `test_targeted_followup.py::test_provisional_workbench_written_during_run_and_served_before_report` | `run did not terminate` | **20 秒** |
| `test_targeted_followup.py::test_followup_intent_is_persisted_on_the_child_draft` | `wait_for_terminal` 超时 | **20 秒** |

它们的共同模式是：**启动一个后台 offline 调查 run，然后轮询 `manager.snapshot()` 直到终态**（`tests/investigation/conftest.py::wait_for_terminal`，`timeout=20.0`，轮询间隔 20ms）。

在受沙箱约束的环境里，每次文件操作都要经过代理，单次 offline 调查 run 的墙钟时间被拉长到超过这个预算。**判据**：同一个 `wait_for_terminal` 被大量其他用例共用且通过，说明链路本身没问题；失败的三个恰好都是"需要额外一次子 run 或额外一次投影轮询"的用例——属于**预算边际**，不是功能错误。

**所以正确说法是**：

> 本机正常环境下全量是 **779 passed, 2 skipped**（2026-09-21 归档后的记录）。我在受限沙箱里重跑得到 788 passed / 3 failed / 2 skipped，3 个失败全是"轮询后台 run 到终态"的 2–20 秒时限断言，在文件操作被代理拖慢的环境下达不到——不是逻辑失败。

**不要做的事**：不要说"全部通过"，也不要把 3 个失败说成"无关紧要"而不解释。**说出机制**比说结论可信。

### 1.3 为什么测试数量本身不是卖点

面试官问"你如何证明系统真的跑通了"时，**报测试数量是最弱的回答**。正确姿势是说明**每组测试对应哪个系统不变量和失败窗口**——见下一节。

## 2. 五类关键测试证据

### 2.1 Recovery Matrix：证明恢复控制流

`tests/e2e/test_recovery_matrix.py`

直接构造每种持久状态，覆盖：`created` / 无 active step / `deciding` / `decision_accepted` / `action_running` / `observation_ready` / `reducing` / `committed + continuation` / `terminal`。

**关键**：每行不只断言"最终完成"，还断言 **model、resolver、adapter、processor、reducer 各自的调用次数**，以及 `step_id`、`attempt`、`action_id`、`revision`。

**举例**：Observation 已保存时，**adapter 调用必须为 0**。否则即使最终结果正确，系统也可能重复了外部请求——**结果对不代表过程对**。

### 2.2 `ACTION_RUNNING` 跨进程缓存恢复：证明窗口 A

`tests/e2e/test_action_running_recovery.py`

测试步骤：

1. 让旧 Executor 调用 provider，**把成功结果写 cache**，但**不把 Observation 写入 state**——精确模拟崩溃窗口；
2. 用**全新的** registry、adapter、executor、cache 和 loop resume；
3. 断言：fresh adapter 调用 **0 次**、原 `action_id` **不变**、state `revision` **只增加一次**。

这是"at-most-once 复用已持久化成功结果"的直接证据。

### 2.3 100 步 / 640 条 Evidence 长轨迹：证明 Context 有界且确定

`tests/integration/test_context_long_trajectory.py`、`tests/integration/test_loop_context_growth.py`

构造 100 个 committed step、80 个 Source/Candidate、640 条 Evidence，含 contested Claim、Position、Narrative，以及**恶意 section marker**。

固定 80K 预算下断言：

- 10 / 50 / 100 步**都能编译**；
- required catalog **不超过 64**；
- coverage sample **不超过 16**；
- **两次编译 hash 相同**；
- **JSON resume 后 rendered / plan / hash 相同**。

**这证明的是有界性、确定性、以及"没有进程内隐藏状态"**——不只是"prompt 没报错"。

### 2.4 14 路 prompt injection 矩阵：证明信任标签不被洗白

`tests/security/test_context_injection_matrix.py`

覆盖 14 个注入路径：

```text
search snippet / reader excerpt
MCP structured content / MCP unstructured content
模型 query / 模型 focus / 模型 reflection
gap rationale / Decision prose
ToolError message / validation error / completion rejection
checkpoint resume
伪造的 section marker
```

统一断言：

- 哨兵内容**只能**出现在 untrusted section；
- **L0 / L1 不受污染**；
- trusted control **不包含** provider / model prose；
- **resume 不提升 trust**。

**诚实口径**：这个矩阵证明的是**来源与信任标签保持、边界转义等结构性质**，不是"抗注入成功"——它不保证模型不会被说服，只保证被说服的内容**没有指令权限**。

### 2.5 Contract 与真实边界 E2E

- `tests/contract/`：Fake / Brave / Jina / MCP adapter 共享同一套内部 contract。
- `tests/e2e/test_real_mcp_tool.py`：**真实本地 stdio MCP** 走完 discovery → allowlist → schema pin → Registry → Executor → adapter → SDK transport → `ToolResult` 全链路。
- `tests/e2e/test_web_server.py` / `test_investigation_web.py`：Web E2E 覆盖启动 run、SSE、snapshot、取消、历史恢复、报告。
- `tests/e2e/test_tool_fallback.py`：provider fallback 端到端。

**两个默认 skip 是需要真实 provider key 的 live-gated smoke**，不是静默跳过核心测试——这一点要主动说，否则听起来像在藏。

## 3. 人工质量检验（三个数字）

**这三组数字是人工检验的，不是 benchmark。** 必须带口径说。

### 3.1 检索召回 60%

```text
口径：6/10 人工标注必中清单，逐项独立搜索验证
```

**为什么不是 10/10，缺口在哪**（这个"为什么"比数字本身更有价值）：

- **候选 66% 来自单一聚合站**（`news.qq.com`），**原发媒体站零覆盖**——聚合站偏向直接压低了必中率。
- **反爬读取失败 6/17**（qq / sohu 系）。
- **证据摘录选择是单点**：4 条 partial finding **全部**是"引语在原文里，但摘录没摘到"。

### 3.2 忠实性 71% 完全支持、100% 零虚构

```text
口径：14 条 finding 人工逐条核对；71% = 10/14 完全支持
```

**关键的一半是"100% 零虚构"**：所有 partial 都是**摘录召回不足**，**没有一条是编造**。这两件事必须分开说——"支持率 71%"听起来一般，但"零虚构 + 缺口全部来自召回"说明**问题在检索层，不在生成层的可信度**。

### 3.3 对抗回放 2/3

```text
口径：7 篇真实文档 + 3 篇埋点文档，检查三类对抗行为是否按预期发生
```

| 埋点 | 结果 |
|---|---|
| 更正说明 | ✓ **完全采纳** |
| 反方稿 | ✗ 已读、已摘 5 条证据，但**零 finding 引用** |
| 错误数字（3160.3 亿 vs 真实 316.03 亿） | ✓ **未传播**——但靠的是"未轮到综合"，**不是矛盾检测** |

**第三个的诚实版本很重要**：数字没传播是好事，但**机制不是我们设计的那个**。数字护栏只验**出处**不验**可信度**，所以真实值 316.03 亿和埋点值 3160.3 亿在库里**静默并存**。这个"结果对但原因不对"的区分，是面试里很能体现工程诚实度的点。

产物位置：`artifacts/adversarial-cases/sanjiu-2026-09/`。

## 4. 一次真实 live run 的完整记录

**事件**：三九胃泰中秋广告争议（真实中文公开舆情事件）
**方式**：Web API `mode=live` 创建
**产物**：`artifacts/live-runs/investigations/runs/{f045d7ee…, 9b1bf7d6…}/`

### 4.1 主 run（60 步）

| 指标 | 数值 |
|---|---|
| 步数 | 60（走完全流程） |
| 搜索 | 17 次 |
| 读取 | 17 次 |
| findings | 14 条 |
| 证据引用 | 92 处 |
| review | 执行（6 supported / 8 partial） |
| completion gate 拒绝 finish | **18 次** |
| 终态 | `partial`（必答问题仍 open） |

### 4.2 对照 run（20 步）

同一题目的另一次运行停在 **20 步**、终态 `partial`。诊断显示：

- `committed_steps = 20` **恰好等于默认上限** `max_steps = 20`；
- 预算只用了 **16%–45%**。

**结论：这是配置问题，不是逻辑问题。** 把 `max_steps` 调到 60 之后就完整跑完了（即 4.1）。

**这个对照很有价值**——它说明诊断链能区分"跑不动"和"跑不完"。

### 4.3 这次 run 的诚实计数

- 搜索失败：**0**
- 读取失败：**3**（UI 总览明示"缺失材料不代表没有新进展"）
- 来源关系：**全部标"未核实"**，不冒充独立
- stop_reason：`Decision recovery was exhausted: The model response did not match the decision schema.`
- 模型本轮未提出可用 facets，投影**如实回退 general 视图**

**注意最后两条**：系统没有因为"决策结构化失败"就伪造一个漂亮结果，也没有因为"模型没给 facets"就编一个默认分类。**如实回退**是可靠性机制的一部分。

## 5. 报数字的纪律

面试里最容易失分的不是数字低，是**数字说不清口径**。三条纪律：

### 5.1 每个数字配一个分母

| 别这么说 | 这么说 |
|---|---|
| "召回率 60%" | "**6/10** 人工标注必中项，逐项独立搜索验证" |
| "忠实性 71%" | "**10/14** 条 finding 人工逐条核对完全支持，且 100% 零虚构" |
| "跑了 60 步" | "60 步走完全流程：17 搜 / 17 读 / 14 findings / 92 处引用" |

### 5.2 区分"实测"和"设计"

| 类型 | 例子 | 怎么报 |
|---|---|---|
| **实测** | 60 步 live run 的数字、18 次拒绝、召回 6/10 | 直接报，带口径 |
| **构造** | 100 步 / 640 Evidence 长轨迹 | **必须说"这是构造状态的压力测试"**，不能暗示"真实模型自主跑出来的" |
| **设计内** | 2 个 live-gated skip | 主动说"需要真实 key 才启用" |
| **环境** | 3 个时序失败 | 说机制，不说"无关紧要" |

### 5.3 不报没有来源的数字

这一条是**给自己立的规矩**。报一个漂亮但无出处的改进幅度（"修复后提升了 3 倍"），一旦被追问"怎么测的"就崩了。**能证明什么就说什么**。

## 6. 已知限制（主动说）

面试官问"你最大的不足是什么"时，有准备的清单远好过临场编造。以下每一条都能指出**具体的观测证据**：

| 限制 | 证据 |
|---|---|
| **单一搜索引擎固定结果数** | Brave 固定返回；`TaskFrame` 的时间/语言/域约束**已解析但未传给 provider** |
| **聚合站偏向** | 候选 **66%** 来自 `news.qq.com`，原发媒体站零覆盖 |
| **反爬读取失败** | qq / sohu 系 **6/17** 读取失败 |
| **证据摘录选择是召回瓶颈** | 4 条 partial finding **全部**是"引语在原文但摘录未摘到" |
| **反方材料已读未用** | 对抗埋点里反方稿已读、已摘 5 条证据，**零 finding 引用** |
| **模型不会主动收口 `not_found`** | 长期无证据的问题不会被显式从 `open` 转 `not_found`——这是 gate 拒 finish **18 次**的直接原因 |
| **数字护栏只验出处** | 只检查"数字是否在摘录里出现"，不检查可信度；真实 316.03 亿与埋点 3160.3 亿**静默并存** |
| **决策结构化成功率是瓶颈** | 一次 live run 的 stop_reason 就是 `The model response did not match the decision schema.` |
| **无 benchmark** | 只有人工标注的领域质量检验 |
| **无分布式保证** | 单机单写者；缓存只有文件原子性 + 进程内锁 |
| **缺少 artifact 局部重读 action** | Context 压缩后模型无法主动取回局部原文 |

**主动说这些的收益**：它把面试从"你做的够不够好"转成"你知不知道自己做到哪了"——后者是更高级的信号。
