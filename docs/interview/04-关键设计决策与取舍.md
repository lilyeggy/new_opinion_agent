# 04 · 关键设计决策与取舍

> 面试里"你做了什么"只占一半，"你为什么这样做、代价是什么"占另一半。
> 每一条的结构是：**背景 → 决策 → 替代方案与代价 → 代码落点 → 一句话答法**。
> 分组：A 架构级 / B 执行可靠性 / C 状态与数据 / D 上下文与安全 / E 完成控制 / F 边界纪律。

---

## A · 架构级决策

### A1 自研显式 async loop，不用 LangGraph

**背景**：LangGraph 提供图节点、状态快照、条件边、持久化接口和 HITL，能显著加快业务 Agent 的交付。

**决策**：自己实现显式 async loop + Run/Step 双生命周期 + step transaction + 纯 Reducer + checkpoint/resume + Completion Control。

**替代方案与代价**：

| 方案 | 得到 | 失去 |
|---|---|---|
| 用 LangGraph | 成熟生态、图组合、已有 checkpointer、HITL | 执行语义被框架决定；项目退化为"会写节点和条件边" |
| 自研（当前） | 拥有并验证全部执行语义；边界窄、机制透明 | 自己承担 Runtime 正确性与维护成本；没有生态 |

**判断标准**：**Agent Runtime 是"实现手段"还是"要交付的能力"**。前者选框架，后者自研。

**代码落点**：`runtime/loop.py`（`AgentLoop`）、`runtime/transaction.py`（`classify_resume`）。

**一句话答法**：
> 如果目标是快速搭一个业务 Agent，我会直接用 LangGraph。但这个项目要交付的正是"状态何时更新、工具调用如何恢复、step 如何提交、context 如何重建、finish 如何验收"——用图执行会把这些藏起来。脱离场景说谁更好都不专业。

**追问准备**：既然最终还是 while loop，自研价值在哪？——答：普通 while loop 只有控制流，没有事务语义。这里每轮都从可持久化状态经纯 `classify_resume` 决定下一动作；每个副作用前后都有 checkpoint boundary；commit 同时更新领域状态、step 历史、action ledger、游标和 continuation 标记。价值不在 `while`，在围绕它的协议、不变量和恢复证明。

### A2 不做多 Agent（试过并砍掉）

**背景**：实现过一版分层多角色流水线——程序化 Orchestrator 维护全局计划与预算，Research Director 负责策略，Research Agent 在局部预算内自主搜索，Evidence Analyst 把冻结材料转成原子判断，Reviewer 在隔离上下文核查引用。

**决策**：2026-09-21 评估后归档到 `archive/harness-pipeline/`，理由三条：

1. **重复了已有能力**——PagePlan 驱动的骨架渲染 + targeted search 已经提供了同样的覆盖结构。
2. **绕过了 Runtime 的可靠性机制**——多角色路径没有走 step transaction / checkpoint / completion gate。
3. **不解决真正的瓶颈**——如果单 Agent 不知道该覆盖哪些维度，复制成四个只会**并行地产生更多散乱材料**。

**替代方案与代价**：

| 方案 | 得到 | 失去 |
|---|---|---|
| 多 Agent | 理论上可并行调查不同维度 | 任务分配、状态合并、冲突解决、并发 checkpoint、失败传播；且不改善语义覆盖 |
| 单 Agent（当前） | 单一权威状态、恢复语义简单、可解释 | 不能并行；覆盖质量依赖单 Agent 的领域策略 |

**代码落点**：`archive/harness-pipeline/README.md`（完整决策记录）；`docs/opinionsearch-current-vs-multi-agent-architecture.md`（提案与最终结论）。

**一句话答法**：
> 实现过，评估后砍掉。理由不是做不了，而是它重复了已有能力、绕过了 Runtime 的可靠性机制，而且不解决真正的瓶颈——真正的瓶颈是"单 Agent 不知道该覆盖哪些舆情维度"，把这个复制成四个 Agent，只会并行地产生更多散乱材料。

**注意**：这题**必须答"试过并砍掉"**，说"没做过"会浪费手里最好的一张牌。

### A3 一个 Runtime + 两个组合根

**背景**：项目有两条产品路径——单问题舆情搜索（CLI/legacy console）和公开事件调查工作台（Web 主页面）。

**决策**：不做"一套通用领域模型"，而是让 Runtime 保持领域无关，由两个组合根分别装配。`AgentLoop` 的 12 个注入点里 11 个是 `Protocol`、1 个是 `Callable`（见 `02 §4`）。

**代价**：两套领域语义高度重叠（gap/claim/narrative vs issue/finding/review），长期维护迟早要收敛；`context/` 与 `memory/` 栈只有一半是共享的，新人容易误以为全共享。

**代码落点**：`app/service.py::_build_loop` 与 `investigation/service.py::build_loop`——两个函数都调用 `AgentLoop(...)`，注入各自的实现，`runtime/` 零改动。

**一句话答法**：
> 这是"Runtime 领域无关"的可验证证据。但作为长期维护的项目，两套领域语义重叠，迟早要决定收敛到哪一套——这一点我会主动说。

---

### A4 只深做两层，明确五个非目标

**决策**：只做 ① Agent Harness / Runtime；② Tool / MCP / Context / Run-scoped Memory。不做 Environment/Sandbox、Control Plane、Trace/Observability 平台、Eval/Benchmark 平台、Model Serving。

**代价**：没有 benchmark 分数、没有分布式执行、没有观测平台。这三项都是面试时会被问到的"缺什么"。

**为什么值得**：**边界纪律**。什么都在项目里做一点，就什么都讲不清。而且这三个方向都需要先有稳定的单机语义才有意义。

**一句话答法**：
> 不是没能力，是边界纪律。Eval 平台和 Control Plane 会让项目从"讲得清取舍"变成"什么都做了一点"。

## B · 执行可靠性决策

### B1 checkpoint 存全量 State，而不是事件日志

**背景**：两种主流方案——状态快照 vs 事件溯源（event sourcing）。

**决策**：存全量 State 快照。

| 方案 | 得到 | 失去 |
|---|---|---|
| 事件日志 + 重放 | 存储小、可审计每一步 | 恢复要重放整个历史；reducer 有 bug 时历史不可修复；恢复时间随 run 增长 |
| 全量快照（当前） | 恢复语义明确（读出来就是状态）；`classify_resume` 只看快照就能定位；单机单写者场景下简单 | 存储大；每次都要序列化整个 State |

**为什么当前场景选快照**：单机单写者，State 规模可控（一次 run 几百条 evidence），恢复语义的确定性比存储效率更重要。

**代码落点**：`runtime/checkpoint.py::JsonCheckpointStore._save_sync`（`state.model_dump(mode="json")`）。

**一句话答法**：
> 单机单写者场景下，快照比重放简单且恢复语义明确——`classify_resume` 靠快照就能定位该做什么。代价是存储和序列化开销，这个规模下可以接受。

---

### B2 每个 step 是一个七阶段事务，阶段与载荷硬绑定

**决策**：`StepPhase` 七阶段线性推进，每阶段对"该携带哪些信封"有硬约束，由 pydantic validator 强制。

**代价**：写新代码时要同时维护"阶段 → 载荷"表；某些看似合理的中间状态（比如"有 decision 但 phase 还是 opened"）构造不出来。

**为什么值得**：**反序列化一个被篡改或半写的 checkpoint 会直接失败**，而不是带着脏状态继续跑。这个校验不是靠 code review 守的，是靠类型系统让非法组合**构造不出来**。

**代码落点**：`runtime/protocols.py::_STEP_PAYLOAD_FIELDS_BY_PHASE`、`StepRecord.validate_recovery_invariants`。

**一句话答法**：
> 每个 phase 对"该携带哪些载荷"有硬约束，`ACTION_RUNNING` 必须已有 decision 和 action、但绝不能提前有 observation。半写的 checkpoint 在构造时就失败，不会带着脏状态继续跑。

---

### B3 成功结果按 action_id 落盘（at-most-once 复用，不是 exactly-once）

**决策**：工具成功结果按 action identity 缓存到磁盘（`action_results/`）。进程在"缓存已写、observation 未落盘"之间死掉时，resume 复用而不重复调用 provider。

**边界（必须主动说清）**：

| 保证 | 不保证 |
|---|---|
| 状态效果幂等（同一 delta 只产生一次状态变化） | 外部服务 exactly-once |
| 已持久化成功结果的 at-most-once 复用 | 两个进程并发恢复时的互斥 |
| —— | "provider 已收到请求、结果未写缓存"之间的重发 |

**前提**：舆情工具是**只读**的，重发是安全的。如果引入有副作用的工具，这个承诺就不成立了。

**生产化还需要**：run ownership/lease、action record 的 compare-and-set、provider 支持时传 action_id 作为幂等键、有副作用工具的补偿或人工确认。

**代码落点**：`tools/persistent_cache.py::JsonActionResultCache`、`runtime/loop.py::EXECUTE_ACTION` 分支。

**一句话答法**：
> 准确承诺是 at-most-once 复用已持久化的成功结果，加上状态效果的幂等——可以说 effectively-once state effect，但不是外部 exactly-once。而且这个承诺依赖"舆情工具只读"这一前提。

---

### B4 `execution_profile` 进 checkpoint

**背景**：resume 时如果换了模型或工具组合，"重放同一个 action"的语义已经变了。

**决策**：checkpoint 里存一个不透明的 execution profile 摘要（`sha256(parts)[:16]`），加载时不匹配直接拒绝。

**代价**：改配置后旧 checkpoint 无法 resume——但这正是想要的行为。

**为什么不直接存配置**：配置里有 API key。摘要既能检测变化，又**不保存密钥和 provider 配置本身**。

**代码落点**：`app/service.py::_execution_profile_id`、`runtime/checkpoint.py::_load_sync` 的 `CheckpointProfileError`。

**一句话答法**：
> 换模型或换工具组合后，重放同一 action 的语义已经变了，必须在动作重放**之前**拒绝，而不是让新模型去解释旧决策。它是不透明摘要，不保存密钥。

---

### B5 工具层不重试 `CancelledError`

**决策**：`ToolExecutor` 里 `asyncio.CancelledError` **永远不捕获**，直接向上传播到 `AgentLoop` 的取消处理。

**为什么**：取消必须能穿透到 `_await_operation` 的竞速，让 `asyncio.wait(FIRST_COMPLETED)` 正常工作。如果在工具层吞掉它，取消就失去了"能中断正在等待的 await"这个能力。

**同时**：其他任何意外异常都归一化成 `UNKNOWN_PROVIDER_ERROR`，且 message 是**固定字符串不含 `repr`**。

**唯一的例外**：缓存 identity 冲突**不**转成 `ToolError`，而是让 `ToolCacheConflictError` 继续抛——因为那是**程序错误**，不是运行时可恢复的情况。

**代码落点**：`tools/executor.py::ToolExecutor.execute`、`runtime/loop.py::_await_operation`。

**一句话答法**：
> 取消必须能穿透到竞速层，让"操作"和"取消信号"先完成者胜出。如果在工具层吞掉它，取消就失去了中断正在等待的 await 的能力。但缓存 identity 冲突是程序错误，不能伪装成 provider 失败。

---

### B6 熔断器状态只在内存

**决策**：`ProviderCircuitBreaker` 的状态**不进 checkpoint**，进程重启即重置。

**为什么**：熔断器是**执行健康度**，不是领域状态。进 checkpoint 会带来"恢复时该不该恢复熔断状态"这种没有好答案的问题——如果恢复，一次临时故障会被永久记住；如果不恢复，存它干什么。

**代价**：多 worker 环境需要共享 provider health 或 Tool Gateway，当前不支持。

**代码落点**：`tools/circuit.py` 的 docstring 明确写了 "State is intentionally in-memory"。

**一句话答法**：
> 它是执行健康度，不是 Domain State，不该进 checkpoint。多 worker 生产环境需要共享 provider health 或 Tool Gateway——这是单 Runtime 的明确边界。

---

### B7 只有"中毒类"错误计入熔断

**决策**：`_POISONING_KINDS = {TIMEOUT, RATE_LIMITED, SERVER_ERROR, UNKNOWN_PROVIDER_ERROR}`。`AUTHENTICATION` / `PERMISSION` **不计入**。

**为什么**：auth/permission 是**配置问题**，不是 provider 健康度。如果它们计入熔断，一次配错的 API key 会把这个 provider 静默屏蔽，**掩盖真正的配置错误**。当前设计让它在下一次运行仍然可见。

**代码落点**：`tools/circuit.py::_POISONING_KINDS`（含原注释）。

**一句话答法**：
> 配置错误必须下一次仍然可见，不能被熔断器用冷却时间假装自愈。

---

### B8 熔断 key 是 `(tool_name, provider_id)`

**决策**：熔断隔离粒度是工具与 provider 的组合，不是单独一个。

| 方案 | 问题 |
|---|---|
| 只按 provider | 某个工具接口故障会让该 provider 的**其他能力一起不可用** |
| 只按 tool | 一个 provider 的故障会**遮蔽另一个健康 provider** |
| `(tool, provider)`（当前） | 粒度正确，状态数略多 |

**代码落点**：`tools/circuit.py::ProviderCircuitKey`。

---

### B9 不自动跟随 redirect

**决策**：`HttpxTransport` 设置 `follow_redirects=False`，3xx 交给 adapter 正规化。

**为什么**：Brave 使用自定义 credential header。跨域 redirect 时**不能假设 HTTP client 会剥离所有非标准鉴权头**。

**代价**：牺牲自动跳转便利。

**一句话答法**：
> 牺牲自动跳转便利，换 credential 不被意外带到第二个域名。

---

### B10 MCP：allowlist + schema pin + 原子注册 + 递归过滤

**决策**：MCP 只作为 adapter，内部 Tool Protocol 先成立。四个收紧位置：

1. **discovery 原子注册**——先全部验证（allowlist 匹配 + schema hash + Registry 冲突），再一次性注册。任何一步失败 Registry 保持不变。
2. **schema pin**——canonical schema 的 SHA-256 固定远端契约；变化必须由应用显式更新。
3. **递归元数据过滤**——`_meta` / `meta` / `annotations` 在**每一层嵌套**都要剥离，且必须**先过滤后验证**。
4. **output schema fail closed**——声明了 output schema 但返回非结构化 content，**直接失败**，不降级成"尽量解析文本"。

**替代方案**：动态注册 server 返回的所有工具。**问题**：discovery 是能力发现，**不是授权**。动态全注册会让 server 通过新增工具扩大 Agent attack surface，也会让模型上下文和行为在应用未变更时漂移。

**代码落点**：`tools/adapters/mcp.py`、`tools/adapters/mcp_sdk.py`。

**一句话答法**：
> HTTPS 证明传输加密和服务器身份，不证明返回内容拥有系统指令权限。信任按内容生产者划分，不按传输是否加密划分。

## C · 状态与数据决策

### C1 Reducer 是纯函数，且是唯一写入口

**决策**：`reduce_opinion_state(old_state, accepted_delta) -> new_state`。没有 `self`、没有 I/O、没有时钟、没有随机。无变化时返回原对象、**不递增 revision**。

**为什么必须纯**：

1. **可重放**——窗口 B 的恢复就是"重新构造 delta 并提交"。
2. **可测试**——给定旧状态和 delta 就能断言，不需要 mock。
3. **恢复语义可判定**——如果 reducer 里有时钟，同一份 checkpoint 在不同时间恢复会得到不同状态。

**责任分工**：I/O 在 `ActionExecutor`，翻译在 `Processor`，纯状态合并在 `Reducer`。

**代码落点**：`domain/opinion/reducer.py`、`domain/investigation/engine.py::reduce_state`。

---

### C2 Decision / Action / Observation / Delta 四对象分离

**决策**：四个对象代表四个不同的事实阶段，属于四个不同的责任主体。

```text
Model proposes Decision
Runtime validates and resolves Action
Environment returns Observation
Domain processor proposes StateDelta
Reducer commits new State
```

**为什么不能合并**：

| 合并方式 | 问题 |
|---|---|
| Decision = ToolCall | `reflect` / `finish` 要么被伪装成假工具，要么绕开统一生命周期；模型会知道 provider 存在 |
| ToolResult = Observation | 内部动作（reflect/finish）也要产生 Observation；Observation 需要 run/step/attempt/action_id 关联 |
| 没有 Delta | 同一个 SearchResults 需要经过 URL 正规化、domain 过滤、去重、excerpt 选择才能进 State；这些领域规则没有落点 |

**代码落点**：`runtime/protocols.py`（四段信封）、`domain/opinion/processor.py`（翻译）、`domain/opinion/reducer.py`（合并）。

**一句话答法**：
> 它们代表四个不同的事实阶段，也属于四个不同的责任主体。合并之后，模型可能绕过校验产生副作用，工具返回可能绕过领域规则直接成为事实，Runtime 也无法判断崩溃发生在"动作未执行""结果已获得"还是"状态已提交"。

---

### C3 权威状态最小化，派生对象不得成为第二事实源

**决策**：只有领域 State 是权威。`WorkingMemory` / `CompiledContext` / `PagePlan` / `OpinionCoverageCell` / 报告投影全部是**派生对象**，可以持久化用于诊断，但不得写回。

**代码落点**：`investigation/page_plan.py` 的 docstring——"intentionally rebuilt from EventProfile, Issue and Finding records instead of becoming another mutable authority in the checkpoint"。

**一句话答法**：
> 一旦能写回就有两个事实源。渲染层失效、PagePlan 计算错误、覆盖率统计 bug，都会污染领域事实。

---

### C4 `Candidate → Source → Evidence` 三级分离

**决策**：搜索 snippet 只能生成 `CandidateSource`；页面成功 read 并正规化后才产生 `Source`；从正文中选出的可定位 excerpt 才是 `Evidence`。正文以内容寻址 artifact 保存。

**为什么**：snippet 是搜索供应商**截断和重写**的导航信息，不是原文。把它当证据等于把供应商的摘要当事实。

**配套**：进入 State 前过滤推广/登录/注册/导航密集/信息量不足的 block，重复内容去重，按 read focus 确定性排序，每个 Source 默认最多 3 条 Evidence。

**代码落点**：`domain/opinion/processor.py::_select_evidence_excerpts`、`domain/opinion/state.py` 的 `CandidateSource` / `Source` / `Evidence`。

---

### C5 幂等 commit + 精确重放判定

**决策**：`commit_step` 检查 `action_id` 是否已在 `committed_action_ids` 里；是则只做关联校验、返回原 state。Reducer 层面也有 `_is_exact_closed_gap_replay` 做逐项比对。

**为什么**：恢复时会重放同一个 delta。但"重放"和"非法修改已关闭的 gap"必须精确区分——所以判定是**逐项完全一致**，不是"看起来差不多"。

**代码落点**：`runtime/transaction.py::commit_step`、`domain/opinion/reducer.py::_is_exact_closed_gap_replay`。

---

## D · 上下文与安全决策

### D1 Context 是 compiler，不是消息历史

**决策**：每轮从 committed State 重新投影 Working Memory，再经确定性的四段流水线生成一次性输入：`collect → select → compact → render`。

**替代方案**：`messages.append()`。**问题**：

| 问题 | 后果 |
|---|---|
| 历史线性增长 | 系统指令被挤出 |
| 重复内容堆积 | 浪费预算 |
| 外部文本与控制指令混杂 | prompt injection |
| 依赖进程内消息对象 | resume 后无法重建 |

**代码落点**：`context/compiler.py::OpinionContextCompiler.compile`、`investigation/context.py::Compiler.compile`。

**一句话答法**：
> 长程 Agent 的上下文不是聊天记录，而是一个受模型窗口、任务相关性、信任边界和恢复要求共同约束的临时执行环境。

---

### D2 信任边界写进 pydantic validator，而不是靠约定

**决策**：

```python
_ALWAYS_UNTRUSTED_ORIGINS = {MODEL, TOOL, PROVIDER}

if (self.origin in _ALWAYS_UNTRUSTED_ORIGINS
        and self.trust is TrustBoundary.TRUSTED):
    raise ValueError("model/tool/provider origin can never be trusted")
```

**为什么**：**"永不信任"这种事靠 code review 守不住**。加一个新 section 的人可能没注意到规则，或者注意到了但觉得"这次特殊"。写成 validator 之后，非法组合**构造不出来**。

**配套**：

- L0 section 必须 `required + trusted + app_config + NEVER`，否则构造失败。
- 混合内容**拆分**：tool error 的控制信息 trusted、message untrusted；完成拒绝的 disposition trusted、reason untrusted。
- 渲染层转义伪造的 `[CONTEXT_SECTION` 标记（用全角字符替换）。

**代码落点**：`context/models.py::ContextSection.validate_required_layers`、`render_sections` / `_escape_embedded_section_markers`。

**一句话答法**：
> commit / checkpoint / resume 只赋予持久性，不洗白信任。这不是约定，是构造期约束——非法的 trust 组合根本构造不出来。

---

### D3 `acquired_for_gap_id` ≠ semantic coverage

**决策**：获取意图（`target_gap_id` / `discovered_for_gap_ids` / `acquired_for_gap_id`）与语义关系（Evidence 对哪个 gap / claim / position / narrative 有作用）**分开存储**。后者必须由 Reflect 显式提交，Validator 检查引用存在，Reducer 才写入。

**为什么**：一个页面可能为找反叙事而读，但正文只提供事实；也可能为事实基线而读，却包含某个主体的立场。

**落地**：Evidence catalog 的选取分组里，"语义覆盖当前 gap"（组 1）**优先于**"仅为当前 gap 获取"（组 3）；coverage cell 的 `source_ids_for_gap` **只看 semantic_gap_ids**。

**不做这个区分的后果**：把"搜索过某个方向"当成"这个方向已被证据覆盖"。

**代码落点**：`context/catalog.py::_rank_current_gap`、`domain/opinion/provenance.py::ProvenanceIndex.source_ids_for_gap`。

---

### D4 必需上下文放不下时 typed partial stop，不截断

**决策**：`required ∪ NEVER` 锁定段超预算 → 抛 `RequiredContextOverflow` → run 以 `PARTIAL` 收尾。

**替代方案**：截断最终 rendered prompt。**问题**：截断会让"必需"名不副实——L0 系统规则被砍掉一半，模型行为就不可预测了。

**三级降级**：先按降级序 TRUNCATE（只对 `compaction == TRUNCATE` 的段），再按降级序 DROP（只对非 required 且非 NEVER 的段），还是放不下就抛错。

**降级序**：`(untrusted 优先, L3 优先, 低 priority 优先, section_id 确定性打破平局)`。

**代码落点**：`context/compactor.py::compact_context_sections`、`_degradation_rank`。

**一句话答法**：
> 截断会让"必需"名不副实。宁可 typed partial stop，也不静默破坏语义。

---

### D5 有界 Evidence catalog

**决策**：`required_evidence_limit = 64`、`history_chunk_size = 64`、`coverage_sample_limit_per_gap = 16`。

**为什么需要**：模型 Reflect 时必须**准确复制不透明的 Evidence ID**（不能自己编顺序别名），所以关键目录必须在场；但全量 required 目录会随 run 无限增长，最终把系统指令挤出去。

**三档设计**：当前窗口 required + NEVER（预算不够直接抛错）；历史块 optional + DROP；覆盖率每 gap 采样 16 条但**同时保留精确的 count**，所以模型知道"还有多少没看到"。

**代码落点**：`context/catalog.py::EvidenceCatalogPolicy`。

---

### D6 不做向量检索 / 长期记忆

**决策**：当前是 run-scoped 投影，没有 embedding、没有跨 run 记忆、没有 memory service。

**为什么**：单 run、几百条 Evidence 的规模下，首先需要的是**确定性引用和可恢复**，不是百万文档召回。向量库会引入 embedding 版本、召回不确定性，以及"第二事实源"的风险——**检索结果不确定，"相同 State 生成相同 Context"这条性质就没了**。

**演进方向**：等 artifact 规模超过结构索引能力时，可以把向量检索作为**派生索引**加入，但不能取代 State。

**代码落点**：`agent-infra-interview-deepening.md` §2 的明确非目标清单。

---

## E · 完成控制决策

### E1 finish 只是 proposal

**决策**：模型提 `FinishDecision`，由 `CompletionPolicy` 对**已提交状态**独立评估，返回四种处置之一。

**为什么**：模型会受上下文长度、最近材料、生成偏好和推理预算影响，**不能同时当研究者和验收者**。它有"想收工"的激励。

**代码落点**：`runtime/completion.py`、`domain/opinion/completion.py`、`domain/investigation/engine.py::completion`。

**一句话答法**：
> 完成判定必须是程序对已提交状态的独立判断，而不是模型对自己工作的验收。

---

### E2 拒绝必须附带可执行的下一步

**这是本项目最有价值的一条经验。**

**背景**：原始实现的拒绝理由只有一句 `"Required investigation questions remain open."`。模型知道被拒了，但**不知道该做什么**，于是反复重试 finish——一次真实 live run 里 completion gate 拒绝了 `finish` **18 次**，直到步数耗尽，终态是诚实但代价高昂的 `partial`。

**决策**：闸门对每个 open 问题输出：

1. 该问题下**未处置的已保存证据**（数量 + 前 3 条的 ID 与摘录前 80 字）；
2. 该问题下**未读的候选**（数量 + 第一个 URL）；
3. **三条合法出路**——处置已保存证据（reflect/retrieve）、继续获取（read/search）、或诚实关闭问题（`not_found` 仅在 scoped 搜索完成后，否则 `unavailable`）。

**为什么有效**：它把"程序已经能看见的事实"直接摆给模型。`_undisposed_evidence` 和 `_issue_id_for_evidence` 本来就计算得出来——只是原来没有暴露。修复不是让模型更聪明，而是**让程序已经知道的事变成模型的输入**。

**一般化**：**拒绝是一种反馈，反馈必须有下一步**，否则拒绝就退化成了死循环。

**代码落点**：`domain/investigation/engine.py::_open_questions_guidance`；回归测试 `tests/investigation/test_finish_guidance.py`。

**诚实口径**：这条修复有单元回归覆盖，但"修复后同题 live 能达到什么效果"**没有可引用的对照数字**——不要编造改进幅度。可以说的是"修复把不可执行的拒绝变成了可执行的拒绝，并有回归测试锁定这个性质"。

---

### E3 发布保留段设在 2/3

**决策**：模型调用用掉 `ceil(limit * 2/3)` 之后，`ConsolidationValidator` 把动作空间锁成三步——无 finding 必须合成、有未审查必须审查、全部已审查必须 finish。

**为什么是 2/3**：设太晚（如 9/10）会出现"预算跑完但一堆 unreviewed finding"——成果都在，但没有一条经过证据审查，报告不可交付。设太早会挤压调查时间导致材料不足。2/3 留出 1/3 给 review + finish，是从"必须留够收束预算"倒推的。

**关键**：它**缩小动作空间**，不是替模型做决定。模型仍然自己选具体动作，但选项被限制在正确的类别里。

**配套**：`investigation/context.py` 在同一时刻注入 `memory.consolidate` section，用自然语言告诉模型同一个约束。**Context 与 Validator 成对**——前者告诉模型"该做什么"，后者保证"不做就不行"。

**代码落点**：`investigation/service.py::ConsolidationValidator`、`investigation/context.py` 的 `memory.consolidate`。

---

### E4 提示词不够，需要程序强制

这条是 E2/E3 的共性，也是本项目反复出现的教训。

**证据**：

- `required_next_action` 的注释："Prompt advice alone did not stop a live quality run from spending its full model budget without creating a Finding."
- `ConsolidationValidator` 的 docstring："Prompt instructions are useful for choosing a good action, but a live model can still spend the reserved requests on another search."

**模式**：**先用提示词引导，再用 Validator 强制，同时把程序已知的约束显式摆进 Context**。三者缺一都会退化——只有提示词会被忽略，只有校验会让模型反复撞墙。

---

### E5 `not_found` 需要前置条件

**决策**：说"没有回应"必须满足三个条件——三个 scoped 搜索方向（`official_response` / `event_response` / `followup`）都有实质性结果（`candidates` 或 `empty`，**不是 error**）、没有读取错误、没有还没读的候选。

**直接效果**：**provider 失败不能解释成 not_found**。一次搜索报错不会让那个 purpose 计入 `covered`。

**代码落点**：`domain/investigation/engine.py::response_search_complete`。

**一句话答法**：
> 一次 provider 失败会被错误地解释成"没有回应"，这是最危险的语义滑坡之一。所以"没找到"必须证明"认真找过"。

---

### E6 否定存在性主张要特殊对待

**决策**：只要存在"含回应标记 + 与 finding 主题重叠"的**未处置证据**，就拒绝 finish，并给出退出路径（一次 reflect 引用该证据即可）。

**为什么**：否定存在性主张（"X 尚未回应"）是 live 调查里**最陈旧的判断**——后来抓到的证据可以静默地反驳它，而主张本身看起来仍然成立。实测场景：一次 live run 发布了"该品牌尚未公开回应"，而证据库里已经存着官方回应，只是读了但没转成 finding。

**分寸**：闸门**不判断真伪**，只检查"有没有可能反驳的未处置证据"。程序不越界做语义判断，只做它确定能做的检查。

**代码落点**：`domain/investigation/engine.py::_stale_negative_findings`、`_NEGATIVE_EXISTENCE`。

---

### E7 审查绑定 finding 内容哈希

**决策**：`accepted_review` 只在 `review.finding_hash == finding_hash(finding)` 时才算有效。改写 finding 会让审查自动失效。

**为什么**：堵住"先让一个弱 finding 通过审查，再改写成强主张"的路径。比"审查后禁止修改"更实用——允许修改，但代价是重新走审查。

**代码落点**：`domain/investigation/models.py::finding_hash` / `accepted_review`。

---

### E8 模型审查 + 程序复核双层

**决策**：审查是模型辅助的，所以有一个**确定性守卫** `unbacked_specifics`——提取 finding 里的数字/百分比/度量，检查是否出现在被引用摘录中；审查结果 `supported` 但有缺失项时**程序降级为 `partial`**。

**为什么**：模型审查可能被一段长复合句带偏（看起来整体支持，但其中一个具体数字没有出处）。

**分工**：模型判断**语义支持性**，程序确定性检查**具体数字是否真的有出处**。

**代码落点**：`investigation/service.py::unbacked_specifics`。

---

## F · 边界纪律

### F1 不接登录态社交平台

**决策**：`SOCIAL_DOMAINS`（微博/抖音/小红书/B站/知乎/贴吧/快手/微信公号等）在 Resolver 里被显式 `-site:` 排除，`allowed_url` 也做二次拦截。

**为什么**：那类数据需要登录、不可审计、且平台条款不允许。**主动排除并写进代码**，比"以后再说"要诚实。

**代码落点**：`domain/investigation/engine.py::SOCIAL_DOMAINS` / `allowed_url`、`Resolver.resolve`。

---

### F2 不声称来源独立性

**决策**：完成标准里"至少两个来源"是 **URL 级别的记录多样性**，**不等于出版方独立性**。

**为什么**：实现里没有媒体所有权数据，`source_kind` 又只是模型标签。**能证明什么就说什么**，不夸大。

**代码落点**：`domain/opinion/completion.py` 的 `semantically_linked_source_ids` 检查。

---

### F3 报告措辞避开过度承诺

**决策**：Markdown brief 明确区分 evidence-linked claims、attributed stakeholder positions、contradictions、remaining gaps、sources 和**公开 Web 样本的局限**；**不声称全网情感或触达**。

investigation 域的完成理由甚至直接写着 "this is not a truth guarantee"。

**代码落点**：`domain/opinion/brief.py`、`domain/investigation/engine.py::completion`。

---

### F4 已知限制主动说

面试时主动列出的限制（来源：README "Known limitations"）：

| 限制 | 说明 |
|---|---|
| 单一搜索引擎固定 5 结果 | `TaskFrame` 的时间/语言/域约束已解析但**未传给 provider** |
| 证据摘录选择是召回瓶颈 | 60% 召回的缺口主要来自摘录选择与聚合站偏差 |
| 模型不会把证据不足的问题收成 `not_found` | 倾向于给部分回答 |
| 数字类主张只做 provenance 检查 | **未做冲突交叉核对** |
| 缺少 artifact 局部重读 action | 压缩后模型无法主动取回局部原文 |
| 没有 benchmark | 只有人工标注的领域质量检验 |

**主动说的价值**：面试官问"你这个系统最大的问题是什么"时，有准备的答案比临场编造可信得多。
