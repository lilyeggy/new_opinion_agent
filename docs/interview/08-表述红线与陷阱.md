## A · 架构类红线

### A1 ❌ "我们做了多 Agent 编排"

**为什么错**：多角色流水线（planner / research / analyst / reviewer）已于 2026-09-21 评估后归档到 `archive/harness-pipeline/`，**从未提交进 git**，生产路径始终是单 `AgentLoop`。

**正确说法**：
> 我实现过一版多角色流水线，评估后砍掉了。三条理由：重复了 PagePlan + targeted search 已有的能力；绕过了 Runtime 的可靠性机制；而且不解决真正的瓶颈——单 Agent 不知道该覆盖哪些维度时，复制成四个只会并行地产生更多散乱材料。

**注意**：这题**必须答"试过并砍掉"**。说"没做过"会浪费手里最好的一张牌；说"我们用了多 Agent"则与代码直接冲突。

---

### A2 ❌ "我们基于 LangGraph 做了二次开发"

**为什么错**：`pyproject.toml` 里没有 LangGraph，`runtime/loop.py` 是完全自研的 async loop。

**正确说法**：
> 自研显式 async loop。判断标准是 Agent Runtime 属于"实现手段"还是"要交付的能力"——这个项目要交付的正是执行语义本身。

---

### A3 ❌ "我们做了一个通用的 Agent 框架"

**为什么错**：项目**明确只深做两层**（Harness/Runtime + Tool/MCP/Context/Memory），五个非目标（Sandbox / Control Plane / Observability 平台 / Eval 平台 / Model Serving）都是刻意不做的。

**正确说法**：
> 边界纪律：只深做两层。什么都在项目里做一点，就什么都讲不清。

---

### A4 ❌ "两套 domain 共用同一套 Context Compiler / Working Memory"

**为什么错**（这是最容易犯、也最容易被追穿的一条）：

- 两个域**真正共享的只有** `context/models.py`（section 模型）和 `context/compactor.py`（压缩算法）；
- `context/compiler.py`、`selector.py`、`catalog.py` 与整个 `memory/` **只被 `app/service.py`（opinion 路径）使用**；
- **有两个 compiler**：`context/compiler.py` 的 `OpinionContextCompiler`（硬类型检查 `OpinionSearchState`）和 `investigation/context.py` 的 `Compiler`；
- **`WorkingMemory` 只存在于 opinion 域**，investigation 侧零引用。

**正确说法**：
> `collect → select → compact → render` 是共享的**描述**，但 collect 和 select 两个域各自实现；真正共享的是 compact 与 section 模型。Working Memory 是 opinion 域的实现细节，不是 Runtime 概念。

**追问准备**：为什么 investigation 不复用 `OpinionContextCompiler`？→ 它硬类型检查 `OpinionSearchState`；investigation 的上下文要携带 issues / findings / page_plan / `next_action_constraint` / consolidate 指令，形状不同。

---

### A5 ❌ "Reducer 在 `runtime/` 里"

**为什么错**：`runtime/` 下**没有** `reducer.py`。Reducer 是领域职责——`domain/opinion/reducer.py::reduce_opinion_state` 和 `domain/investigation/engine.py::reduce_state`。

**正确说法**：
> Reducer 属于领域层，因为状态不变量属于领域语义。Runtime 只提供"提交"这个动作（`commit_step`），不提供"怎么合并"。

---

### A6 ❌ "这些框架都不行 / 太重 / 都是玩具，所以自研"

**为什么错**：这是典型的 NIH 表述。面试官会立刻判断你没认真用过框架，或者没分清 LangChain / LangGraph / LlamaIndex / AutoGen 各是什么层。

**正确说法**：
> 先看 workload：舆情搜索是垂直 deep research，胜负手在研究策略和证据纪律，不在编排。公开的产品级实现都自己拥有 loop（OpenAI / Gemini / Anthropic），LangChain 自己的 deep research 作者后来也在拆高层结构。框架能做 demo；我不用的原因是结构要放在领域层，而框架把结构放在编排层。

**追问准备**：如果面试官追问"那你从框架学到了什么"？→ checkpoint-after-side-effect、interrupt-before-action、reducer 合并、durable execution 的边界划分——这些思想这里都有对应机制，区别是它们是契约而不是 API。

---

### A7 ❌ "Deep research 都不用框架"或"Deep research 都用 LangGraph"

**为什么错**：两个极端都错。LangChain 的 open_deep_research 明确用 LangGraph，并排在 DeepResearch Bench 前列；而 OpenAI / Gemini / Anthropic 的公开实现都是自研 agentic system。关键不是"用没用"，是**结构放在哪一层、能不能随时拆**。

**正确说法**：
> 框架能做出 deep research，LangChain 自己就做了一个；但作者复盘说，高层编排结构会变成瓶颈，最后只保留 low-level 原语。产品级实现都自己拥有 loop，因为研究策略和证据纪律才是差异。

**追问准备**：Jina / dzhng 怎么解释？→ Jina 是自研 search→visit→reflect→answer 循环 + gap 队列 + token 预算；dzhng 的目标就是"最简实现"，<500 行。它们都不是"编排框架驱动"，而是"策略驱动"。

## B · 恢复与一致性类红线

### B1 ❌ "我们保证 exactly-once"

**为什么错**：结果缓存只有**单机文件原子性和进程内锁**。两个进程同时恢复同一个未缓存的 action，仍可能都调用 provider。而且"provider 已收到请求、结果尚未写缓存"这个窗口无法消除。

**正确说法**：
> 准确承诺是 **at-most-once 复用已持久化的成功结果**，加上**状态效果的幂等**——可以说 effectively-once state effect，但不是外部 exactly-once。这个承诺还依赖"舆情工具是只读的"这一前提。

---

### B2 ❌ "100 步是真实模型自主跑出来的"

**为什么错**：100 步 / 640 Evidence 是**构造状态的压力测试**（`tests/integration/test_context_long_trajectory.py`），用来证明 Context 有界且确定，不是一次真实模型运行。

**真实数字是**：一次 live run 跑满 **60 步**（17 搜 / 17 读 / 14 findings / 92 处引用）。

**正确说法**：
> 长轨迹是构造状态的压力测试，证明 Context 的有界性与确定性；真实模型自主跑的是 60 步那次。

---

### B3 ❌ "每个 checkpoint 边界崩溃都能无缝恢复，零重复调用"

**为什么错**：`ACTION_RUNNING` 阶段存在**无法完全消除**的重复外部调用窗口。

**正确说法**：
> 七个持久 phase 各有明确的恢复动作，而且恢复矩阵会断言各组件的**调用次数**——比如 Observation 已保存时 adapter 调用必须为 0。但 `ACTION_RUNNING` 是唯一存在重复外部调用窗口的阶段，缓存把它缩小到"仅当崩溃发生在缓存写入之前"，不能消除。

---

### B4 ❌ "取消会立即终止一切"

**为什么错**：取消在 `OBSERVATION_READY` / `REDUCING` 阶段会被**延迟**——先把已观测的结果 commit 恰好一次，再终止。

**正确说法**：
> 取消用竞速实现（`asyncio.wait(FIRST_COMPLETED)`），但顶部判定显式排除 `REDUCE_OBSERVATION`。如果 Observation 已落盘，这一步必须被提交一次再终止——否则同一个 Observation 的命运会取决于取消时序。而且取消只中止本地协程，**不承诺远端回滚**。

---

### B5 ❌ "checkpoint 存的是事件日志"

**为什么错**：存的是**全量 State 快照**（`schema_version = 4`），不是事件溯源。

**正确说法**：
> 单机单写者场景下，快照比重放简单且恢复语义明确——`classify_resume` 靠快照就能定位该做什么。代价是存储和序列化开销，这个规模下可以接受。

---

## C · 上下文与安全类红线

### C1 ❌ "trusted / untrusted 是模型 API 层面的权限隔离"

**为什么错**：它**只是上下文里的来源标签与结构约束**。它不改变模型的能力，也不做真正的权限控制——它保证的是"被注入的内容没有指令权限"这个**结构性质**。

**正确说法**：
> 它是 Context 里的来源与信任标签，由 pydantic validator 强制：`model/tool/provider` 三种来源永远不能标 trusted。它保证的是结构性质——外部内容不会获得指令地位——不是运行时的权限隔离。

---

### C2 ❌ "注入矩阵证明抗注入成功"

**为什么错**：14 路矩阵证明的是**来源与信任标签保持、边界转义等结构性质**。它**不保证模型不会被说服**，只保证被说服的内容**没有指令权限**。

**正确说法**：
> 注入矩阵证明的是结构性质：哨兵内容只能出现在 untrusted section，L0/L1 不受污染，trusted control 不含 provider/model prose，resume 不提升 trust。它不声称"抗注入成功"。

---

### C3 ❌ "我们有长期记忆 / 向量检索"

**为什么错**：当前只有 **run-scoped 投影**。没有 embedding、没有跨 run 记忆、没有 memory service、没有向量库。

**正确说法**：
> 当前是 run-scoped 投影。不做向量库的理由是：单 run 几百条 Evidence 的规模下，首先需要的是确定性引用和可恢复；向量检索的召回不确定性会破坏"相同 State 生成相同 Context"这条性质。等规模超过结构索引能力时，可以作为**派生索引**加入，但不能取代 State。

---

### C4 ❌ "上下文压缩是有损的，可能丢证据"

**为什么错**：压缩只影响"这一轮模型看见什么"，**不删除 Full State 和 Artifact**。溯源链完整：`Claim/Narrative → Evidence ID → Source ID → artifact_ref → 原始正文 + locator`。

**但要说清一个真实缺口**：
> 压缩是可逆的"本轮视图选择"，不是删除事实——`ProvenanceIndex` 保存了所有关系，人工审计和报告溯源都在。**但目前缺少让模型主动 re-read artifact 局部内容的专用 action**，这是下一步可补的能力。

---

### C5 ❌ "token 估算和 DeepSeek tokenizer 一致"

**为什么错**：`HeuristicTokenEstimator` 是 `ceil(字节数 / 4)` 的启发式估算，可注入测试 estimator 替换。

**正确说法**：
> 当前是启发式估算，不保证与 provider tokenizer 逐 token 一致。项目证明的是"选择和降级机制有界"，不是"估算公式绝对精确"。生产化应使用模型 tokenizer 并保留 provider length error 兜底。

---

## D · 工具与 MCP 类红线

### D1 ❌ "模型可以调用任意工具"

**为什么错**：模型看到的是**稳定 `ToolDefinition`**，而且只限于 Registry 里注册过的；它不知道 provider 存在，也不能动态注册工具。

**正确说法**：
> 模型只看到 `search.web` / `read.web` 这样的能力声明（name / description / input_schema），看不到 API key、provider id 或 transport。MCP 工具还要经过应用自己的 allowlist。

---

### D2 ❌ "MCP 接上就能用，我们动态注册 server 的工具"

**为什么错**：MCP discovery 必须**全部验证通过后原子注册**——allowlist 匹配、canonical schema hash 校验、Registry 冲突检查。任何一步失败，Registry 保持不变。

**正确说法**：
> discovery 是**能力发现，不是授权**。动态全注册会让 server 通过新增工具扩大 Agent attack surface，也会让模型上下文和行为在应用未变更时漂移。

---

### D3 ❌ "熔断器是全局的，一个 provider 挂了就整体降级"

**为什么错**：key 是 `(tool_name, provider_id)`。只按 provider 会让某工具故障拖垮该 provider 的其他能力；只按 tool 会让一个 provider 故障遮蔽另一个健康 provider。

**正确说法**：
> 熔断按 tool/provider 组合隔离。而且只有"中毒类"错误（timeout / rate_limited / server_error / unknown_provider_error）计入；auth / permission 是配置问题，**必须下一次仍然可见**。

---

### D4 ❌ "工具失败会重试，最多试 N 次"

**为什么错**：`max_attempts_per_provider` 是**单 provider 内**的次数；跨 provider 还会 fallback。而且不同错误类型的策略不同。

**正确说法**：
> 三组策略：可重试（timeout / rate_limited / server_error）、立即停止（invalid_arguments / unknown_tool / cancelled）、可跨 provider 回退（auth / permission / not_found / unreadable_content / content_too_large / unknown_provider_error）。`ToolInvocation.attempt` 是**跨 provider 的全局物理计数**，而 `action_id` 全程恒定。

## E · 质量与效果类红线

### E1 ❌ "完成了 benchmark 评测"

**为什么错**：项目**明确不做 Eval 平台**。有的是人工标注的领域质量检验。

**正确说法**：
> 没有 benchmark。有的是三组人工检验数字：检索召回 6/10、忠实性 10/14 完全支持且 100% 零虚构、对抗回放 2/3。这些都是人工标注的领域检验，不是自动化评测。

---

### E2 ❌ "报告质量分 X 分"

**为什么错**：不存在综合质量分。只有召回率、忠实性、对抗回放三组数字。

**正确说法**：报具体的三个数字并带口径，不要合成一个分数。

---

### E3 ❌ "系统已经能保证结论正确 / 不会幻觉"

**为什么错**：完成判定的理由里明确写着 "**this is not a truth guarantee**"。程序能保证的是"每个必答问题有明确处置"+"active finding 通过证据审查"。

**正确说法**：
> 系统限制的是**模型能改变的范围**，不是保证它说得对。程序能保证引用完整性、对象类型、时间范围、状态转换和完成标准；语义正确性仍然依赖模型推理 + 审查。`FinalSynthesis` 的 summary 文本也还没有做逐句 entailment 校验。

---

### E4 ❌ "source diversity 已经做到媒体所有权独立"

**为什么错**：完成标准里的"至少两个来源"是 **URL 级别的记录多样性**。实现里没有媒体所有权数据，`source_kind` 又只是模型生成的分析标签。

**正确说法**：
> 是 URL 级记录多样性，不等于出版方独立性。`source_kind` 是模型提出的**不可信分析标签**，Runtime 的完成判定**从不把它当成已核实的来源质量**。

---

### E5 ❌ "Web 主页面是那个单问题 demo 控制台"

**为什么错**：`/` 是**调查工作台**（investigation 域），旧的单问题 demo 控制台在 `/legacy`。

**正确说法**：
> 三个页面：`/` 调查工作台（主产品）、`/legacy` 旧版单问题控制台、`/dev` 开发者控制台。两套 API：`/api/investigations` 和 `/api/runs`。

## F · 数字口径红线

### F1 ❌ "测试全部通过"

**为什么错**：项目记录是 **779 passed, 2 skipped**（正常环境）。而我在受限沙箱里重跑得到 **788 passed / 3 failed / 2 skipped**，3 个失败是轮询后台 run 到终态的时限断言被拖慢。

**正确说法**：
> 正常环境全量 779 passed / 2 skipped（2 个 skip 是需要真实 key 的 live-gated smoke）。我在受限沙箱里重跑是 788 passed / 3 failed / 2 skipped——3 个失败全是"轮询后台 run 到终态"的 2–20 秒时限断言，在文件操作被代理拖慢的环境下达不到，不是逻辑失败。

**原则**：**说出机制比说结论可信。**

---

### F2 ❌ "召回率 60%，读入率 80%"

**为什么错**：**"读入率 80%" 没有出处**。可引用的只有检索召回 60%（6/10 必中清单）。

**正确说法**：
> 检索召回 60%，口径是 **6/10 人工标注必中清单，逐项独立搜索验证**。缺口来自聚合站偏向（候选 66% 来自单一聚合站，原发媒体站零覆盖）和反爬读取失败（6/17）。

---

### F3 ❌ "修复后提升了 N 倍"

**为什么错**：凡是**没有可引用对照实验**的改进幅度，都是编的。

**正确说法**：
> 这条修复有单元回归覆盖，但"修复后同题 live 能达到什么效果"**没有对照数字**。可以说的是修复把不可执行的拒绝变成了可执行的拒绝，并有回归测试锁定这个性质。

**原则**：**能证明什么就说什么。** 报一个漂亮但无出处的数字，被追问"怎么测的"就崩了。

---

### F4 ❌ "跑了 60 步、60 次搜索"

**为什么错**：步数和搜索次数不是一回事。

**正确说法**：
> 60 步走完全流程，其中 **17 次搜索、17 次读取**，产出 14 条 findings、92 处证据引用。

## G · 六道陷阱题

这些题问法看起来无害，但**第一直觉的答案往往是错的**。

### G1 "你的 Agent 怎么调用工具的？"

**错误直觉**：描述 tool calling / function calling 机制。

**为什么错**：本项目的模型**不调用工具**，它输出**语义决策**。

**正确答**：
> 模型输出的是 `SearchDecision(query, target_gap_id, purpose)` 这样的领域决策。`ActionResolver` 把它翻译成内部 `ToolAction`，`ToolExecutor` 才去执行。模型从来不知道背后是 Brave 还是 Serper。

---

### G2 "状态更新是原子的吗？"

**错误直觉**：答"是，用了锁"。

**为什么错**：原子性不是靠锁，是靠**不变量 + 一次性构造**。

**正确答**：
> `commit_step` 一次性改六个字段（领域状态、清空 active_step、追加历史、追加 ledger、推进游标、设置 continuation_pending）。`RunState` 的 validator 检查它们互相一致——分两次改，中间那个状态是非法的，**构造不出来**。这是用不变量强制原子性，不是靠锁。

---

### G3 "你们的 Agent 有没有自我反思？"

**错误直觉**：答"有，reflect 动作就是自我反思"。

**为什么错**：`reflect` 是**领域动作**，不是通用反思。而且更重要的——**反思的结论不自动生效**。

**正确答**：
> 有 `reflect` 动作，但它不是"通用自我反思"。它是**领域语义提交**：模型提出 claim / position / narrative / gap assessment，Validator 检查引用的证据真实存在、维度与语义记录类型匹配，Reducer 才写入。
>
> 也就是说，模型不能靠"我认为这个维度解决了"就把维度关掉——它必须提交**能被程序验证的语义记录**。

---

### G4 "怎么防止模型幻觉？"

**错误直觉**：列举各种 prompt 技巧（"要求它只引用原文""加 few-shot"）。

**为什么错**：本项目的答案**不是让模型更准，而是限制它的写权限**。

**正确答**：
> 不是"让模型更准"，是"**限制模型能改变的范围**"：
> - 模型可以提出不存在的 Evidence ID → state-aware validator 拒绝；
> - 模型可以说某个维度已解决 → 缺少对应语义记录时提交不了；
> - 网页可以含恶意指令 → 它只能是 untrusted 内容；
> - 模型可以提前 finish → Completion Gate 拒绝；
> - 模型不能直接生成新 State 覆盖已有证据。
>
> 至于 summary 文本的逐句 entailment，**目前还没有做**，这是后续可增加 claim-level citation coverage 的位置。

---

### G5 "Agent 跑很久会不会上下文爆炸？"

**错误直觉**：答"我们会定期做摘要压缩"。

**为什么错**：本项目**不做 LLM 摘要**（那是 `agent-infra-interview-deepening.md` §3.3 明确的非目标）。

**正确答**：
> 不用摘要。Context 每轮从 State 重新投影，结构上就有界：L0/L1 是固定地板，Evidence catalog 有界（required 64 + 历史块），近期交互只取最近 3 步。放不下时按降级序 TRUNCATE / DROP 可选段；必需段放不下就 typed partial stop，不截断。
>
> 而且因为不用摘要，**相同 State + 配置 + estimator 必须生成字节一致的 Context**——这一点由 `content_sha256` 和长轨迹测试锁定。

---

### G6 "多进程/多 worker 部署怎么办？"

**错误直觉**：答"支持，我们做了分布式"。

**为什么错**：当前是**单机单写者**，明确不做分布式。

**正确答**：
> 当前是单机单写者，恢复语义清晰。扩展到分布式分三步且**不需要改 Runtime 语义**：run ownership/lease、把 checkpoint 与 action result 换成支持 CAS 的持久后端、给有副作用工具加 idempotency metadata。熔断器需要共享 provider health 或 Tool Gateway。
>
> 之所以说不用改语义，是因为 `CheckpointStore` 和 `ToolResultCache` 本来就是 `Protocol`，替换实现即可。
