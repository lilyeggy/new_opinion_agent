# 11 · 第 0 阶：运行骨架与三个概念

> 这一阶不属于六层里的任何一层，但六层全都长在它上面。
> 目标只有一个：**听到任何一个机制时，能立刻说出"它在第几步、哪个阶段、写不写盘"**。
> 唯一事实源：`opinion_search_agent/src/`。校准时间 2026-10-27。

---

## 1. 这一阶要解决的三个问题

1. 一次 run 到底在循环什么？（**七个阶段**）
2. 什么东西是"真的"、什么东西是"算出来的"、什么东西"落到了盘上"？（**三个概念**）
3. 在任意一个点上断电，重启后会发生什么？（**恢复矩阵**）

答不出第 3 个，说明前两个没真懂。

## 2. 三个概念

### 2.1 权威状态：`RunState`

它是**唯一真相**，是 `checkpoint` 里唯一存的东西。

| # | 字段 | 含义 | 谁改它 |
|---|---|---|---|
| 1 | `run_id` | 一次调查的 ID | 创建时固定 |
| 2 | `status` | `created / running / completed / partial / failed / cancelled` | `start_run` / `terminate_run` / `apply_continuation` |
| 3 | `domain_state` | 领域状态（`OpinionSearchState` 或 investigation `State`） | **只有 `commit_step` 里的 reducer** |
| 4 | `next_step_index` | 下一步编号 | `commit_step` +1 |
| 5 | `active_step` | 正在进行的这一步（`StepRecord`） | 各阶段转移函数 |
| 6 | `committed_steps` | 已提交的步（追加） | `commit_step` |
| 7 | `committed_action_ids` | 已提交的动作 ID（追加） | `commit_step` |
| 8 | `continuation_pending` | "刚提交完，还没做完成判定" | `commit_step` 置真 / `apply_continuation` 置假 |
| 9 | `stop_reason` | 为什么停 | `terminate_run` |
| 10 | `failure` | 失败详情（typed） | `terminate_run` |

**第 3 条是整条设计的核心**：`domain_state` 只有 reducer 能改，reducer 是纯函数
`(state, delta) -> state`。模型碰不到它。

**`StepRecord` 只有 7 个字段**（`runtime/protocols.py`）：

| 字段 | 含义 |
|---|---|
| `run_id` / `step_id` | 身份 |
| `attempt` | 第几次决策尝试（失败重试 +1） |
| `phase` | 七阶段之一 |
| `decision` | 已接受的决策信封 |
| `action` | 已解析的动作请求（含 `action_id`） |
| `observation` | 已落盘的观察信封 |
| `failures` | 本步的失败历史（有序） |

### 2.2 派生视图：算出来的东西

| 视图 | 从哪来 | 存在哪 | 能不能恢复 |
|---|---|---|---|
| `WorkingMemory` | `project_working_memory(domain_state)` | 内存 | 不需要——重算 |
| `CompiledContext` | `compile(state)` | 内存 | 不需要——重算，且只存 `content_sha256` |
| `report.md` / `outcome.json` | `SearchOutcome` → `brief` 投影 | 盘上 | 可重算（**确定性投影**） |

这三样都满足 `f(state)`。**视图可以丢，状态不能丢。**

### 2.3 落盘物：三种，职责不同

| 落盘物 | 内容 | 写入时机 | 用途 |
|---|---|---|---|
| **checkpoint** | `{schema_version:4, execution_profile, state: RunState}` 全量快照 | 每个阶段边界 | **恢复**（`classify_resume` 只读它） |
| **journal** | 每步一条 `StepJournalRecord`：模型调用 + `context_hash` + 决策 + 动作 + 观察 + 状态指纹 | 提交时，**先于 checkpoint** | **回放与审计**（不参与恢复） |
| **artifact** | 网页正文原文（内容寻址） | 读取时 | **溯源**（Evidence 指向它） |

**写入顺序是有讲究的**（`runtime/recording.py` 的模块注释）：

```text
journal append  →  checkpoint save  →  清理 inflight
```

- 崩在 1 和 2 之间：journal 多一条 → `load` 时**截掉**那条。
- 崩在 2 和 3 之间：留下陈旧 inflight → `load` 时**丢弃**（因为对应 step 已不是 active）。

这个顺序的含义：**宁可 journal 多一条（可截），不可 checkpoint 领先（不可逆）。**

### 2.4 `StepRecord` 存在哪？（高频误解）

**它存了，而且就存在 checkpoint 里**——不是"只存 RunState"，而是 `StepRecord` 被 `RunState`
的两个字段包着：

```python
active_step:     StepRecord | None          # 0 或 1 条，正在进行的这一步
committed_steps: tuple[StepRecord, ...]     # N 条，全部已提交的步
```

项目里**没有**独立的 `steps.jsonl` 或 `steps/` 目录参与恢复。恢复路径
（`classify_resume` + `commit_step` 的幂等判定）直接读 `RunState` 里的这两个字段。

**为什么不拆成单独文件：原子性。**
`JsonCheckpointStore._save_sync` 是 `tmp 文件 → fsync → os.replace` 的单次原子替换，
一次替换就保证「领域状态 + 步历史 + 游标 + continuation 标记」是**同一时刻的一致切片**。
拆成两个文件就必须处理"写了 A 没写 B"的中间态，恢复时要判断哪份更新——那等于自己造一个两阶段提交。

**代价是真实的，有实测数据**（`artifacts/live-runs/investigations/runs/f045d7ee…`，20 步）：

| 项 | 体积 | 占比 |
|---|---|---|
| `state` 总计 | 277 KB | 100% |
| `committed_steps` | **237 KB** | **86%** |
| `domain_state` | 38 KB | 14% |
| `committed_action_ids` | 1.2 KB | <1% |

- 平均 **~12 KB/步**，最大单步 **61 KB**（一次 read 的 evidence + sources + reviews）。
- 60 步量级约 **700 KB–1 MB**，且**每次 save 全量重写**——写放大是真的。
- 结论：单机单写者下可接受，但不是免费的。

**为什么没爆：大块正文被外置了。** 原始 action result（68 KB）落在 `observations/` 或
artifact store，`StepRecord.observation` 只留摘要与引用（3.2 KB）。**没有这层外置，checkpoint 会失控。**

**为什么不用 journal 重建状态（事件溯源）**：journal 只存决策 + `context_hash` + 状态指纹，
**不存 `domain_state` 的增量**。要重建就得从头跑 reducer，成本高且依赖配置一致。
所以选了快照，而不是重放。

**什么时候会改**：分布式部署时。`CheckpointStore` 是 Protocol，换成支持 CAS 的后端即可；
但 `committed_steps` 大概率要改成 append-only step log + 索引，否则每次提交全量重写不可扩展。

## 3. 七个阶段

### 3.1 阶段表

| 阶段 | 做什么 | 谁执行 | 落盘边界 | 崩了之后 |
|---|---|---|---|---|
| `OPENED` | 分配 `step_id`，`attempt=1` | `open_step` | `STEP_OPENED` | 重新决策 |
| `DECIDING` | **编译上下文 → 调模型 → 校验** | `AgentLoop` + `ModelClient` + `DecisionValidator` | `DECIDING` / `DECISION_ACCEPTED` | 重新决策 |
| `DECISION_ACCEPTED` | 决策已存，动作未解析 | `ActionResolver` | `DECISION_ACCEPTED` | 重新解析动作（**不重问模型**） |
| `ACTION_RUNNING` | 执行工具 | `ActionExecutor` → `ToolExecutor` | `ACTION_RUNNING` | 重新执行（**不重问模型**，缓存兜底） |
| `OBSERVATION_READY` | 观察已存 | `Processor.build_delta` | `OBSERVATION_READY` | 重算 Delta |
| `REDUCING` | 构造 Delta → 纯函数 reducer | `commit_step` | `REDUCING` | 重算 Delta |
| `COMMITTED` | 提交完成，`active_step=None` | `commit_step` | `STEP_COMMITTED` | 做完成判定 |

**只有 `DECIDING` 调模型。** 全项目一处调用点：`runtime/loop.py:317`。

### 3.2 `classify_resume` 全文（判定的优先级就是它的书写顺序）

```python
def classify_resume(state):
    if state.status is RunStatus.CREATED:        return START_RUN
    if state.status in _TERMINAL_RUN_STATUSES:   return RETURN_RESULT
    if state.continuation_pending:               return EVALUATE_CONTINUATION
    if state.active_step is None:                return OPEN_STEP

    phase = state.active_step.phase
    if phase in {OPENED, DECIDING}:              return REQUEST_DECISION
    if phase is DECISION_ACCEPTED:               return RESOLVE_ACTION
    if phase is ACTION_RUNNING:                  return EXECUTE_ACTION
    if phase in {OBSERVATION_READY, REDUCING}:   return REDUCE_OBSERVATION
    raise InvalidTransactionState(...)
```

八个 `ResumeAction`：`START_RUN / RETURN_RESULT / EVALUATE_CONTINUATION / OPEN_STEP /
REQUEST_DECISION / RESOLVE_ACTION / EXECUTE_ACTION / REDUCE_OBSERVATION`。

**四个必须讲清的细节：**

1. **函数只读 `RunState`，不读任何内存变量。** 这就是"首次执行与崩溃恢复同一条路径"的机制来源。
2. **`continuation_pending` 的判定在 `active_step is None` 之前。** 顺序一换，提交完就会直接开下一步、跳过完成判定。
3. **终态判定在最前面。** 已经结束的 run 即使 `continuation_pending` 为真也直接返回结果。
4. **`COMMITTED` 永远不会作为 `active_step.phase` 出现。** `RunState` 的 validator 明确禁止（`active_step cannot already be committed`）。

### 3.3 阶段 ↔ 载荷不变量

`StepRecord` 的 validator 用一张表强制"这个阶段只允许带这些载荷"：

| 阶段 | 允许存在的载荷 |
|---|---|
| `OPENED` | ∅ |
| `DECIDING` | ∅ |
| `DECISION_ACCEPTED` | `{decision}` |
| `ACTION_RUNNING` | `{decision, action}` |
| `OBSERVATION_READY` | `{decision, action, observation}` |
| `REDUCING` | `{decision, action, observation}` |
| `COMMITTED` | `{decision, action, observation}` |

多一个或少一个都构造不出来。**这是"非法状态不可表示"的直接实现**——不是靠流程检查，是靠类型。

### 3.4 十个 checkpoint 边界

```text
RUN_STARTED / STEP_OPENED / DECIDING / DECISION_ACCEPTED / ACTION_RUNNING
OBSERVATION_READY / REDUCING / STEP_COMMITTED / CONTINUATION_APPLIED / RUN_TERMINATED
```

每次 `save()` 不只写盘，还触发 `LoopHook.after_checkpoint(boundary, state)`——
Web 端的 SSE 就是靠它推进度，**Runtime 和 Domain 一行都不用改**。

## 4. 一次 step 的完整执行（对照 `loop.py`）

```text
while True:
  resume = classify_resume(state)          # 纯函数，只看盘上状态

  START_RUN            → start_run()                 → save(RUN_STARTED)
  RETURN_RESULT        → return result_from_state(state)
  EVALUATE_CONTINUATION→ completion_evaluator.evaluate(...) → apply_continuation() → save(CONTINUATION_APPLIED)
  OPEN_STEP            → 检查 max_steps → open_step() → save(STEP_OPENED)
  REQUEST_DECISION     → compile(state)              # 可能抛 ContextOverflowError → partial 终止
                       → model.decide(context)       # 唯一模型调用
                       → decision_validator.validate()
                       → accept_decision()           → save(DECISION_ACCEPTED)
  RESOLVE_ACTION       → action_resolver.resolve()   # 失败 → repair_accepted_decision（重试决策）
                       → mark_action_running()       → save(ACTION_RUNNING)
  EXECUTE_ACTION       → action_executor.execute()   # 工具：缓存/重试/熔断/fallback
                       → record_observation()        → save(OBSERVATION_READY)
  REDUCE_OBSERVATION   → processor.build_delta()
                       → mark_reducing()             → save(REDUCING)
                       → commit_step(state, delta, reducer)
                                                     → save(STEP_COMMITTED)
```

**每一个分支都以 `continue` 结尾**——回到 `while True` 顶部重新判定，没有嵌套流程。
这是"状态分发器"而不是"流程编排器"。

## 5. 崩溃演练：`ACTION_RUNNING`

### 5.1 崩的那一刻，盘上是什么

```json
{
  "run_id": "run-1",
  "status": "running",
  "next_step_index": 8,
  "active_step": {
    "step_id": "run-1:step-7",
    "attempt": 1,
    "phase": "action_running",
    "decision": {"decision": {"action": "search", "query": "...", "target_gap_id": "..."}},
    "action":   {"action_id": "act-7a", "tool_name": "search.web", "arguments": {...}},
    "observation": null,
    "failures": []
  },
  "committed_steps": ["…前 6 步…"],
  "committed_action_ids": ["act-1a", "act-2a", "…"],
  "continuation_pending": false
}
```

### 5.2 重启后的六步

```text
1. classify_resume → active_step.phase == ACTION_RUNNING → EXECUTE_ACTION
2. 不调模型（decision 已在盘上），不重新解析动作（action 已在盘上）
3. executor.execute(action)  →  ToolExecutor 先查缓存：key = action_id = "act-7a"
   3a. 命中  → 直接拿 ToolResult，adapter 调用 0 次
   3b. 未命中 → 重新调 provider，attempt 从 1 重新计
4. record_observation → save(OBSERVATION_READY)
5. build_delta → commit_step（幂等：action_id 已在 committed_action_ids 则原样返回）
6. save(STEP_COMMITTED) → 下一步
```

### 5.3 三个窗口，只有一个是真风险

| 崩在哪 | 外部调用 | 能否消除 |
|---|---|---|
| 调用前 | 1 次（重发） | 能——`ACTION_RUNNING` 是"副作用前最后一个点"，此时还没发请求 |
| provider 已返回、缓存未写 | **1 次（重发）** | **不能**。这是 at-most-once 的真实边界 |
| 缓存已写、observation 未落盘 | **0 次**（命中缓存） | 能——这就是结果缓存存在的唯一理由 |

**准确承诺**：at-most-once **复用已持久化的成功结果** + 状态效果幂等。
不是 exactly-once，也不是"零重复调用"。

### 5.4 测试怎么断言（`tests/e2e/test_action_running_recovery.py`）

1. 旧 executor 调 provider，**写缓存但不写 observation**——精确制造这个窗口；
2. 用全新的 registry / adapter / executor / cache / loop 恢复；
3. 断言：fresh adapter 调用 **0 次**、原 `action_id` **不变**、`revision` **只 +1**。

**"结果对不代表过程对"**——所以断言调用次数，不只断言最终状态。

## 6. 七个阶段的崩溃对照表

| 崩在 | 会重问模型吗 | 会重发外部请求吗 | 会重复提交吗 |
|---|---|---|---|
| `OPENED` / `DECIDING` | **会** | 不会 | 不会 |
| `DECISION_ACCEPTED` | 不会 | 不会 | 不会 |
| `ACTION_RUNNING` | 不会 | **可能**（缓存未写时） | 不会 |
| `OBSERVATION_READY` | 不会 | 不会 | 不会 |
| `REDUCING` | 不会 | 不会 | 不会（`commit_step` 幂等） |
| `COMMITTED` | 不会 | 不会 | 不会 |

**这张表的正确读法**：模型调用是唯一会重复的"贵"操作，且**没有缓存兜底**
（我们只缓存工具结果，不缓存决策）。所以"崩溃会多花钱"是真的，只是花在决策上，不在工具上。

## 7. 四个最容易讲错的地方

**① "checkpoint 存的是事件日志"**
错。存的是**全量快照**（`schema_version = 4`）。单机单写者场景下快照比重放简单、恢复语义明确。
代价是存储与序列化开销。

**② "每个边界崩溃都能零重复"**
错。`ACTION_RUNNING` 有一个无法消除的重复外部调用窗口。

**③ "取消会立即终止"**
错。顶部判定**显式排除** `REDUCE_OBSERVATION`（`loop.py:218`）：
如果 observation 已落盘，这一步必须先被提交一次再终止——否则同一个 observation 的命运会取决于取消时序。
而且取消只中止本地协程，**不承诺远端回滚**。

**④ "`COMMITTED` 是一个可以停住的阶段"**
错。它只是一个瞬时标记：`commit_step` 同时把 `active_step` 置 `None`、`continuation_pending` 置真。
重启后 `classify_resume` 看到的是 `EVALUATE_CONTINUATION`，不是 `COMMITTED`。
