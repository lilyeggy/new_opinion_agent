# 06 · 故障复盘故事

> "讲一个你踩过的坑"是面试里出现率最高的问题之一。**能讲好故事的人，比能讲好架构的人少得多。**
> 每个故事的骨架是：**现象 → 定位 → 根因 → 修复 → 验证 → 一般化**。最后那一步是拉开差距的地方——只讲修复是"修好了 bug"，讲出一般化才是"理解了系统"。
>
> 本文只收录**在代码或实现记录里能找到证据**的故事。没有出处的改进幅度一律不写。

## 故事 1 · 空拒绝让模型空转 18 次

**这是最好的一个故事**，因为它同时包含机制设计、实测证据和可一般化的教训。

### 现象

一次真实 live 调查（三九胃泰中秋广告争议，60 步）跑完后，诊断数据里出现一个异常信号：

```text
completion gate 拒绝 finish：18 次
终态：partial
```

18 次拒绝不是"模型不听话"——它一直在尝试收工，但**每次都被拒，然后不知道该怎么办**。

### 定位

看拒绝理由，只有一句：

```text
Required investigation questions remain open.
```

**这句话是对的，但不可执行。** 模型知道"还有问题没解决"，但它看不到：

- 哪些问题还开着？
- 每个问题下现在有什么可用的东西？
- 我有哪些合法的下一步？

于是它的行为退化成一个循环：**尝试 finish → 被拒 → 再尝试 finish**。

### 根因

**拒绝是一种反馈，而反馈必须包含下一步。** 原来的实现只传递了"不行"，没有传递"那要怎样"。

更深一层的根因是：**程序其实已经知道答案，只是没有把它暴露出来**。

`_undisposed_evidence(state)` 能算出哪些已保存的证据还没被任何 finding 或 assessment 引用；
`_issue_id_for_evidence(state)` 能把证据映射到问题；
`state.candidates` 和 `state.read_attempts` 能算出哪些候选还没读。

这些数据**在拒绝发生的那一刻全都算得出来**——只是拒绝理由里没写。

### 修复

`_open_questions_guidance(state, open_required)` 对**每个** open 问题输出三类信息：

```text
Required investigation questions remain open.
- issue-xxx (问题前 60 字):
  N saved evidence excerpts for this question are not disposed by any
  finding or assessment (ev-1 «摘录前 80 字»; ev-2 «...»). Reflect to
  dispose them, or retrieve the saved page with a new focus.
  M discovered candidates remain unread (e.g. https://...). Read one
  before another search.
  No saved evidence and no unread candidates address it. Search a
  different direction (new alias, origin, or material type), or reflect
  to close it honestly: not_found only after the scoped response searches
  complete, otherwise unavailable.
```

结构是：

| 元素 | 作用 |
|---|---|
| 问题 ID + 问题前 60 字 | 让模型知道**是哪个**问题 |
| 未处置证据数 + ID + 摘录前 80 字 | 让模型知道**手上有什么没用** |
| 未读候选数 + 第一个 URL | 让模型知道**还有什么可以读** |
| **三条合法出路** | 让模型知道**能做什么** |

三条出路的设计尤其重要——它们覆盖了所有可能状态：

```text
处置已保存证据（reflect / retrieve）
继续获取（read / search）
诚实关闭问题（not_found 需 scoped 搜索完成，否则 unavailable）
```

**注意第三条**：如果既没有未处置证据、也没有未读候选，闸门**不会**让模型无路可走，而是明确告诉它"可以诚实关闭，条件是……"。这防止了另一种死循环：模型觉得"没有材料就没法解决"，但不敢标 `not_found`。

### 验证

- 回归测试：`tests/investigation/test_finish_guidance.py`
- 断言的性质：拒绝理由必须**可执行**——包含问题 ID、未处置证据、未读候选，以及合法出路

### 一般化（这是要讲的部分）

> **拒绝是一种反馈，反馈必须有下一步。**
>
> 这个教训不只适用于 finish 闸门。整个项目里有一条反复出现的模式：**先给提示词，再用 Validator 强制，同时把程序已经算出来的约束显式摆进 Context**。三者缺一都会退化——
>
> - 只有提示词 → 会被忽略（`required_next_action` 的注释里写着实测："Prompt advice alone did not stop a live quality run from spending its full model budget without creating a Finding"）；
> - 只有校验 → 模型反复撞墙，因为它不知道**为什么**被拒；
> - 只有 Context 里的约束 → 模型可能选择忽略。
>
> 所以修复的本质不是"让模型更聪明"，而是**把程序已经知道的事变成模型的输入**。

### 诚实口径

这条修复有单元回归覆盖，但"修复后同题 live 能达到什么效果"**没有可引用的对照数字**。面试时不要编造改进幅度；可以说的是"修复把不可执行的拒绝变成了可执行的拒绝，并有回归测试锁定这个性质"。

## 故事 2 · 空 Decision：reasoning token 吃掉了输出上限

### 现象

模型调用**成功返回**（HTTP 200，无异常），但结构化 `Decision` 是空的——解析出来没有任何有效载荷。

这种失败最麻烦的地方是：它**看起来不像失败**。没有超时、没有错误码、没有异常栈。

### 定位

三步定位：

1. **独立连通性请求**——用最小请求确认 provider 和凭证没问题，排除基础设施因素；
2. **checkpoint 稳定复现**——同一份 checkpoint 重跑，失败稳定复现，说明不是随机网络抖动；
3. **安全响应 metadata**——检查响应里的 `finish_reason`，发现是 **`length`**。

**根因**：reasoning 类模型的**思考 token 也计入输出上限**。当上限设得偏低时，模型把预算全部花在思考上，还没开始输出结构化 JSON 就被截断了。所以"调用成功但内容为空"。

### 修复

两条：

1. **取消请求体里的硬 token 限制**——不再在请求里写死一个偏小的输出上限；
2. **增加 contract assertion**——把"响应必须包含可解析的决策"变成显式断言，而不是靠调用方猜。

配套地，`LiveConfig.model_max_output_tokens` 的注释记录了这条经验：

```python
# Reasoning-style models can drain a low cap on thinking alone; the client
# doubles this on output-cap truncations up to the transport budget.
model_max_output_tokens: int = Field(default=4096, gt=0)
```

也就是说，客户端在遇到输出截断时会**翻倍重试**，直到传输层预算上限。

### 一般化

> **"成功"和"有结果"是两件事。** 一个 200 响应可以携带零信息量。所以 Runtime 里有一组专门的失败类型来描述这类情况：`MODEL_EMPTY_RESPONSE` / `MODEL_MALFORMED_RESPONSE` / `MODEL_REFUSAL`，它们和 `MODEL_TIMEOUT` / `MODEL_RATE_LIMITED` 一样，走 `RETRY_ATTEMPT`。
>
> 另一个一般化是：**定位这类问题不能靠"再跑一次看看"**，要靠"用最小请求隔离基础设施因素 + 用 checkpoint 稳定复现 + 看响应 metadata"。前两步排除噪声，第三步才是根因。

### 代码落点

`models/openai_compatible.py`、`app/config.py::LiveConfig.model_max_output_tokens`、`runtime/errors.py::RuntimeFailureKind`。

## 故事 3 · Evidence ID 被改写成顺序别名

### 现象

模型在 `reflect` 里引用证据时，**不复制真实的不透明 ID**，而是自己编了一套顺序别名（比如把 `ev-3f8a...` 写成 `ev-1`、`ev-2`）。结果 Validator 报"引用不存在的证据"，决策被拒。

### 定位

问题不在模型"不听话"，而在**任务本身的反直觉性**：

- Evidence ID 是 `sha256` 派生出来的不透明字符串（`stable_domain_id("evidence", url, gap_id, excerpt)`），**对人眼毫无结构**；
- 但模型必须在每一轮里**精确复制**它们；
- 一旦上下文里 ID 的数量变多，或者 ID 在压缩中被部分丢弃，模型就会倾向于"编一个好记的"。

### 一个关键的决策：不做模糊匹配

这里有一个**看起来很方便但会毁掉系统**的选项：在 Validator 里做模糊匹配——"如果模型说的 `ev-1` 找不到，就按顺序映射到第一条证据"。

**没有这么做。** 理由是：

- 模糊匹配会把"模型编造引用"这个**严重错误**变成一个静默的、看起来正常的操作；
- 一旦允许猜测，"证据引用"就不再是可验证的事实，`ProvenanceIndex` 和整个溯源链都失去意义；
- 而且猜错的后果是**把结论挂到错误的证据上**——这比拒绝更糟。

### 修复：保持严格，但让上下文可恢复

三件事同时做：

1. **保留严格的 validator**——引用不存在就是拒绝，`DecisionValidationError`，不猜；
2. **有界但确定的 required Evidence catalog**——`context/catalog.py` 保证当前需要的 Evidence ID **一定在场**（`required_evidence_limit = 64`，`required=True` + `NEVER` 压缩，预算不够直接抛 `RequiredContextOverflow` 而不是静默截断）；
3. **L0 复制规则 + 可修复反馈**——在不可变指令里明确写"Evidence IDs are opaque. Copy them exactly; never invent sequential aliases."，并且拒绝理由带上**当前合法的 ID 列表**，让重试能真正改对。

```python
_OPINION_SEMANTIC_INSTRUCTIONS = """...
- Evidence IDs are opaque. Copy them exactly; never invent sequential aliases.
..."""
```

### 验证

- `tests/unit/context/test_catalog.py`——有界分区与语义优先排序
- `tests/integration/test_context_long_trajectory.py`——640 条 Evidence 下 required catalog 仍不超过 64，关键 ID 不丢
- `tests/unit/domain/opinion/test_decisions.py`——引用未知证据被拒

### 一般化

> **严格契约必须配合可恢复的上下文。**
>
> 只严格不给信息，模型会一直失败；只给信息不严格，引用就失去可验证性。正确的组合是：**契约不让步，但把履约所需的信息完整、有界、确定地摆到模型面前**。
>
> 这也解释了为什么 Evidence catalog 必须**有界**：它同时服务两个目标——"关键 ID 必须在场"（不能太少）和"目录不能无限增长"（不能太多）。64 条这个数字是这两个约束的交点，而且它不是猜的：超预算时抛错而不是截断，所以"不够"会以显式失败的形式暴露出来，而不是静默退化。

## 故事 4 · MCP metadata laundering 的两轮失败

这个故事的特别之处是：**第一版修复不够，第二版修复引入了新问题，第三版才对。** 讲这个能体现"处理边界情况"的真实难度。

### 背景

MCP 是外部协议，远端 server 控制着工具列表、schema、description、annotations 和返回的 content。如果把这些直接暴露给模型或 Runtime，等于让外部服务**动态扩大 Agent 权限**并向上下文注入控制信息。

所以策略是：**`_meta` / `meta` / `annotations` 这类元数据必须剥离**，它们不是内容，但可以被用来传递指令。

### 第一版：只剥顶层 —— 失败

**做法**：对返回的 content block 做顶层字段剥离。

**问题**：存在 **laundering 路径**。远端可以把 metadata 藏在 `EmbeddedResource.resource` 里，或者更深的 content block 中——**经过外层包装之后，它就成了普通 payload**，顶层的剥离检查不到。

### 第二版：先序列化再删 —— 更糟

**做法**：先把整个对象 `model_dump(mode="json")`，再删除 metadata 字段。

**问题**：引入了一个**异常路径**。攻击者可以在"本来应该被丢弃的 metadata 内部"放一个**不可序列化对象**——于是序列化在过滤之前就失败了，**Pydantic 异常直接穿透 adapter**。

这比第一版更糟：原本的目的是"过滤掉危险内容"，结果变成了"危险内容可以让整个调用崩掉"。

### 第三版：先过滤、后验证 —— 正确

最终的策略是六步：

```text
1. 根据 BaseModel 字段名和 alias 判断 metadata
2. 在序列化之前跳过这些字段          ← 关键：过滤先于序列化
3. 对 Mapping / sequence / 嵌套模型递归投影
4. 检测当前递归路径中的循环引用
5. 最后验证整个公开投影是 JsonValue
6. 所有失败归一为固定安全 ToolAdapterError
```

**核心是第 2 步的顺序**：不在不可信对象上先做复杂序列化。

**第 4 步的循环引用检测**是配套的——递归投影必须有环检测，否则一个自引用结构就能让投影无限递归。

**第 6 步**保证所有失败路径的对外表现是一致的、不含 `repr` 的安全错误。

### 配套的其他收紧

同一个边界上还有几件事：

| 措施 | 目的 |
|---|---|
| discovery **原子注册** | 半成功注册会让 Registry 处于"部分工具可信"的中间态 |
| **schema pin**（canonical SHA-256） | 允许工具名 ≠ 允许它随意改参数结构 |
| **output schema fail closed** | 声明了 output schema 却返回非结构化 content → 直接失败，不降级成"尽量解析文本" |
| description 只来自 app config | remote prose 不进入模型上下文 |
| annotations 无策略权威 | 远端不能用 annotations 表达策略 |
| stdio environment 显式 allowlist | 不继承整个进程环境 |

### 验证

- `tests/contract/test_mcp_adapter.py`
- `tests/contract/test_mcp_sdk_transport.py`
- `tests/e2e/test_real_mcp_tool.py`——真实本地 stdio MCP 全链路

### 一般化

> **两件事。**
>
> 第一，**"过滤"和"验证"的顺序是有语义的**。在不可信对象上先做复杂操作（序列化、递归、格式化），等于给攻击者一个在过滤生效前就执行代码的入口。正确顺序永远是：先按结构判定并跳过，再做验证。
>
> 第二，**修复本身会引入新的攻击面**。第一版是"检查不够深"，第二版是"检查方式本身可被利用"。所以处理不可信输入时，不能只问"这样能挡住吗"，还要问"**这个检查动作本身会不会被输入影响**"。这个第二问是这一轮真正的收获。

## 故事 5 · 20 步 vs 60 步：配置问题被误认成逻辑问题

### 现象

同一道题目跑两次，一次停在 20 步、终态 `partial`，另一次跑满 60 步走完全流程。

第一反应是"模型不稳定"——这是最容易走错的方向。

### 定位

看诊断数据，两个数字摆在一起：

```text
committed_steps = 20
max_steps       = 20   ← 恰好相等
预算使用        = 16% – 45%
```

**`committed_steps` 恰好等于上限，而预算只用了不到一半。**

如果真是模型能力不足，应该是"预算耗尽"或"反复失败"；而这里预算是**大量剩余**的——说明 run **不是跑不动，是被上限截断了**。

### 根因

`max_steps` 默认值是 20，对这道题的复杂度不够。

### 修复

把 `max_steps` 调到 60，同一题目完整跑完（即 `05 §4.1` 的那次 run）。

### 一般化

> **"跑不完"和"跑不动"是两种失败，诊断必须能区分。**
>
> 这个区分在本项目里是**结构性**的，不是靠人看日志：
> - **跑不完**（步数上限、上下文溢出、重复行动）→ `PARTIAL`，**保留已提交成果**；
> - **跑不动**（reducer 不变量、checkpoint 损坏、修复耗尽且无成果）→ `FAILED`，带 `RuntimeFailure`。
>
> 而且 `RunState` 里 `stop_reason` 是**必填**的终态字段——所以"为什么停了"永远可回答。诊断数据（`committed_steps` / `budget.snapshot()` / `stop_reason`）放在一起看，就能区分"能力问题"和"配置问题"。
>
> 顺带一句：**这也是为什么预算和步数是两套独立的限制**。如果只有一套，就区分不出"截断"和"耗尽"。

### 代码落点

`app/config.py::LiveConfig.max_steps`、`investigation/storage.py::Budget`、`runtime/loop.py` 的 `OPEN_STEP` 分支。

## 故事 6 · "过去 30 天"带空格不解析

小故事，但很适合展示"修得干净"。

### 现象

时间范围表达式 `过去 30 天`（**带空格**）解析失败。

### 定位

解析逻辑用了 `strip()`——只去掉**首尾**空白，中间的 `30 天` 之间的空格还在，正则匹配不到。

### 修复

```python
# 之前
value.strip()

# 之后
re.sub(r"\s+", "", value)
```

**顺带补了回归测试**，覆盖 **4 种空格变体**（比如 `过去 30 天` / `过去30天` / 前后带空格 / 全角空格）。

### 一般化

> 两条。
>
> 第一，**`strip()` 和"去掉所有空白"是两个不同的操作**，写解析代码时特别容易混。用户输入里的空白位置是不受控的。
>
> 第二，**修一个解析 bug 时，顺手把等价输入类补进回归**。只修一个具体字符串，下一种空格变体还会再挂一次。这里补 4 种变体，成本极低，收益是这一类问题不会再回来。

### 代码落点

`domain/opinion/framing.py`；回归测试 `tests/unit/domain/opinion/test_framing.py`。

## 怎么用这些故事

### 按问题类型选故事

| 面试官问 | 讲哪个 |
|---|---|
| "讲一个你踩过的坑" | **故事 1**（最完整，有机制 + 实测 + 一般化） |
| "你怎么定位线上问题" | **故事 2**（三步定位法） |
| "你怎么处理模型不可靠" | **故事 3**（严格契约 + 可恢复上下文） |
| "你怎么处理安全边界" | **故事 4**（两轮失败，体现真实难度） |
| "你怎么看自己的不足" | **故事 5**（区分配置问题与逻辑问题） |
| 时间不够，只要一个小故事 | **故事 6**（短、干净、有回归意识） |

### 讲故事的四个必答句

不管讲哪个，骨架都是这四句——**缺任何一句，故事都会显得浅**：

1. **我观察到什么现象**（具体数字，不是"有问题"）
2. **我怎么定位到根因**（方法，不是运气）
3. **我改了什么**（机制，不是"改了一行"）
4. **一般化成什么原则**（← 这一句是拉开差距的地方）

### 一个反面清单

以下说法会让故事掉价：

- ✗ "我加了个 try-catch 就好了"——没有根因。
- ✗ "修复后性能提升了 3 倍"——没有口径的改进幅度。
- ✗ "这是框架的 bug"——推卸。
- ✗ "我们后来重构了"——没说清原来错在哪。
- ✗ 讲一个没有验证的故事——没有回归测试或断言，等于没修完。
