## 1. 两天交付什么

交付一个范围明确、能够演示并有验证记录的公开 Web 事件调查版本。目标用户是愿意核查原文的研究人员；合格产物是可供人工审核的调查初稿。

唯一主路径：

```text
提交一个具体事件
→ 识别事件与必要澄清
→ 形成调查问题及需要查明的事项
→ 按事项搜索、阅读、重新检索正文
→ 从证据形成判断，按剩余缺口补查
→ 审查判断
→ 生成统一框架与事件专项内容的页面
→ 点击判断核查原文
→ 请求补查
→ 查看有依据的判断变化，旧版本保持可核查
```

**按期收尾是承诺，质量达标是需要验证的结果。** 截止时间不因失败自动延长。最终必须选择第 11 节的一种交付状态，不能用“还在完善”代替结果。

两事件的最小闭环是开发关口；V1 合格验收继续遵守已有边界：两个开发案例、一个保留案例、至少一次更新、一次真实联网调查和同材料摘要对照。不能把两案例机制通过改称完整 V1 通过。

## 4. 两天内采用的最小设计

### 4.1 单一状态源

继续使用现有 State、Issue/components、SearchAttempt、Evidence、Finding、Review 和 Processor → Delta → Reducer 提交链。通用 Runtime 不加入舆情规则。

“调查蓝图”在这两天仅代表一个**可重建的需求视图**，从已提交状态生成；不引入第二份事实数据库。可以新增一个小的领域辅助模块，将 PagePlan 中已有的调查需求提取为纯函数，供 Context、完成判断和 PagePlan 共用。

每个需求视图只需回答：

- 所属 issue 和必答子项是什么；是否来自用户必答问题。
- 需要查明什么；如“机构是否承诺退款”和“是否有实际执行证据”分别处理。
- 关联哪些现有 Finding/Evidence；剩余缺口是什么。
- 哪些搜索方向已尝试，结果是新增候选、重复、无结果还是失败。
- 下一步建议为读取候选、正文内检索、外部补查、整理判断或审查。

首先复用 issue_id、组件原文、module/field、target_gap 表示关联。若缺少精确关联就显示“关联待确认”，不得依靠字符串猜测宣称某段证据支持某个需求。一个正文可支持多个问题，不能由第一次搜索归属限制后续使用。

只有实际故障证明现有字段无法表达关联时才增加可选字段；必须同时说明旧 checkpoint 行为。若需要大规模 schema 迁移，两天内不做，保留明确限制。

### 4.2 谁负责决定搜索内容

| 环节 | 程序职责 | 模型职责 |
|---|---|---|
| 事件理解 | 保存用户问题、范围、解析状态和限制 | 提议事件主体、别名、3–6 个问题 |
| 需求整理 | 合并既有必答子项与相关专项字段，保留依据 | 解释当前问题还缺什么 |
| 选择行动 | 提供合法动作、候选、预算与历史；拦截无进展循环 | 选择当前最有价值的需求和行动 |
| 形成查询 | 校验问题关联、分页、域名和时间范围 | 组合事件实体、具体缺口、材料类型及别名 |
| 材料处理 | 保存正文、检索片段、验证定位与关联 | 判断片段支持的事实、归因、诉求与回应 |
| 结束 | 检查必答处置、审查、重大未完成及预算 | 提出有依据的处置、限制与核心判断 |

不要求所有搜索目的都完成才允许分析。回应“未发现”的特殊查询前提继续保留，但一次 purpose 标签或一份公告不等于实际完成语义核查。

### 4.3 收敛与模型输出

顺序必须是先验证已实现的第二版门禁，再决定是否修改。不得先重写 Agent，随后才测原有修复。

若仍出现实际失败，只修对应契约问题：

1. 整理阶段允许只提交当前证据支持的原子 Finding，不要求同一调用处置所有复合问题。
2. 未知问题可以暂不提交 assessment；不使用非法 component 状态、不伪造 not_found。
3. 必须区分“没有读到证据”和“已经有证据但没有整理为 Finding”。后者优先整理或 retrieve，不能一直补外部搜索。
4. 首个 Finding 之后仍观察后续进展，不能用一条无关判断永久绕过收敛。
5. 进展用新增相关证据、判断变化、问题处置或审查结果衡量。仅改 query、reason 或计数不算进展；数量增长也不证明语义质量。
6. 在已有证据时，连续两个完整采集动作没有新增证据/判断/处置，转向有界整理或说明缺口；正文仍有未读候选时先判断读取价值。阈值作为机制保护，不作为材料充分性的判断。
7. 剩余资源不足时保留审查空间，输出 meaningful partial；不得为了成功状态放松引用、归因或回应约束。

如果上述增强需要新增复杂阶段管理器，先保留已有机制并将失败计入最终限制，不在截止日前建设新框架。

### 4.4 页面填充契约

统一页面顺序：当前判断与限制 → 时间线 → 争议和回应 → 事件专项内容 → 原文证据与范围。沿用现有导航与组件，按屏幕可用性微调顺序即可。

- 规则调整显示新旧措施、对象、时间等实际相关字段。
- 计费补救显示计费口径、处理措施、办理路径及执行证据等实际相关字段。
- 可选字段为空不扩大调查。缺失的必答内容显示具体原因。
- provisional、经审查判断、证据分歧和无法判断有不同标签；技术 ID 不成为主界面标题。
- 页面内容来自同一版本的 State/report/workbench；HTML 与 Markdown 不另写一套结论。
- “没有公开说明”可成为有边界的未知说明；预算耗尽、读取失败或审查未完成仍按已有规则标记 partial，不通过放宽 completed 来验收。

## 6. 案例、材料与评分

### A：已有计费/回应开发案例

复用 `artifacts/report-quality/2026-09-13-s1/cases/billing-dev-v1/manifest.json`。当前 8 份正文主要围绕重庆燃气收费争议及后续公开材料。

- 先验证已有 SHA256，冻结用户任务和必答问题，不为通过验收删除原问题。
- 重点检查：企业说法与独立核实、2024 与 2025 材料变化、回应与落实、退款实际到账及公众满意的未知边界。
- T0 仅开放已确定的早期材料；T1 才开放后续材料。当前登记 T0=m01/m02、T1=m03–m08 需要复核后使用。
- 后来获取的早期文章只能称“冻结材料时点回放”；没有当时网页快照时，不声称还原了历史当日网页状态。

### B：第二开发案例

选一个身份明确、材料较短、适用对象及生效时间清楚的公开规则/服务调整事件。与 A 具备不同专项字段。目标 3–6 份可访问正文，数量只是工作量上限建议，不是事实充分的门槛。

冻结 4–6 个实际问题，至少包含一个需要保留的未知或部分回应。不得只选择公告信息齐全、没有争议的事件来冒充完整舆情分析。

### H：保留验收案例兼联网发现验收

选择与 A/B 不同的事件，提前冻结任务、关键问题及禁止结论。评分资料保存在生产上下文外。模型通过实际 Web 搜索获取材料；运行结束冻结所用正文，供评分复核。

执行开发的 agent 不根据 H 的答案调提示词或模板；检查者可读取材料打分。若依据 H 结果改代码，该事件失去保留资格，来不及准备新的 H 则保留验收为 NOT_RUN。

### 人工审核的最小安排

执行 agent 先准备“问题—参考原文—系统判断—引用—建议评分”表，请用户或指定审核者在明天保留约 45–60 分钟逐项确认。这个时长是排期估计，不代表足够覆盖任意长度报告。

审核者至少核对全部必答子项和全部核心断言，进一步覆盖所有具体数字、时间、归因和回应/落实判断。禁止先看结果再减少评分分母。模型可以预标注和辅助找原文；只有真人确认的条目标记 human_reviewed。

| 指标 | 固定计分方式 |
|---|---|
| 必答处置 | 正确回答或恰当未知的子项数 / 全部预先定义必答子项数 ≥90%；逐案例公布 |
| 重要断言 | 获原文支持或正确降级的断言数 / 全部重要断言数 ≥95%；公布逐项表 |
| 引用定位 | 每一个已输出引用均命中正确正文版本、范围与原文，100% |
| 禁止错误 | 归因变事实、转载当独立验证、回应当解决、旧文当新进展均为 0 |
| 更新 | 至少一处真实有依据的判断变化；没有变化时如实记录，不能强造反转 |
| 有价值的产物 | 必须有实质回答，不能靠全部填未知或删除所有判断获得高分 |

样本少时同时报告原始数量。任何关键误导性错误都阻断合格交付，不能被总体百分比稀释。人工审核未完成时明确 PENDING_HUMAN，不能把 reviewer=supported 代作人工 PASS。

| C3：必要时最终 A 验证 | 24 | 0 / 0 | 20 分钟 |
| B 开发案例 | 24 | 0 / 0 | 20 分钟 |
| A T0 | 16 | 0 / 0 | 15 分钟 |
| A T1 更新 | 24 | 0 / 0 | 20 分钟 |
| A 简单摘要基线 | 2 | 0 / 0 | 5 分钟 |
| H Web 联网 | 32 | ≤12 / ≤16 | 20 分钟 |
| 合计 | **146** | 联网运行 ≤12 / ≤16 | 按阶段闸门执行 |

材料准备另外最多 6 次外部搜索、8 次正文抓取；若使用 Brave/Jina 也计入总账。因此两天最多 18 次外部搜索、24 次外部正文抓取；记录所用工具，不能隐去“测试之外”的采集成本。普通本地测试的伪调用不计入远端请求。

这些额度不需要用满。C3 仅条件触发；任一关口失败即取消依赖运行。没有独立“再试一下”额度；重试、planner、reviewer、解析恢复和 Provider transport attempt 全部计入。

执行注意：

1. 每批先写预算、模型、配置指纹、任务、材料 hash 和停止条件，再启动；使用新目录，恢复不清零。
2. `run_replay_case(timeout_seconds=...)` 只是调用方等待期限，不能代替 `Budget`。必须配置 `OPINION_INVESTIGATION_MODEL_CALLS/SECONDS/SEARCHES/READS`，并核对实际保存的 budget.json。
3. 固定输出上限并确认生产客户端接收；可沿用已验证 wiring 的 16,384，但要核对实际 Provider 能力。基线与 Agent 用同一模型和输出配置。
4. 请求次数不是金额；记录 Provider 返回的 input/output tokens、推理用量、耗时；取不到成本就标 unknown，不估报“只花几元”。
5. 本地预算计入发起的请求，不声称控制了 Provider 内部重试或全局 exactly-once。
6. 为每个 run 保留至少最后约 1/3 模型预算用于整理、审查和结束；一旦明显不足，主动收缩剩余探索并保留 partial。
7. 外部故障最多消费本批内部重试上限；同一认证、限流、空输出错误重复两次后终止该批。不得循环换模型或改回超大默认预算。
8. 若更换模型，单独登记不同实验条件；不能沿用旧模型结果宣称前后机制改善。

不得重跑已经成功且代码与输入未变化的昂贵运行。最终改动使某批语义证据失效时标 STALE；剩余预算不足就降低交付等级，不能偷偷追加调用。

## 8. 具体修改位置与边界

下表代码路径均相对于 `opinion_search_agent/src/opinion_search/`。

| 工作 | 优先检查文件 | 验收重点 |
|---|---|---|
| 模型合法输出和首次/后续收敛 | `domain/investigation/engine.py`、`investigation/context.py`、`investigation/service.py` | 有限步形成合法 Finding，避免强制整份问题处置 |
| 最小需求视图 | `investigation/page_plan.py`、`domain/investigation/models.py`、必要时一个小的纯函数模块 | 问题与专项字段同源；不从页面空槽无限扩搜索 |
| 搜索反馈关联 | `engine.py` 的 SearchAttempt 提交、`context.py` | 新增候选与有效证据分开；失败与无结果分开 |
| 页面投影 | `investigation/workbench.py`、`presentation.py`、`export.py` | 同版本、同判断、同引用；不足原因可见 |
| Web 主路径 | `web/assets/app.js`、`workbench.js`、`evidence.js`、`api.js`、CSS | 进度、刷新、证据、更新、版本、下载可用 |
| 真实模型及基线 | `investigation/replay.py`、`baseline.py` | 生产 planner/loop/reviewer；不得把期望答案注入输入 |
| 更新材料隔离 | `manager.py`、现有 replay builder | 子版本沿用事件身份，T0 无法获得 T1 材料 |

已有 `run_replay_case()` 创建独立调查，不等同于 T0→T1 更新。复用 Manager 的 parent/update 路径及相应 replay builder；必要时补一个仅用于验收的 Python helper，不能用两次无关联 create 冒充版本更新。

回放中的“成功搜索三个 purpose”不能作为真实世界已查遍回应的证据。报告注明冻结材料范围；真正的发现验收只由 H 的 Brave/Jina 运行提供。

## 9. 测试与浏览器验收

### 9.1 关键自动化行为

只为变动机制补针对性测试，复用已存在的异常矩阵：

- 证据充足但尚无 Finding、首个 Finding 后再次停滞、没有证据时不得强迫编造判断。
- 只提交支持内容的 reflect 合法；未处置的问题保留；非法状态能在有界恢复内结束。
- 修改关键词不能无限绕过无进展保护；仍有有价值候选与无候选两种路径。
- 归因不能省略主体；部分回应不能记充分回应；not_found 与读取失败分开。
- 必答子项不丢；可选专项字段缺失不强迫搜索；已有证据待整理时优先整理。
- 全文二次检索；重复正文、转载关系；证据定位；恶意网页不改变动作约束。
- 更新后旧版本及原文不变；同 URL 新正文新版本；T0/T1 不泄漏。
- 预算恢复不重置；取消、断线、崩溃后的已提交状态不重复应用；索引可重建。

已核实的测试执行入口（从 `opinion_search_agent/` 执行；使用现有 Python 环境）：

```bash
.venv/bin/python -m pytest tests/investigation/test_decision_validation.py tests/investigation/test_context_integrity.py tests/investigation/test_response_coverage.py tests/investigation/test_page_plan.py -q
.venv/bin/python -m pytest tests/investigation tests/e2e/test_investigation_web.py -m 'not live' -q
.venv/bin/python -m pytest -m 'not live' -q
.venv/bin/python -m compileall -q src
git diff --check
```

若 `.venv/bin/python` 不存在，使用项目已经配置的等价解释器；不借此迁移依赖。变更 JS 后对相关文件作语法检查，并由浏览器验证交互。这里的命令尚未在本次文档工作中执行。

### 9.2 浏览器验收清单


`<本批隔离目录>` 是待填参数，不得原样运行。服务已有时先核对代码与存储，再决定复用或为验收另开空闲端口；没有新增 CLI 产品功能。

### 9.3 同材料摘要对照

优先复用最终 A 的输入材料、用户问题与模型，调用已有 baseline。两组允许策略不同，但材料集合、原文、问题和输出上限必须明确且一致；分别公布实际读过的材料与成本。

比较四件事：必答子项是否覆盖；归因/回应/执行是否区分；是否保留反证与未知；是否能核查原文。逐项写出 Agent 增益或退步及额外模型调用。

不要求 Agent 必须获胜。双方失败、差异不明显或成本不值得都可以成为结论，但不能宣称相对质量改善。冻结对照不代表搜索策略优越；查询价值仍需看联网检索轨迹。

## 11. 最终交付等级与停止规则

| 交付状态 | 条件 | 可以声明 |
|---|---|---|
| V1_LIMITED_PASS | 三真实案例、人工90%/95%、定位100%、关键禁止错误0、真实更新、Web主路径、联网及可说明的相对改善均通过 | 在已验证的有限公共服务事件中，可生成可核查、可更新的调查初稿 |
| EXPERIMENTAL_CLOSED_LOOP | 至少完成一条真实模型调查与有依据更新，Web可核查；但案例数、人工评分、联网或比较仍未满足全部门槛 | 已演示部分场景闭环；逐项说明未完成验收，不宣称稳定质量 |
| ENGINEERING_ONLY | 真实模型仍不能产生可用判断，或关键证据/更新正确性失败 | 执行与恢复机制已有验证，业务闭环未通过，交付可复现失败与限制 |

具体质量问题不能靠改名称消失。即使产物等级较低，也必须提交最终代码状态、证据和下一步最小问题说明，这就是按时收尾。

强制停止条件：

- 9/15 14:30 停止增加功能；18:00 完成最终结论。
- 同类核心错误在已有修复后的验证中继续出现，停止该链路扩建和后续依赖付费任务。
- 触达批次请求/时间上限，保存已提交结果并结束；不得新建 run 绕过预算。
- 无独立人工复核，不宣称人工评分通过。
- 保留案例失败，不以该案例答案定制生产代码。
- 引用错位、版本污染或归因变事实出现未解决问题，不能发布为合格 V1。
