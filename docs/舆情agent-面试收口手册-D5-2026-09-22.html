舆情 Agent 面试收口手册

D5 收口 · 2026-09-22 · 状态：项目封存，本手册为面试唯一入口 · 所有数字可复核（报告 / run.json / tests）

一、3 分钟电梯陈述（脱稿版）

一句话定位：这是一个「显式单 Agent Harness」项目——舆情调查只是验证 workload，真正的技术内容在 Agent 运行时和工具/上下文这两层基础设施上。

要解决的真问题：LLM agent 跑几十步的长任务时，三件事一定会出：进程会挂、外部工具会抖、模型上下文会爆还会被注入。大多数 demo 级 agent 对这三件事的处理是「祈祷」。这个项目把这三件事当成分布式系统问题来解。

核心设计（三条）：

  • Decision ≠ ToolCall，ToolResult ≠ Observation。模型提议的每一步都要经过校验、修复、解析成内部 action 才执行；工具的原始返回是 untrusted 内容，必须规范化后才能进入 state 提议。信任边界就在这层转换里。
  • Loop 只管时序，Reducer 独占 State 写权。状态变更走 Processor→Delta→Reducer 的纯函数事务，所以 checkpoint 之后 resume 是确定性的，回放是可复现的——100 步 / 640 条证据的压力测试验证 resume 后上下文逐字节一致。
  • Checkpoint 属于 Runtime，不是日志。它记录相位（decision/action/observation/commit）和 attempt，崩溃恢复能精确分类到相位：工具成功但提交前挂掉的步，从成功缓存复用结果，不重复打外部 API。

验证方式（分层）：779 个单测守住机制；14 条路径的 prompt 注入矩阵守住信任边界；然后是真刀真枪——一个真实中文舆情事件（三九胃泰中秋广告争议）跑完整 live 闭环：60 步、17 次搜索、17 次读取、14 条 finding、92 处证据引用，审查阶段 6 条 supported / 8 条 partial，完成闸门拒绝了 18 次 finish 直到步数耗尽——系统宁愿 partial 也不强行收尾。

我最想讲的一个失败：第一次 live 复跑以 partial 收场，但诊断链让根因无所遁形——committed_steps=20 恰好等于默认步数上限，而预算只用了 16%–45%。是配置问题不是逻辑问题，runner 层调参零源码改动就解了。这套「失败 → 九阶段诊断 → 定位 → 修复 → 复跑验证」的循环，本身就是 harness 设计正确性的最好证据。

收尾：质量数字我也有：检索召回 60%、忠实性 71% 完全支持 / 100% 零虚构、对抗埋点 2/3。每个数字都知道短板在哪、下一步怎么修——这些「下一步」清单比数字本身更能说明我对系统的理解。

三、§16 十四问 · 要点答案

每题控制在 3–6 句、结论先行。加粗处是必须说出来的关键词。

1. 为什么项目只深做 Agent Infra 前两层？

岗位匹配 + 可验证深度。前两层（Harness/Runtime、Tool/MCP/Context/Memory）决定 agent 的可靠性，且能用软件工程手段验收——单测、压力测试、注入矩阵、崩溃恢复演练，全是可证伪的。Control Plane/Eval/Data Infra 公开参考多、差异化低，做了也只能讲「我见过」。宁可两层做穿，不做全栈皮毛。舆情 workload 存在的唯一理由就是证明前两层，不是产品目标。

2. Harness、Tool Runtime 和 Control Plane 的边界是什么？

Harness 拥有 run 生命周期和 state 提交权；Tool Runtime 是 Harness 的下游，只管单次工具调用的重试、熔断、缓存、超时、跨 provider fallback——它不知道也不该知道 investigation 是什么；Control Plane 管多 run 的调度、配额、租户策略，本项目显式不做（§17 决策摘要第 8 条），因为单 run 正确性没做穿之前做多 run 调度是无本之木。

3. 为什么 Decision 不是 ToolCall，ToolResult 不是 Observation？

Decision 是模型意图，可能非法、可能重复、可能需要修复——它经过校验与 repair 才被 resolve 成内部 action。ToolResult 是外部世界的原始返回，untrusted、可能畸形、可能带注入内容；Observation 是规范化后、获准进入 state 提议的那一份。中间这层转换就是所有安全与可靠性机制的挂载点：如果 Decision=ToolCall，你就没有地方做校验；如果 ToolResult=Observation，你就没有地方建信任边界。

4. 为什么 Loop 只管理时序，Reducer 才拥有 State 写入权？

单一写者原则。Reducer 是纯函数：同样的 delta 序列必然得到同样的 state。这让 checkpoint/resume/replay 的确定性变成一个可证明的属性，而不是祈祷。如果 Loop 也直接改 state，恢复语义就要靠代码审查保证；现在它靠结构保证。Loop 的职责被压缩到只剩时序：提议→校验→执行→观察→提交→持久化，一步一事务。

5. run lifecycle 与 step lifecycle 为什么要分开？

它们是两个频率完全不同的状态机。run 级是 completed/partial/cancelled/failed（外加发布用的 finalizing 中间态）；step 级是 decision/action/observation/commit 的事务相位加 attempt 计数。分开之后，崩溃恢复用 classify_resume 精确定位到「死在哪一相」——尤其是「工具成功、observation 未提交」这个最容易丢钱的相位。混在一起，恢复逻辑就是一团 if-else。

6. 工具返回后、State 提交前崩溃如何恢复？

action_results 成功缓存：工具成功结果按 action identity 先落盘，再进 observation。进程在「缓存已写、checkpoint 未写」的窗口死掉，resume 时从缓存复用这份结果——不再调用 provider，然后正常走 observation→commit。这是 at-most-once 的持久化成功复用，配合只读工具的安全重试，合成 state effect 的恰好一次。

7. 为什么只能追求 effectively-once state effect，而不是声称外部请求 exactly-once？

外部 HTTP 请求不可回滚，发出去了就是发出去了，任何「恰好一次」的声称在物理上都是假的。能做到的是把不确定性全部推到边界上：工具只读、可安全重试；成功结果按 action identity 缓存；提交走幂等 delta；崩溃按相位分类。最终效果是 state 的变化恰好发生一次——这是诚实且可实现的承诺，我拒绝说更大的话。

8. checkpoint 为什么属于 Runtime，而不是 Data/Observability 平台？

checkpoint 的存在理由是正确性：相位、attempt、已提交 delta 序列，少一个字段恢复就错。把它放进 Data 平台，它会退化成事后日志——写日志的人不会为恢复语义负责。Observability 可以消费 checkpoint 的投影，但 checkpoint 的 schema 必须由 Runtime 的正确性需求定义。本项目刻意不建 Trace/Data 平台，就是这个决策的另一面。

9. MCP 为什么只是 Tool adapter？

不给 MCP 任何特权通道。MCP 内容永远是 untrusted input：注册前用 allowlist 的 schema SHA-256 校验远端契约，不匹配则 Registry 不变；调用时递归剥离 _meta/meta/annotations，非 JSON 内容变成固定报错；生产端点强制公网 HTTPS。MCP 与其他 provider 走同一个 ToolExecutor——同样的重试、熔断、缓存。它的价值是生态接入，不是架构地位。

10. Context Compiler 相比 messages.append() 解决了什么？

append 是 O(n²) 增长、无界、无信任分级的。Compiler 把每步的模型输入临时编译出来：分层（L0 不可变指令只接受 app-config 内容）、token 预算、required window + 可丢弃 history chunks（默认 64/块，gap 采样 16）、每节带内容来源标记和 SHA-256。关键性质：required context 不随 run 增长，且编译结果永不入 checkpoint——resume 后重新编译，压力测试验证逐字节一致。它解决的不是「省 token」，是「上下文也是一个要工程化的资源」。

11. Full State、Working Memory、Recent Interaction、Artifact 和 Context 有何区别？

一个权威 + 四个投影。Full State 是权威事实，只有 Reducer 能写；Working Memory 是从 state 派生的工作视图，可重建、可丢弃；Recent Interaction 是步记录（谁提议了什么、结果如何）；Artifact 是正文快照，SHA-256 寻址，不直接进上下文，由证据 locator（块号+字符偏移）引用；Compiled Context 是前四者每步临时编译出的瞬时模型输入。混淆这五层是 agent 项目最常见的腐烂起点。

12. 如何保证 compaction 不删除矛盾或创造事实？

compaction 只作用于派生层，永远不动 Full State。证据目录分 required current window + droppable history chunks，删的只是可重建的历史窗口；矛盾（contradictions）是 state 的一等公民，不在可删除范围；「不创造事实」由信任标记保证——压缩产物不得被标记为 trusted，模型/工具内容 commit/checkpoint/resume 全程不洗白。14 路径注入矩阵里专门有针对 compaction 的攻击面。

13. prompt injection boundary 如何建立？

三层。标记：每节上下文带内容来源，model/tool/provider 内容永不可信，这个属性不随 commit/checkpoint/resume 改变——防止「信任漂变」。结构：MCP 元数据递归剥离、工具内容结构化投影、证据以 locator 引用而非全文注入。验证：14 条注入路径的对抗测试矩阵是 CI 的一部分，不是一次性演练。边界的核心思想是：不信任任何一段文本，只信任出处。

14. OpinionSearch 如何证明 Runtime 机制，而不是遮蔽 Runtime？

四条结构性证据：① 所有舆情规则（时间窗、必答问题、回应判定）都在 domain 层，通用 Runtime 零舆情语义；② offline 模式用确定性 fake providers 跑同一个 loop、同一份 checkpoint 格式——机制可脱离外部世界验收；③ execution profile 锁定 live 组合，换 profile 拒绝 resume，防止「同名不同物」；④ live 与 offline 的差异只在 adapter 层。所以 workload 是可插拔的验证件，不是和 Runtime 长在一起的产品外壳。

五、失败 → 诊断 → 修复 → 复跑：完整故事链

第一幕 · s3-live（09-14）：首次真实 live 批次——8 份正文、44 条证据、40 次模型请求、0 个 Finding。不是模型笨，是流程断在「证据→finding」的转换处。

第二幕 · 九阶段诊断：沿诊断链逐段排查，根因包括首次研判闸门过严、发布保留段截断、时间解析不识别「过去 30 天」（空格）。逐项修复并加回归测试。

第三幕 · s5-a（09-21，默认 20 步）：复跑仍 partial。但这次诊断链让根因 5 分钟现形：committed_steps=20 恰好等于默认上限，预算仅用 16%–45%——是配置不是逻辑。runner 层 model_copy 调步数，零源码改动。

第四幕 · s5-b（60 步）：全流程真正走完——review 执行（6 supported / 8 partial）、3 次 reflect、completion gate 18 次拒绝 finish 直到步数耗尽。报告 92 处证据引用，中新网评/央广网/新京报回应/既往「毒广告」模式全部带 locator。

这个故事为什么值钱：它证明诊断链（checkpoint + 相位记录 + 失败不粉饰）在真实失败上 worked as designed。两次 partial 都不是「系统坏了」，而是「系统诚实地报告了自己的不足并留下了完整证据」。这比一次侥幸的 completed 更能说明 harness 的价值。

六、已知限制（主动讲，别等问）

  • 搜索源偏向聚合站：Brave 单引擎、固定 5 条/次、无分页；候选 2/3 来自聚合站。TaskFrame 解析出的时间窗/语言/域名未传导到 Brave 参数（freshness/search_lang 全缺）。
  • 证据摘录召回是单点：4 条 partial finding 全是「引语在原文、摘录没摘到」；反方稿已读已摘却零引用。
  • 模型不会主动收口：长期无证据的问题停在 open 而不显式转 not_found/unavailable——这是 completion gate 拒 finish 18 次的直接原因。
  • 数字护栏只验出处不验可信度：真实数字 316.03 亿与埋点错误数字 3160.3 亿在证据目录静默并存，无矛盾检测。
  • 反爬无对策：qq/sohu 等 6/17 读取失败，当前只靠失败计数兜底。

七、下一步清单（面试谈资：我知道怎么修）

  1. 约束传导（P0，成本最低）：把 TaskFrame 时间窗/语言/域名传进 Brave 查询参数——不是新技术，是把已解析的契约执行到底。
  2. 结构化 QueryPlan + 第二引擎：查询由规划器产出（目的/时间窗/站点偏好），聚合站域名降权，打破 66% 单源偏向。
  3. 事件内二次检索（FTS5/BM25）：对已读 artifact 全文建索引，finding 生成时按问题检索相关段落——直接命中「摘录没摘到」和「已读未引用」两个失败模式。
  4. 矛盾检测：同一主体的数字声明冲突时显式生成 contradiction 对象，而非静默并存。
  5. 收口动作：允许模型把 open 问题显式标记 not_found/unavailable（有界搜索完成后），让 completion gate 的拒绝变成有出口的拒绝。
  6. 评测体系化：必中清单标注 + 对抗埋点从一次性活动变成回归套件。
