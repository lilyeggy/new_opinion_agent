二、效果实测：同一冻结案例 v1 → v3

测试纪律：三版跑的是完全相同的冻结材料（7 篇真实快照 + 3 篇对抗埋点）与真实模型，唯一变量是代码版本。

指标v1（修复前）v2（A+B+C）v3（+持续综合）
步数20（步数耗尽）20（步数耗尽）13（墙钟预算耗尽）
reflect 次数112
active findings349（3 倍于 v1）

持续综合硬拒绝——0（引导起效，非惩罚）

三个数字里最值得注意的是硬拒绝 0 次：模型看到编译器注入的 next_action_constraint 后主动选择了第二次 reflect——机制以引导方式起效，而不是以惩罚方式。这符合设计意图：程序不做真相判断，只做"证据必须被显式处置"的会计，处置出路永远留给模型。

三、一个诚实的权衡

v3 的 13 步只读了 10 篇材料中的 6 篇——三个对抗埋点（反方稿、更正、错误数字）本次没有被读到。原因不是机制缺陷：模型端点延迟约 100 秒/调用，24 次模型调用烧完 40 分钟墙钟预算时，read 配额（6/24）还远未用尽。时间预算先于读取配额耗尽，是模型慢这个工程约束的直接后果。

这暴露了持续综合机制的真实代价：更多 reflect = 更多模型调用 = 在慢端点上覆盖更少来源。单位证据的判断密度换取了来源覆盖的牺牲。在端点速度正常时这个交换明显划算（v1 用 20 步读 10 篇只产 3 条判断；v3 用 13 步读 6 篇产 9 条）；但在端点极慢时，阈值（8 条）可能需要与预算联动调整——这是已记录的后续优化点，不是本次要解决的问题。

  • 唯一失败 test_running_snapshot_never_claims_terminal_without_report：它要求 offline run 在 2 秒轮询窗口内完成，而本机 pytest 环境 run 耗时 5-10 秒（手动环境 0.24 秒——环境 IO 税约 40 倍）。用 git 还原实验证明与本次改动无关：还原全部 4 个改动文件后该场景耗时不变（34.12s vs 34.85s），属既有时序敏感断言的环境抖动。

五、这轮修复的面试叙事价值

这轮迭代完整走了一遍「实测 → 诊断 → 机制修复 → 同例回放验证」的闭环，恰好是 harness 工程能力的最直接证据：

  • 失败先变成数字再变成机制：「感觉质量不行」→ 转化率 50%、401 全灭、finish 空转 29 次 → 三处确定性机制，而不是调 prompt。
  • 机制可证伪：每个修复都有「什么情况算它错」的明确答案——B 的防误报测试（无关企业的回应证据不得触发）、D 的阈值测试（7 条不拦、9 条拦）。
  • 验证复用冻结案例：v1→v3 同例回放是零新基础设施的 A/B 实验，回放设施在 D4 建成后第三次兑现价值。
  • 诚实记录权衡：v3 覆盖面下降的代价被识别、解释、记录，而不是被 3 倍 findings 的数字掩盖。
一句话总结：上午的检验报告说「质量上限被分析/收口层压住」，下午的三个修复全部落在那一层——证据必须被显式处置的会计机制（闸门引导、持续综合、陈旧判断防护）+ 供应商抖动的熔断语义（401 重映射），回放实测转化率 18%→68%。Runtime 骨架一行未动，这正是当初分层设计的回报。
