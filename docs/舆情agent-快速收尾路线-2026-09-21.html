关 键 判 断

这个项目距离「完成」不是差一堆功能，而是差一次真实成功：最后一次真实联网尝试（09-14 s3/s4）以 0 Finding 和决策恢复耗尽收场，修复后的策略至今没有复跑验证。所以收尾的关键路径只有一条：用真实模型+真实材料，让闭环成功跑一次。其余所有动作——砍 fork、出数字、练故事——都是围绕这一件事的收口。

01完成定义（面试可用 = 四条全部满足）

✓ Definition of Done

  1. 单一系统：一套 harness、一条产品路径，5 分钟能讲清，没有讲不出取舍的 fork；
  2. 真实闭环：一个中文真实事件，真实模型+真实搜索，完整跑出带证据、带诊断的报告（completed 或诚实标注的 partial 均可，但必须走完全流程）；
  3. 三个数字：检索召回、忠实性、对抗点命中——各一个可引用数字，不追求体系；
  4. 讲得出来：3 分钟电梯陈述 + 13 个核心问题（设计文档 §16）+ 一个失败修复故事，脱稿。

02五天路线

D1

砍 fork，统一叙事（纯删除与记录，零风险）

  • harness/ 整体移入 archive/（或加 EXPERIMENTAL.md 标记冻结），README 记一笔决策：「评估过多角色流水线拓扑，因违反单 runtime 原则且与生产路径能力重复，归档不采用」。
  • 统一口径：唯一 harness = runtime AgentLoop；产品路径 = investigation 域 + PagePlan 渲染；面试词汇只留一套（Evidence/Finding/Review）。
  • 不改任何运行时代码。今天结束时系统行为与昨天完全一致，只是讲得清了。
产出：完成定义 ① · 「为什么砍第二个 loop」成为减法故事
D2–D3

关键路径：真实闭环复跑（s5）

  • 选 1 个中文公开争议事件（目标域，非英文科技稿），真实 Brave+Jina+生产模型，跑修复后策略（首次研判闸门 + 发布保留段）。
  • 跑之前先修两个已知阻塞项：UI placeholder「过去 30 天」空格不解析（用户照抄示例即静默失效）；确认 live_model() 的 max_output_tokens 与预算配置真实进入执行边界（§19.13 已修，验证即可）。
  • 跑挂了就靠已有的九阶段链路诊断定位：只修阻塞闭环的 bug，不顺手优化。每个修复记录「现象→诊断信号→修复→复跑结果」，这就是面试素材。
  • 若 D3 结束仍跑不通：降级方案 = 用冻结材料+真实模型回放（§19.10 设施已就绪）完成闭环演示，live 限制如实写进报告——诚实降级也是完成。
产出：完成定义 ② · 全程自动生成「失败→修复→验证」故事链
D4

三个数字（一天出齐，不建体系）

  • 检索召回：拿 D2 的事件材料，人工标 8–10 篇「必中清单」，对照实际读取，recall = 命中/必中；
  • 忠实性：抽报告里 15–20 条 finding，人工核对「证据是否真的支持」，支持率 = 通过/抽样；
  • 对抗点：往冻结材料里塞 3 个已知点（一篇反方稿、一条更正、一个错误数字），跑 replay，命中 x/3。
产出：完成定义 ③ · 「我怎么验收我的 harness」有了答案
D5

面试收口

  • 电梯陈述定稿：一句话定位 → 架构图 → 三个数字 → s3→s5 失败修复故事；
  • 设计文档 §16 的 13 个问题过一遍，每个能讲「为什么」而不是「是什么」；
  • README 定稿：定位、运行方式、架构图、验收数字、已知限制（已知限制主动讲，是加分项）；
  • implementation memory 记最后一笔：s5 结果与三个数字，封存。
产出：完成定义 ④ · 项目封存

03明确不做（做了就超期）

✗ 一律不碰

  • 代码级 harness 合流 / 任何运行时重构；
  • 搜索管道改进（QueryPlan、第二引擎、BM25 二次检索、freshness 传导）——全部写进 README「下一步」讲给面试官；
  • 异步化、checkpoint 增量化、Controller 清理；
  • 评测体系化（基线设施、自动化评分）——D4 的手工数字足够；
  • 报告排版与前端的任何打磨。

⚠ 唯一的风险点与对策

D2–D3 的真实复跑可能再次暴露收敛问题（s4 就是修复后仍耗尽决策恢复）。对策已经内置：冻结材料回放兜底 + 诊断信号定位 + 只修阻塞项。即使 s5 最终是 partial，只要诊断链完整记录了「系统如何发现自己的不足」，这在面试里依然是成功——这个项目最值钱的本来就是可靠性机制，不是某次报告内容。
