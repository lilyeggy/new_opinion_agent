## 3. 最终要证明的报告能力

好的报告至少让用户回答下面五个问题，每个重要回答能定位依据：

1. **当前处于什么状态？** 区分历史背景、最新事件变化、机构表述与可核实执行结果。
2. **争议到底是什么？** 按具体措施和受影响主体拆分，保留各方原本表达；没有证据不强造对立。
3. **回应覆盖了什么？** 回应充分、事实问题解决、用户满意分别记录。
4. **哪些仍不能判断？** 说明缺失要素、查找范围、截止时间和读取失败影响。
5. **新材料改变了什么？** 区分加强、削弱、修订、撤回、未复评和新发现旧材料。

“有深度”不以字数或材料数衡量。应该体现在：识别实质缺口、拆开容易混淆的概念、发现时间或来源依赖、解释判断为何改变，并告诉用户下一步需要核查什么。

## 5. S1：先修会污染评价结果的语义缺口

### S1-A 必答子问题无法判断，却可能整轮 completed

基线已复现：required issue 为 disputed，其 component 为 unavailable，其他活跃判断均通过审查时，`completion()` 可返回 ACCEPT_COMPLETE。

执行要求：

- 新增最小回归，覆盖 required issue 的 answered/disputed/not_found/unavailable 与 component 的组合，特别是读取失败造成的关键未知。
- 使用既有含义：disputed 表示存在证据分歧，不能用来隐藏材料不可得；not_found 需要查找范围；unavailable 说明无法完成判断。
- required 子项 unavailable 或仍未处置，应影响整轮 partial；不能被父问题标签掩盖。
- 范围内恰当“未发现”可以成为完成处置，但要提供查找证据和范围，不可把 unavailable 改名为 not_found。
- 不要默认把所有局部未知都当作失败，也不要引入另一套全局分数替代明确的状态规则。

验收：上例不再 completed；已有合法的证据分歧、恰当未知与提前结束案例不回归；Web/导出在对应子项显示原因。

### S1-B 专项字段的文字差异不等于事实冲突

基线实现 `_facet_fields()` 用不同字符串值判断冲突。在同一上下文里，“居民用户”和“本市居民用户”可能相容；不同日期、地区或人群的规则也不能直接互判矛盾。

执行要求：

- 先冻结三个机制案例：同义表述、不同适用范围、真实互斥值。
- 保留原始值与引用。完全一致可以归并；未经判断的不同表述先标为“多种表述，待核对”。
- 真冲突需确认主体/对象、有效时间和适用范围可比较，并有互斥依据。不能靠删地名、删日期或模糊字符串相似度自动合并。
- 允许保守显示多个有依据的值，不为使模块 ready 强行选一个。
- 优先做最小领域修正，不建设通用语义匹配系统。更丰富的归一化留给真实案例失败驱动。

验收：相容表述不显示为已确认矛盾；不同时间/范围并列；真正冲突仍可见并阻止无依据的唯一答案。

### S1-C 数字护栏的使用边界

现有 `unbacked_specifics()` 检查数字是否出现，不验证数字与单位、对象、时间的对应。例如原文“退款100元、涉及200户”，判断“退款200元”不能只因出现 200 就当作正确。

保留该护栏，补充这种错误的测试/人工检查样本；审查应检查完整断言及 module_fields。单位换算或合理计算不因字符串不同自动判错，需保留推导依据。不要声称一个正则表达式已解决事实核验。

### S1-D 回放生命周期与材料隔离预检

- `run_replay_case()` 超时或缺澄清答案会抛异常，但当前没有在所有这些出口显式取消 Manager worker。正式批次前验证并补齐停止/取消/清理，避免调用端退出后仍在扣费。
- `load_replay_case()` 当前允许内联正文、也允许快照省略 sha256。正式真实材料案例必须要求文件和哈希齐全；哈希不一致阻止运行，不靠加载器的宽松输入自动放行。
- 模型输入不应包含 expected、人工答案或评分表。案例 manifest 仅包含任务与开放材料。
- 记录 `evaluation_mode=frozen_model` 等实验标签。当前报告的 `mode=live` 只说明模型分支，不能单凭它判断是否进行了联网搜索。

完成 S1 后，运行定向测试及调查回归。只有修改触及 API/UI 时追加对应 Web 验收，不反复全仓测试消耗时间。

### 6.2 原始材料保存规则

每份材料保存请求/最终 URL、标题、实际获取时间、可获得的发布时间/更新时间、正文文件、sha256、角色和已知转载/引用关系。日期无法确认填 null，并记录日期依据。

可复用已保存正文，但必须核对 artifact 与证据定位；本地快照丢失则不能只拿报告里的节选冒充完整正文。若只取得片段，标明片段并限定评价范围。

材料必须来自真实公开文本，不用模型改写后的正文作为原始资料。遵循来源的访问与使用限制；保存可审计依据不等于获准对外分发全文。

没有历史当日快照时，实验名称使用“按材料批次回放”，不声称重建了历史互联网全貌。发布时间早也不能证明该页面当时已包含现在的全部内容。

### 6.3 回放 manifest

当前 `ReplayCase` 接受的实际字段如下。该示例只是格式说明，文件名、URL、哈希均必须替换为核对后的真实值才能运行：

```json
{
  "case_id": "billing-dev-v1",
  "request_question": "真实事件名称及需要调查的问题",
  "focus": "适用范围、办理路径、执行证据与尚缺事项",
  "clarification_answers": [],
  "materials": [
    {
      "url": "https://example.org/REPLACE_WITH_VERIFIED_SOURCE",
      "final_url": "https://example.org/REPLACE_WITH_VERIFIED_SOURCE",
      "title": "替换为来源原题",
      "snapshot_path": "snapshots/source-01.txt",
      "sha256": "REPLACE_WITH_ACTUAL_SHA256",
      "published_at": null,
      "updated_at": null,
      "role": "original"
    }
  ]
}
```

`role` 只允许 original/reporting/commentary/unknown。案例 registry 使用 `source_role` 等更丰富元数据；不要把两个格式视为相同输入，做显式转换并校验文件/哈希。人工 expected 单独保存，禁止传给 planner/Compiler。

### 6.4 人工标注

在看到模型报告之前，按原文标注：必答子问题、重要性、可接受回答、允许的未知说明、关键引用、主体归因、时间关系、禁止结论、T1 预期变化。

Agent 可以整理候选与预标注，但必须标为 `model_preannotation`。用户或指定人工审核后才可标 `reviewed_by_human=true`。没有人工审核时，可以继续调试机制，质量结果标为 `UNREVIEWED`，不能自评为人工通过。

| 组 | 输入与机制 | 回答的问题 |
|---|---|---|
| A 当前 Agent | 真实 planner/决策/reviewer，冻结 Search/Reader，正常调查与报告管线 | 反复取证、问题处置和审查能否改善材料理解 |
| B 简单摘要 | 同一个任务、同一模型，直接提供同一冻结正文；一次生成，标注引用 | 额外 Agent 循环是否有可说明的价值 |

固定模型标识、可设置的生成参数、材料版本与任务文本；记录上下文窗口、最大输出长度、实际 token 和请求数。两组成本通常不同，明确报告质量—成本取舍，不称为“同成本证明”。

材料应能完整放进基线上下文；若放不下，先缩小双方共同材料范围或冻结共同的确定性切片策略。不能只截断基线、却让 Agent 读取全文后宣称公平胜出。

现有 `ReplaySearchAdapter` 对任何 query/purpose 返回同一组材料。这个对照不验证 query 质量、排序、召回率或真实网络发现；要单独验证这些能力，执行 S6。

### 7.2 执行入口及注意事项

复用 `run_replay_case(root, case_path, config=..., env_file=...)`，不要再造一套简化 Agent。代码位于 `investigation/replay.py`。执行前：

1. 检查批次获批额度，设置并验证该 run 的环境预算；`.env` 加载后再次读取生效值。
2. 使用新目录 `<batch>/runs/agent/<run-label>/investigations` 作为 Manager root。不要直接写入用户正在运行服务的目录。
3. 将 env 文件路径传给现有加载函数；不打印其中内容。`timeout_seconds` 是调用方等待期限，不能代替 worker 预算或取消机制。
4. 保存生成的 draft、budget、checkpoint、report.json、report.md、workbench.json 与 case 正文；失败时保留已有产物。
5. 基线复用现有模型客户端，以独立的受控验收脚本运行。当前没有现成“质量基线命令”，不要把伪命令写成已可执行接口。

若 planner 要求澄清，回答只能用于确定任务对象，不向模型泄漏 expected。若问题来源于案例身份不完整，修正案例版本后记录为新实验，不能在同一基线下无痕重试。

### 7.3 模型基线提示模板

> 根据下面给定的公开材料，回答用户任务。区分来源陈述与已确认事实，按具体问题梳理争议、主体说法、回应覆盖、执行证据和未知。不要补充材料以外的事实或推断公众总体态度。每个重要判断标注对应材料编号及原文位置；材料不能支持时明确说无法判断。先给简短的当前状态，再给按问题组织的依据。

材料编号对两组保持稳定；基线引用不强制使用 Agent 内部 evidence_id，由评价器映射到同一源文本。不能因为输出 schema 不同就给基线零分。

## 8. S4：评分与失败诊断

### 8.1 不采用单一总分

| 维度 | 计分单位与检查方式 |
|---|---|
| 必答覆盖 | 事先标注的子要求；正确回答或恰当未知记 1，遗漏/错误/不恰当未知记 0；同时报已回答与未知数量 |
| 重要断言支持 | 将段落拆为原子断言，检查对应原文是否完整支持主体、动作、数量、时间与限定 |
| 引用结构完整性 | 引用 → 正文版本 → 哈希/定位均可解析；错误引用不能用另一条替代 |
| 归因与来源依赖 | 自述不升级为事实；转载不成为独立验证；未知关系明确标示 |
| 回应与执行 | 按问题逐项核对回应覆盖，区别承诺、启动、结果与独立核验 |
| 更新正确性 | 对每项预标注变化核对分类、前后判断与新依据；未变化项不得凭空变化 |
| 研判价值 | 人工判断能否看清现状、实质争议、关键未知与下一步核查方向，记录具体好坏例子 |
| Web 可用性 | 从结论找到正确原文、理解限制、发起对应补查、找到新旧差异 |
| 成本与稳定性 | 每组模型/工具/token/时长/失败与重试；失败样本单列不丢弃 |

重要断言集合 = 事先预期的关键断言 + 输出新增的重要断言，不能只选模型写得好的句子。已知答案不回答、统一写“无法判断”，不得获得恰当未知分。

“正确降级”仅指最终文本本身准确表达依据不足或归因限制；错误数字旁边加“仅供参考”不算降级成功。没有可评分断言时记 N/A，不记 100%。

### 8.2 标注文件最小字段

```text
question-checks：requirement_id、expected、observed、verdict、理由、source_refs
claim-checks：claim_id、原子断言、重要性、来源/版本/位置、supported/partial/unsupported/contradicted、理由
response-checks：问题、主体、回应内容、已覆盖、未覆盖、执行证据、预期与实际分类
update-checks：旧判断、新判断、变化类型、新依据、T0是否泄漏T1、错误影响
usability-checks：任务、实际动作、结果、证据、未运行项
```

机器校验定位，人工判断语义。可以用模型协助预标注，但执行模型的 reviewer 不能作为最终独立人工评分来源。

### 8.3 闸门

- 原有最终门槛保持：引用及定位结构完整性 100%；必答子要求正确回答或恰当未知至少 90%；人工检查的重要断言至少 95% 支持或正确降级；关键归因、转载、回应遗漏和更新反转用例全部通过。
- 首批一例若有错对象、关键数值/归因错误、错误引用、把材料失败说成“没有进展”等严重问题，不扩大付费批次。
- 单案例达到比例只是“该案例通过”，三案例通过只是“小样本通过”；不能据此声称原 10 案例保留验收通过或产品已稳定。
- 样本较小时同时展示分子/分母与逐例结果，不仅展示百分比。
- 完全没有有价值内容但格式完备的报告不能通过：已知关键答案遗漏会扣覆盖分，研判价值还要给出人工实例说明。

### 8.4 失败如何决定下一步改什么

| 失败表现 | 优先检查 | 合理改动 | 不应做 |
|---|---|---|---|
| 必要材料根本没被发现 | query、别名、官方域名、主体与失败方向 | 修查找策略，进入联网诊断 | 用冻结回放的全量返回证明召回强 |
| 材料已有但关键段没进入证据 | 正文完整性、FTS、片段选择与上下文丢弃 | 修 retrieve 或证据选择 | 直接增加结论字数 |
| 证据已有但判断错误 | 归因、时点、单位、否定、复合断言 | 拆原子判断并重新审查 | 只降低 reviewer 门槛 |
| 内容正确但专项字段错 | 字段绑定、作用范围、各字段证据 | 修投影或字段级审查 | 给错误字段附一组通用引用 |
| 覆盖不足却 completed | components、状态组合与查找证明 | 修领域结束判定 | 删掉用户问题 |
| 摘要冗长、看不清现状 | findings 粒度、优先级、跨时点关系 | 组织当前判断、变化和重要未知 | 只改 CSS 或扩展更多卡片 |
| 阅读困难或引用难核查 | 真浏览器动作、路由、选中引用与布局 | 修对应交互 | 用 API 200 代替操作验收 |

一次只修最影响该案例的一类原因，保存修改前后证据。相同配置复验最多一轮；再次失败先提交原因与预算影响，不无限试 prompt。

## 9. S5：更新能力与 Web 完整链路

### 9.1 T0/T1 必须物理隔离

T0 的 manifest、SearchAdapter、ReaderAdapter 和可检索 corpus 中不得出现 T1 正文；不能只提示模型“忽略后续材料”。

T1 增加新材料时，同一 URL 在该阶段 manifest 中只提供一个明确的当前正文；旧正文由父版不可变 corpus 保留。不要把两份同 URL 条目交给当前 `ReplayReaderAdapter.by_url`，其字典会覆盖其中一份。

当前 `run_replay_case()` 只封装首次创建，不封装 T0→T1 更新。复用同一调查根目录的 Manager，以 T1 的 `replay_loop_builder()` 创建指定 parent_id 的子版，保留现有 update_intent 与关联规则；如需辅助函数只写在验收边界内。

禁止直接在普通 live 服务上点冻结报告的“补查”来假装冻结更新：该服务若未注入 frozen builder，可能转用真实 Brave/Jina。冻结阶段只读展示；真正点击补查创建应在明确注入冻结 adapters 的隔离验收服务，或在获批联网批次执行。

### 9.2 更新验收清单

- 新增材料：旧文新发现、新发布材料、同 URL 正文变化各自正确分类。
- 判断：加强、削弱、修订、撤回、未复评分别检查；承诺升级为执行结果必须有新证据。
- 定向：用户选择的问题优先调查，相关依赖变化可以触发重开并保留理由；无关判断不机械清空。
- 版本：旧 report/workbench/正文哈希不变，跨版本引用不能错指；新版本失败或 partial 不隐藏上一完整结果。
- 无变化：不得把供应商故障、预算不足、没有读取关键材料包装为无新增进展。
- 时间：报告生成、查找截止、事件发生和材料发布时间不混淆；当前代码初始化 State.cutoff 的行为要与页面表述核对，不能仅因字段名称分开就认为语义已验证。

### 9.3 页面核心展示

使用真实长内容，不再只看合成案例：

```text
提交明确事件 → 必要澄清 → 看见问题与查找进展
→ 总览理解当前状态 → 报道对照 → 查看某条主张对应的第二条引用
→ 核对原文和限定 → 补查具体缺口 → 查看新版本
→ 比较判断变化 → 切回旧版本 → 下载本版 HTML / Markdown
```

1280/768/390px 至少各走一次关键阅读动作；不仅检查无横向溢出，也检查摘要是否挡住正文、证据能否关闭、限制是否在对应结论附近、焦点能否返回。

总览建议呈现：一条简短当前判断、最多三个关键变化/未决事项、最重要限制、来源核查入口。不要仅截断长句；如由模型重新概括，概括自身也必须绑定并核查依据。未做新概括时可以选用已审查的短原子判断。

## 10. S6：扩到三个案例，再验证真实联网发现

开发案例 A 通过且没有关键错误后，再执行 B 和保留案例 C。保持模型、预算和评分协议冻结；跨案例报告各自的失败，不只展示最好的一次。

真实联网至少选一个已冻结身份与必答问题的事件，使用原 Web → Brave/Jina → 报告链路，允许其发现冻结集合以外的新材料。

- 统计找到多少已知关键来源、哪些问题得到了足够材料，而非“全网召回率”。冻结集合本身也不是互联网全集。
- 将未发现、无关、重复、读取失败分开；审阅新增来源可能改变原人工答案的部分，保留标注修订记录。
- 与固定材料回放分开报告：回放好、联网差，优先修发现/阅读；两者都差，优先修问题建模/取证/审查；两者内容好、用户仍读不懂，再优先修呈现。
- 若做联网基线，使用同模型的一次搜索 + 有界读取 + 总结，预先冻结读几篇及选择策略，报告实际资源差异；不能把冻结材料摘要基线标为联网搜索基线。
- 公开访问的新材料可确认“本次可获取的现状”，历史快照缺失时不能推断历史当日已经知道这些信息。

三案例和一次联网完成后，先交付小样本结果，再决定是否继续填满原 10 案例。没有质量收益时，可以保留正确性改进并缩减无收益步骤，不为证明 Agent 优越而挑选结果。

## 11. 最终交付与停止条件

必须交付：

1. 基线与批次清单：commit、模型/参数、材料哈希、预算及实际消耗，运行状态。
2. 完整案例包与人工标注状态：至少说明哪些是开发、哪些是保留、是否接触过答案。
3. Agent 与基线原始输出、逐子问题/逐重要断言评分、错误例子和成本对照。
4. 一条真实 Web 用户链路的操作证据；冻结、联网、脚本模型证据分开。
5. 改动前后可解释的改善及仍未解决的问题；失败和 partial 产物保留。
6. `comparison.md` 用明确结论：通过了哪些案例、改善在哪里、未证明什么、下一步是否值得消耗额度。

状态词统一：`PLANNED`、`IN_PROGRESS`、`PASS`、`FAIL`、`NOT_RUN`、`BLOCKED`、`UNREVIEWED`。工具测试通过不能把人工评分从 UNREVIEWED 改为 PASS。

遇到以下任一情况停止扩大执行：批次预算耗尽；关键材料不可获取且不能替代；人工复核缺失；关键引用/身份/归因错误；两次同类失败无新诊断；需要超出范围的架构变化。报告具体缺什么，以及还能继续完成的离线工作。

实现后同步 canonical、执行计划和实现记录：记录已验证事实、模型/材料/预算条件与未运行项。计划与代码入口存在不是结果，不得写成 P5 完成。
