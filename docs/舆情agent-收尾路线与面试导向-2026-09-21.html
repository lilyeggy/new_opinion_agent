收尾决策 · 秋招面试导向

项目思路对不对？先改哪里？
——一份以「面试能讲透」为验收标准的收尾路线

前提：秋招进行中，可用时间按 1–2 周计 · 核心技术叙事锚定 Agent Harness 构建 · 2026-09-21
两 个 问 题 的 直 接 回 答

Q1 · 整体思路对不对？——对。「只深做 Agent Harness/Runtime 与 Tool/MCP/Context/Memory 两层，舆情作验证 workload」这个定位，和 agent 构建开发岗的面试考点几乎逐项对齐：loop 设计、状态机、崩溃恢复、effectively-once、工具协议、上下文工程、失败模型——你们的设计文档 §16 列的面试题就是证据。思路不需要转向，需要收尾。

Q2 · 先合流再改质量？——顺序对，但「合流」必须换一种做法。现在距离面试是以周计，不做代码级大重构，做「决策级合流」：确立唯一 harness、隔离或归档第二套循环、统一叙事。质量修改也要换成「面试友好」的版本：不做搜索管道大改，做质量基线测量——因为面试里「我怎么验证我的 harness 有效」比「我又加了什么功能」值钱得多。

01一个必须先点破的事实：harness/ 第二层循环违反了你们自己的 canonical design

设计文档 §4.1 白纸黑字：「第一版不做 planner/researcher/writer/verifier 多 Agent 拓扑，也不做 subagent」。而 harness/ 目录恰好就是 planner + research + analyst + reviewer 四个角色的流水线，且只接在 mock 和测试里、没进产品路径。

这反而让合流决策变得容易了：不是「两套实现选一套」的工程取舍，而是「要不要遵守自己已经签发的契约」。处理方案有三个：

方案成本面试效果结论
甲 · 归档 B：harness/ 整体移入 archive/ 或标记 experimental，canonical design 补一条「曾评估多角色流水线拓扑，因违反单一 runtime 原则与维护成本，决策不采用」 半天 「为什么砍掉第二个 loop」是绝佳的 scope discipline 故事——面试官最缺的就是见过「会做减法」的候选人 推荐
乙 · 叙事保留 B：把 B 改造成 A 之上的「确定性调度策略」（上次报告的 P0-1 完整合流） 1–2 周，有风险 故事最好（「两种拓扑在同一 runtime 上」），但秋招前做不完或做不扎实，反而引入新的讲不清楚的半成品 秋招后再做
丙 · 维持现状：两套并存，面试被问「为什么有两个 loop」时现场解释 0 减分项。一个讲不出取舍理由的 fork，会让面试官怀疑系统是不是你主导设计的 不可接受

选甲之后，「骨架→渲染」这个产品思路并没有丢——它在生产路径里已经由 PagePlan + Workbench 实现了（事件专项模块白名单、程序投影、模型不碰 HTML），那是讲渲染差异化的正当载体。harness/ 目录只是这个想法的一个没被接线的草稿。

02面试视角下，这个项目的资产盘点

秋招面试里，这个项目能打的牌按价值排序——你会发现好牌几乎全在 harness 层，缺的只有一张「验收牌」：

已经有的硬牌（直接可讲，且有测试背书）

  • 相位状态机 + 三个崩溃窗口的恢复语义：工具返回后、状态提交前崩溃怎么办——这是 agent loop 面试的「区分度题」，你们有测试显式覆盖。
  • effectively-once 的诚实表述：不吹 exactly-once，用稳定 action ID + 幂等 Reducer + 内容寻址缓存逼近——这种「知道边界在哪」的表述比吹概念更加分。
  • Context Compiler 四层结构 + 100 步 / 640 证据压力测试：有数字的上下文工程，全场没几个候选人拿得出。
  • Tool Runtime 的错误分类学：invalid_args 不重试 / timeout 有限重试 / auth 立即失败 / cancelled 不重试——成体系的失败模型。
  • 真实生产失败 → 确定性修复的完整故事：s3-live 批次 40 次模型请求 0 Finding → 链路诊断定位 → 首次研判闸门 → 发布保留段 → 机制回归。这是你们最有价值的一张牌：它同时展示了调试能力、权衡能力（不用 prompt 哀求模型，用程序约束）、和诚实（文档里写明「尚未用真实模型复跑，不能宣称改善」）。
  • 「模型提议、程序处置」的一贯立场：review 数字护栏、PagePlan 白名单渲染、Completion Gate——这条主线贯穿全项目，是你回答「agent 可靠性怎么保证」的总纲。

缺的一张牌：验收数字

现在被问「你的 agent 效果怎么样」，只能答「机制测试全过 + 一份 live 报告」，没有检索质量数字。面试官顺着问「你怎么知道搜索质量够好」就会露出「从未评测」的底。这就是质量工作在面试语境下的正确定位：不是产品打磨，是 harness 的验收工程——补齐「我怎么验证我的系统」这一环叙事。

03收尾路线：三个阶段，约 7–9 个工作日

D1–D2

阶段一 · 决策级合流（不重构）

  • harness/ 归档或标记 experimental；canonical design §4.1 补决策记录（试过、权衡过、不采用、原因）。
  • 统一叙事：唯一 harness = runtime AgentLoop；产品形态 = investigation 域 + PagePlan 渲染；README 与 implementation memory 同步。
  • 统一概念词汇表的「讲法」（不逐字重构代码）：面试口径里 Evidence/Finding/Review 只有一套，harness/ 里的重复概念作为「已归档探索」处理。

产出：系统 5 分钟能讲清，fork 变成减法故事。风险：零。

D3–D6

阶段二 · 质量基线（验收工程，不是产品优化）

  • 给两套冻结材料标「必中清单」（合格调查必须找到的文档/段落，半天人工）；
  • 跑 replay 出 recall@k / 无关证据比例 / 时间窗符合率 三个数字；
  • 在合成事件里埋 3–5 个对抗点（已知反方文档、已知更正、已知数字错误），验证反叙事命中与数字护栏拦截；
  • 把数字护栏从 finding 推广到 FinalSynthesis 逐句（如果 D6 前来得及；来不及就列为已知限制）。

产出：「我的 harness 检索召回 xx%、忠实性支持率 xx%、对抗点命中 x/5」——面试里可直接引用的验收数字。顺带把「placeholder 写着过去 30 天但解析器不识别空格」这种真 bug 修掉，又是一个小故事。

D7–D9

阶段三 · 面试资产收口

  • 用自己的话过一遍设计文档 §16 的 13 个问题（opinion_search_interview_guide/ 已有基础，补齐「为什么」而非「是什么」）；
  • 准备一张架构图 + 三个数字（压力测试、恢复窗口、质量基线）+ 一个失败故事（s3-live），这是 3 分钟电梯陈述的全部弹药；
  • 把「已知限制」练成加分项：主动讲「搜索约束未传导到 provider、来源独立性按 URL 计数是简化」——能讲清自己系统短板的人，比假装没有短板的人可信十倍。

秋招前明确不做（做了就是负资产）

  • ✗ 代码级 harness 合流重构（方案乙）——大改必引入新的讲不清楚的中间态；
  • ✗ 搜索管道大改（QueryPlan 对象、第二引擎、BM25 二次检索）——都是对的，但都改变系统行为，改完需要重新验证，时间不够；写进「下一步计划」讲给面试官听即可；
  • ✗ 全异步化、checkpoint 增量化——纯工程优化，面试零增益；
  • ✗ 任何「让报告看起来更好」的表面打磨——面试官不评报告排版，评你对系统的理解深度。

04最后一句话

这个项目对秋招的价值，不在于它还能加什么功能，而在于它已经有的深度能不能被你在 30 分钟内完整讲出来。思路不用转向，harness 定位不用动摇。收尾的正确姿势是三件事：砍掉那个违反自己契约的 fork（并把这个取舍讲成故事）、给 harness 补上验收数字（而不是给产品补功能）、把已有深度练成流畅的讲述。做完这三件，这就是一个完整、自洽、有真实失败与修复、有验收证据的 agent harness 项目——比 90% 的「玩具 demo + 华丽报告」型项目硬得多。

依据：canonical design §4.1 与 §16、前两轮分析（搜索质量评估、harness 设计评估）、harness/ 与 runtime/ 源码、opinion_search_interview_guide/ 既有资产。本路线假设可用时间 1–2 周；若面试时间更紧，阶段三优先于阶段二（讲述能力 > 新数字）。
