# OpinionSearch 事件现状页与搜索组织设计

本方案将主要交付物定义为“有时间边界、可核查、可继续探索的事件现状页”。报告是同一状态的阅读和导出视图。本文包含外部实现参考、指标口径、搜索策略、数据契约和交互设计；属于设计提案，不表示相关功能已经实现。

分析日期：2026-09-11。现阶段继续使用公开公告、文件、新闻、研究和评论文章，不增加社交平台采集、自动监测、多 Agent 或向量数据库。页面画布中的事件、材料与数值均为虚构交互样例。

## 1. 产品定位：把事件的信息状态作为主要交付物

研究报告型 Agent 通常把调查结果组织为一个有引用的长答案。事件现状产品需要保留更多并存结构：事件进展、讨论议题、归因观点、争议关系、机构回应、材料分布、剩余未知和版本变化。

产品可以定义为：

> 围绕指定事件，主动发现和核查公开材料，构建当前讨论结构，并用可追溯的交互页面呈现事件进展、主要议题、多方观点与回应。

“当前”必须落实为页面可见的时间信息：材料涵盖时间、此次搜索完成时间、最新可核实进展时间、缺失和延迟。按需更新的页面不能标为实时监测。

“没有唯一标准答案”适用于多方立场、价值取舍和不同解释；日期、数字、措施内容、归因等事实仍须核实。保留不同观点，不等于让事实错误与确证事实具有相同地位。

差异不能简单概括为“其他 Agent 只写报告，我们做页面”。已有系统也支持探索和可视化。实际要建立的能力是：可靠形成事件的结构化状态，用户点击图表后能追到材料，也能由一个缺口发起有目的的补查。

## 2. 外部参考与可借鉴机制

以下是公开文档和源码分析，不是这些产品的亲测效果或性能比较。各实现路线可借鉴机制，不需要迁移到它们的框架。

| 参考 | 公开机制 | 对本项目的启发 | 不直接照搬 |
|---|---|---|---|
| LangChain Open Deep Research | 范围整理、研究任务分解、检索与研究压缩、最终报告 [1] | 每个搜索任务要有明确研究目标与结果回收 | 多 Agent 编排、以写报告作为唯一结束目标 |
| GPT Researcher | 先生成研究问题，再搜集、整理来源并汇总 [2] | Query 应从任务计划派生，不能只围绕事件名换词 | 把文章摘要直接当图表统计单元 |
| STORM | 多视角提问、依据检索材料提出后续问题 [3] | 用主体、措施、阶段拓展搜索，主动发现遗漏 | 把模拟视角当作真实存在的公众意见 |
| Co-STORM | 用户参与引导探索，并以动态思维导图组织信息 [4] | 用户和系统共享一份可探索的事件结构 | 机械展示模型对话和内部推理 |
| Brandwatch / Talkwalker | 对过滤后的 mentions/documents 集合按时间、主题、情感等聚合 [5–7] | 图表先定义材料集合与分母，再进行计数与下钻 | 用网页搜索结果冒充全量声量或人口态度 |

由这些参考推导出的方案是：保留搜索 Agent 的动态调查能力，增加舆情分析需要的数据集、分类、统计和交互层。图表由已提交的数据计算，模型负责提议归类和解释，不直接编写百分比。

## 3. 一个现状页应回答哪些问题

| 页面区域 | 用户想知道 | 最小数据要求 | 初版表现 |
|---|---|---|---|
| 事件快照 | 现在到底发生到哪一步？ | 已核查的关键事实、最新材料、截止时间 | 2–4 条状态摘要和局部限制 |
| 主要讨论议题 | 公开材料主要围绕什么讨论？ | 去重材料与多标签议题归属 | 可点击的横向条形图 |
| 多方观点 | 针对某个具体问题有哪些立场？ | 明确对象、主体、归因原文、立场分类 | 议题内观点分布与原话 |
| 核心争议 | 分歧究竟发生在哪里？ | 同一问题下可比较的主张与依据 | 对照卡或主体×问题矩阵 |
| 回应覆盖 | 机构答了什么、没答什么？ | 诉求/问题与回应的对应关系 | 已覆盖、部分覆盖、未覆盖、未知 |
| 典型材料 | 哪些文章最能解释这些观点？ | 代表性选择理由、日期、来源关系 | 每个观点的典型文章卡 |
| 进展与变化 | 新材料改变了什么？ | 版本化事件时间、判断与材料 | 事件时间线和版本差异 |
| 样本与限制 | 这些图到底统计了什么？ | corpus、纳入/排除规则、失败、分母 | 图表旁摘要及可展开方法说明 |

“事实问题得到解决”“机构作出回应”“被影响的人满意”分别存储和呈现，不相互推出。

页面应该允许部分区域先可用：事实区已有材料时可展示；观点还在分类时显示待核查；没有可比较时间窗口时不画趋势。不能用空白或填满的假图表制造完成感。

## 4. 饼图的正确建模

### 4.1 必须先选择统计单元

以下数值都可能计算，但含义不同，不能混用：

- 文章比例：多少篇纳入材料包含某类表达。
- 归因表达比例：去重后的观点表达中，多少属于某个类别。
- 发表主体比例：被观察到的可辨识主体中，多少表达某种态度。
- 互动量份额：具有同口径互动量的材料中，某类材料占多少互动。
- 人口态度比例：特定人群中多少人持某种态度，需要另外的抽样或调查依据。

本项目首版最适合提供前两种，并标明“本轮收集材料”。不能从前两种推出后两种，不能把文章中引用的居民观点等同于整篇文章作者的立场。

### 4.2 两种图表，承担不同工作

**议题涉及率：用条形图。**

一个文本可能同时涉及价格、实施时间与信息透明度。对每个议题计数包含该议题的去重材料，每篇在同一议题只计一次。各议题百分比之和可以超过 100%，因此不构成一个可直接画饼图的分割。

**单个议题下的立场构成：可以用饼图/环图。**

固定具体对象，例如“是否支持将工作日末班车提前到 22:00”，每个纳入表达单元只归入一个互斥类别：支持、反对、有条件支持、混合、无法判断。主体的诉求理由另设多标签字段。

```text
某类别份额 = 该类别纳入表达单元数 / 当前选定议题的全部纳入表达单元数
```

“无法判断”包含在分母和图中；图表同时显示各项数量与总数。样本不足或多数无法判断时优先显示数量和未知，不通过隐藏未知放大确定感。

类别未必只能用支持/反对。对“如何处理计费争议”，也可采用互斥的主要处理诉求，但必须有“多种诉求”和“无法归类”，并说明主要诉求的判定规则。多标签观点主题仍用条形图。

### 4.3 归因表达单元

建议保存：

```text
ObservationUnit
  id, corpus_version, issue_id, stance_target
  speaker_id?, speaker_role, attribution_kind
  source_version_id, excerpt_id, original_origin_id?
  stance_label, reasons[], classification_status
  expressed_at?, published_at?, retrieved_at
  duplicate_cluster_id?, membership_reason
  classifier_version, review_record
```

归因必须能追到原文。同一段原话被多个网站转载，观点内容统计只计同一原始表达一次；另外保留其传播记录。无法识别原始出处时，不要武断合并所有相似观点，也不能断言它们互相独立。

同一主体对不同措施或不同时点可能有不同态度，不能永久贴为“支持者”。匿名受访者也不能跨文章凭相似描述强行合并成同一人。

### 4.4 一张图的统计契约

```text
MetricSnapshot
  metric_id, definition_version, corpus_version, taxonomy_version
  issue_id?, target?, time_window, source_filters
  unit_of_analysis, dedup_policy
  numerator_members_by_category, denominator_members
  unknown_count, excluded_count, pending_count
  query_policy_version, membership_hash
  generated_at, freshness, comparability, limitations
```

图表、典型文章、数量与下载应来自同一 snapshot。点击一个扇区必须能取出其成员，计数等于实际成员数。分类修正后生成新统计版本；不能在保留旧版本百分比的同时更换其底层原文。

注意“成员齐全可审计”和“分类语义正确”是两个要求。还要抽查模型误分、归因错误、重复归并错误和对 unknown 的滥用。

## 5. “最火”“激烈”“多方”应拆成哪些指标

| 想表达的含义 | 可实现指标 | 所需材料 | 不应推出的结论 |
|---|---|---|---|
| 哪个议题被频繁提到 | 当前 corpus 的议题涉及材料数/率 | 稳定去重单位与议题分类 | 全网最热 |
| 哪个观点比较常见 | 指定议题的表达数和构成 | 归因表达单元 | 多少公众支持 |
| 哪个观点在传播 | 原始表达对应的转载/引用出现数 | 内容关系与出处链 | 独立认可人数 |
| 哪个观点获得互动 | 同平台、同口径的互动量 | 可取得的互动字段及采样时间 | 跨平台同等影响力或真实受众态度 |
| 哪个议题在上升 | 可比较窗口中的材料发生数变化 | 相同采集规则、发布日期、完整度说明 | 不同搜索力度下的热度上升 |
| 分歧集中在哪 | 同对象下相冲突/不同取舍的主张 | 可比较观点及理由、主体覆盖 | 文字负面即讨论激烈 |
| 哪个回应充分 | 对明确问题组成部分的覆盖 | 问题—回应证据关系 | 已解决、已满意 |

首版推荐把“最火观点”呈现为“本轮材料中的主要观点”，把“讨论最激烈”呈现为“核心分歧”。不是删除产品价值，而是选用数据确实能支持的指标。

若后续获得稳定、授权的监测数据，可增设平台内互动趋势；这属于数据能力扩展，不能通过替换标题让当前 Brave/Jina 获得该能力。

不建议首版发布一个混合负面程度、数量和互动量的“舆情风险 87 分”。先分别展示变量，保留可解释性。

## 6. 搜索的组织：两类任务，共享一套执行器

这是本方案最重要的搜索改造。

### 6.1 基础观察任务：形成可描述的样本

基于事件身份、别名、时间窗口、语言和来源类型，生成固定且记录版本的基础 query 组。尽可能使用不预设立场的词，例如“公告”“实施”“采访”“评论”“后续”，并记录结果排序、分页和纳入规则。

基础 corpus 的目标是稳定、透明地描述本轮获取到的材料，不是宣称随机抽样或全量采集。固定 query 仍会受到索引、排名、日期识别和读取成功率影响，不能据此计算公众态度的抽样误差。

### 6.2 自适应调查任务：解释与补全

依据已发现内容，针对缺口搜索：新主体、反证、原始出处、相冲突的统计口径、后续修正、机构回应和用户指出的遗漏。

自适应任务负责提高理解深度。它主动寻找缺失观点，因此会改变所见材料的构成。

**关键规则：定向补查结果不能静默进入已展示饼图的原分母。**

例如原 corpus 有 12 条观点，用户点击反对类别并要求补查，系统找到 8 条新的反对表达。可以显示“补查发现 8 条相关表达”，不应直接说“反对比例从 42% 升至 65%，舆情恶化”。这也可能只是采集方向变了。

定向材料可以在下一轮整体 corpus 重建时纳入，但需要新的 query/corpus 版本、纳入解释和可比性标记。用户提供材料也应保留发现渠道，默认用于证据补查而非悄悄改变统计口径。

两类任务不是两个 Agent，也不需要两套 Runtime。只是在 SearchTask 中明确采集目的和统计纳入政策。

### 6.3 初次搜索覆盖矩阵

按事件实际需要选择矩阵单元，不执行所有维度的笛卡尔积：

| 维度 | 示例 | 搜索目的 |
|---|---|---|
| 身份 | 事件名、机构名、地点、措施别名 | 排除同名不同事件 |
| 阶段 | 初始公告、争议出现、回应、实施、修订 | 区分背景与当前状态 |
| 来源角色 | 原始文件、现场采访、评论、研究 | 避免单一材料类型 |
| 主体 | 执行机构、受影响者、专家、其他利益方 | 检查主体缺失，身份由材料证实 |
| 议题 | 可及性、成本、程序、透明度等 | 动态发现，不强行套固定主题 |
| 证据关系 | 原始出处、转述、支持、反驳、回应 | 建立可核查主张关系 |

例如公交事件首先检索“城市+线路+调整公告”，确认身份；随后根据公告与采访发现的问题去搜工作日服务、替代接驳、运营方后续说明。不能一开始就把假设的争议类别当作已存在观点。

### 6.4 排序与预算

采用可解释的优先队列：身份错误和关键事实冲突优先；其次是用户重点、重要主体缺失、回应空白；再是观点多样性和背景补充。

每项任务记录：目标缺口、预期可观察结果、query 或本地检索条件、来源/时间约束、预算成本、完成结果、统计纳入政策。

无新增结果不等于调查无价值：确认原网页未变化可支持时效性判断；找到一篇原始文件可能比多找十篇转载更有价值。任务收益按它改变了什么理解记录，不用 URL 数量作为唯一进度。

当前默认预算为 20 次搜索、24 次 Reader 和 80 次模型请求，不能承诺海量舆情普查。首版应交付精读后的有限公开材料状态页。更大的样本需要另行设计数据取得与预算，而非只增加搜索提示词长度。

Brave 的 count/offset 有界，分页可能重叠；freshness 是基于网页相关日期的过滤，而非事实发生时间认证。因此获取后仍须核对元数据和正文。[8]

## 7. 核心 loop 的改变

保留 `search/read/retrieve/reflect/review/finish` 和现有事务恢复骨架。新增领域上的搜索计划、材料集合、观点单元和指标投影即可；不要把每个页面控件变成一种 Agent action。

```text
读取用户目标、范围与上次发布快照
  → 形成事件身份和初始搜索计划
  → 执行基础观察任务并保存正文
  → 判相关、归并转载、提取议题与归因表达
  → 建立事件、观点、回应和冲突关系
  → 检查事实、归因、分类及覆盖缺口
  → 选择下一项搜索/读取/本地重查工作
  → 提交已验证的领域变化
  → 程序计算指标，发布一致的阶段性页面快照
  → 有重要缺口则继续；可交付或预算受限则结束本轮
```

模型职责：提议问题、query、议题归类、归因和观点分类、争议解释、进一步调查工作。

程序职责：身份与引用约束、预算、样本纳入、去重策略执行、计数、版本、取消、恢复、统计口径、页面可见状态。

只要当前材料已经形成可审查的事实/观点，就可以发布阶段性内容。发布须原子关联语料、分类、指标与证据的版本，避免刷新时出现图表和列表不一致。

结束条件包括：事件身份明确；必答问题已处置；可获得的主要主体与材料类型得到检查；重要冲突有解释或未知；关键断言与归因通过审查；样本统计可重算；重大未完成事项明确标注。

某个议题只有一方材料时如实显示，不能为了页面对称制造“另一方”。搜索空间仍可能有未发现材料，因此“本轮可交付”不等于穷尽所有观点。

## 8. 前端画布：事件现状、观点、材料共享一个上下文

### 8.1 页面结构

顶部：事件身份、材料窗口、本轮截止、最新可核实进展、更新状态。

主区依次为：当前事件摘要；议题分布与选中议题的多方观点；争议与回应覆盖；典型材料；新进展与版本变化。

在桌面可以把议题选择、分布图、材料列表组成相邻区域；手机按阅读顺序堆叠。证据详情在局部展开，避免用户来回切换丢失议题和时间上下文。

每个区块显示自己的状态：有材料支持、分类待核查、材料不足、查找受限、未重新评估。整体 completed 不能覆盖某个区块的未知。

### 8.2 三种重要联动

1. 点击议题 → 更新该议题的观点分类、争议解释、回应覆盖和材料列表。
2. 点击扇区 → 展示分子对应的全部纳入表达，以及各自归因原文；保留整个议题的分母说明。
3. 点击补查 → 发起明确的调查任务，界面显示已收到、已生效、查找中、发现材料或未解决，不伪装成筛选操作。

“典型文章”选择依据包括与类别中心观点的匹配、归因清楚、原始出处、时效、可读性；同时展示反例或细分意见，避免每类只挑最极端的一篇。可以按典型度和时间分别排序，不让“典型”暗示点击量最高。

### 8.3 筛选与调查要明确区分

时间、来源、议题、立场筛选默认只操作已保存快照，不发出远端请求。筛选后各图和材料列表共享同一条件，显示匹配数量和分母。

“继续搜索”“补充新进展”“核查这个观点”才调用 Agent。用户点击不会自动消耗预算。后台仍保持已确认的按需更新模式，不增加定时自动监测。

用户修正分类时记录为待处理反馈；经校验和复核形成新分类版本。允许修正映射，不允许用认可按钮把判断变成事实。

## 9. 时间与变化：避免把搜索过程画成事件趋势

至少分别保存：事实发生时间、观点表达时间（可获得时）、材料发布/更新时间、首次发现/本次获取时间、调查截止时间。

“今天新增找到 20 篇”可能是今天扩大了搜索范围，不能画成“今天讨论量上涨”。有可靠发布日期的材料可按发布日期分桶，未知日期另列，但只描述该 corpus 中的分布。

在版本比较中至少区分：

- 新发生且有材料支持的事件进展。
- 新发布的材料，但所述事实可能更早。
- 首次发现的旧材料。
- 已知网页内容发生变化，确切修改时间可能未知。
- 分类、去重、query 或统计定义发生变化。
- 单纯因样本成员变化导致的比例变化。

若要比较“观点变化”，优先比较同一主体针对同一措施的前后表达并展示证据。若比较比例，应提供同口径窗口；口径不一致则显示不可直接比较，不能做无说明的上升箭头。

## 10. 数据与现有代码的衔接

建议在现有 domain/investigation 基础上补充这些概念，不建立独立的第二套状态源：

- EventProfile：身份、范围、别名、重要时间与机构。
- SearchTask / SearchPlan：基础或自适应任务、缺口、参数、结果、纳入政策。
- CorpusSnapshot：固定成员、来源筛选、发现渠道、去重与版本。
- Topic：议题语义、分类定义、示例和版本。
- ObservationUnit：针对具体对象的归因表达。
- SourceRelation：重复、引用、转述、原始出处及关系证据。
- ResponseRelation：问题组成部分、回应证据、覆盖、遗漏与理由。
- MetricSnapshot：程序聚合值、分子分母成员和定义。
- LandscapeSnapshot：事件事实、议题/观点、指标、回应、局部状态、整体截止与版本。

现有 Evidence 与 SourceVersion 继续承载正文定位；Finding 继续承载可核查判断。不要直接对 Findings 的数量画观点饼图：同一表达可能被拆成多个 findings，一条 finding 也可能是事实或模型解释。

ReportVersion 和 LandscapeSnapshot 引用同一已发布状态，Markdown 从中生成。页面成为主要消费方式，报告仍保留审计和离线阅读价值。

SQLite FTS5 继续支持全文重查；图表计数可由本地确定性聚合实现。现在不需要图数据库或向量数据库来支持这些概念。

## 11. 最小可验证实现顺序

### 第一轮：先验证一个议题、一张图的真实性

选一个实际事件，保留 15–30 篇可读取的公开材料作为目标规模示例；若材料不足则用实际数量，不强行凑数。固定一个具体措施和议题，人工复核表达单元、归因、分类和去重。

完成“议题选择 → 分布图 → 扇区 → 成员 → 原文”的链路。真实数据缺失时只做明确标注的交互样例，不宣称已进行舆情测量。

### 第二轮：让页面缺口真正驱动搜索

接入 SearchTask 和观察/调查两种目的；页面补查入口创建具体缺口任务。检验缺少机构回应时确实发起机构/事件后续查询，用户聚焦某一观点时保持原统计快照不被静默重写。

### 第三轮：发布和更新事件快照

建立时间、语料、分类、指标版本关联，发布局部可用状态；支持新材料与旧判断比较。发生读取失败或 provider 故障时保持旧快照可读，显示受限状态。

### 第四轮：增加样本趋势与更广来源

只有可比采集窗口和日期质量达到要求才引入趋势图；需要互动量或更广泛平台分布时另行评估数据取得和预算，不把它塞进第一轮。

## 12. 验收指标

### 12.1 数据正确性

- 每个图表成员能追到 source version 和原文定位；完整性 100%。
- 每个扇区计数等于下钻成员数量；同一单选分类的总和等于分母。
- 转载同一表达不使观点内容比例重复增加；传播数量与观点单元数分别计量。
- 多议题材料不被强制单选；unknown 不被静默排除。
- 来源独立性未知时不当作独立证据。
- 变更分类或 dedup policy 后，旧快照仍能按原规则重现。

### 12.2 搜索质量

- 在有人工标注的保留材料上检查重要议题召回、主体覆盖、归因和观点分类。
- 检查假冲突：是否把不同日期、对象、口径的说法当成同一事实的对立。
- 检查漏冲突：是否把实质不同的观点合并为一条“大家关注”。
- 记录每轮搜索带来的新原始材料、新主体、新议题、已解决缺口和重复率；不只报调用数。
- 观察类与定向类材料纳入规则可验证；定向搜索不会造成无标记比例跳变。
- 真实联网发现测试与固定材料语义测试分开，模型自评不替代人工评估。

### 12.3 用户理解与交互

- 用户能说明图中的百分比代表材料表达而非公众人数。
- 用户能在少量操作内找到一个观点的原始依据。
- 用户能识别当前最重要分歧和未覆盖回应。
- 用户能区分筛选已有材料与发起新的搜索。
- 用户补充一个缺口后，能看到调查方向改变及相应证据结果。
- 无资料时页面诚实显示不足，不展示空数据推导的趋势和风险分。

## 13. 推荐的下一项产品决策

先确认事件现状页的三个核心对象：**议题、观点、依据**。对每个对象定义可见字段和用户操作；再确认图表统计单元及语料纳入政策。

第一版页面采用：事件快照 + 议题涉及率条形图 + 选中议题的立场环图 + 争议/回应对照 + 可下钻典型材料。趋势与互动量暂不进入主界面。搜索计划围绕这些对象的缺口组织，避免为填满所有图表而搜集不相关材料。

这样，前端画布不是事后的包装。它会暴露数据缺口和决策缺口，并成为搜索 Agent 下一步调查的入口。
