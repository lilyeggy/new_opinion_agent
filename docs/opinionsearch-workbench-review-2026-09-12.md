## 1. 当前判断

**新版已经有可用的调查与证据工作台骨架，工程机制和视觉样式都比上一版完善；当前最需要补强的是“怎样形成当前事件研判”，以及“页面承诺的交互是否真的影响调查”。**

现阶段的主要缺口不是组件数量，而是三条链没有完全接通：

1. **调查问题 → 搜索资源分配 → 多方材料 → 问题完成判断。** 已经能按问题搜索，但缺少对子问题、缺失主体和材料独立性的充分约束；“已有材料回答”有时掩盖重要未知。
2. **事件侧重点 → 专项内容结构 → 页面。** 当前主要切换模块名称，同一批通用 findings 会填进不同模块，尚未形成真正的新旧规则对照、退费路径或整改进展结构。
3. **用户点击 → 正确证据/定向补查 → 状态恢复。** 引用错选、导出链接失效、定向选择未进入模型上下文、刷新丢失视图等问题仍存在。

建议保留已有架构，优先修正这些链路，再调整页面层次。继续只改圆角、阴影、间距，不能解决报告缺少洞察的问题。

## 4. 当前实际 Agent loop 与质量瓶颈

### 4.1 它现在如何工作

当前链路可概括为：

```text
Web 请求与必要澄清
  → Manager 构造 request、必答问题、调查计划和初始 State
  → Compiler 汇集任务、问题、判断、搜索覆盖、预算、候选、来源和证据
  → 模型选择下一步 Decision
      search：绑定 issue / purpose / target_gap 搜索
      read：读取已发现候选
      retrieve：重新检索已保存正文
      reflect：形成判断、回应分析与问题处置
      review：独立调用检查判断与证据
      finish：选择已审查判断作为核心结论
  → Validator / Resolver / 工具 / Processor / Delta / Reducer
  → checkpoint 与阶段投影
  → completion 判定 completed 或 partial
  → report.json / report.md
  → workbench 投影与在线/HTML 呈现
```

这是可继续深化的结构。主要问题发生在领域规则与投影之间，不需要换通用 Runtime 或增加多 Agent。

### 4.2 一次真实运行揭示了什么

保存的 `014aa9b7…` 报告：

| 事件 | 重庆燃气费计费争议 |
| 终态 | completed |
| 问题 / 活跃判断 / 核心结论 | 5 / 10 / 8 |
| 来源 / 证据 | 13 / 67 |
| 搜索 / Reader / 模型请求 | 20 / 20 / 61 |
| 读取失败 | 7，其中有多份公告 PDF |
| 搜索目的 | original 9、followup 9、official_response 2 |
| positions / independent 搜索 | 本次记录中均为 0 |

优点是保留了“公司称”“拟处罚”“尚未取得验收结论”等限定，也没有把 ESG 满意度直接当成全体公众态度。

但这轮调查明显集中在机构通报、企业披露和整改后续。问题包含用户、企业、监管部门各自说法，最终活跃判断却没有形成单独的受影响用户主张条目。**没有反驳证据本身不是错误；缺少针对缺失视角的查找或明确处置，才是需要补强的地方。** 不应为了多方展示而制造对立意见。

该运行使用的预算上限是 2,400 秒 / 120 次模型请求，实际约 1,276 秒。代码默认仍是 1,200 秒 / 80 次模型请求。因此它不能作为“默认 20 分钟预算下已稳定通过”的证据。比较改进前后效果时必须冻结实际配置。

### 4.3 为什么现有结果仍像材料汇编

`finish` 只能从通过审查的 findings 中选择核心结论，这是一个有价值的防幻觉约束。但当前 finding 仍经常是一整段通报摘要，包含多个数字、多个动作和多个时点。选出八段摘要，并不自动成为“当前状态研判”。

需要先形成可核验的内容层：本轮最重要变化、哪些承诺已落实、哪些只到回应层、关键矛盾、重要未知。短摘要可以由已审查判断压缩得来，但新增的概括同样要绑定判断与引用并接受检查，不能绕过现有审查直接生成新的确定性结论。

## 5. 剩余问题与修复验收

优先级：P0 为影响证据可信度或核心调查意图的缺口；P1 为主流程失效、内容结构或关键体验问题；P2 为后续完善。这里的优先级表示修复顺序，不等同于安全事故等级。

### F01 · P1：三个导出入口实际没有链接

**浏览器已复现。** 水费工作台顶部“打开静态页”“下载 HTML”“下载 Markdown”的 DOM `href` 均为 null；“版本比较”的 hash 链接有效。

原因：`web/assets/ui.js:28` 的 `el()` 只接受绝对 HTTP(S) URL 或 hash；`api.js` 返回的是 `/api/...` 相对路径。修复 hash 支持没有同时解决同源路径。

验收：从真实工作台点击三个入口，分别打开静态报告、获得 HTML 下载和 Markdown 下载；核对 run 与 snapshot。不能以直接请求导出接口成功代替点击验收。修复需保留危险协议防护，并明确允许的同源路径，不可简单接受所有字符串。

### F02 · P0：点击第二条引用却回到第一条，存在错误兜底

**浏览器已复现。** 报道对照 → 第一篇公告 → 点击 `[2]` → 右栏显示“正文引用角标 `[1]`”，定位仍为 `0:46`。

原因：`workbench.js:321` 的整个 article 绑定首条引用；内部引用按钮点击继续冒泡，父级再次选择第一条。`paintInspector()` 又使用 `find(selected) || citations[0]`，选中无引用材料时可能显示无关的第一条证据。

验收：同一篇文章的每个引用独立定位；无证据材料显示该材料未形成引用的状态；无效选中项不得回退到另一条原文。材料点击也应提供键盘可操作入口，不能只让 article 响应鼠标。

### F03 · P0：专项模块尚未实现内容适配，发布状态过宽

**源码与内存构造验证。** `presentation.py:41–74` 对每个 facet 调用同一个 `_facet_items(findings_by_issue)`，读取全部问题的活跃判断。`confirmed_profile()` 没有利用传入 issues 建立专项问题绑定。

因此，`rule-comparison` 与 `billing-remedy` 可以拥有完全相同的 items，只换标题和解释。终态存在任意 active finding 即标为 ready，不要求专项字段齐备或判断通过审查。本轮构造“公交判断 + 两个 facets + unreviewed finding”，两个模块内容一致且均 ready。

与设计指南 §3.3/3.4 的偏差：ready 原本要求通过模块发布检查；新旧规则、补救安排应有不同字段及证据；总览最多三个重点。当前前端 `overviewView()` 还遍历所有 facet 模块，没有使用已计算的 highlights 上限。

修复方向：先做两类真实结构。例如规则模块包含旧值、新值、适用对象、生效时间与各自证据；费用模块包含计费口径、适用范围、办理路径、时限、实际执行证据。问题/判断按相关性绑定，未知值保留，不能用无关事实填满卡片。

验收：同一事件有两个 facets 时，内容不能仅改标题；计费证据不足不能因已有公交事实变成 ready；partial 中未经审查的判断不能借专项模块获得“可发布”的含义；总览实际最多显示三个重点。

### F04 · P0：定向补查选择只保存，没有进入调查决策

**源码确认，未新建 live run。** `manager.py:254` 验证 issue_ids / finding_ids 并保存到草稿 followup，但 `_investigate()` 和 `Compiler.compile()` 不消费这一选择。传入 focus 会影响 request；只勾选问题、不填写 focus 时，选中目标不会进入模型上下文。

更新当前还会重开全部旧问题、将全部旧判断置为 inactive，而非区分用户指定目标及其依赖。profile 继承已经修复，但 aliases 仍来自新建的默认 PlanProposal，存在丢失旧别名的问题。

右栏“补查这个问题”又调用无参 `onUpdate()`，没有传入当前问题。`app.js:368` 每次点击提交重新生成 client_request_id，网络响应丢失后再次提交也无法复用同一逻辑请求的 key。

修复方向：让选中问题、判断、缺口成为 State/编译上下文里的显式更新意图；保留必要依赖检查，但不无条件全量重做。幂等键在一次提交意图生命周期内稳定保存。

验收：同一父版只选择问题 A 与只选择 B，编译上下文和首轮调查目标可区分；选中 finding 映射到对应问题与证据；旧别名保留；响应丢失重试复用同一子 run。不能只断言 followup 已写进 draft。

### F05 · P0：正文验证失败后，静态导出仍可能显示为可核对原文

**源码与构造验证。** `manager.py:480` 在正文读取或 `verify_evidence` 失败时跳过该 context；`export.py:350` 和 `:380` 只要 report 中存在 evidence，仍会用其 excerpt 渲染高亮原文。验证失败、未检查与上下文恰好为空被混成同一种 `{}`。

构造结果：传入空的已验证上下文映射，引用区域仍生成 `<mark>`，未出现“缺少可核对的保存正文”。这里不是说 excerpt 一定错误，而是导出丢失了“当前无法核验归档正文”的状态。在线引用附录也直接消费 report.evidence；右栏读取失败与附录成功展示可能不一致。

验收：在隔离副本中让正文缺失、引用范围错误、正文与 excerpt 不一致，在线与导出均在该引用位置说明不可核验；可以保留“此前提取的摘录”，但必须区分其性质。正常原文验证仍通过，旧版本不得引用别版正文。

### F06 · P0：整题 answered 与多子问题完成之间缺少约束

**源码与保存报告共同支持。** `engine.py:114` 对 answered/disputed 主要检查 evidence_ids 非空；completion 检查 issue 状态、活跃判断和审查结果，没有逐项检查复合问题的子要求。

真实报告中，“用户范围、退费标准、执行时间”被放在同一必答问题内，整题 answered，但 note 和 finding.uncovered 同时说明这些要素缺失。“用户、企业、监管各自归因”问题也以官方归因链为主要回答。

不是要求有未知就一律失败。恰当未知本身可以完成调查，但必须有子要求的明确处置、查找范围和失败影响；不能靠把整题标为 answered 绕过 unavailable 对 partial 的约束。

另一个审查边界：一条真实 review 明确写“个别措辞……在摘录中未直接出现，但不影响核心事实成立”，仍给 supported。这说明长段复合 finding 会让审查把局部无支持内容一起放行。

验收：复合问题的每项要求都有 answered/disputed/not_found/unavailable 的处置；关键未知显式上浮；包含一个无依据数字或措施的长句必须修订或降级；不得仅以整段“大意正确”发布。

### F07 · P1：当前搜索缺少可解释的覆盖分配，来源关系停留在未核实

`Compiler` 已提供搜索覆盖与 target_gap，值得保留。但真实样本的 20 次搜索都分配给 original、followup、official_response，未单独安排 positions 或 independent；也未形成用户观点条目。

同时，review 已识别某几条证据来自“同源重复文本”，但 report 的来源关系仍全部未核实。精确正文哈希去重不能替代转载、摘编、转述关系。当前页面“来源关系未核实”是诚实的，但分析能力尚未闭环。

修复方向：每个必答问题维护已覆盖/缺失主体、证据类型、失败原因和下一次查找的价值。不是每个事件机械执行固定配额，而是明确说明为何某方向必要、已经充分或无法取得。关系可由模型提议并给出原文依据，再由程序约束 ID 和引用链。

验收：需要多方归因的事件能找到并保留各方表达，或解释哪一方在何范围内未找到；重复通报不能作为多个独立支持；无法打开原始 PDF 时记录失败影响，不把转载数量当作取证深度。

### F08 · P1：页面每个视图都被长摘要阻挡，窄屏尤其明显

`workbench.js:51` 在动态 contentBox 之前固定渲染 heading 和 summary。切换“报道对照”“议题与核查”只替换下面的 contentBox。因此每个视图都会先经过同一段长摘要，材料和争议正文被推到下方。

真实样本的八条核心结论接近两千字。即使 CSS 更精致，把它们永久放在每个视图前面，仍会让工作台像长报告顶部外挂导航。

本轮 390px 视口检查：无横向溢出，但正文可用宽度只有 270px；摘要起点约 y=940；证据栏约 y=1357；总览业务内容约 y=2008。无溢出不等于好用。`body.wide main` 同时影响外层与嵌套 main，叠加 padding；≤850px 将不可折叠的证据栏前置，也增加正文到达成本。

验收：窄屏首屏能识别事件、状态和下一步；切换视图能立即到达相应内容；证据按需展开并能返回触发位置；内外容器职责明确。不要只验证 scrollWidth。

### F09 · P1：报道“对照”仍是来源列表，证据关系没有指出对应判断

材料卡当前主要是角色、日期、来源关系、标题和引用。没有该文主要说法、表达主体、回应哪个问题、与其他材料差异。因此“同一事件，不同报道角度”的标题超出了实际信息组织程度。

证据栏多次显示“支持一条已提交判断”，但不展示是哪条判断、属于哪个问题、是否仍有效；relations API 当前还包含 inactive finding 的关系，前端没有区分历史判断。

验收：每个重要材料能展示一句受约束的内容摘要、表达主体与相关议题；点击支持关系定位具体判断；历史关系有明确标识；价值诉求与事实断言采用不同说明。可以先做并列主张卡，不必立即增加图表。

### F10 · P1：刷新恢复了调查 ID，没有恢复用户阅读位置

**浏览器已复现。** 报道对照页刷新后回到事件总览。`state` 固定初始化为 overview，`go()` 不写入路由；日期、议题、类型筛选与选中引用也仅存在内存中。

“恢复同一 run”与“恢复同一工作视图”应分开验收。当前用户点击浏览器返回，也不能按刚才的视图切换顺序导航。

验收：路由保存 view / issue / date / evidence 等非敏感阅读状态，并绑定 run/snapshot；刷新恢复；无效或跨版本引用显示提示，不选另一条证据。浏览器本地状态不替代服务端调查状态。

### F11 · P1：版本快照标识与度量下钻还有契约缺口

**两类确定性问题。**

1. `workbench_revision()` 仅依据 run_id、cutoff、state_revision。将同一 report 的 status 改为 partial，投影内容变化但 ID 不变。`Manager.workbench()` 在每次 GET 时按当前代码重建终态投影，发布时没有固定保存终态 workbench。因此历史报告 JSON 虽未覆盖，旧页面内容/排序仍可能随投影策略变化而改变，原 snapshot_id 无法完整识别这一变化。
2. 发布分布按 URL 计文档，coverage 列表按 SourceVersion 展示。构造同 URL 两个同日正文版本，柱子 count=1，但成员含两个版本，日期筛选可能展示两条材料。新增 issue_involvement 的计数一致性没有解决发布分布这一另一口径。

此外 `generated_at=report.cutoff`，而 State.cutoff 在初始化时设置；真实样本之后运行了约 21 分钟。它不能同时准确代表开始、取证截止与报告生成时间。

验收：明确报告内容版本、投影策略版本、页面生成时间；旧版内容稳定或产生新投影 ID；同一快照的图表和下钻按同一计数单位呈现，正文版本可在文档内部展开；严格区分开始时间、观察/查找截止时间、材料日期与报告发布时间。

### F12 · P1：演示与验收的语义基线仍然不足

**浏览器与源码已确认。** 最新水费示例展示公交末班车结论，不是旧 run 遗留现象。`offline.py` 的 PAGES / OfflineModel 固定为公交，仅 offline_plan 按词切换 facet。

这可以测试通用管线，却不能证明“两类事件自然长出不同内容”。`test_event_facets.py` 主要断言模块类型；`test_targeted_followup.py` 主要断言存储；导出测试主要检查生成字符串。它们恰好漏掉了内容错配、补查未消费、入口不可点等问题。

10 案例 registry 当前仍全部 blocked、materials 为空、无人工标注。实现记录已承认质量门槛未达标，应保留这个边界。

另需收紧“用户永远可以往前走”的产品解释：连续澄清或回答“不知道”后，当前通过 prompt 要求模型选最常见理解；若模型仍返回 clarification，manager 仍接受它。自动继续并非程序保证。假设说明主要在报告限制里，进度页没有足够醒目的对象纠正入口。匿名事件若选错对象，会得到一份引用完整但回答错题的报告。

验收：演示只开放有对应材料的案例，或明确提示任意输入仍演示固定案例；至少两套互不混用的完整材料与预期。澄清兜底显示“本次按 X 调查，可改正”，不虚构确定身份；超限行为有确定性处理，不能只靠提示词。

## 6. 前端下一轮应怎样调整

### 6.1 保留框架，重新安排信息层次

以设计参考 [professional-event-workbench.reference.html](design/professional-event-workbench.reference.html) 和 [实施指南](opinionsearch-adaptive-workbench-implementation-plan-2026-09-11.md) 为依据，保留稳定导航与证据核查能力，不迁移框架。

| 页面区域 | 应优先展示 | 当前调整重点 |
|---|---|---|
| 事件头部 | 明确对象、调查截至何时、结果状态、最重要限制 | 隐藏 facet 英文枚举和内部快照哈希；合并重复品牌栏；区分“生成时间”和“查找截止” |
| 事件总览 | 一条当前判断、2–3 个关键变化/未决问题 | 八段长结论改为分层阅读；其余结论放在相应议题中 |
| 本事件专项 | 真正的新旧规则、费用路径或整改状态 | 先补结构化数据和证据，不用通用判断堆成“专项卡” |
| 报道对照 | 同一问题下不同主体的说法及依据 | 每张卡写清主要说法与差异；支持切换相关问题 |
| 议题与核查 | 子要求、已知、争议、回应覆盖、未知 | 避免整题绿色 answered 掩盖缺口；补查按钮对应具体缺口 |
| 证据面板 | 选中判断、原文高亮、来源与时间、支持/冲突理由 | 正确定位、可关闭、可返回，异常在对应引用处显示 |
| 更新与比较 | 本次变化、变化依据、未复评事项 | 同一事件归组，版本可以切换；区分新发现旧文与新进展 |
| 历史首页 | 事件入口、最近状态、版本数、筛选 | 当前重复事件按 run 铺开，很难辨别版本关系；增加事件级分组与模式筛选 |

### 6.2 图表优先级

目前不建议优先做“支持/反对饼图”。当前缺少稳定的观点编码、转载归并和样本分母，真实样本的搜索还集中在机构材料。此时做比例图，会把发现策略造成的材料分布误读为舆情分布。

先做两种可解释的可视化：

1. 事件节点与材料发布时间分开展示；日期缺失明确列出，不从标题强推。
2. 问题 × 主体/材料的覆盖矩阵，展示查到什么、缺什么，并可点开成员。

未来若展示观点构成，标题应说明“本次收录、去重并编码的表达”，定义计数单位、重复与多立场处理；绝不能命名为“公众支持率”。

## 7. 建议执行顺序与完成标准

### 第一轮：修复用户看得见的错误与可信度缺口

范围：F01、F02、F04、F05、F10；同时修正演示案例错配。保留现有 UI 风格，不扩大架构。

必须完成的浏览器链路：

```text
历史调查 → 报道对照 → 点击第二条引用 → 核对正确原文
→ 选择某个问题补查（验证提交意图进入上下文）
→ 刷新恢复 → 切回旧版本 → 点击三个导出入口
```

验收应同时检查用户动作、API payload、编译上下文与最终页面。修一个按钮之后只测接口不够。

### 第二轮：让专项内容和当前研判成立

范围：F03、F06、F07、F09。选择两类事件，先冻结对应材料，再定义子问题处置、专项字段、引用与来源关系。

交付：两套语义完整的回放案例；能够解释“一次搜索为何发生、补了哪项缺口、改变了哪条判断、为什么页面显示这个模块”。不要求填满所有模块，不要求出现对立观点。

先以人工检查小样本发现明确错误，再扩充 10 案例。保留案例不能用于模板硬编码；90%/95% 门槛仍按原计划计算，不因测试数量增加而放宽。

### 第三轮：用真实内容重排页面，并补强版本语义

范围：F08、F11、F12 的澄清与假设交互部分。使用真实长标题、十余篇材料、多时点、部分未知、长原文来走查。

验收不仅包括 390/768/1280px 不溢出，还包括：首屏是否回答“这是什么事件、当前到哪一步”；切换视图是否立即看到目标内容；证据是否挡住正文；读完后能否找到对应补查入口。

版本、指标、时间与导出验证要覆盖同 URL 多正文版本、读取失败、partial 更新和新发现旧材料。

## 8. 执行边界与停止条件

- 继续 Web 优先；不新增 CLI，不迁移框架，不扩展社交平台采集、自动监测、多 Agent、向量数据库、多租户或分布式调度。
- 保留 async loop、Processor → Delta → Reducer、checkpoint、预算、CaseLock、旧报告只读和不可变正文机制。
- 不让模型生成 HTML/CSS/脚本，不让模型直接填百分比，不用前端补写证据不足的业务结论。
- 不把固定虚构材料的成功当成 live 质量，不把模型 reviewer 的 supported 当作人工事实认证。
- 修复语义失败需提交可复现的材料/输入和预期；不要仅增加断言内部字段存在的测试。
- 无可用材料或额度不足时，交付明确的未完成事项；不通过删除问题、降低门槛或改状态把结果包装为完成。
- 本文是只读审查产物；后续实施需同步 canonical design、执行计划与实现记录，但本轮未改动这些文件。

当前最值得投入的下一步，是让一个具体事件真正完成“知道现在发生了什么 → 看清争议与回应 → 核查依据 → 补查自己关心的缺口”的闭环。它会同时提升报告质量和页面可信度，也比继续增加通用卡片更能展示项目的专业能力。
