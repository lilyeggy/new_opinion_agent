## 1. 为什么采用“事件工作台”

### 1.1 专业参考与适配

以下依据官方公开资料，属于设计参考，不代表对付费产品进行完整亲测，也不构成专业机构认证。

| 参考 | 借鉴的组织方式 | OpinionSearch 的落点 | 数据能力边界 |
|---|---|---|---|
| [Meltwater Explore](https://community.meltwater.com/meltwater-product-answers-428/meltwater-explore-10974) | 搜索范围、浏览筛选、材料流分别组织 | 显示本次调查范围；浏览筛选不改变调查任务 | 不复制其监测数据覆盖、传播量或受众能力 |
| [NewsWhip Spike](https://www.newswhip.com/spike-real-time-media-monitoring/) | 时间变化与相关内容联动，区分媒体报道与公众互动信号 | 事件节点关联报道；收录材料按发布时间分布 | 材料数量不命名为公众热度；无互动数据时不展示互动趋势 |
| [Ground News](https://help.ground.news/en/articles/5224577) | 同一事件聚合多来源，支持报道比较 | 同问题下比较标题、关注点、引用对象与来源关系 | 不迁移左右政治标签；媒体级评价不能代替单条证据核查 |

### 1.2 产品需要帮助用户完成的判断

1. 这件事目前发展到哪一步，最新可确认的变化是什么？
2. 争议针对什么具体措施、事实或程序？哪些分歧仍然存在？
3. 哪些主体表达了什么，他们的依据是什么？
4. 机构回应具体回答了哪些问题，还有哪些没有回答？
5. 当前判断能追溯到什么材料，下一步最值得补查什么？

完整报告是这份事件状态的阅读和导出视图。首页、证据面板、版本比较和 Markdown 必须来自同一份有版本的调查结果。

| 机制和 HTTP 测试 | `tests/investigation/`、`tests/e2e/test_investigation_web.py` | 保留基线，新增与本轮契约直接相关的测试 |

实现记录 §20.9 记载过真实联网完成调查及 partial 更新，也记录过 636 passed 的非 live 回归；这是历史记录，本次未重新执行或逐项审计其产物。不能把该记录推广为所有事件质量达标。

当前 `tests/investigation/cases/registry.json` 仍为 10 个 blocked 案例槽位，未包含正式材料与人工答案。它不是已经完成的质量评测集。

### 2.2 本次静态发现，应优先处理

| 缺口 | 代码依据 | 后果与处置 |
|---|---|---|
| SSE 断流后没有恢复浏览的闭环 | `api.js` 的 `source.onerror` 调用 close；`app.js` 的进度订阅传入空的结束回调 | 网络抖动可能让页面停住；增加连接状态、快照补取和有界重连 |
| “未发现重复”被当成独立来源 | `report.py` 用 `source.duplicate_of is None` 设置 independent | 改为明确的重复/转述/来源关系；来源数量与独立验证分开，未知保持未知 |
| 页面仍以顺序报告块为主 | `report.js` 顺序渲染全部章节 | 需要工作台投影与视图选择，不只换颜色和 CSS |
| 引用按钮暴露内部 ID | `report.js` 的 evidenceChips 直接显示 evidence_id | 改为局部引用序号或来源短名，内部 ID 留在程序与开发者视图 |
| 调查中只展示聚合进度 | `app.js` 的 paintProgress | 增加已提交材料、当前问题与阶段结果，明确“待核查” |
| 当前 latest 指针可指向 partial | `Manager._publish` 对 completed 和 partial 都更新 latest.json | 保留最近一次结果的含义，另加完整结果指针，不能让 partial 隐藏上一份完整判断 |
| 更新目前仅接受 focus | `Manager.create(parent_id=...)` 拒绝其他更新字段 | 定向补查需显式扩展契约与测试，不能前端偷偷发送 issue ID 假定有效 |
| 暂停后的累计用时语义需要补齐 | `Budget.pause()` 清空 started_at；当前 snapshot 只计算这次 started_at 后的时间 | 必须复现澄清/暂停/恢复是否丢失已用时长；持久化累计活动用时，避免恢复后重获一整轮时间预算 |

这些是实施目标，不应在本文完成后标为已修复。对缺口先写能复现的检查，再改代码。

## 3. 不同事件如何安排不同页面内容

### 3.1 一个固定框架，有限内容模块

固定部分：事件标题、地域和时间边界、当前判断与限制、三个主视图、证据面板、更新和版本入口。

三个主视图：

- **事件总览**：当前状态、重要进展、适合此事件的重点模块。
- **报道对照**：按议题组织材料，比较不同报道的关注点、归因与来源关系。
- **议题与核查**：必答问题、各方主张、回应对应、冲突证据与待查事项。

变化部分：重点模块的选择、顺序、标题、字段、默认议题与时间窗口。不同事件共用组件，不能每遇到一个事件就生成一份 HTML 或创建一个新页面模板。

模块必须由已有证据支撑。有问题但证据不足时呈现未知；不适用的非必要模块可不展示。用户明确提出的问题，即使暂无材料，也必须可见。

### 3.2 用“事件属性”补充行业分类

行业类别只决定搜索词和背景知识，不能独自决定页面。例如公交事件既可能是规则调整，也可能是停运恢复；水费事件既有计费解释，也有调查和纠正。

首版使用四种可组合的分析侧重点，加一个通用回退。它们是产品配置，不是新的 Agent 类型。

| 侧重点（建议配置名） | 适用特征 | 总览优先呈现 | 必需证据 | 无证据时 |
|---|---|---|---|---|
| 规则与适用范围 `rule_change` | 有规则修改、适用人群、执行日期 | 新旧规则对照、适用边界、过渡安排 | 可归属的规则文本及有效时间 | 单侧规则已知；旧规则待查，禁止模型补写旧值 |
| 服务可用性 `service_change` | 停运、关闭、时段调整、恢复 | 受影响服务、时间段、替代安排、恢复进展 | 服务公告、明确日期和适用对象 | 计划恢复与已经恢复分开 |
| 费用与补救 `billing_remedy` | 计费、票务、收费、复核、退费 | 计费口径、办理路径、补救范围与时限 | 机构说明、规则、可核实处理记录 | 受理渠道不等于已退费；金额不明不填 0 |
| 调查与纠正 `investigation_correction` | 调查、补充回应、修正、处置 | 已采取行动、结果与承诺、判断变化 | 公告及其后续材料 | 启动调查、作出结论、措施落地区分 |
| 通用事件 `general` | 材料较少或难以归类 | 时间线、议题、来源与未知 | 最基本的事件和证据关联 | 如实显示调查范围与缺口 |

不把灾害、医疗诊断、投资建议、影视口碑、品牌全网情绪等扩成首版专项。输入超出当前来源能力时说明可调查的公开材料范围；不通过套模板假装获得平台舆情。

### 3.3 内容选择算法及稳定性

建议引入 `EventProfile` 和确定性的 `PresentationPolicy`：

1. 模型依据用户任务提出侧重点，并引用相关用户问题；有材料后补充支持的 finding/evidence 引用。
2. 程序确认侧重点在允许集合中，且不删除用户必答问题。无需为普通页面偏好增加一轮用户澄清。
3. 按侧重点列出候选模块，再执行数据可用性检查。
4. 用户明确关注的模块优先；其次是新进展、重要事实冲突和未回答的实质诉求；剩余按配置的固定顺序。
5. 总览最多突出 3 个业务模块，其余放在对应主视图；这是展示上限，不是调查问题上限。
6. 没有适配结果时使用 general；多个侧重点可并存，不强行选唯一行业标签。
7. 调查中不因每轮推理让模块随意跳位；保持导航和已显示模块位置，新增内容按稳定位置加入。
8. 新发布版本可调整模块顺序，保存选择理由、配置版本和所属结果版本；旧版不重新排版成新版内容。

模型不得输出 HTML、CSS、脚本、任意组件名、像素布局或统计百分比。前端只渲染白名单模块与结构化字段，外部文章无权改变此规则。

### 3.4 模块可用状态

| 状态 | 含义 | 用户呈现 |
|---|---|---|
| `ready` | 数据与引用通过该模块的发布检查 | 显示内容及依据 |
| `provisional` | 已提交结果，重要语义尚待审查 | 展示材料或归因说法，局部标待核查；不得进入核心断言 |
| `insufficient` | 相关且必要，但现有材料不足 | 显示具体缺口与补查入口 |
| `unavailable` | 读取、搜索或处理失败阻碍判断 | 显示失败影响和已尝试范围 |
| `not_applicable` | 与任务无关 | 非必要模块不占总览空间 |

其中 `not_applicable` 不允许用来隐藏用户明确问题、核心事实冲突或供应商故障。

## 4. 页面与交互规格

### 4.1 创建、澄清与历史

- 首页输入事件及关注点；时间、地区、参考链接可选。
- 时间解析失败或事件身份歧义必须澄清；明确任务直接开始，不增加例行提纲确认。
- 草稿与已提交澄清保存在服务端。未提交的输入不承诺已经持久化；如增加自动保存，要显示保存状态并测试刷新恢复。
- 首次创建产生 run；刷新、切换标签或 SSE 重连不创建新 run。
- 历史项显示事件名、调查时间、状态与版本，不以哈希作为主要标题。
- 保留离线/联网模式清晰标识；示例数据永远不能混入真实事件结果。

### 4.2 总览

顺序为：事件身份与范围 → 2–4 条当前判断及各自依据/限制 → 事件进程 → 自适应重点模块 → 相关材料入口。

“最新进展”依赖事件发生时间和材料支持，不能用抓取时间替代。未知日期单独列出，不按字符串猜测顺序。相对时间相对于材料发布时间解析，无法确认时保留原表达与 unknown。

材料分布图只在存在可靠发布日期时显示。标签为“本次收录材料，按发布日期，篇”；另列发布时间未知数量。不得命名为全网声量、舆情热度或社会风险趋势。

事件时间线和材料发布时间分布是两个口径：对节点的点击应按关联关系检索材料；对日期柱的点击才按材料发布日期筛选。不得要求事件证据一定发布在事件当天。

### 4.3 报道对照

每项显示：来源/作者（可得时）、发布日期、材料性质、标题、针对当前议题的报道角度、原始/转载/引述关系、证据入口。

- 比较同一问题下的报道，不把完全不同措施的支持/反对放在一行。
- 文章中被采访者的观点保留主体；不得变成媒体自身立场。
- 转载可折叠，但必须可展开，并保留来源依赖信息。
- 默认排序采用相关议题内的发布时间；可提供原始材料优先。缺日期排到明确标注的组，不用抓取时间伪装发布时间。
- “推荐阅读”说明选中原因，如原始规则、关键采访、相反解释、后续修正。选择依据须受证据审查，不生成隐含可信度分数。
- 关键对立主张即使只有一份材料也可以显示，标明材料单薄；不为页面对称虚构另一方。

### 4.4 议题与核查

每个议题依次呈现：具体问题 → 主体与主张 → 支持/反驳依据 → 对应回应 → 未覆盖部分 → 本轮处置 → 补查入口。

回应仍使用五类：直接回答、部分回答、涉及但未实质回答、范围内未发现可对应回应、无法判断。

复合问题按子问题判断：例如“是否启动调查、是否完成调查”不可因前半句有公告而整体标为直接回答。可拆成两个问题组成部分，不必膨胀为两个顶级 issue。

事实、归因说法、解释和诉求分别呈现；诉求不能作为待判真假的事实。回应充分、事情解决、群体满意分别记录，不相互推导。

“范围内未发现回应”必须附截止时间、机构定向查询、事件回应查询、后续材料查找及未处理失败情况。与该问题有关的读取失败存在时用无法判断；不可让一个无关页面的失败永久污染所有议题，是否有关须有记录。

### 4.5 证据面板

点击判断、引用、报道或规则对照单元，都应定位到相应依据。面板必须显示：

- 来源标题、请求/最终 URL（请求 URL 可折叠）、发布日期/更新时间/获取时间。
- 保存正文的目标片段、适量上下文与定位；日期缺失直说未知。
- 该材料与该条判断的关系：支持、反驳、部分支持、背景或尚待判断。
- 转载/引述原始出处及其未知情况。
- 当前查看的报告版本，明确旧版本原文不会随新网页改变。

Unicode 字符定位沿用后端定义。Python 字符下标与 JavaScript UTF-16 下标不能直接混用；优先由后端返回已切好的前文、引文和后文，或使用统一码点处理并测试 emoji/扩展字符。

证据缺失、哈希或定位失败显示在点击位置，禁止回退到任意“相近”原文，也不能静默过滤无效引用使正文看似完整。

### 4.6 三类操作的边界

| 操作 | 改变什么 | 是否消耗调查预算 | 持久化方式 |
|---|---|---|---|
| 浏览：日期/来源/议题筛选、展开引用 | 当前视图 | 否 | URL/hash 参数；不改变调查状态 |
| 定向补查：追问某议题、补充新进展 | 新一轮调查目标 | 是 | 显式提交，创建关联父版的新 run |
| 更正疑似误归类或遗漏 | 一条需要复核的用户反馈 | 复核需要预算 | 作为带来源的补查输入，不直接改写已发布判断 |

首版运行中仅支持浏览、取消与恢复；定向补查在 completed/partial 结果上发起。活动调查中显示“本轮结束后补查”，不建设实时向运行 loop 注入指令的队列。

补查表单保留 issue、被质疑的 finding、用户文字和父版关联；向用户展示正常问题文本。用户提供的说法是待验证输入，不能直接成为事实或审查结论。

### 4.7 连接、刷新、取消和终态

- 页面取得服务端快照后订阅 SSE；SSE 提供快照版本通知或一致的快照，不是唯一状态源。
- 断线保留最后内容，显示“连接中断，正在恢复”；先补取 snapshot，再以有界退避重连。达到上限提供手动重试。
- 使用 run ID 与页面请求令牌丢弃旧请求结果，防止快速切换事件时旧响应覆盖新页面。
- 依据单调 revision 拒绝过期快照；合并不得把旧版图表和新版材料混在一起。
- 取消只取消调查，页面保留已提交材料；取消响应失败时不得先把本地状态改成已取消。
- completed、partial、failed、cancelled 分别显示；无实质新变化是有查找范围的更新结果属性，不能用来覆盖运行失败状态。
- 一页内连接状态、运行状态、内容审查状态分别表达，避免把“网络恢复”当成“调查恢复”。

### 4.8 视觉与可访问性

沿用认可画布的克制布局：紧凑应用导航、明确标题、足够正文空间、少量语义色、右侧证据面板；不做满屏 KPI 卡片和装饰性仪表盘。

- 桌面并列内容与证据，窄屏将证据变为可关闭的下方区域或符合焦点规则的抽屉。
- 支持 320/768/1024px 和大屏，正文与控件不溢出；长标题与中文能换行。
- 按钮、标签、键盘操作、焦点、加载/错误状态完整；关面板后焦点回到触发位置。
- 状态同时用文字表达，不仅依赖颜色；支持当前明暗主题。
- 不在主要界面暴露内部 ID、模型推理、工具 JSON、环境配置和密钥。
- 参考片段的虚构水费案例只用于设计和机制测试，不复制为真实结果默认值。

## 5. 搜索如何支撑工作台

### 5.1 完整链路

```text
用户任务和可选范围
  → 请求校验、时间解释、事件身份和必要澄清
  → 3–6 个初始问题，保留所有用户问题，最多 8 个顶级问题
  → 事件属性建议 + 初始搜索任务
  → 问题级 search → 候选相关性判断 → read 保存正文版本
  → 本地 retrieve 重查已读长文 → 提取定位 Evidence
  → reflect 提议事件节点、主张、回应、来源关系和缺口
  → Processor 校验 → Delta → Reducer → checkpoint
  → 工作台投影形成阶段内容（明确待审查）
  → 依据重要缺口选择下一动作
  → 独立 review 调用检查核心断言和对应原文
  → 修订/补证/降级 → 判断结束条件
  → 发布一致的工作台快照、报告和 Markdown
  → 用户核查并提出补查 → 新 run → 新版本及变化依据
```

继续使用 search/read/retrieve/reflect/review/finish。页面模块不是新的 Runtime action；不要为“画图”“写时间线”“显示饼图”各造一个 Agent。

### 5.2 搜索任务契约

在现有 SearchDecision/SearchAttempt 附近补充可持久化的 SearchTask/覆盖记录。名称可按仓库惯例调整，语义不能省略：

| 字段 | 语义 |
|---|---|
| task_id、issue_id、origin_question_refs | 程序维护关联；说明为哪个问题工作 |
| purpose | 原始材料、主体诉求、独立核查、机构回应、后续修正等 |
| discovery_mode | 基础发现、定向补查、用户提供 |
| query、constraints、page | 实际发送的条件及有界分页 |
| target_gap、success_observation | 缺口和可观察的完成结果，不是保证找到答案 |
| outcome | 候选、空结果、无关/被过滤、重复、读取失败、供应商错误等 |
| related_candidate/source/evidence_ids | 连接搜索与后续有效材料 |
| membership_policy_version | 材料是否进入某项统计及其理由 |

基础发现与定向补查共用一个 loop。基础搜索也不是随机抽样；只是更容易记录和复现的有限材料发现方式。

### 5.3 下一步动作如何选

优先级采用可解释规则，不先引入训练或复杂收益评分器：

1. 身份或时间冲突，影响整个调查对象。
2. 用户必答问题、核心断言缺引用或审查失败。
3. 同一事实的数字/时间/对象/统计口径冲突，可能改变结论。
4. 关键主体缺失、重要诉求未对应回应、原始出处未找到。
5. 新进展与后续修正。
6. 补充背景与材料多样性。

能用已有正文回答时先 retrieve；需要新材料才 search/read。相同 query/page 无意义重复时转向新别名、原始出处、机构域名或另一材料类型。工具瞬时错误的有界重试仍由现有执行层处理并计预算，不能算作“无材料”。

覆盖记录是“已查过哪些范围、哪些未解决”，不是全网召回率。查询成功也不意味着证据真实，机构文件也须区分公告主张与外部事实。

### 5.4 审查和结束

关键检查：引用是否支持断言、归因是否保留、数字/时间/否定/限制是否遗漏、转载是否误作独立验证、回应是否答非所问、公众态度是否超出样本。

审查模型配置与原文依据保存。它是独立调用，不是独立事实来源或真值证明。失败后补证、改写、降级或撤回；不得删校验门来提高 completed 比例。

必答问题要有处置：已回答、存在分歧、范围内查找后未发现、无法判断。重大未完成事项保留 partial。非必需图表不完整不阻止结束；必答问题不能因隐藏其模块而绕过结束条件。

默认预算保持 20 分钟、20 次搜索、24 次读取、80 次模型调用，约 15 分钟后优先整理与审查。使用已有 `OPINION_INVESTIGATION_*` 配置；恢复读取原 run 的预算，不重新分配。慢模型实验提高预算必须独立记录，不当作默认预算下的改善。

## 6. 数据与职责契约

### 6.1 分层

```text
领域 State（权威）
  ├─ 调查事实、问题、证据、主张、事件节点、来源关系
  └─ 任务覆盖、审查、事件属性与用户补查意图
          ↓ 确定性投影
WorkbenchSnapshot + ReportView + MetricSnapshot
          ↓ Web API / SSE
前端路由、筛选、组件渲染、证据交互
```

模型提出内容；程序维护 ID、关联、预算、统计和发布。布局选择和组件实现不进入通用 Runtime；浏览器不直接修改领域 State。

### 6.2 建议增加/扩展的最小契约

| 契约 | 最小信息 | 权威归属 |
|---|---|---|
| EventProfile | facet、提出理由、关联问题/证据、配置版本 | 领域中经提交的分析侧重点 |
| EventNode | 发生时间/区间、精度、事件描述、关联 finding/evidence、时间依据 | 领域事实；不得纯靠标题生成 |
| SourceRelation | 来源版本端点、关系类型、支持依据、复核状态 | 重复/转载/引用/修订关系；unknown 合法 |
| QuestionComponent / ResponseAssessment | 同一问题的组成部分、回应 finding、covered/uncovered、理由与证据 | 先扩展已有 Finding 的回应字段；必要时拆分 |
| SearchTask / CoverageRecord | 问题、目的、范围、尝试、结果、缺口和归属 | 领域状态或可从提交记录确定性重建的视图 |
| CorpusManifest | 当前材料成员、发现渠道、纳入/排除理由、去重与范围版本 | 可追溯材料集合；正文仍由 SourceVersion 引用 |
| WorkbenchSnapshot | 来源 state revision、run/版本、profile、模块、视图数据、限制 | 可重建投影；已发布内容版本化保存 |
| ModuleView | 固定 module_type、状态、标题、依据/数据引用、选择理由 | PresentationPolicy 输出 |
| MetricSnapshot | 统计定义、材料集版本、分子/分母成员、未知/排除数、口径 | 程序计算，模型不可写百分比 |
| FollowupIntent | parent_run、issue/finding_refs、用户补充、触发来源 | 创建更新的持久化输入 |

不要第一阶段把整张表全部建成复杂数据库表。先实现总览、规则对照、时间线和证据所需的字段；每个新字段必须有生产者、验证者、消费者和测试。

### 6.3 来源关系与“独立性”

- 正文一致可以记录重复；不是所有相似文章都应该合并。
- 不同域名可能转述同一公告；同一网站也可能有不同采访，不能凭域名判独立。
- 来源有多种关系：同文、转载、引用、独立采访的可观察依据、关系未知。
- 文章可以同时引用公告并包含独立采访；依赖关系应能关联具体主张，不能强制整篇只有一种身份。
- 首版对外显示收录文档数、正文版本数、已识别转载数和出处未知情况；不发布未经证实的“独立来源 N 个”。
- 已保存且无依赖标记不等于已经证明独立。现有 `independent` 字段可暂保留兼容，但新页不能继续使用其布尔值作独立验证统计。

### 6.4 快照与版本原子性

建议工作台使用独立格式标识 `opinion-workbench/1`。它与领域 `schema_version=2`、通用 checkpoint envelope 的格式版本分别演进，不统一加同一个版本号。

阶段投影至少携带 `run_id`、`state_revision`、`snapshot_id`、`generated_at`、`publication_state`。模型输出未提交前不能进入可见结果；审查未通过可作为 provisional，不得包装成核心事实。

已发布结果包含与其绑定的正文/证据、材料清单、模块配置版本、统计和 Markdown；先完整写入版本产物，再原子发布 manifest/引用。崩溃后的半成品不能被读取为正式版本。

新工作台投影缺失时允许基于旧结构化报告只读生成兼容视图，标明“不支持该模块/历史字段缺失”；不得臆造旧数据，不写回旧报告或旧正文。

领域新增可选字段能安全兼容时使用显式默认；无法解释旧字段语义时升级领域格式/profile 并明确拒绝不兼容续跑。不要自动把旧未完成 run 转换后继续。

## 7. 图表与统计的启用条件

首版必须做到时间与材料可下钻；观点饼图列为后续有条件模块，不作为第一阶段交付门槛。

| 展示 | 可采用口径 | 不满足条件时 |
|---|---|---|
| 材料发布时间分布 | 指定材料集合中的文档，按已知发布时间计数；同 URL 多正文版本不多算文档 | 列出日期未知材料；无可靠日期则不画时间曲线 |
| 议题涉及程度 | 每篇材料在同一议题只计一次，多标签允许跨议题重复 | 用数量和材料列表；总比例可以超过 100%，不能画成饼图 |
| 单议题观点构成 | 同一对象下去重的归因表达，互斥分类，未知计入分母 | 不稳定归因或分类不足时用观点对照，不显示百分比 |
| 来源构成 | 当前材料集的来源类型/已识别来源关系 | 不改名为“公众构成”或“可信度” |
| 版本变化 | 已审查判断的新增/加强/修订/削弱/撤回及其依据 | 未复评就是未复评，不是撤回 |

图表必须同时保存定义版本、查询/纳入规则、过滤条件、材料集版本、成员列表与成员哈希。点击某项得到的成员数必须等于显示计数；比例由服务端确定性计算，显示舍入不得改变原始数量。

定向搜索某一立场会改变取样方向。补查材料可以作为证据，但不得静默进入旧分母再声称“反对比例上升”。新版本若改变采集、分类或去重口径，标记不可直接比较。

新发现的旧材料、网页正文修订和事件的新进展分别记录。发布日期更新本身不足以证明事件发生了变化。

不引入“负面分 87”“风险高”“公众满意 68%”等未经方法和数据支持的综合指标；不设置任意样本量阈值来伪装统计有效性。

## 8. Web 接口与模块拆分

### 8.1 沿用的接口

已有 `/api/investigations` 创建/列表，`/{id}` snapshot，`/{id}/events` SSE，`/{id}/evidence/{eid}`，`/{id}/report` Markdown，`/{id}/versions`，`/{id}/diff`，以及 clarify/cancel/resume/update。保留语义和现有调用者。

### 8.2 建议的最小扩展

以下是待实现接口，不是当前可调用功能。

| 接口/字段 | 用途与要求 |
|---|---|
| `GET /api/investigations/{id}/workbench` | 返回当前一致工作台投影；可用 `snapshot_id` 读取绑定快照，不能静默切到最新 |
| `GET .../{id}/materials?snapshot_id=...&issue_id=...` | 同一快照内筛选和有界分页；总数与列表同口径；小集合可首版随投影返回 |
| 现有 SSE 增加 workbench revision/reference | 客户端发现更新后读取一致快照；旧客户端可忽略新增字段 |
| 现有 evidence 接口增加 relation/context | 保留旧字段；检查证据确属所选 run/版本/快照，不能跨事件引用 |
| 现有 update 增加 optional issue_ids、finding_ids、client_request_id | 校验父版引用；普通 focus 更新仍可用；同一请求重试返回同一创建结果 |
| 现有 diff 增加 change basis 与 comparability | 比较前后具体判断和证据；口径变化单列，不能只比较文本差异 |

`client_request_id` 只保证本地 Web 创建操作的幂等范围，不承诺模型或远端工具全局 exactly-once。不同内容重用同一个 key 应拒绝；并发创建仍受 CaseLock 约束。

错误至少区分参数无效、引用不存在/不属于当前版本、事件忙、格式不兼容、快照不可用和供应商失败。定义结构化错误 code 与用户消息；常见可映射 400/404/409/503，沿用现有兼容行为并在契约测试中冻结。

快照 GET、筛选、证据 GET、SSE 重连不得产生收费调查。外部 URL 仍按既有公开 URL 与域名规则验证；浏览器渲染文本要转义，禁止插入模型生成的可执行 HTML。

### 8.3 建议文件职责

以现有目录为根，按需要分阶段增加：

- `domain/investigation/models.py`：扩展领域实体与引用约束。
- `domain/investigation/engine.py`：校验与提交；明显膨胀后再拆领域策略文件。
- `investigation/workbench.py`：纯投影、兼容转换、模块可用性与顺序。
- `investigation/presentation.py`：仅当配置/策略确实需要独立文件时添加，不建设通用页面构建平台。
- `investigation/metrics.py`：有图表统计需求时增加，负责可重算指标。
- `web/assets/app.js`：启动和路由；抽离首页、调查进度、比较页面，避免继续膨胀。
- `web/assets/workbench.js`：主视图和局部状态联动。
- `web/assets/modules/`：timeline、coverage、issues、rule-comparison 等真实复用模块。
- `web/assets/evidence.js`：证据面板和焦点处理。
- `web/assets/api.js`：请求、结构化错误、连接恢复。
- `web/assets/style.css`：统一设计 tokens 与响应式布局；不为每个事件生成样式。

文件名是建议，不要求机械创建空文件。测试文件跟随实际职责组织。

## 9. 按需更新、旧版保护与报告一致性

1. 从 completed/partial 父版提交补查，保留事件身份、旧正文和旧判断；附加补查目标。
2. 一个事件仅一个活动调查。已有活动任务时展示正在执行的调查链接，不创建并发覆盖。
3. 调查过程中继续能读旧版；新 run 的阶段数据明确属于新 run。
4. 旧网页变动新增 SourceVersion，旧引文仍指向旧版本。新发现的旧文按其发布时间归类。
5. 复核新材料是否改变旧判断：加强、削弱、修订、撤回、未变；没有复评的保留“尚未重新评估”。
6. 对照页面显示结论文字、理由与前后证据，而不仅是状态标签。
7. 建议保留 `latest.json` 表示最近发布的可读调查结果，新增 `latest_completed.json` 表示最近完整结果。页面若默认打开 partial，必须就近提供上一完整版本并展示未复评事项。
8. failed/cancelled 的结果仍可在历史中查看；不把失败推进为新的完整结果引用。
9. 无新增材料只能表述为“在本次成功检查的范围内，未发现实质变化”，附范围和截止；存在关键读取失败时使用无法判断。
10. Markdown 保留完整报告结构与证据附录，与本版工作台一致；浏览器筛选不偷偷改变完整下载内容。

指针职责在实施时写入 canonical design 与测试。迁移前先读取现有目录；不得为了调整 latest 语义覆盖旧版 report.json。

## 10. 实施次序与退出条件

每阶段完成后保存范围、验证命令/结果、产物路径、未验证项和下一步。未完成用 `pending` 或 `blocked`，不估算完成百分比。

### P0：冻结基线与输入输出契约

任务：

- 读取当前 git 状态，保留已有修改；记录实现入口、现有报告样本与配置。
- 复现 SSE 断线行为、来源独立性统计、引用 ID 暴露和 partial 最新版本行为。
- 验证预算的暂停/恢复累计用时；请求次数不重置与时间不重置是两项独立契约。
- 保存至少两个现有不同类型报告的基线；没有真实材料时明确待补，不用虚构冒充真实基线。
- 冻结 WorkbenchSnapshot 的最小字段、模块状态和引用规则。
- 同步 canonical design 与执行记录的计划入口。

退出：明确现有/新增字段、兼容方式、最先修复的问题及可重现结果。此阶段不启动全面 UI 重写。

### P1：先完成一个可信的公共工作台

任务：

- 修复来源统计命名与断线恢复；引用改成人类可读标记。
- 在现有报告上生成通用工作台投影，完成总览/报道/议题三个视图与证据联动。
- 保留已有新建、澄清、取消、历史、更新、版本、Markdown 主链。
- 加入局部未知、失败、无日期和单方材料状态。

退出：一个已有调查可在实际浏览器中完成“浏览现状 → 找到分歧 → 打开正确原文 → 提出补查”，旧链不回归；不能仅以 HTML 外观或 HTTP 200 验收。

### P2：让两类事件自然长出不同内容

任务：

- 首先实现 `rule_change` 与 `billing_remedy` 两种侧重点及 general 回退。
- 新旧规则对照与计费/补救模块各有领域证据输入、降级状态和选择理由。
- 同时实现事件节点与材料发布日期区分，混合侧重点不冲突。
- 在终态报告投影稳定后，再让运行中展示同契约的 provisional 模块。

退出：两类不同事件在同一套页面中显示不同重点；输入不足时回退；没有任何事件专用 if/else、答案硬编码或样例文字泄漏。此处允许按 facet 分支，不允许按具体事件名分支。

### P3：补齐调查组织与定向交互

任务：

- 增加问题级 SearchTask/覆盖记录与发现渠道。
- 让当前缺口、用户关注点和来源关系影响下一次搜索。
- 接通 issue/finding 定向补查、幂等创建与关联校验。
- 补上 service_change、investigation_correction 侧重点，复用已有模块。
- 为页面顶部摘要保留逐条引用和审查状态，防止投影重新夸大已限定判断。

退出：能解释每次搜索要解决哪个缺口；一次用户追问能进入正确新 run；失败不伪装成无进展；恢复不重置预算和已提交状态。

### P4：完成版本变化与有条件统计

任务：

- 完成快照一致性、版本指针、差异依据和未复评展示。
- 上线可下钻材料分布及议题涉及数量。
- 只有表达归因、去重和分类评估通过后才上线观点构成；否则保留观点对照，统计模块标 pending。

退出：图表与成员数一致、定向补查不污染旧分母、同 URL 变文不改变旧引用、partial 不掩盖上一完整结果。

### P5：真实案例和完整 Web 验收

任务：按下一节执行机制回放、固定材料模型运行、联网发现和人工检查，分别记录。冻结模型、材料、预算和对照方法后再比较。

退出：关键场景全部通过，达到门槛且有证据。若材料或额度不足，交付已通过的子范围并列明未完成门槛；不得把 P1–P4 的代码完成当作 P5 通过。

### 额度不足时的优先级

先完成 P0/P1 的可信主链和 P2 的两类事件，再做 P3 的定向补查。暂停新增图表、更多侧重点、装饰动效与额外可视化。

保留至少一个真实事件的“已知—分歧—未知—证据—更新”完整体验。不要为展示丰富度牺牲原文核查，也不要用扩大预算掩盖动作重复或审查失败。

## 11. 测试与验收清单

### 11.1 三类证据分开

- **机制测试**：fake/scripted 数据，验证程序约束、错误、重放、计数及 UI 交互。
- **固定材料语义回放**：真实模型、冻结真实正文，验证问题提取、归因、回应、审查和模块选择。
- **真实联网调查**：真实模型/Brave/Jina，验证材料发现、时效性、失败和报告质量。

实际浏览器交互是另一项独立要求。接口测试、DOM 强制 click、截图存在不能替代用户能够正常点击、键盘操作和刷新恢复的验收。历史定位点击超时要定位原因并验证，不能长期通过强制点击绕过。

### 11.2 必测场景

| ID | 场景 | 通过条件 |
|---|---|---|
| W01 | 明确事件与歧义事件 | 明确直接开始；歧义/无法解析时间持久化澄清后继续 |
| W02 | 规则调整与费用补救两类事件 | 同一工作台呈现不同重点；选择理由有任务或证据支持 |
| W03 | 混合类型、未知类型、材料不足 | 可组合与 general 回退；不生成空洞或虚构模块 |
| W04 | 用户明确问题不符合模板 | 问题保留，未知说明可见，结束条件不被绕过 |
| W05 | 时间节点与文章发布时间不同 | 节点关联正确材料，日期柱只筛发布时间；未知日期不乱排序 |
| W06 | 长文末尾包含关键否定 | retrieve 能取到正确片段；摘要保留否定与限制 |
| W07 | 同文转载、公告转述、原创采访混合 | 不凭域名计独立；可展开来源关系与归因 |
| W08 | 一篇文章包含多主体观点 | 各观点关联其主体；媒体不继承被采访者态度 |
| W09 | 复合问题仅一部分有回应 | 标部分覆盖或分组件显示，不将整体判为直接回答 |
| W10 | 未发现回应与读取失败 | 前者有范围和成功查找依据；后者明确无法判断 |
| W11 | 点击结论、规则单元和报道 | 定位到本版正确正文；Unicode/emoji 位置正确 |
| W12 | SSE 断线、晚加入、快速切换页面 | 保留数据并恢复；不新建 run，不被过期响应覆盖 |
| W13 | 阶段结果尚未核查 | 标 provisional；不能进入已核实核心判断 |
| W14 | 取消、预算耗尽、发布中崩溃 | 保留提交结果，恢复预算不归零，半成品不发布 |
| W15 | 定向补查重复点击/网络重试 | 同 key 同请求只建一个 run；跨事件引用拒绝 |
| W16 | 同 URL 变文、新发现旧文 | 新增正文版本；旧引用不变；旧材料不叫近期进展 |
| W17 | 新证据改变判断 | 对比显示修订/撤回原因及前后依据；未复评不叫撤回 |
| W18 | partial、failed、无新材料 | 状态和限制不同；保留上一完整结果入口 |
| W19 | 筛选、图表、列表、下载 | 相同快照成员计数一致；筛选不更改整版 Markdown |
| W20 | 外部正文要求删规则/改 UI | 内容只作为材料，不能改变控制、模板与引用 |
| W21 | 旧格式报告与新模块 | 只读兼容、缺字段明确降级；不改写旧文件 |
| W22 | 索引损坏或删除 | 从正文重建，证据和图表引用仍正确 |
| W23 | 320/768/1024px、键盘、长标题 | 无遮挡/溢出；焦点顺序与关闭恢复正确 |
| W24 | 定向检索改变材料构成 | 旧分母不变；新口径不可直接比较的提示可见 |

### 11.3 正式案例与门槛

保留原来的 10 个案例槽位：公共交通、公共设施、文旅服务、规则调整、回应修正各 2 个，每类 dev/holdout 各 1 个。事件属性与该分类是两个维度，可一个案例覆盖多个 facet，不因此另造 10 个案例。

每个案例保存原文、哈希、可得时间信息、必答问题、关键依据、禁止结论、预期模块与未知说明。更新案例严格分隔 T0/T1 可访问材料；T1 不能预先进入 T0 的本地索引、提示词或候选。

人工标注与模型预标注明确区分，holdout 答案不用于生产规则和 query 调参。当前 registry 为 blocked；取到真实材料并标注后才更新状态。

沿用门槛并补充页面要求：

- 引用、定位、版本与图表成员结构完整性 100%。
- 保留案例必答问题至少 90% 正确回答或恰当未知。
- 人工检查的重要断言至少 95% 得到引用支持或正确降级；标题、摘要、图表说明都计入。
- 关键归因、转载、回应遗漏、更新反转、旧引用、断线恢复用例全部通过。
- 模块选择逐案有依据；必答内容可见，不适用模块不硬填。
- 主路径经过实际浏览器操作，材料发现与人类质量分开报告。
- 相同模型、材料和预算与当前版本比较；界面改善用完成核查任务的操作步骤/成功情况说明，搜索质量用必答覆盖和断言支持说明。

问题数量、断言数量与错误类型须一并报告，小样本百分比不能被包装成总体质量。达不到门槛时列明分母、失败用例与下一步，不能只写“总体效果良好”。

## 12. 给下一位执行者的工作规则

1. 开始先确认 cwd、git status 和已有产物，读本文 §2 与相关源码，修正过时基线。
2. 不运行 git clean、git reset --hard，不覆盖用户修改、不删除旧 run/报告。
3. 按 P0 → P1 → P2 → P3 → P4 → P5，小步实现；每一步说明用户可见变化与验证证据。
4. 用代码职责决定修改位置，不把舆情规则放到通用 Runtime 或前端组件。
5. 模块可扩展只限本文几种事件属性；不建设任意低代码页面生成平台。
6. 不通过放宽引用、回应、审查门槛或假数据来交付看似完整的页面。
7. 结构测试通过、画布完成、历史联网成功、当前人工质量达标分别记录。
8. 遇到不兼容存储格式、无法验证引用、无真实材料或额度耗尽时，停止相关扩展，保留证据并列出 blocked 的具体依赖；继续独立的已授权工作。
9. 已授权范围内可自行修复、拆分和测试，不为普通实现选择重复确认；超出本文来源、部署或产品范围才另行讨论。
10. 每个重要实现节点同步 canonical design、执行计划和实现记录；实现记录只追加已验证事实。

## 14. 最终交付定义

应当能完整展示以下主路径，并说明每一步的数据从哪里来：

**提交事件 → 必要澄清 → 看见调查与适配内容展开 → 比较报道与议题 → 核查原文 → 补查具体问题 → 对比前后判断 → 下载本版报告。**

至少两种事件通过同一工作台呈现明显不同且有依据的内容；缺材料时仍然诚实、可用。演示者能够解释一次搜索为什么发生、改变了哪个判断、页面为什么显示某个模块，以及哪些结论仍不能作出。

本文交付仅表示该实施指南和参考已写入仓库；所有新增业务能力在对应阶段验证完成前均为待实施。
