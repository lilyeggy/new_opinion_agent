面试核心叙事：为什么通用 ReAct 无法胜任深度舆情核查？
舆情调查真实痛点 通用 ReAct / 普通 RAG 的典型失效模式 OpinionSearch 的底层机制设计 (Infra for Domain) 代码落点与验证指标
1. 舆论场“通稿洗稿”回声室效应
10 家媒体转发同一篇公关稿或爆料贴		 把 10 篇转载当成 10 份独立证据，浪费读取预算并在正反对比中严重夸大单方证据权重。 确定性同源聚类 + 独立信源簇计权：入库归约时计算核心摘录 CJK 2-gram Jaccard，≥75% 自动建立 repost/same_text 关系；视觉拔河条与拓扑图通过 Union-Find 按独立信源簇计权。 engine.py :: _auto_detect_syndicated_relations
projector.py :: _build_source_cluster_map
2. 长篇报道“首读漏抽”与上下文淹没
长文前 70% 铺陈背景，后 30% 才有核心回应与反转数字		 单一查询 Top-K 切片只取到开头背景段；20 步后大量未引用边缘摘录撑爆 Context 或稀释关键反方证据。 多视角首读提取 + 三级生命周期压缩：首读联合匹配 focus + question + open components 并叠加引语/日期/数值密度重排；已引用证据与未处置反方证据设为 NEVER，边缘旧摘录设为 TRUNCATE。 service.py :: _read_material
storage.py :: Corpus.retrieve
context.py :: Compiler.compile
3. 细粒度数值编造与“伪精确”幻觉
模型把 316.03 亿写成 3160.3 亿，或在总结时脑补百分比		 普通 LLM Self-Check 极易放过数字小数点移位或单位换算错误，导致报告出现致命事实错误。 原文字符偏移强校验 + 确定性数值守卫：verify_evidence 强制校验 content[start:end] == excerpt；Reviewer 之后运行 unbacked_specifics 正则量纲比对，未锚定数字一律降级为 partial。 storage.py :: verify_evidence
service.py :: unbacked_specifics
llm_planner.py
4. “暂未回应”陈旧结论与预算耗尽死锁
早期下了“未回应”结论，后期读到回应却未更新；或收敛期卡死		 早期结论一直留在列表中直至发布；或者最后几步因页面 403 读取失败在 finish 门控前无限死循环。 陈旧否定结论拦截 + 收敛储备期有界放行：_stale_negative_findings 自动检测未处置的含回应词证据并拦截 finish；最后 1/3 预算由 ConsolidationValidator 接管，允许有界 reflect/retrieve 闭合开放问题。 engine.py :: _stale_negative_findings
service.py :: ConsolidationValidator
5. “罗生门”式相对时间错位与多方各执一词
报道大量使用“昨日”、“10月13日”，正反双方口径对立		 时间轴因缺少完整年份把关键节点丢进未解析列表；长文本堆砌导致读者看不清谁支持、谁反对、谁回应了什么。 发布时间锚定消歧 + 视觉拓扑/拔河/泳道渲染：结合 SourceVersion.published_at 自动将相对日期锚定为 ISO 日期；通过三层 SVG 拓扑图、正反拔河条与三栏立场泳道直观呈现多方博弈结构。 projector.py :: _anchor_relative_time
renderer.py :: _render_relation_graph
