# OpinionSearch 2026-09-15 收尾验收结论

## 结论

本批次只能标记为 **工程验收成立，V1 报告质量未通过**。

系统已经形成一条真实、可恢复、可审计的 Web 链路：用户在页面提交事件，服务端识别事件并生成动态问题，Agent 搜索和读取正文，正文与证据定位不可变保存，页面展示进行状态，刷新后由服务端恢复，运行结束后生成交互工作台、静态 HTML 和 Markdown。失败或未完成时，系统会保留 `partial`，不会伪装成成功报告。

但三条真实模型链路都没有产出满足 V1 门槛的完整报告：

- 开发案例 A 在修复后产生并审查了判断，但 8 条判断中仅 1 条达到 supported，且没有形成结论。
- 开发案例 B 形成 17 条判断，其中最后一轮改写使 11 条判断重新处于未审查状态，最终没有形成结论。
- Web 保留案例 H 形成 11 条有证据的判断，但在审查前达到 20 个提交步骤上限，6 个必答问题仍为 open，0 条可发布结论。
- 更新案例 T0 没有形成 Findings，因此 T1 没有合法的判断变化分母，未执行。

因此当前项目适合展示为“具有可信失败语义、证据追溯和生产链路诊断的公开事件调查原型”，不能宣称“稳定生成有深度、有价值的舆情报告”。

## 本批次实际完成

### 搜索与调查链路

- 用户输入先经过事件身份、地点、时间、主体与事件侧重点识别。
- 每个事件动态生成 3–6 个调查问题，本次 Web 案例生成 6 个问题及 24 个可单独处置的组成项。
- 搜索动作绑定 `issue_id`、目的与待补缺口，记录搜索失败、读取失败、未读候选与未尝试方向。
- 正文按版本保存，证据绑定正文版本和字符区间；Web 保留案例的 34 条定位全部与保存正文一致。
- 页面明确区分机构原文、新闻报道、来源关系未核实、读取失败、未审查判断和可发布结论。

### 收束与可信度机制

- 新增运行后段的强制收束规则：无判断时只能 reflect；有未审查判断时只能 review；全部审查后只能 finish。
- partial 报告不再完全空白，可呈现阶段问题、证据和未审查判断，但不会把它们升级为核心结论。
- 诊断视图从已提交状态派生，不维护第二套监控真相。本次 H 案例准确显示 3 个 blocker：必答问题未处置、必答子项未处置、当前判断未审查。
- 更新回放入口复用 Manager、父子关系、锁、checkpoint 和冻结适配器；没有用旁路脚本伪造更新结果。

### Web 与导出

- 已在真实浏览器完成：提交事件、查看动态问题、观察搜索进展、服务重启后恢复、打开证据页、展开原文定位、打开静态 HTML、查看链路诊断。
- 动态页与下载文件绑定同一 `snapshot_id`，避免页面和导出内容漂移。
- 静态页包含事件总览、事件专项分析、问题与回应、来源关系、原文证据和生产链路诊断。
- 最新定向回归为 43 passed；JavaScript 语法检查、Python compileall 和 `git diff --check` 通过。冻结前完整测试为 771 passed、2 skipped。

## 未通过原因

### 1. 搜索预算和发布预算仍然冲突

H 案例配置了 32 次模型预算，但 Runtime 在 20 个已提交步骤时停止。动作分布为 7 次搜索、5 次读取、7 次正文内检索、1 次 reflect，没有机会 review 或 finish。也就是说，模型预算尚未耗尽，但步骤预算已经终止运行。

这说明“约 2/3 预算后进入收束”只按模型调用数计算还不够。收束触发必须同时考虑：提交步骤上限、剩余可用动作数量、当前未审查判断数量，以及每个必答问题的处置成本。

### 2. 搜索顺序仍受单个问题吸附

H 案例对“听证过程与观点”连续搜索 4 次，但公众负担、运营成本和实施后情况分别有 0 次搜索。虽然第一篇长公告通过正文检索补到了部分数据，这仍然不等于问题覆盖均衡。

下一版应使用程序化调度：每个必答问题先获得一次最小证据机会，再允许对高价值缺口追加搜索；同一问题连续追加搜索需要满足明确的信息增益条件。

### 3. 关键结论审查仍依赖运行尾部

三个真实案例都表明“先批量形成 Findings，最后集中 review”很脆弱。只要最后一次 reflect 修改判断，先前 review 就会失效；只要步骤或时间预算提前结束，所有判断都会停留在 unreviewed。

下一版应改为小批量闭环：`read/retrieve → reflect 2–4 条 → review 当前批次 → 再搜索`。审查通过的判断默认冻结，除非新证据明确触发重开。

### 4. 来源结构不足以支撑“舆情状态”

H 案例 4 个页面中 3 个来自同一政府域名，另 1 个为新闻报道，来源关系全部未核实，明确观点主体数不足 2。它能回答部分规则事实，却不能代表公众意见分布，更不能生成观点占比图。

产品目前不采集社交平台，因此首页不能把“观点饼图”作为默认承诺。只有在样本定义、去重、主体识别和覆盖边界都满足时，才能展示“本次材料中的观点构成”；否则展示“已识别观点与材料数量”，并明确它不是公众支持率。

### 5. 前端已经专业化，但仍有信息架构问题

- 静态页仍显示 `rule_change` 等内部标识，交互页却显示中文名称，两个出口不一致。
- 正文中已有日期，但 4 篇材料的结构化发布日期全部未知，导致时间分布无法绘制。
- partial 页面同时按问题、来源和引用重复展示未审查判断，阅读长度过高。
- 切换到证据视图后，一些复选式控件在无障碍树中丢失文本标签；视觉上可用，但键盘和读屏体验不足。

这些属于已确认的后续问题，本批次冻结后没有继续修改代码。

## 后续唯一优先级

如果继续开发，只保留一个质量目标：**让单个真实事件在固定预算内完成“问题覆盖—小批量审查—结论发布”的闭环**。

建议把下一轮限制为以下四项，并禁止新增页面模块：

1. 将 Runtime 的提交步骤上限纳入收束预算，保证至少预留 `review + finish` 的确定动作额度。
2. 改为问题轮转和小批量审查，避免单个议题吸走搜索预算，避免最后一次 reflect 使全部 review 失效。
3. 用 A、B 两个开发案例迭代，直到它们能产生 reviewed conclusions；期间不触碰 H。
4. 只在冻结后运行一个新的保留案例 H2；若仍无 reviewed conclusions，则项目维持“实验性原型”标签并停止扩展。
